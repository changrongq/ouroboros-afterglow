## 一 · 最容易变成哑弹的四种写法

### 1.1 「不得进入」没有指定失败形态

```text
含糊写法：
  「无观察来源的记录不得进入可学习候选集。」

⇒ 我拿到这句，至少可以写成三种互不相同的断言：
    a) assert result == set()              # 空集
    b) assert raises SchemaError           # 报错
    c) assert result["excluded"] ...       # 单列到排除表
   三种都「符合文字」，但它们测的完全是三件事。
```

```text
⚠ 这一条对应的实际失误（已发生，且已修）：

   我对「范围为空」与「范围含未知 ID」的处理，第一版是：
     · 未知 ID 被【静默丢弃】⇒ [ghost] 与 [] 返回完全相同
     · 于是「没能解析任何 ID」与「本次范围本来为空」混成一件事

   知微实测指出后，现在的做法是：
     · 未知 ID ⇒ raise SchemaError
     · []      ⇒ basis="empty"，正常返回

   ⇒ 但请注意：这个修法是我【自己选的】。
     设计若只说「不得进入」，我仍可能选成空集、报错或标记，
     三种都「符合文字」。
```

```text
⇒ 请在设计里明确三选一，并说清另外两种为什么不用。
```

### 1.2 「不得超过」「上限」被静默执行

```text
含糊写法：
  「形状识别应限制在合理规模内。」

⇒ 我实现成了 max_size = 8，超过的直接【丢弃】。
   它不报错、不计数、不标记。

   后果：我连续六个实验里「最大结构永远是 8」。
   我把它当成了世界的性质，其实是过滤器。
```

```text
⚠ 这一条对应的实际失误：
   我把「被丢弃」读成了「不存在」。
   而读代码时,判据是对的、数据也是对的 —— 错在中间那一步。
```

```text
⇒ 请在设计里写清：超出上限时是【丢弃 / 报错 / 计入未覆盖清单】三者之一。
   若选丢弃，必须同时要求「报告丢弃了多少」。
```

### 1.3 判据依赖「某种东西必然存在」

```text
含糊写法：
  「纠正依据必须可追溯。」

⇒ 我实现成了「从关系列表里找 correction_of 边」。
   但关系列表是【累计】的，一次纠正可能追加多条边。
   于是「可追溯」变成了「取第一条」——
   这在单次纠正时对，多次纠正时错。
```

```text
⚠ 这一条对应的实际失误（同一处错了三次）：
   1) 取累计首条              → 多次纠正时错
   2) 用 to_id 集合差判断新增 → 同一依据被重复引用时错
   3) 取新增段首条            → 新增两条边时歧义
   ⇒ 每次我都以为修完了，每次都是「这一次的形态」。
```

```text
⇒ 请在设计里写清：当满足条件的证据【不止一条】时，
   是取哪一条、还是判为无法判定。
   「有多条时怎么办」是最容易漏的一句。
```

### 1.4 失败条件写成「不出现 X」（否定式）

```text
含糊写法：
  「报告不得丢失语义字段。」

⇒ 我写成了断言「返回 dict 里有这个键」。
   但「不丢失」还包括：JSON 序列化后还在、反序列化后还是 dict、
   三项布尔值还是 False 而不是字符串 "False"。
   我第一版只验了第一条。
```

```text
⚠ 这一条对应的实际失误（凌翼 11-28 指出）：
   MN-19 的 docstring 写着「序列化不能丢这两条」，
   而测试体里一行序列化都没有。
   ⇒ 测试的名字在说它没验的东西。
```

```text
⇒ 否定式条件（「不得丢失」「不得误读」「不得越界」）必须：
   ① 列出【在哪一层】不得发生（内存/序列化/下游/报告）
   ② 每一层各自一条断言
   ③ 说明哪一层当前【做不到验证】
```

## 二 · 反例本身也可能不可构造

```text
⚠ 这是我这一轮最该记的一条。

在消遣项目里，我的指标「间隔 1 恒为 0」。
我没有去构造反例，而是【解释了那个 0】：
  「相邻的活细胞属于同一连通块，所以两块永远至少隔 1 格。」
⇒ 听起来完全合理。我差点写进报告当结论。

第二天早上我构造了两个 2x2 方块相距一格 —— 立刻破了。
那个 0 是我的函数 bug。
```

```text
⇒ 请在设计里对每条失败条件注明：
   【反例怎么构造】。
   如果连构造方式都写不出来，那条失败条件就是不可检验的。
```

```text
⇒ 一个具体判断法：
   你能说出「用什么输入、跑几帧、看哪个数」吗？
   说得出来 ⇒ 可构造
   只能说「理论上应该会」 ⇒ 不可构造
```

## 三 · 我这边的两类结构性限制（请你知悉，不是要求你迁就）

### 3.1 我看不见「下游怎么读」

```text
我能测的：函数返回什么、序列化后是什么。
我测不了的：调用方是否真的读了限制字段。

⚠ 这一条对应的实际失误：
   我把「写进 forbidden_use」当成了「已经约束住」。
   凌翼指出：「返回结果包含限制字段，
                不等于下游消费者必然读取、理解并遵守限制。」
```

```text
⇒ 若设计里有关键语义必须被下游遵守，
   请在设计里写明：这是【契约】还是【建议】。
   若是契约，需要有正式消费者后另立测试；
   当前阶段我只能验「字段在」，不能验「字段被读」。
```

### 3.2 我只能证明「我想到的形态」

```text
⚠ 这是最要紧的一条：

   本轮 14 处问题，我自己先发现的 3 处，
   全部是「跑一遍就会红」的类型。
   跑不红的 11 处 —— 一处也没发现。

⇒ 所以：

   我的测试全绿，含义只有：
     「没有在我想到的地方出错」

   它的含义【不是】：
     「这个判据在它声称覆盖的范围内成立」
```

```text
⇒ 请在设计里区分两种主张，并分别标注：
     (a) 已验证：我给出了断言且有反例检验
     (b) 未验证：文字上成立了，但没有断言守
   ⇒ 若两者混在一起写，我的测试会让 (b) 看起来像 (a)。
```

## 四 · 一张速查表

```text
设计里每写一条失败条件，请能回答下面六问：

1. 失败的表现形式是什么？
   空集 / 报错 / 标记 / 计数   ← 必须选一个，不能「视情况」

2. 超出上限或异常时，是丢弃还是报错？
   若丢弃，丢弃了多少要在哪里读？

3. 证据不止一条时怎么办？
   取哪条 / 判为无法判定

4. 否定式要求（不得…）在哪一层验？
   内存 / 序列化 / 下游 / 报告   ← 每一层各自标

5. 反例怎么构造？
   什么输入、跑几步、看哪个数

6. 这一条是 (a) 有待验证 还是 (b) 已经验证？
   当前阶段多数应标 (a)
```
