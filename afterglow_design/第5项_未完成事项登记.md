**① · 多次纠正归因（凌翼静态核对发现）**

```text
两次核对，两个不同的失效方式（同一函数、同一位置）：

【第一次】从当前 relation 列表取【第一条】correction_of 就停。
  correct() 是追加边 ⇒ 多次纠正时首条属于最早那次。

        取该版【新增】边。

  ⚠ 修复中又抓到第二层：第一处跃变就 break 会错，
    记录可【退出 → 恢复 → 再次退出】，当前 basis 由最后一处跃变决定。
    已改为扫到底、最后那次胜出。

【第二次】用【to_id 集合差】判断新增边。
  同一条依据被重复引用时，两次 to_id 相同 ⇒ 集合差为空 ⇒ 误判无新增边。

  修法：按【边数差】取尾部新增，不看 to_id 是否重复。

⚠ 两次都说明同一件事：我修的是【这一次的形态】，不是【这一类】。
```

### BASELINE_FRESHNESS —— 已修（凌翼 2026-11-27 §3.2）

```text
原缺口（知微 2026-11-27 实测两条）：
  ① 基线子进程替为 exit 0、零用例输出 ⇒ 仍 COMPLETE / 0
  ② 已有成功报告 + 模拟基线 exit 1 ⇒ 进程正确 exit 1，
     但结果路径字节不变，仍是上次的 COMPLETE
```

```text
修法（凌翼：「校验基线真实执行，并为每次运行建立独立身份、
            失败状态及旧报告失效机制」）：
  ① 基线核验四项，不只看退出码：
       exit == 0
       用例确实运行（n_case > 0，不是「exit 0、零用例」）
       无 FAIL / ERR
       探针可解析
  ② 每次运行生成 run_id（UTC 时间戳 + uuid8）与 commit
  ③ 基线失败也【写本次报告】，verdict=EVIDENCE_FAIL，
     并带 baseline_detail.reason
  ⇒ 消费者读到 run_id 与本次不符 ⇒ 可判「读到旧报告」
```

**反例测试：`test_baseline_freshness.py`（4/4）**

```text

BF-2  基线 exit 1 + 有旧报告  → 报告被本次覆盖，run_id 已变 / reason=baseline_nonzero_exit
BF-3  基线 exit 0 但有 FAIL  → reason=baseline_cases_failed
BF-4  正常基线（对照）        → exit 0 / baseline_ok=True / n_case=32
```
