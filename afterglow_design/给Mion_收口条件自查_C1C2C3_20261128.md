**⇒ 这就是 E-23 那条自查问题的第四次出现：**

```text
我在报告里写下了「它是前置条件，不是防线」——
而代码里它仍然是一个 assert。
⇒ 边界写在了注释里，没有落在代码结构上。
⇒ 「注释也是一种文字」，而文字不能改变测试的计数方式。
```

### 现在的状态

```text
改前（违规）：
    # [一段注释说明它不是防线]
    assert cov["hits"], "E-25-1 violated: 扫描结果为空，断言无对象"

改后：
    # ─── 前置条件（不是断言）───
    #   REQUIRE_HITS = cov["hits"] 必须非空
    #   ⚠ 它不是断言，因为它【不能单独红】：
    #      · 探针被命中      ⇒ hits 必然非空
    #      · real_hits >= 2  ⇒ hits 必然非空
    #   ⇒ 它没有分辨力，只有说明力。
    if not cov["hits"]:
        raise RuntimeError("前置条件不成立：扫描结果为空。...")
```

**四条处置（§二 ①-④）逐条对照：**

| # | 要求 | 我做了什么 |
|---|---|---|
| ① | 名字不得含 assert / check 前缀 | 从 `assert` 改为 `raise RuntimeError`，标识为 `REQUIRE_HITS` |
| ② | 不得计入「通过 N 条」 | 汇总按 **case 数**统计（16 条），`raise` 不产生 `RESULTS` 条目 |
| ③ | 必须与真实防线分开写 | 用 `─── 前置条件（不是断言）───` 分隔块，物理隔开 |
| ④ | 保留理由 = 读代码的人知道前提 | 注释写明它被哪两条蕴含、为什么不能单独红 |

### ② 的具体验证：计数口径

```text
汇总打印：合计 16  通过 16  失败 0
⇒ 16 = @case 装饰的函数个数
⇒ 不是 113（全部 assert 数）
⇒ 也不是 15+1（若 raise 被算作一条防线）

⚠ 我要说明清楚：**「16 条」这个数字本身也不完全等价于「16 层防线」。**
  因为一个 case 内有多条 assert（T-12 有 20 条），
  它们共享一个 case，通过数只 +1。
  ⇒ 所以 16 是【用例数】，不是【断言数】。这个口径原来就是这样。
  ⇒ 而 C-3 要防的是「被蕴含项被算成一层防线」——
    现在的口径不会：raise 不算一条，case 才算。
```

## 三 · C-2：OPEN 登记齐了，但我先删了一条过期的 NOT_CHECKED

**当前 OPEN：**

### ⚠ 我顺手查出一处：NOT_CHECKED 里有一条【已经过期】

```text
条目：SCAN 表外的新调用点
原文：「E-25-1 已用 AST 扫全仓并逐项比对 ⇒ 新增调用点会红。
       但仍有一条不覆盖：E-26-2 的别名化消费（AST 不做数据流）。」

⇒ 它自己写着「已用 AST 扫全仓」⇒ 它【不是】未检查项，是【已覆盖项】。
⇒ 而它留在 NOT_CHECKED 里，会让读的人以为还有这个缺口。
⇒ 已删除。别名化消费那条（E-26-2）独立保留。
```

**⇒ 删的理由：**

```text
NOT_CHECKED 的意思是「本阶段【不】检查」。
一条写着「已经检查了」的条目放在 NOT_CHECKED 里，是【名实不符】。
⇒ 而名实不符的登记，比不登记更危险 ——
   它让一个已覆盖的东西占据一个未覆盖的位置，
   于是真正的新缺口来了也看不出多了一条。
```

### NOT_CHECKED vs OPEN 的分界（我请你也核一下这个划分对不对）

```text
NOT_CHECKED（5 条）：本阶段【不】检查，因为不可验或不在范围内
  真实通路是否受控 / 归属性 / 真实历史 / B1·B2 / 别名化消费 E-21-2

OPEN（1 条）：已知【未修】的缺陷
  OPEN-EXISTING-1 test_mutations_gate.py

⇒ 两者不得混算：
  NOT_CHECKED 不是「欠的债」，它是「本阶段的能力边界」；
  OPEN 是「欠的债」。
⇒ 若你认为某条 NOT_CHECKED 其实应该升级成 OPEN，我改。
```
