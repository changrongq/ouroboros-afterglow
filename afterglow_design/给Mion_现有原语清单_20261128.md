## 一 · 存储层：`RecoveryStore`（`afcore.py`）

### 1.1 它是什么

```text
「最小可信历史存储」——写入不覆盖，同一 record_id 的新版进入版本链。
```

### 1.2 公开方法（17 个，全部已实现）

| 方法 | 作用 |
|---|---|
| `insert(record)` | 写入一条记录 |
| `get(record_id)` | 取当前版本 |
| `history(record_id)` | 取全部历史版本（按 revision 升序） |
| `revise(record_id, changes, reason)` | 修订。**来源字段一律不许动** |
| `correct(record_id, new_content, correcting_record_id, reason)` | 纠正。要求依据记录已存在，追加 `correction_of` 边 |
| `record_observed(id, observed_origin)` | 记录一次系统侧观测。**只在 revision==1 且从未被修改时可用** |
| `origin_of(id)` | 最初来源（origin_* 五字段），与当前来源并列给出 |
| `was_corrected(id)` | 是否【被纠正过】（不是「被改过」） |
| `pseudo_first_person(id)` | 是否被判为伪亲历（派生标记，非第五个枚举值） |
| `observed_chain(id)` | 观测链（每次 record_observed 一条） |
| `observed_chained(id)` | 观测是否已进链 |
| `verify_chain()` | 校验记录摘要链 |
| `verify_observed_chain()` | 校验观测链 |
| `snapshot_token()` | 当前库状态的指纹，用于识别「检查后对象被替换」 |
| `sqlite_rows()` | 全部当前记录 |
| `load_seed(...)`、`write_log(...)` | 见源码 |

### 1.3 六个闭集（**只能用这些值**）

```text
OBSERVED_ORIGINS     = human_input / model_generation /
                       system_dispatch / unknown_origin
PARTICIPATION_BASES  = first_person_report / third_person_report /
                       record_only / unknown
BASIS_CONFLICTS      = none / asserted_contradicts_observed /
                       observed_absent / observed_unresolved
COMMITMENT_STATES    = not_a_commitment / proposed / accepted /
                       fulfilled / withdrawn / expired / unknown
SOURCE_KINDS         = user_utterance / third_party /
                       model_echo / system_generated / unknown
RELATION_TYPES       = correction_of / elaborates / contradicts /
                       same_fact_different_time / unknown
UNKNOWN_REASONS      = never_observed / field_absent /
                       ref_dangling / value_conflict / not_applicable
MATCH_KINDS          = exact / subset / superset / disjoint
```

### 1.4 一个必须知道的设计约束

```text
revise() 拒绝改这五个字段：
  source_kind / source_ref / participant_id /
  participation_basis / basis_ref

⇒ 想改来源，必须走 correct()，
  而 correct() 要求提供一条已存在且有 source_ref 的【纠正依据记录】。

⇒ 这条约束是「结构的结果」，不是「靠注释维持」。
   它由 class-level 的 _SOURCE_FIELDS 守着。
```

## 二 · 恢复层：`afrecover.py`

### 2.1 三个主要入口

| 函数 | 签名要点 | 已经能做什么 |
|---|---|---|
| `verify_recovery(store, query_ref, selector, expected_ids, ran, ...)` | 需要 selector 谓词 | 判断一次取回是否命中期望集合 |
| `summarize_conflicts(store, record_ids=None)` | 给记录 ID 列表 | 汇总「声明 vs 观测」的冲突状态，含两个比例 |
| `check_integrity(store, record_ids=None)` | 可给范围 | 完整性检查 |

辅助：`classify_match`（四分：exact/subset/superset/disjoint）、
`build_per_record`、`check_registration`、`check_unknown_preserved`。

### 2.2 一个已知的接口差异（**不要混用**）

```text
summarize_conflicts 与 afimportance.synthetic_ratios
对「重复 ID」的处置不同：
  · summarize_conflicts  → 去重（集合语义）
  · synthetic_ratios     → 拒绝（raise SchemaError）

⇒ 二者【不】接受同一原始列表。
   对「唯一、已知 ID 构成的同一取回集」，两者结果一致（有测试 MN-9/MN-10）。
   ⇒ 不得互换入口。
```

## 三 · 重要性原型：`afimportance.py`（**这是第 5 项的产物**）

### 3.1 五个公开函数

| 函数 | 作用 |
|---|---|
| `importance_candidates(store, trace, exclude)` | 候选资格集合（**是 set，不是分数**） |
| `synthetic_trace(store, events)` | 构造合成召回事件流，并校验 record_id 真实存在 |
| `recall_counts(trace)` | 每条记录被召回多少次 |
| `retrieval_scope(store, scope_ids)` | 「取回集」的**唯一实现**（两个指标共用） |
| `synthetic_ratios(store, trace, scope_ids)` | 两个覆盖比例 + 本次补充的 attrition 系列 |

### 3.2 它**明确不做**的事（写在模块头）

```text
✗ 不计算 importance_score / 任何数值
✗ 不训练
✗ 不排序（返回 set，不是有序列表）
✗ 不读写 reports/ 中的任何「重要性结论」
✗ 不引入相似度 / 召回计数 / 频次 这些统计量（除合成事件流）
```

### 3.3 返回结构里有哪些「约束字段」

```text
importance_candidates 返回：
  status（EVALUATED / NOT_EVALUABLE）
  candidates（set）
  denominator_size
  excluded（按规则分组的排除清单）
  active_rules
  measurement_scope（合成标记）
  allowed_use / forbidden_use / note

synthetic_ratios 返回（两分支键集合一致，共 20 键）：
  unverifiable_ratio / record_only_ratio
  denominator_size / record_only_denominator_size
  never_observed_count / observed_but_unresolved_count
  denominator_attrition / _ids / _cause / _unknown
  denominator_attrition_cause_semantics   ← 结构化语义（见下）
  basis（empty / nonempty）等
```

```text
⚠ denominator_attrition_cause_semantics 是 2026-11-28 新增的：
     value_is               = correction_basis_record_id
     is_operator_identity   = False
     is_trust_attestation   = False
     may_support_accusation = False
     role_verdict           = REQUIRED_SUMMARY_SIGNAL

   ⇒ 它存在的理由：睫指出「写在 forbidden_use 字符串里 ≠ 已守住」。
   ⇒ 现状：有测试守其内容（MN-17/18/19/20），
     但【没有下游消费者】强制读取它（MN-21 把这条写成了断言）。
```

## 四 · ★ 只有字段、没有行为的部分（请勿当作可用能力）

```text
我用脚本扫了全部 Record 字段，核对哪些被【判定逻辑】读取，
哪些只在 schema 校验或摘要计算里出现。
```

| 字段 | 状态 | 说明 |
|---|---|---|
| `commitment_state` | **只在 schema 校验** | 校验「在闭集内」「非 not_a_commitment 时 committed_to 必须非空」，但**没有任何函数按它做判定** |
| `committed_by` / `committed_to` / `commitment_ref` | **同上** | 仅校验，无行为 |
| `unknown_reason` | **只在 schema 校验** | 闭集定义完整，但无函数读它做判断 |
| `relation`（`RELATION_TYPES` 五值） | **部分** | `correction_of` 被 attrition cause 读取；`elaborates` / `contradicts` / `same_fact_different_time` **无任何行为** |
| `content` | 只在摘要 | 不参与任何判定 |

```text
⇒ 含义很具体：
   如果你在设计中假设「系统知道这条记录是不是一个承诺」，
   当前代码【不知道】——它只检查这个字段填得对不对。
```
