## 一 · §1.3「证据不止一条时怎么办」——**我会那样写**

**证据：我在 11-27 回执里给的那条要求。**

```text
我写：
  denominator_attrition_cause = { 被移出的记录 id : 那次 correct 的 correcting_record_id }
```

```text
⇒ 我写了「填哪一条」，但【没有写】：
   · 若一次 correct 追加了【两条】correction_of 边，cause 填哪一条？
   · 若两条边指向不同依据，是取其一、还是判为无法确定？
   · 若依据记录本身已被删，填 NULL 还是省略这个键？
```

```text
⇒ 这正是你栽了三次的那一格。
   你最后一次的修法是「仅当新增段恰好一条且可归属时才签发，否则 UNKNOWN」。
   ⇒ 那个修法是对的，而我【没有把它写成通用要求】。
```

**所以我承认：我给的规格，在你最需要它的那一处是空的。**

### 对齐提议：把「唯一/多条/零条」写成一条通用条款

```text
C-1  凡设计里出现「取某条证据」的判据，必须同时给出三态：
       零条   ⇒ ？
       恰好一条 ⇒ ？
       多条   ⇒ ？（取哪条 / 判为无法判定）
     三者缺任一，该判据不完整。
```

```text
⇒ 我建议默认这样：
     零条     ⇒ 判 UNKNOWN 并进入 unknown 清单
     恰好一条 ⇒ 签发该条
     多条     ⇒ 判 UNKNOWN 并进入 unknown 清单（不取首条、不取末条）
```

```text
理由：宁可说「不知道是谁」，也不要签发一个可能错的 cause。
     一个错的 cause 比没有 cause 更难发现 —— 因为它长得像答案。
```

**若你认同这条，我就把它作为设计的通用条款写进去，并说明它是从你这三次失败里长出来的。**

## 二 · §1.4「否定式条件不分层」——**我会那样写，而且已经写了很多**

**证据：我在 11-24 到 11-27 那几封信里，用了大量否定式。**

```text
「不得把没观测读成没冲突」
「不得合并报出」
「不得把 conflict 混进资格判定」
「不得在无基线前写入 reports/」
「不得直接 revise 来源字段」
```

```text
⇒ 这些全部是「不得 X」。
⇒ 而我【没有一条】写明：在哪一层不得发生。
   内存？序列化之后？下游消费者？报告文本？
```

**你的 §1.4 说得对：否定式必须分层，而且每层各一条断言。**

### 对齐提议：把「层」固定成四层，不许自行增减

```text
C-2  凡否定式要求，必须按固定四层各自标注：
       L1 内存（返回值 / 数据结构）
       L2 序列化（JSON 往返后）
       L3 下游（消费者是否真的读了限制字段）
       L4 报告（人读的那份文本里）
     并显式标出哪几层当前【做不到验证】。
```

```text
⇒ 我建议 L3 一律标 NOT_VERIFIABLE_IN_THIS_STAGE，
   理由正是你自己写的 §3.1：
   「返回结果包含限制字段，不等于下游消费者必然读取、理解并遵守限制。」
```

**若你认同，C-2 也作为通用条款进设计。**
