# C-1 · 受限令牌的权限例外不能跨账户套用

## 1.1 我的 v2 原文（错误）

> **官方原文（`CreateProcessAsUserW` → `hToken`）**：
> If `hToken` is a restricted version of **the caller's** primary token, the `SE_ASSIGNPRIMARYTOKEN_NAME` privilege is **not required**.
>
> **优点**：…官方明确"若 hToken 是 caller 主令牌的受限版本，则不需要 SE_ASSIGNPRIMARYTOKEN"——**降低了权限前提**。

## 1.2 凌翼的指正（成立）

> 受限令牌必须是**调用进程自身主令牌**的受限版本。
> 如果控制器不是 `afterglow_worker`，那么通过 `LogonUser(afterglow_worker)` 获取的令牌，**并不会自动符合这个例外**。

**我核对措辞，确实如此**：例外条件写的是 `the caller's primary token`。我们的控制器跑在 `Administrator`（或某操作账户），而 worker 是 `afterglow_worker`——**`LogonUser(afterglow_worker)` 拿到的不是 caller 的主令牌**，因此**不满足例外**。

**我把一个只适用于"给自己派生受限令牌"的特例，套用到了"为另一个账户创建进程"的场景。**

## 1.3 勘误后

```text
PATH_B_PRIVILEGE_PRECONDITION = NOT ESTABLISHED
```

**路径 B 的权限前提现在明确为未建立。** 需要验证：

| # | 验证项 | 为什么 |
|---|---|---|
| P-1 | 控制器是否持有 `SE_INCREASE_QUOTA_NAME` | `CreateProcessAsUser` 通常需要 |
| P-2 | 控制器是否持有 `SE_ASSIGNPRIMARYTOKEN_NAME` | 跨账户时**不能靠例外规避**，需实际持有或另行取得 |
| P-3 | `STATUS_DLL_INIT_FAILED` 是否会复现 | **此前实际遇到过**，不是假想 |
| P-4 | window station / desktop 权限是否足够 | 此前遇到过；官方文档要求调用方显式授予目标账户 |
| P-5 | 用户 profile 如何处理 | `CreateProcessAsUser` **不加载** profile；现有链路用 `LOGON_WITH_PROFILE` |
| P-6 | session 差异 | `CreateProcessWithLogonW` 新建会话；`CreateProcessAsUser` 复用 token 会话 |

**P-3 与 P-4 是"此前实际遇到过"的项，我在此前报告里没把它们写进路径 B 的前提清单**——这是遗漏，不是新发现。

# C-2 · `HANDLE_LIST` 与 `FALSE` 继承开关不能混用

## 2.1 凌翼的指正（成立）

> 使用 `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` 时，应将 `bInheritHandles` 设为 **TRUE**，且列表中的句柄必须具备可继承属性。

**我自己的实测记录也印证了这一点**（`c_verify_m1_inherit_premise.py`，`8acc27c`，已登记为越界执行）：

```text
(a) inherit=False, no list      -> ok=True  err=0
(b) inherit=True,  with list    -> ok=True  err=0
(c) inherit=False, WITH list    -> ok=False err=87  (ERROR_INVALID_PARAMETER)
```

**我在 v2 的 W-BD2 里一边写"`bInheritHandles=FALSE`"，一边写"或 `HANDLE_LIST` 精确白名单"，把互斥的两种配置并成了一句。**

## 2.2 勘误：路径 B 必须分成两个**互斥**模式

| 模式 | 继承参数 | 作用 | 能否承载标准 IO 白名单 |
|---|---|---|---|
| **B0** | `bInheritHandles=FALSE` | 不继承调用者的任何可继承句柄 | **不能**（无列表机制） |
| **B1** | `bInheritHandles=TRUE` + `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` | **只**继承明确列出的句柄 | **能**（列表即白名单） |

**明确：B0 与 B1 不可同时成立。**

**标准输入输出通道（v2 的 CH-1 / CH-2）只能在 B1 实现**，因为需要 `HANDLE_LIST`。
**若选 B0，则标准句柄传递必须靠 `STARTUPINFO` 的 `STARTF_USESTDHANDLES`（独立于继承开关），而不是白名单。**

## 2.3 路径 A 的证据范围必须收紧

凌翼：

> 路径 A 没有 `bInheritHandles` 参数，**并不能单凭这一点就证明所有控制器句柄都不会传入**。
> 现有 Profile B 的正负对照实验，支持的是**已登记目标句柄、指定创建路径和测试条件下的非继承证据**，不应被扩写成普遍安全定理。

**我接受这个收紧。** v2 §2.2 把路径 A 的保证写成"该 API 无 `bInheritHandles` 参数 ⇒ 不继承"，这是**从参数缺失推出普遍结论**，与凌翼反复禁止的"把观察升格为定理"同类。

**勘误后的表述**：

```text
路径 A 的非继承证据范围 =
  已登记目标句柄（forbidden handle）
  + 指定创建路径（CreateProcessWithLogonW）
  + 测试条件（Profile B 正负对照实验的具体配置）
  ≠ 所有控制器句柄在所有条件下都不传入
```

**冻结合同原文保持不变**，只在新报告中明确证据适用范围。

# C-3 · 观察者语义与适配器代码不一致（凌翼标为最需立即修改）

## 3.1 我的 v2 原文（错误）

> | 责任 | 归属 | 现有组件 |
> |---|---|---|
> | 可信观察者 | **必须是独立主体** | `probe_read_access`（独立观察） |
> | Reset 后目标仍被拒 | 由观察者提供 `access_ok` | `judge_reset(access_ok=...)` |

## 3.2 我读了代码，凌翼的指正完全成立

`afterglow_harness/q3_reset_adapter.py` → `prove_persistent_isolation()`（第 412 行起）明确写着：

> **(2) CONTROLLER-side corroboration** = a handle audit for THIS worker + the REAL target
> （凌翼 R2: the controller's independent contribution is the handle audit + identity binding —
> **NOT its own read, which a privileged controller would always 'succeed'**）

代码实际返回：

```python
controller_seal_ok=False,        # not a real independent seal
controller_verdict="HANDLE_AUDIT",
```

**即：适配器刻意不使用控制器自己的 `probe_read_access` 读结果作为拒绝证据。**

v2 声称"可信观察者 = `probe_read_access`"，**与代码的正确设计相反**——而代码这么做正是因为"特权控制器的读取会永远成功"（wall-door，`睫第202句` 亦有记载）。

**我把冻结 Q3 probe 路径的观察者，移植成了持久业务 worker 的证明。** 这两者不是同一件事。

## 3.3 时间顺序：DACL 恢复不等于同一观察窗口

凌翼：

> 代码中 DACL 恢复发生在 worker 退出确认之后。…不能简单要求「DACL 已恢复 AND worker 仍被拒绝读取」，这两项不一定属于同一个有效观察窗口。

**代码核实（`_cleanup()`，第 732 行起）**：

```text
L743:  Order: stop the worker + confirm exit FIRST; only THEN restore the ACL.
L752:  if worker_exit_confirmed is not True: ...
L772-773: if worker_exit_confirmed is not True:
              # Protect the (possibly) still-live worker: DO NOT restore the boundary.
L784:  # (2) Worker exit CONFIRMED -> it is now safe to restore the original ACL.
```

**确认为串行且互斥**：worker 未确认退出时**明确不恢复**。

## 3.4 勘误后的证据事件表（凌翼要求：时间顺序、观察主体、权限身份、证据来源）

| # | 阶段 | 时刻 | 观察主体 | 权限身份 | 证据来源 | 边界状态 |
|---|---|---|---|---|---|---|
| **E-1** | 边界安装 | $t_1$ | 控制器 | 特权（`Administrator`） | `deny_read_for_sid` + `save_dacl` | **正在安装** |
| **E-2** | worker 启动 | $t_2 > t_1$ | 控制器 | 特权 | `spawn` 返回 + token SID + create_time | **已生效** |
| **E-3** | worker 自我尝试读 | $t_3$ | **worker** | **受限（`afterglow_worker`）** | worker 回报（nonce + pid 绑定） | 已生效 |
| **E-4** | 控制器独立佐证 | $t_3$ 同窗口 | **控制器** | 特权 | **句柄审计 + 目标身份绑定**（**非**控制器自读） | 已生效 |
| **E-5** | Reset 状态观察 | $t_4$ | 独立主体（见 3.5） | — | 冻结 Q3 `judge_reset` 语义 | 已生效 |
| **E-6** | worker 终止确认 | $t_5$ | 控制器 | 特权 | `_process_is_gone` + 退出码 | 已生效 |
| **E-7** | DACL 恢复 | $t_6 > t_5$ | 控制器 | 特权 | `restore_dacl` + `verify_sd_equal` | **已拆除** |

**关键约束（v2 缺失）**：

- **E-3 的观察主体是 worker 自己**，其自报**只作一致性交叉检查**（代码：`worker_self_report={...} (consistency only)`），**不是独立证据**
- **E-4 才是控制器的独立贡献**，且它**是句柄审计，不是控制器自读**
- **E-6 必须在 E-7 之前**：worker 未确认退出时**不得**恢复 DACL
- **"worker 被拒绝" 与 "DACL 已恢复" 不共存于同一时刻**——前者要求边界生效，后者要求边界拆除

## 3.5 一个我必须留白的点

**E-5 的"独立主体"是谁，我没有答案。**

- 冻结 Q3 probe 路径的观察者是 probe 本身（短生命周期，独立进程）
- **持久业务 worker 场景下，谁能在边界生效期间、以非特权身份、独立地"尝试越界"？**
- 代码没有这个角色；`judge_reset` 的 `access_ok` 入参**由谁填**，本轮未确定

**我不把 `probe_read_access` 填进去**——那正是 C-3 的错误。


# C-4 · 网络能力不天然被受限令牌消除

## 4.1 我的 v2 原文（错误）

> | 网络（若 worker 有网络能力） | **未控制** | 需受限令牌去除网络能力，**未实测** |

## 4.2 凌翼的指正（成立）

> `CreateRestrictedToken` 能限制令牌中的 SID 和特权，**并不天然等价于关闭普通进程的网络访问**。

**我核对后接受。** `CreateRestrictedToken` 的作用对象是**令牌中的 SID 与特权**（禁用 SID / 降权 / 限制模式），而**网络访问能力主要由 SID（如 `Everyone`、`Users`、网络相关组）与防火墙策略决定，不由令牌 API 本身关闭**。

**我把"受限令牌"当成了"网络已隔离"的候选证明——这是推测，不是机制。**

## 4.3 勘误后

```text
NETWORK_PATH_CONTROL = NOT ESTABLISHED
```

**网络通路必须单独声明控制机制与验证办法**，不能借用受限令牌。候选（**均为候选，未验证**）：

| 候选 | 说明 | 状态 |
|---|---|---|
| N-1 通过 DACL/防火墙阻断出站 | 需系统级策略，超出进程级设计 | **未验证** |
| N-2 令牌中禁用网络相关 SID | **我不确定这是否足以阻断** | **未验证** |
| N-3 在无网络命名空间/容器中运行 | Windows 下等价物我未核实 | **未验证** |

**当前状态：网络通路在威胁覆盖中标记为"未控制"，且我没有给出可信控制机制。**

# 5 · 凌翼肯定的三点，我照录

> 第一，Coder 学会了区分事实、推论和待验证假设。
> 第二，新增 G-6、G-7、G-8 是正确的。
> 第三，Job Object 的地位得到合理修正。

## 5.1 Job Object 的补充约束（凌翼要求）

> `KILL_ON_JOB_CLOSE` 的终止作用取决于：① 进程已经纳入 Job；② 关闭的是**最后一个相关句柄**；③ **不存在破坏进程树约束的 breakaway 情况**。它增强生命周期控制，**却不证明 Reset 后没有数据残留**。

**照录并采纳**，附加到 v2 §5.2 的结论：

```text
JOB_OBJECT_ROLE = LIFECYCLE_AID_ONLY
前提：进程已纳入 job ∧ 关闭最后一个相关句柄 ∧ 无 breakaway
不证明：Reset 后无数据残留
```
