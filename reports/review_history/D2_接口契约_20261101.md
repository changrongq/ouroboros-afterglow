## 契约 IC-1 · 四要素

### (0) 收据必须可被引用（2026-11-01 自查补）

```text
⇒ IC-2 的 S3 必须引用"S2 的收据"。
⇒ 但原 ReceiptRecord 定义【没有唯一标识符】：
     authority_record_key 指向的是【被确认的权威记录】，不是收据本身。
⇒ 无标识符 ⇒ 不可引用 ⇒ S3 的"引用 S2"无法落地。

⇒ 已补字段：

⇒ 该键同时是去重键（见下）。
⇒ 后续所有对收据的引用（S3、replay、审计）一律使用此键。
```

**契约版 ReceiptRecord 定义（本文正式版本）：**

    （【2026-11-01 四次修正（睫 NB-59）】原文写「唯一标识兼去重键」。

### (1) 提交方身份

```text
⇒ 必须是【可独立核验的身份】，不是自填字符串。

身份来源（三选一，按可得性排序）：
  (a) 由记录者在 ACK 中回应并绑定的 submitter_id
      ⇒ 记录者先记录了「谁提交了 event_id」
      ⇒ ACK 回显该 submitter_id，提交方校验一致
  (b) 由控制主体在放行时核验的进程身份
  (c) 若无 (a)(b) ⇒ SUBMITTER_IDENTITY = NOT ESTABLISHED

⇒ 禁止：仅凭 ReceiptRecord.received_by 字段声称身份成立。
```

### (2) 收件事实来源

```text
⇒ 收件事实必须【与记录者的发送记录可对上】。

可核验的收件证据 = 满足以下两项：
  (i)  记录者侧存在 ACK_SENT 记录，且其 attempt_id 与本次一致
  (ii) 提交方侧的 ReceiptRecord 引用同一 authority_record_key

⇒ 只有 (ii) 没有 (i) ⇒ RECEIPT_SOURCE = NOT ESTABLISHED
⇒ 只有 (i) 没有 (ii) ⇒ 只证明「发了」，不证明「收到」
```

```text
⇒ 两者都有，才构成【双方对得上】的收件事实。
⇒ 这不是握手协议，是【证据交叉校验】。
```

### (3) 持久化位置

```text
⇒ ReceiptRecord 必须持久化在【与 EventRecord 不同的位置】，
   否则提交方可以连带改写记录者的证据。

推荐（设计约束，非实现）：
  · EventRecord 流（记录者侧）
  · ReceiptRecord 流（提交方侧，独立文件/独立目录）
  · 两者不得由同一写权主体在无隔离条件下同时可写

⇒ 无隔离 ⇒ RECEIPT_INDEPENDENCE = NOT ESTABLISHED
```

### (4) 独立校验方式

```text
⇒ 控制主体在作出 STAGE_RELEASED 前，必须【分别读取两侧证据】：

  完整收件验证谓词 RECEIPT_PREDICATE（c1–c7，唯一判定入口）：
    c1  （来源·发送侧）存在发送侧 AttemptRecord A，其 sent_state = ACK_SENT；
        A.authority_record_key 解析到已建立的权威 EventRecord E；
        A.event_id == E.event_id，
        且 A.authority_record_key 符合该 event 的唯一权威绑定。
        ！【不】要求 A.attempt_id == E 创建时的 attempt_id
           （见下「合法重试」说明）
    c2  （来源·收据侧）存在 receipt_fact = ACK_RECEIVED 的 ReceiptRecord，
        其 receipt_record_key 可完整解析（含 receipt_seq）
    c3  （键匹配）c1 与 c2 的 event_id / attempt_id / authority_record_key 三者一致
    c4  （身份）c2 的 received_by 与记录者侧该 attempt 的 submitter_id 一致，
        且该 submitter_id 来源符合 (1) 的 (a)/(b)，不得为自填
    c5  （写权边界）两侧证据位于【不同位置】，且不存在同一写权主体
        可无隔离改写两者（即 RECEIPT_INDEPENDENCE 成立）
    c6  （持久化）发送侧与收据侧【分别】具备各自的持久化成功证据
        —— 不得以一个总状态代替两侧
    c7  （收件来源路径）c2 的收据由【经审查的接收组件】在其实际接收并
        校验 ACK 之后产生，而非由普通业务路径依已知键直接写出
        ⇒ 详见 §IC-1(5)

  ⇒ c1–c7 全部成立 ⇒ RECEIPT_VERIFIED
  ⇒ 任一不成立     ⇒ RECEIPT_VERIFIED = NOT ESTABLISHED（不是 INVALID）
```

### (5) 收件来源路径（2026-11-01 四次新增，知微 Z-D2-01 剩余）

**为什么需要这一节：**

```text
⇒ c1–c6 只回答「有没有这两条记录、键对不对、身份一致否、隔离够不够、落盘没有」。
⇒ 它们都不回答：「这条收据【是不是】由实际接收产生的」。
⇒ 反例（知微给出）：
     记录者正确登记并发送 ACK，包在传输中丢失；
     接收方身份真实、两侧写权隔离正确；
     但接收方的【错误分支】依已知 event/attempt/authority key 提前写出收据。
   ⇒ c1–c6 可全部成立，而实际接收没有发生。
```

**契约要求（四项，均为可审查前提）：**

```text
(a) 指定接收组件
    ⇒ 必须明确【哪个注册组件负责实际接收并校验 ACK】。
    ⇒ 该组件须作为【明确受信任的组件】纳入边界，不得隐式假定。

(b) 核验内容
    ⇒ 该组件在实际接收时须核验：
         event_id / attempt_id / authority_record_key / received_by 的绑定
    ⇒ 【成功核验前不得产生收据】。

(c) 绑定与控制
    ⇒ 控制主体凭什么把某条收据绑定到【该组件的该次接收处理】，
       须有可审查依据（如组件签发的接收序号或等价关联）。
    ⇒ 并且必须能阻止【普通业务路径自行生成同等有效的收据】。

(d) 前提缺失时
    ⇒ 该来源前提无证据 ⇒ 不签发 RECEIPT_VERIFIED ⇒ 不放行。
```

```text
⇒ 允许在有界模型内【明确相信一个经审查的接收组件】。
⇒ 不要求证明恶意内核不可能作假，也不要求现在实现密码学或 Windows 原型。
⇒ 但「接收组件受信任」+「该收据来自它的实际接收路径」
   必须是【显式、可审查的前提】，不能用字符串匹配代替。

RECEIPT_SOURCE_PATH_TRUSTED = NOT ESTABLISHED（当前）
```

**与 (1)(a) 的关系（知微补充）：**

```text
⇒ (1)(a) 的 ACK 回显 submitter_id 只用于【核对绑定】。
⇒ 记录者的 submitter_id 必须【先来自可信身份核验】。
⇒ 回显本身不是身份认证，不自行建立身份来源。
```

### (6.1) 四个必答问题（凌翼 IF-1 第 1–4 项）

**问 1 · 提交方可信身份从哪里取得？**

  (a) 记录者在接受 SUBMIT 时核验并写入 submitter_id，
      该值随 ACK 回显；
  (b) 若无 (a)，由控制主体在放行时核验；
  (c) 两者皆无 ⇒ SUBMITTER_IDENTITY = NOT ESTABLISHED

⇒ 【禁止】从 ReceiptRecord.received_by 反向认定身份。
   ⇒ received_by 是【被校验方】，不是校验来源。
⇒ producer_id ≠ submitter_id：
   producer_id 是【记录生产者】，submitter_id 是【提交方】。
   两者可以是同一进程，但语义不同，不得互相替代。
```

**问 2 · `ACK_SENT` 与权威 `EventRecord` 如何绑定？**

```text
⇒ 通过 AttemptRecord.authority_record_key 直接绑定：

AttemptRecord.attempt_id ──(同一条记录)──> authority_record_key
                                              │
                                              └─> EventRecord(recorder_id, epoch, seq)

⇒ 即：ACK_SENT 不是"某次发送"的自由标签，
   而是【针对某个特定权威记录】的一次 attempt。
⇒ 无 authority_record_key 的 ACK_SENT ⇒ 不予接受（c1 不成立）。
```

**问 3 · `ReceiptRecord` 如何绑定到同一次 ACK？**

```text
⇒ 通过三元组 (event_id, attempt_id, receipt_seq) + authority_record_key：

ReceiptRecord.attempt_id          == AttemptRecord.attempt_id
ReceiptRecord.authority_record_key == AttemptRecord.authority_record_key
ReceiptRecord.event_id            == AttemptRecord.event_id

⇒ 三者同时相等 ⇒ 该收据绑定到【那一次具体的 attempt】，
   而不是「同一 event 下的任意 attempt」。
```

**问 4 · 合法重试时如何避免把不同 attempt 的发送与收件记录错误拼接？**

```text
⇒ 关键：attempt_id 是【拼接的禁止面】。

规则 RETRY-NO-CROSS-BIND：
   收据与发送必须 attempt_id 相同才能配对。
   ⇒ 不同 attempt 的记录【永不拼接】，
     即使 event_id 与 authority_record_key 相同。

⇒ 这正好回答了为什么 receipt_record_key 要含 attempt_id：
   它是防止跨 attempt 拼接的【结构手段】，
   而不是为了排序。
```

```text
⚠ 这条同时解释了凌翼问的「相同 event_id 下合法重试」：
   ⇒ 每次重试有独立 attempt_id
   ⇒ 每次重试可以有自己的 ReceiptRecord
   ⇒ 但它们【互不相通】，谓词只为其中【一次】签发 VERIFIED
   ⇒ 该次的 matched_receipt_key 就是它与其它 attempt 的分界
```

   否则等于定义一条永假的规则」。
⇒ 【这个推导不成立】。

⇒ 反例：注册动作规定依次写 F1、F2。
    F1 正常写完关闭，F2 正常写完关闭，动作随后正常返回。
    在这条成功路径上，「该动作要求的两次写入均已完成」【可以为真】，
    即使中间状态曾可见、崩溃时可能只留下 F1。

⇒ 不存在原子性，并不使「动作级完成」永假。
⇒ 那是两件不同的事，我把它们混成了一件。
```

**四件事必须分开（知微的分层）：**

```text
① 单次文件写入正常完成
② 注册动作要求的【所有步骤】均正常完成
③ 跨文件提交具有原子性
④ 观察结果构成一致快照

⇒ ① 不能推出 ②（动作可能有多步）
⇒ ② 不能推出 ③（步骤全完成 ≠ 原子）
⇒ ③ 不能推出 ④（原子提交 ≠ 快照一致）
⇒ 但 ③④ 不存在，并不使 ①② 永假。
```

**动作级完成需要的定义（本契约给出框架，判定属 IC-2）：**

```text
对每个注册动作，须定义：
  · 预期子步骤集合（哪些文件、哪些写入实例）
  · 归属（execution / arm / action）
  · 哪些完成或异常记录参与判断
  · 聚合规则：全部完成 ⇒ 动作完成；部分完成 ⇒ 动作未完成

⇒ 可引用现有绑定结构，不要求新增字段。
```

**因此：**

```text
GRANULARITY = PER_FILE_WRITE

⇒ 每次 STATE_WRITE_COMPLETED 只覆盖【一个文件】。
⇒ 多文件完成【不】意味着原子提交（凌翼原文）。
⇒ 整个注册动作的完成按 IC-2 的 ACTION_COMPLETION 及本节子步骤聚合规则判断，
   【不要求跨文件原子提交】。
⇒ 若另行提出原子提交保证，则须设计相应机制并按适用流程申请授权；
   本契约【不提供】该保证。
