# 一 · IC-1 · 来源可信性

## 凌翼的要求

```text
"明确 ReceiptRecord 的提交方身份、收件事实来源、持久化位置和独立校验方式。
 仅有提交方自行填写的 ACK_RECEIVED，不能自动满足可靠证据的要求。"
```

## 当前缺口（自查确认）

```text
ReceiptRecord {
    event_id
    attempt_id
    authority_record_key
    receipt_fact            ACK_RECEIVED
    received_by             提交方身份      ← 【自填，无校验】
    receipt_seq
}

⇒ 问题：received_by 与 receipt_fact 都由提交方自己写。
⇒ 一个进程可以自行写一条"我收到 ACK 了"，
   而没有任何第三方能验证它是否真收到。
⇒ 这正是凌翼指出的「不能自动满足可靠证据」。
```

## 契约 IC-1 · 四要素

### (0) 收据必须可被引用（2026-11-01 自查补）

```text
⇒ IC-2 的 S3 必须引用"S2 的收据"。
⇒ 但原 ReceiptRecord 定义【没有唯一标识符】：
     authority_record_key 指向的是【被确认的权威记录】，不是收据本身。
⇒ 无标识符 ⇒ 不可引用 ⇒ S3 的"引用 S2"无法落地。

⇒ 已补字段：
     receipt_record_key = (event_id, attempt_id, receipt_seq)

⇒ 该键同时是去重键（见下）。
⇒ 后续所有对收据的引用（S3、replay、审计）一律使用此键。
```

**契约版 ReceiptRecord 定义（本文正式版本）：**

```text
ReceiptRecord {
    receipt_record_key      = (event_id, attempt_id, receipt_seq)   ← 唯一标识兼去重键
    event_id
    attempt_id
    authority_record_key    指向被确认的权威记录
    receipt_fact            ACK_RECEIVED
    received_by             提交方身份（须符合 (1) 的要求，不得自填即算）
    receipt_seq             该 (event_id, attempt_id) 下的单调序号
}
```

```text
⇒ 与第一节「当前缺口」处所引的旧结构相比，本版新增 receipt_record_key。
⇒ 旧结构那份保留，用于说明缺口是什么；【不得】作为定义引用。
```


### (1) 提交方身份

```text
⇒ 必须是【可独立核验的身份】，不是自填字符串。

身份来源（三选一，按可得性排序）：
  (a) 由记录者在 ACK 中回应并绑定的 submitter_id
      ⇒ 记录者先记录了「谁提交了 event_id」
      ⇒ ACK 回显该 submitter_id，提交方校验一致
  (b) 由控制主体在放行时核验的进程身份
  (c) 若无 (a)(b) ⇒ SUBMITTER_IDENTITY = NOT ESTABLISHED

⇒ 禁止：仅凭 ReceiptRecord.received_by 字段声称身份成立。
```

### (2) 收件事实来源

```text
⇒ 收件事实必须【与记录者的发送记录可对上】。

可核验的收件证据 = 满足以下两项：
  (i)  记录者侧存在 ACK_SENT 记录，且其 attempt_id 与本次一致
  (ii) 提交方侧的 ReceiptRecord 引用同一 authority_record_key

⇒ 只有 (ii) 没有 (i) ⇒ RECEIPT_SOURCE = NOT ESTABLISHED
⇒ 只有 (i) 没有 (ii) ⇒ 只证明「发了」，不证明「收到」
```

```text
⇒ 两者都有，才构成【双方对得上】的收件事实。
⇒ 这不是握手协议，是【证据交叉校验】。
```

### (3) 持久化位置

```text
⇒ ReceiptRecord 必须持久化在【与 EventRecord 不同的位置】，
   否则提交方可以连带改写记录者的证据。

推荐（设计约束，非实现）：
  · EventRecord 流（记录者侧）
  · ReceiptRecord 流（提交方侧，独立文件/独立目录）
  · 两者不得由同一写权主体在无隔离条件下同时可写

⇒ 无隔离 ⇒ RECEIPT_INDEPENDENCE = NOT ESTABLISHED
```

### (4) 独立校验方式

```text
⇒ 控制主体在作出 STAGE_RELEASED 前，必须【分别读取两侧证据】：

  校验清单：
    c1  EventRecord 流中存在对应的 ACK_SENT，attempt 匹配
    c2  ReceiptRecord 流中存在 ACK_RECEIVED，authority_record_key 匹配
    c3  两侧的 event_id / attempt_id 一致
    c4  两侧 commit/持久化状态均已达 L3

  ⇒ c1–c4 全部成立 ⇒ RECEIPT_VERIFIED
  ⇒ 任一不成立   ⇒ RECEIPT_VERIFIED = NOT ESTABLISHED（不是 INVALID）
```

```text
⇒ 为什么是 NOT ESTABLISHED 而非 INVALID：
   缺证据不等于观察到矛盾。
⇒ 但若 c1 与 c2 【都存在且互相矛盾】（如 attempt 不符）⇒ INVALID
```

## IC-1 的状态声明

# 二 · IC-2 · 阶段放行

## 凌翼的要求

```text
WINDOW_CLOSE 的权威记录成立
→ 提交方收件证据成立
→ 控制主体作出 STAGE_RELEASED
→ 后继阶段才允许开始

每步都应有明确来源和可复核的事件绑定。
TIME_GATE 通过不能替代对象身份、写权限隔离和双文件快照一致性。
```

## 契约 IC-2 · 四步链条

```text
步骤        前置条件                          证据来源        失败时
S1          WINDOW_CLOSE 的权威记录成立        记录者侧        NOT ESTABLISHED
            = (recorder_id, epoch, seq) 已持久化
            ！且已达注册判定点（若相关）

S2          收件证据成立                      两侧交叉       NOT ESTABLISHED
            = IC-1 的 c1–c4 全部通过

S3          STAGE_RELEASED 由控制主体作出      控制主体       NOT ESTABLISHED
            = 引用 S2 的 receipt_record_key

S4          后继阶段开始                       ——            不得开始
```

```text
⇒ 每步必须【引用前一步的记录键】，不得只说"已满足"。
⇒ S3 的 STAGE_RELEASED 必须携带 receipt_record_key，
   否则无法复核它是基于哪一次收件作出的放行。

⚠ 【2026-11-01 自查修正（提交前）】
   原文 S3 写「引用 S2 的 ReceiptRecord」——但 ReceiptRecord
   【没有唯一标识符】，无法被引用。
   （authority_record_key 指向的是被确认的权威记录，不是收据本身。）
   ⇒ 已在 IC-1 的 ReceiptRecord 定义中补 receipt_record_key。
```

## IC-2 的边界声明（照录凌翼原文）

```text
TIME_GATE 通过【不能】替代：
  · 对象身份稳定
  · 写权限隔离
  · 双文件快照一致性

⇒ 即：S1–S4 全部通过，也只说明【时序门】通过。
⇒ 不说明快照一致、不说明对象未被替换、不说明可作科学证据。
```

## 与 D1-2 的 TIME_GATE 关系

```text
⇒ D1-2 的 TIME_GATE 三项 = S1 + S2 + 顺序证据。
⇒ 本文 S1–S4 是其【展开】+ 增加 S3 的显式放行者。
⇒ 不冲突；TIME_GATE 保持其在 D1-2 中的定义。
```

# 三 · IC-3 · 协议版本一致性

## 凌翼的要求

```text
"明确从旧 EventRecord.commit_state、WRITE_COMMIT 到新结构的映射及弃用规则。
 另须固定事件粒度：某个写入完成事件对应一次底层文件写入，
 还是整个注册干预动作。多文件完成不天然意味着原子提交。"
```

## 契约 IC-3a · 字段映射与弃用

| 旧结构 | 新结构 | 弃用规则 |
|---|---|---|
| `EventRecord.commit_state` | 移出 → 独立 `StateTransition` 流 | 旧字段**不再有效**；不得从旧记录读状态 |
| `WRITE_COMMIT` | 拆为四个事件 | **名称弃用**；旧文档中出现的不得解释为已证明的写入提交 |
| 单一 `confirmed` 布尔 | `BINDING_CONFIRMED` / `ACK_CONFIRMED` | 旧布尔值**无法表达两者之分**，不得迁移 |

```text
⇒ 历史文档与冻结规格中的旧名称【不自动改写】（凌翼明令）。
⇒ 但新设计不得再使用。
⇒ 引用旧文档时须注明：该名称已弃用，其证明力为 NOT ESTABLISHED。
```

## 契约 IC-3b · 事件粒度（凌翼要求固定）

**问题：** `STATE_WRITE_COMPLETED` 对应一次底层文件写入，还是整个干预动作？

```text
⇒ 本契约固定为【一次底层文件写入】。
```

```text
理由（基于已核实的源码结构）：
  storage.py L99-105  write_literal  → 写 literal.bin 一次
  storage.py L107-109 write_substrate → 写 substrate.bin 一次
  ⇒ 两个文件是【两次独立写入】，无原子提交。

⇒ 若把粒度定为「整个干预动作」，则需一个跨文件原子提交机制。
⇒ 当前 harness 无此机制（核心原语 = 0）。
⇒ 定义一个当前无法满足的粒度，等于定义一条永假的规则。
```

**因此：**

```text
GRANULARITY = PER_FILE_WRITE

⇒ 每次 STATE_WRITE_COMPLETED 只覆盖【一个文件】。
⇒ 多文件完成【不】意味着原子提交（凌翼原文）。
⇒ 若将来需要「整干预动作」级别，须另建跨文件提交机制并单独授权。
```

```text
⚠ 直接后果：
   「literal 与 substrate 同时处于某一状态」这件事，
   在当前实现下【无法由写入事件推出】。
   ⇒ 只能由快照观测得知，而快照本身非原子（B-1 已诊断）。
   ⇒ 故 CROSS_FILE_ATOMICITY = NOT ESTABLISHED
```

# 七 · 一句

```text
IC-1 的答案其实是：
「提交方说自己收到了」，不是证据。
证据是「记录者说他发了」和「提交方说他收了」两句话对得上。

⇒ 两句话对得上，才叫一次收件。
⇒ 一句话自己说自己，那叫声称。
```
