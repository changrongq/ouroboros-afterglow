```text
ReceiptRecord {
```

## 契约 IC-1 · 四要素

### (0) 收据必须可被引用（2026-11-01 自查补）

```text
⇒ IC-2 的 S3 必须引用"S2 的收据"。
⇒ 但原 ReceiptRecord 定义【没有唯一标识符】：
     authority_record_key 指向的是【被确认的权威记录】，不是收据本身。
⇒ 无标识符 ⇒ 不可引用 ⇒ S3 的"引用 S2"无法落地。

⇒ 已补字段：
     receipt_record_key = (event_id, attempt_id, receipt_seq)

⇒ 该键同时是去重键（见下）。
⇒ 后续所有对收据的引用（S3、replay、审计）一律使用此键。
```

**契约版 ReceiptRecord 定义（本文正式版本）：**

```text
ReceiptRecord {
    receipt_record_key      = (event_id, attempt_id, receipt_seq)   ← 唯一标识兼去重键
    event_id
    attempt_id
    authority_record_key    指向被确认的权威记录
    receipt_fact            ACK_RECEIVED
    received_by             提交方身份（须符合 (1) 的要求，不得自填即算）
    receipt_seq             该 (event_id, attempt_id) 下的单调序号
}
```

```text
⇒ 与第一节「当前缺口」处所引的旧结构相比，本版新增 receipt_record_key。
⇒ 旧结构那份保留，用于说明缺口是什么；【不得】作为定义引用。
```


### (1) 提交方身份

```text
⇒ 必须是【可独立核验的身份】，不是自填字符串。

身份来源（三选一，按可得性排序）：
  (a) 由记录者在 ACK 中回应并绑定的 submitter_id
      ⇒ 记录者先记录了「谁提交了 event_id」
      ⇒ ACK 回显该 submitter_id，提交方校验一致
  (b) 由控制主体在放行时核验的进程身份
  (c) 若无 (a)(b) ⇒ SUBMITTER_IDENTITY = NOT ESTABLISHED

⇒ 禁止：仅凭 ReceiptRecord.received_by 字段声称身份成立。
```

### (2) 收件事实来源

```text
⇒ 收件事实必须【与记录者的发送记录可对上】。

可核验的收件证据 = 满足以下两项：
  (i)  记录者侧存在 ACK_SENT 记录，且其 attempt_id 与本次一致
  (ii) 提交方侧的 ReceiptRecord 引用同一 authority_record_key

⇒ 只有 (ii) 没有 (i) ⇒ RECEIPT_SOURCE = NOT ESTABLISHED
⇒ 只有 (i) 没有 (ii) ⇒ 只证明「发了」，不证明「收到」
```

```text
⇒ 两者都有，才构成【双方对得上】的收件事实。
⇒ 这不是握手协议，是【证据交叉校验】。
```

### (3) 持久化位置

```text
⇒ ReceiptRecord 必须持久化在【与 EventRecord 不同的位置】，
   否则提交方可以连带改写记录者的证据。

推荐（设计约束，非实现）：
  · EventRecord 流（记录者侧）
  · ReceiptRecord 流（提交方侧，独立文件/独立目录）
  · 两者不得由同一写权主体在无隔离条件下同时可写

⇒ 无隔离 ⇒ RECEIPT_INDEPENDENCE = NOT ESTABLISHED
```

### (4) 独立校验方式

```text
⇒ 控制主体在作出 STAGE_RELEASED 前，必须【分别读取两侧证据】：

  完整收件验证谓词 RECEIPT_PREDICATE（c1–c6，唯一判定入口）：
    c1  （来源·发送侧）AttemptRecord 中存在 sent_state = ACK_SENT，
        且其 (event_id, attempt_id) 与 authority_record_key 指向的记录一致
    c2  （来源·收据侧）ReceiptRecord 流中存在 receipt_fact = ACK_RECEIVED，
        且 receipt_record_key 完整可解析（含 receipt_seq）
    c3  （键匹配）c1 与 c2 的 event_id / attempt_id / authority_record_key 三者一致
    c4  （身份）c2 的 received_by 与记录者侧该 attempt 的 submitter_id 一致，
        且该 submitter_id 来源符合 (1) 的 (a)/(b)，不得为自填
    c5  （写权边界）两侧证据位于【不同位置】，且不存在同一写权主体
        可无隔离改写两者（即 RECEIPT_INDEPENDENCE 成立）
    c6  （持久化）发送侧与收据侧【分别】具备各自的持久化成功证据
        —— 不得以一个总状态代替两侧

  ⇒ c1–c6 全部成立 ⇒ RECEIPT_VERIFIED
  ⇒ 任一不成立     ⇒ RECEIPT_VERIFIED = NOT ESTABLISHED（不是 INVALID）
```

```text
⚠ 【2026-11-01 三次修正（睫 NB-58 + 知微 Z-D2-01）】
   原文只写 c1–c4，存在两个缺陷：

   缺陷一（睫 NB-58）：receipt_seq 从未被校验
```

**两个结果域（不得相互代替）：**

| 情形 | 收件证据（本谓词） | 执行处理（D1 规则） |
|---|---|---|
| 尚未执行，能力缺失 | `NOT ESTABLISHED` | 无执行有效性结论 |
| 执行中，仅暂时缺证、仍在允许等待区间 | `NOT ESTABLISHED` | 阻止放行，按注册规则等待 |
| 已执行，已达注册判定点，仍缺必需见证 | `NOT ESTABLISHED` | **`ATTEMPT_VALIDITY = INVALID`**（适用 O-2） |
| 已确认适用的契约违反（c1/c2 存在但冲突） | 不签发 VERIFIED，保留原因 | 按相应停止规则处理，**不靠等待延后** |

```text
⇒ 撤回「唯一 INVALID 入口」这一无条件表述。
⇒ 不把暂时缺证提前判 INVALID，也不把 INVALID 写成科学 FAIL。
```

## 与 D1-2 的 TIME_GATE 关系

> **2026-11-01 三次修正（知微 Z-D2-04）：不能写成「等价展开」**
> ```text
> ⇒ 原文写「D1-2 的 TIME_GATE 三项 = S1 + S2 + 顺序证据」。
> ⇒ 【不等价】。D1-2 的第 (1) 项是「该臂的注册动作已按其语义完成」，
>    而 S1 只定义「WINDOW_CLOSE 权威记录已持久化」。
> ⇒ 记录权威地存在，不能单独证明其之前的注册动作正常完成。
>
> ⇒ 源码依据：write_window().__exit__() 在写入抛异常时
>    仍会关闭逻辑窗口并返回 False 继续传播异常。
> ⇒ 故「窗口确实关了」与「注册动作成功完成」本就可分叉。
> ```

```text
⇒ 正确关系：S1–S4 是【放行链条】，TIME_GATE 是【时序门】。
⇒ 二者交叉但不等价：
     TIME_GATE (1) 注册动作完成   ← S1 不覆盖此项
     TIME_GATE (2) ACK_RECEIVED    ← = S2
     TIME_GATE (3) 顺序证据成立    ← S3/S4 需继承
```

**ACTION_COMPLETION 必须显式保留：**

```text
⇒ S1 必须引用【已验证的动作完成依据】，
   不得由日志 ACK 或 WINDOW_CLOSE 存在性推出。
⇒ STORE_NULL 与 OFF 臂继续使用 D1 的分臂规则

```

**S1 的「且已达注册判定点（若相关）」含义（知微要求澄清）：**


# 三 · IC-3 · 协议版本一致性

## 凌翼的要求

```text
"明确从旧 EventRecord.commit_state、WRITE_COMMIT 到新结构的映射及弃用规则。
 另须固定事件粒度：某个写入完成事件对应一次底层文件写入，
 还是整个注册干预动作。多文件完成不天然意味着原子提交。"
```

## 契约 IC-3a · 字段映射与弃用

| 旧结构 | 新结构 | 弃用规则 |
|---|---|---|
| `EventRecord.commit_state` | 移出 → 独立 `StateTransition` 流 | 旧字段**不再有效**；不得从旧记录读状态 |
| `WRITE_COMMIT` | 拆为四个事件 | **名称弃用**；旧文档中出现的不得解释为已证明的写入提交 |
| 单一 `confirmed` 布尔 | `BINDING_CONFIRMED` / `ACK_CONFIRMED` | 旧布尔值**无法表达两者之分**，不得迁移 |

```text
⇒ 历史文档与冻结规格中的旧名称【不自动改写】（凌翼明令）。
⇒ 但新设计不得再使用。
⇒ 引用旧文档时须注明：该名称已弃用，其证明力为 NOT ESTABLISHED。
```

## 契约 IC-3b · 事件粒度（凌翼要求固定）

**问题：** `STATE_WRITE_COMPLETED` 对应一次底层文件写入，还是整个干预动作？

```text
⇒ 本契约固定为【一次底层文件写入】（PER_FILE_WRITE）。
⇒ 这是【设计选择】，不是唯一可行解。
```

```text
理由（基于已核实的源码结构）：
  storage.py L99-105  write_literal  → 写 literal.bin 一次
  storage.py L107-109 write_substrate → 写 substrate.bin 一次
  ⇒ 两个文件是【两次独立写入】，无原子提交。

⇒ 选择 PER_FILE_WRITE 的理由（修正后）：
   它把「动作完成」单独留给 IC-2 的 ACTION_COMPLETION 处理，
   而不是让一个写入事件同时承担两层含义。
```

```text
⚠ 【2026-11-01 三次修正（知微 Z-D2-05）：删除原「永假」论证】

⇒ 原文写「若粒度定为整个干预动作，则需跨文件原子提交机制，
   否则等于定义一条永假的规则」。
⇒ 【这个推导不成立】。

⇒ 反例：注册动作规定依次写 F1、F2。
    F1 正常写完关闭，F2 正常写完关闭，动作随后正常返回。
    在这条成功路径上，「该动作要求的两次写入均已完成」【可以为真】，
    即使中间状态曾可见、崩溃时可能只留下 F1。

⇒ 不存在原子性，并不使「动作级完成」永假。
⇒ 那是两件不同的事，我把它们混成了一件。
```

**四件事必须分开（知微的分层）：**

```text
① 单次文件写入正常完成
② 注册动作要求的【所有步骤】均正常完成
③ 跨文件提交具有原子性
④ 观察结果构成一致快照

⇒ ① 不能推出 ②（动作可能有多步）
⇒ ② 不能推出 ③（步骤全完成 ≠ 原子）
⇒ ③ 不能推出 ④（原子提交 ≠ 快照一致）
⇒ 但 ③④ 不存在，并不使 ①② 永假。
```

**动作级完成需要的定义（本契约给出框架，判定属 IC-2）：**

```text
对每个注册动作，须定义：
  · 预期子步骤集合（哪些文件、哪些写入实例）
  · 归属（execution / arm / action）
  · 哪些完成或异常记录参与判断
  · 聚合规则：全部完成 ⇒ 动作完成；部分完成 ⇒ 动作未完成

⇒ 可引用现有绑定结构，不要求新增字段。
```

**因此：**

```text
GRANULARITY = PER_FILE_WRITE

⇒ 每次 STATE_WRITE_COMPLETED 只覆盖【一个文件】。
⇒ 多文件完成【不】意味着原子提交（凌翼原文）。
⇒ 若将来需要「整干预动作」级别，须另建跨文件提交机制并单独授权。
```

```text
⚠ 直接后果：
   「literal 与 substrate 同时处于某一状态」这件事，
   在当前实现下【无法由写入事件推出】。
   ⇒ 只能由快照观测得知，而快照本身非原子（B-1 已诊断）。
   ⇒ 故 CROSS_FILE_ATOMICITY = NOT ESTABLISHED
```
