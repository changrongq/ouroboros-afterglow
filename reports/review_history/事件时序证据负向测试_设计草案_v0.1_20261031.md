# 2 · 组 F · 缺失（T-MISS）

## F-1 单条事件缺失

```text
构造：从已完成的事件流中删除一条中间记录（如 WRITE_COMMIT）

杀死哪种错误实现：
  把"能读出的事件"当成"应该存在的事件"的实现 —— 即不校验完整性。

排除的平凡解释：
  "实现本来就允许缺记录" —— 若如此，则该实现无法建立任何顺序，
  用例失败（INVALID 未触发）正好暴露这一点。

期望：INVALID（事件流不完整）
不得：把跳过后的序列当作有效顺序

PASS 也不证明：不能证明完整事件流的顺序正确。
```

## F-2 尾部事件缺失（与崩溃不同）

```text
构造：只删除最后一条记录，其余完整

杀死哪种错误实现：
  只做"前缀校验"、不校验"末尾是否应当有更多事件"的实现。

排除的平凡解释：
  "这只是一次正常结束" —— 必须由预先登记的必需事件集
  （如 WINDOW_OPEN / WINDOW_CLOSE 成对出现）来区分。

期望：INVALID（必需终止事件缺失）—— 直接适用 O-2 裁定
```

## F-3 整段缺失但声称执行过

```text
构造：登记了执行计划，但事件流为空

杀死哪种错误实现：
  把"没有记录"当成"没有失败"的实现。

期望：INVALID
特别要求（凌翼 O-2 原话）：
  尚未启动的执行，不得伪装成一次 INVALID 实验；
  已尝试执行但必需证据缺失 ⇒ INVALID。
  ⇒ 二者必须由【执行前登记】区分，不能由事件流自己区分。
```

# 3 · 组 G · 篡改（T-TAMPER）

## G-1 内容篡改（保持序号）

```text
构造：修改某条记录的 object_id 或 event_type，seq 不变

杀死哪种错误实现：
  只校验序号单调性、不校验内容绑定的实现。

排除的平凡解释：
  "这是合法的记录更新" —— 事件记录必须不可变；
  若允许更新，则必须同时改变 seq，否则与 G-1 无法区分。

期望：INVALID（内容与身份不符）
检测方式：记录必须带内容摘要，且摘要覆盖全部语义字段
```

## G-2 序号篡改（保持内容）

```text
构造：修改 seq 使某事件看起来更早

杀死哪种错误实现：
  用序号做排序却不校验序号与记录绑定关系的实现。

期望：INVALID
注意：若记录带整体摘要，改 seq 必然破坏摘要 ⇒ 可检测。
      若摘要不含 seq，则不可检测 ⇒ 该设计不成立。
```

## G-3 摘要重算型篡改（攻击者会算摘要）

```text
构造：修改内容【并】重算内容摘要，使自洽

杀死哪种错误实现：
  把"自洽"当成"真实"的实现。

⇒ 这是最关键的篡改用例。
⇒ 自洽只能证明"没有随机损坏"，不能证明"没有被改过"。

期望：必须由【独立于记录者的校验】发现
  ⇒ 若没有外部可信锚点（如阶段⑥封存、或先前已确认的头部摘要链）
    则该篡改【不可检测】
  ⇒ 此时应输出：TAMPER_DETECTION = NOT ESTABLISHED
  ⇒ 不得输出 PASS

这条用例的价值在于：
  它会强迫设计承认"自洽 ≠ 真实"。
```

# 4 · 组 H · 重放（T-REPLAY）

## H-1 整段事件流重放（旧执行冒充新执行）

```text
构造：把上一次执行的完整事件流，作为本次执行的事件流提交

杀死哪种错误实现：
  不校验 execution 身份的时序实现。

排除的平凡解释：
  "两次执行本来就相同" —— 必须由 execution_id 区分。

期望：INVALID

现行对照（已核实）：
  q3_qualify.py L184-187 已有同类机制：
    if d.get("run_id") != run_id: return FAIL, "... stale artifact rejected"
  ⇒ 但那只在 Q3 资格链，且判的是 FAIL 而非 INVALID。
  ⇒ 按凌翼 D 项，证据被冒充属"证据不可信"⇒ 应为 INVALID。
  ⇒ 这一点本文标记为【与既有实现不一致】，不自行修改。
```

## H-2 单条事件重放（重复插入）

```text
构造：把一条已确认事件重复插入事件流

杀死哪种错误实现：
  不校验 event_id 唯一性的实现。

期望：INVALID（或识别为幂等重试并去重，二者择一，但必须显式）
注意：必须与 F-1-a 的幂等提交区分：
  幂等重试 = 同一 event_id 的【重新提交】
  重放攻击 = 同一 event_id 出现在【已持久化流中两次】
```

## H-3 部分重放（拼接两次执行）

```text
构造：取执行 A 的前半段 + 执行 B 的后半段

杀死哪种错误实现：
  只校验单条记录、不做跨记录身份一致性的实现。

期望：INVALID
检测要点：execution_id 必须在【每条记录】上都出现，
  而不是只在头部出现一次。
```

# 5 · 组 I · 重排序（T-REORDER）← 本文重点补齐

## I-1 交换两条记录的顺序

```text
构造：把 WINDOW_CLOSE 与 WRITE_COMMIT 对调

杀死哪种错误实现：
  依赖"文件中出现的行序"而不校验 seq 的实现。

期望：INVALID（seq 与位置不符）
```

## I-2 重排序并同步改写 seq（使表面自洽）

**2026-10-31 修正（凌翼第六节）：本项原预期过强。**

```text
原文说：若摘要覆盖 seq 即可检测。
⇒ 这只能检测【没有同步重算摘要】的篡改。
⇒ 若攻击者能重算普通摘要，I-2 仍可绕过检查。

⇒ 因此 I-2 必须与 G-3 的攻击模型一致：
   攻击者有能力重算摘要，则普通摘要不提供保护。
```

```text
构造：对调两条记录【并且】改写其 seq 使单调

杀死哪种错误实现：
  只校验"seq 是否单调"、不校验"seq 是否与内容相符"的实现。

⇒ 这是重排序里最关键的一类。
⇒ 单调性只能证明序列合法，不能证明序列真实。

期望（修正后）：
  · 攻击者【未】重算摘要 ⇒ 可检测 → INVALID
  · 攻击者【已】重算摘要 ⇒ 普通摘要无法检测
    → REORDER_DETECTION = NOT ESTABLISHED
    （需 MAC/签名或外部可信锚点才能检测，本协议均无）
```

## I-3 删尾 + 重排（组合攻击）

```text
构造：删除 WINDOW_CLOSE，并把最后一条记录的 seq 改小

杀死哪种错误实现：
  分别校验"完整性"和"单调性"、但不校验两者组合的实现。

期望：INVALID
为什么单列：F-2（缺尾）与 I-1（重排）各自能检出，
  但若实现把两者做成两个独立检查且都只是"警告"，组合即可绕过。
```

# 9 · 三类"必然输出 NOT_ESTABLISHED"的情形

凌翼 D 项纪律的直接应用：

```text
G-3 摘要重算型篡改     ⇒ 无外部锚点则 TAMPER_DETECTION = NOT ESTABLISHED
I-2 重排+改 seq        ⇒ 无 seq 摘要绑定则 REORDER_DETECTION = NOT ESTABLISHED
J-3 伪造记录者身份     ⇒ 无 OS 隔离则 PRODUCER_IDENTITY = NOT ESTABLISHED
```

```text
这三条的共同点：
  它们不是"测试写得不严"，而是"某些能力确实不存在"。

⇒ 若把它们写成 PASS，会掩盖真实缺口。
⇒ 若把它们写成 FAIL，会把"没能力"说成"测出来不行"（违反凌翼 D 项）。
⇒ 唯一正确输出是 NOT_ESTABLISHED。
```

## 9.1 但 NOT_ESTABLISHED 是能力状态，不是测试结果（凌翼第六节）

```text
⇒ 重要区分：
   CAPABILITY = NOT ESTABLISHED  是【当前能力状态】
   测试是否通过                  是【一次实际测试的结果】

⇒ 二者不能合并。
⇒ 不得把 CAPABILITY = NOT ESTABLISHED 直接当作
   "一条实际测试已通过的输出"。
```

```text
⇒ 因此这三条用例在【将来真正实施】时，仍须各自给出：
   · 明确的拒绝预期（什么样算拒绝成功）
   · 可观测依据（观测什么）
   · 测试成功条件（满足什么才算该测试成立）

⇒ 当前状态应记为：
   DESIGN_STATUS = 用例已设计
   CAPABILITY_STATUS = 未建立
   TEST_EXECUTION_STATUS = 未执行
   ⇒ 三者分开记录，不用一个 NOT_ESTABLISHED 概括。
```
