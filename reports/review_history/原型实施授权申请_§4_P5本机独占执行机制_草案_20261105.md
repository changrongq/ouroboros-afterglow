# 三 · 判定对象：资格（grant），不是存活

```text
⇒ 【P4-5.2 已禁的一条，本节必须承接】
   「原实例已终止」【不构成】独占成立的依据。

⇒ 故本节判定的是【签发资格的授予关系】，不是进程存活状态。
   这是一个容易搞错的地方：
   · 「旧进程已经死了」 ⇒ 只是关于旧持有者的一个事实
   · 「旧持有者的资格已失效或撤销」 ⇒ 才是独占所需的那件事
   前者【不能推出】后者（P4-5.2 / P4-5.2a(iv)c）。
```

```text
⇒ 【承 P4-5.2a(iv)：授予关系须同时表达三件事，且互不替代】
   a. 此刻由哪个【具体实例】持有资格
      —— 不只是「某个 recorder_id 有资格」
   b. 该资格的【适用区间】（世代 / 执行区间）
   c. 原持有者的资格已【失效或撤销】
      —— 不只是「原持有者已终止」

⇒ 【承 P4-5.2a(v)：互斥性】
   同一权威域的重叠区间【不得】向两个实例同时授予可用签发资格。
   竞争者【不得】仅凭观察同一份状态各自宣布获得资格。

⇒ 【承 P4-5.2a(vi)：不可复用】
   旧资格不得被复用来授权新实例。
   后继者获得资格前，须有依据排除【全部】竞争者继续使用原资格，
   而不是仅排除「已知的那一个」。
```

```text
⇒ 【知微反例，本节必须能挡住，否则等于没做】
   旧实例 O 已终止，其终止凭证被持久保存。
   恢复者 N1、N2 都读到【同一份】凭证，都能重复验证，
   都指向同一 recorder_id。
   ⇒ 若本节的机制只是「检查 O 是否已终止」，
     N1 与 N2 会【同时】认为自己有资格。
   ⇒ 两份证据都是真的，但它们都只排除了 O，
     没有排除「N1 与 N2 并存」。

⇒ 故本节的机制必须使
   「N1 与 N2 同时持有可用资格」在【结构上不可能】，
   而不是在【观察上未发生】。
```

# 四 · 本机机制：选定与理由

```text
⇒ 【选定】Windows 本机内核级互斥对象
   （`CreateMutexW` / `WaitForSingleObject(0)`）+ 持久授予记录。

⇒ 【为什么不是文件锁（LockFileEx）】
   ⇒ 文件锁绑定到文件句柄。
     进程异常退出时句柄由内核释放，锁随之消失 —— 这本身是对的，
     但它【无法表达 P4-5.2a(iv)b 的"适用区间"】，
     也【无法表达 (iv)c 的"资格已撤销"】
     —— 锁消失只说明"没人占着"，不说明"谁曾经持有、何时失效"。
   ⇒ 故文件锁可作为【辅助】，不能作为资格的唯一依据。

⇒ 【为什么不是"只写一个锁文件"】
   ⇒ §0 D-2 已定：内容一致 ≠ 独占。
     两个进程都能写同一个锁文件，后写者覆盖前写者，
     双方都不报错。
   ⇒ 故本机互斥必须由【内核对象】裁决，不能由"谁能写文件"裁决。
```

```text
⇒ 【为什么不是命名管道 / socket 端口占用】
   ⇒ 它们确实能提供一次性占用，
     但与互斥对象相比没有额外好处，
     且引入了 §0 B 类左列之外的 OS 行为假设（端口 TIME_WAIT 等）。
   ⇒ 本版不采用，理由记录在此以便复核。
```

## 4.1 两层：内核互斥 + 持久授予记录

```text
⇒ 【第一层：内核互斥对象（裁决"此刻谁在跑"）】
   ⇒ 名称由【权威域标识 + 被管理对象范围】共同确定性派生
     —— 不是随机名，不是任意名。
   ⇒ 命名规则须使：
     · 同一 recorder_id、同一对象范围 ⇒ 同一对象名（这是互斥的前提）
     · 【不同 recorder_id、但对象范围重叠】⇒ 【必须】同一对象名
       —— 否则两个不同 recorder_id 各自指向同一份数据，
          会拿到两个互斥对象，【双双通过】。
          这正是 T-2 要防的"两个可独立签发权威事件的实例"。
     · 对象范围不相交 ⇒ 可以不同名（避免无关域互相阻塞）
   ⇒ 【对象范围必须是互斥对象名的一部分，不得只看 recorder_id】
     ⇒ 反例：A 以 recorder_id=R1 管理文件 F，B 以 recorder_id=R2 管理文件 F。
       若名称只由 recorder_id 派生，A、B 各拿一个对象，
       两者都认为"没有竞争者"，而它们写的是同一份 F。
     ⇒ 故名称的输入须包含【被管理对象的规范化标识】
       （规范化方式须可复现：同一对象路径 ⇒ 同一标识）。
   ⇒ 获取方式：创建后以零超时尝试获得所有权。
     失败 ⇒ 已有实例持有 ⇒ 【不得】自认为持有资格。
   ⇒ 【不用"等待后获得"作为通过路径】
     —— 等待成功只说明前一个释放了，不说明资格转移合法。

⇒ 【第二层：持久授予记录（裁决"资格是否合法转移"）】
   ⇒ 每次获得互斥后，须核对并追加持久授予记录：
     · 记录持有者 instance_id 与本次取得的 epoch
     · 记录上一持有者的资格状态（失效 / 撤销）
     · 记录本次取得的依据（哪条恢复判定允许）
   ⇒ 该记录是【追加】的，不修改既有记录（承 D1 不可变性）。

⇒ 【两层缺一不可】
   ⇒ 只有内核互斥 ⇒ 不能表达 (iv)b/(iv)c 的区间与撤销。
   ⇒ 只有持久记录 ⇒ 落入 D-2 的坑：两个进程都写、都认为自己对。
   ⇒ 【两层的关系是"与"，不是"或"】。
```

```text
⇒ 【与 §3 写权边界的关系（§3 L345-346 要求的澄清）】
   ⇒ §3 5.1(c) 的写权边界回答：「谁能写 ATTESTATION」。
   ⇒ 本节的独占回答：「谁能【签发权威事件】」。
   ⇒ 二者【是不同机制】，且【不得互相替代】：
     · 能写 ATTESTATION ≠ 有签发资格
     · 有签发资格 ≠ 一定是合法写 ATTESTATION 的主体
   ⇒ 覆盖对象不同、判定方式不同、失败出口相同（都 STOPPED）。
   ⇒ 【禁止】：用"我不能写 ATTESTATION"作为"我没有签发资格"的证明，
     或反之。
```

## 4.2 权限边界（回答裁定第①项）

```text
⇒ 【互斥对象的命名空间选择，决定了"权限域"是什么】
   ⇒ 本版选：本地会话无关的全局命名空间
     （`Global\` 前缀）。
   ⇒ 理由：若只在当前会话命名空间内互斥，
     另一会话中的实例将【看不到】该对象，
     于是"两个实例同时持有"在结构上可能发生。
     那会让 (v) 互斥性失效。

⇒ 【前提，属 §0 B 类右列（本地核验义务，不得豁免）】
   须实测确认：
   · 另一会话/另一用户的测试进程确实看到【同一】对象名
   · 若因权限不足无法创建全局对象，
     其结果必须是【明确失败 ⇒ STOPPED】，
     不得悄悄退化为会话内互斥而继续运行。
```

```text
⇒ 【权限边界的五项下限】
   (i)   对象名对【同一权限域内】的竞争者可解析到同一对象；
   (ii)  非该权限域的主体【不得】获得该对象的所有权
         —— 由 OS ACL 落实，本节不另行设计权限模型；
   (iii) 创建失败（权限不足 / 名称冲突 / 其他）⇒ STOPPED
         —— 不得"换个名字再试"；
   (iv)  命名规则本身须可复现：同一输入 ⇒ 同一名称。
         ⇒ 若命名含随机量或含 PID，则互斥即失效。
   (v)   【对象范围须进入命名输入】
         ⇒ 仅凭 recorder_id 派生名称不足（见 4.1 反例）；
           两个不同 recorder_id 管理同一对象时，
           必须落到【同一】互斥对象上。
         ⇒ 规范化须可复现：同一被管理对象 ⇒ 同一标识。
           不得因大小写、短路径、符号链接等写法差异而派生不同名称。
```

```text
⇒ 【(v) 为何单列】
   (i) 只说"同一权限域内可解析到同一对象"，
   但没有说【什么决定"同一对象"】。
   ⇒ 若把"同一对象"理解为"同一 recorder_id"，
     则不同 recorder_id 指向同一文件时互斥完全失效。
   ⇒ 故必须显式要求：对象范围是被管理的数据对象，
     不是 recorder_id 本身。
```

```text
⇒ 【明确不做的（裁定已排除）】
   · 跨主机 / 网络范围
   · 多用户或多权限域之间的协调
   · 高可用与自动故障转移
```

## 4.3 锁或令牌的可信来源（回答裁定第②项）

```text
⇒ 判定"我有资格"所依赖的每一样东西，都必须来自 W 不能伪造的地方。
```

| 依据 | 可信来源 | 若来自 W 会怎样 |
|---|---|---|
| 内核互斥所有权 | OS 内核，由 `CreateMutexW` 裁决 | W 声称"我拿到了"不构成依据 |
| `recorder_id` | 持久身份来源（P4-1.1 / P4-1.3） | W 自填的 id 只是被核验对象 |
| 本次 `epoch` | 持久 epoch 记录（P4-3.1..3.3） | W 申报的 epoch 不得直接采用 |
| 上一持有者的撤销依据 | 持久授予记录（4.1 第二层） | W 的"他已退出"陈述不构成依据 |
| 竞态判定结果 | 零超时等待的 OS 返回码 | W 的时序描述不构成依据 |

```text
⇒ 【一条硬约束（与 §3 判据①同形）】
   本节所有依据都必须由【非 W】取得或裁决。
   ⇒ 反例：W 在启动时写一个文件说"我是唯一活动实例"，
     其他实例读到后退出。
     ⇒ 它排除了"有人不信它"，没有排除"两个 W 都这么写"。
     ⇒ 这不是独占，这是自证。
```

```text
⇒ 【本版不引入密码学令牌】
   ⇒ 裁定第一节已排除生产密钥与真实生产签名。
   ⇒ 若将来引入签名式授予，须新增设计并另行授权，不得并入本节。
```

## 4.4 异常退出后的处理（回答裁定第③项）

```text
⇒ 【裁定 L46 的硬约束】
   「异常退出或独占状态丢失，
     不能直接等同于恢复签名权限。」

⇒ 故本版【故意不把】"内核互斥已释放"当作"可以签发了"。
   释放只说明【没有人在占用】，不说明【资格的转移已被授权】。
```

```text
⇒ 【进程异常终止后的四个事实，必须分别对待】
   ┌ 事实 1：内核互斥对象已释放
   │   ⇒ 由 OS 保证，可以观察到。
   │   ⇒ 但它【只】排除了"旧实例仍在运行"。
   ├ 事实 2：持久授予记录里，旧持有者的资格【仍标记为有效】
   │   ⇒ 崩溃前未写入撤销。
   │   ⇒ 这是正常现象，不是缺陷 ——
   │     因为"进程死了"不等于"资格该被撤销"。
   ├ 事实 3：该 epoch 是否已经产生过签发
   │   ⇒ 须查持久记录，【不能假设没有】。
   └ 事实 4：是否有其他实例也已观察到事实 1
       ⇒ 【必然可能有】。
       ⇒ 这正是 P4-5.2a(vi) 要求的"排除全部竞争者"，不是只排除已知的一个。

⇒ 【结论：进程异常退出后，直接重新签发是禁止的】
   必须走 P4 的恢复判定路径（P4-2.5 / P4-3.1..3.3 / P4-4.3），
   并在恢复成功后才允许新的签发。
```

```text
⇒ 【四个事实任意一个不可确认 ⇒ STOPPED（P4-4.3 独占权一项）】
   ⇒ 尤其：事实 3 不可确认时【不得】假定"尚无签发"。
   ⇒ 依据 P4-4.4：禁止通过"猜测缺失的历史"让恢复成功。
```

## 4.5 与 epoch 持久化状态的关系（回答裁定第④项）

```text
⇒ 【关系总述】
   本节的独占是【单次签发期的】；
   epoch 是【跨重启的世代标识】。二者不同层，须绑定但不得混同。
```

| 问题 | 独占（本节） | epoch（§5 / P4-3） |
|---|---|---|
| 回答什么 | 此刻【哪个实例】有权签发 | 本次执行属于【哪个世代】 |
| 生命周期 | 进程运行期为主，跨异常退出须重建 | 跨重启持续存在 |
| 丢失后果 | 不得签发 ⇒ STOPPED | 不得签发 ⇒ STOPPED |
| 能否互相推出 | **不能** | **不能** |

```text
⇒ 【三条绑定要求（缺一即 STOPPED）】
   (i)  授予记录中的 epoch 必须与持久 epoch 记录【一致】；
        不一致 ⇒ 视为 epoch 冲突 ⇒ STOPPED（P4-4.3 第五条）。
   (ii) 授予记录【不得】用新 epoch 覆盖冲突的旧 epoch
        —— 依据 P4-4.4 最后一项。
   (iii) 「持有资格」与「持有该 epoch」必须由【同一次】追加记录的
        同一条写入表达。
        ⇒ 【禁止】先获得资格、稍后再补写 epoch
          —— 中间窗口会形成"有资格但无世代"的状态，
             而该状态下的签发无法被归类。
```

```text
⇒ 【一处必须说明的不对称】
   ⇒ 独占可以【在进程内】持有，异常退出后可重建；
   ⇒ epoch 【不得】在仅内存中有效 —— 它必须已持久化
     才能作为签发依据（承 §0 D-1：无 fsync 时"已写入"≠"已可靠保存"）。
   ⇒ 故：授予记录的持久化若走在无 fsync 的路径上，
     其"已成立"只能读作"已形成内容"，
     不能读作"已可靠保存"。
```

## 4.6 失效时的 STOPPED 行为（回答裁定第⑤项）

```text
⇒ 【STOPPED 的含义（承 P4-4.3 / P4-4.5）】
   · STOPPED 状态下【不得】签发任何新的权威 EventRecord；
   · STOPPED 状态下【不得】自动恢复为 RUNNING；
   · 须由【外部显式处置】，处置边界见 P4-4.5。
```

```text
⇒ 【本节新增的失效入口，全部指向同一个出口】
   下列任一 ⇒ STOPPED：
   (a) 内核互斥获取失败（已有实例持有）
   (b) 内核互斥【创建失败】（权限/命名问题）
   (c) 全局命名空间不可用，无法保证跨会话互斥
   (c') 对象范围无法规范化到确定性标识
        ⇒ 于是无法保证两个不同 recorder_id 管理同一对象时
          落到同一互斥对象 ⇒ STOPPED
   (d) 授予记录的 epoch 与持久 epoch 不一致
   (e) 无法确认旧持有者的资格是否已撤销
   (f) 无法确认该 epoch 是否已产生过签发
   (g) 授予记录写入失败或状态未知（半写）
   (h) 检测到两个实例同时持有可用资格（互斥被破坏）
```

```text
⇒ 【(h) 的特别说明 —— 这是最坏的情形，须有明确处置】
   ⇒ 若观察到"两个实例同时持有可用资格"，
     说明 (v) 互斥性【已被实际破坏】，
     不只是在设计中未建立。
   ⇒ 处置：两个实例都【不得】继续签发，都进入 STOPPED，
     并保留证据（§0 S5 失败关闭；裁定六类故障之一）。
   ⇒ 【禁止】以"我持有得更早/更久"为由让任一方继续。
     那等于用时间顺序替代互斥判定。
```

```text
⇒ 【STOPPED 不是循环（承 P4 §5 的同一辩护）】
   ⇒ STOPPED 等待外部处置，不是"永远重试直至成功"。
   ⇒ 本节不定义外部处置的具体形式（属 P4-4.5 的范围）。
```

# 五 · 竞争验证（回答裁定 L37）

```text
⇒ 【裁定原文】
   「不支持多实例运行，不等于不测试多实例竞争。
     至少要能够启动两个本机测试进程进行竞争验证。
     成功条件不是两个进程协同工作，
     而是【任何时刻都不能同时获得有效执行权限】。」
```

```text
⇒ 【本节要求的验证形态】
   · 两个独立进程，各自完整走一遍启动与资格获取；
   · 两者都尝试进入可签发状态；
   · 记录每一时刻【声称持有资格】的实例集合；
   · 判据：该集合的势【始终 ≤ 1】。
```

```text
⇒ 【必须验证失败一侧，而不只验证成功一侧】
   ⇒ 必须构造下列情形并确认其进入 STOPPED：
     · 命名空间不可用
     · 授予记录与 epoch 不一致
     · 授予记录半写
     · 强制终止持有者后立即重启
   ⇒ 【只跑"正常启动 1000 次都成功"不构成本节的证据】
     —— 那只是"没撞上竞争"，不是"竞争被排除"。
     （裁定 L156 同一形状：1,000 次没出现失败 ≠ 已证明独占。）
```

```text
⇒ 【不得由本节宣布通过】
   ⇒ 本节定义验证形态；实际是否通过，须由测试运行与外部复核确定。
   ⇒ 故本节状态为
      P5_EXCLUSIVITY_ENFORCEMENT = NOT ESTABLISHED。
```

# 六 · 失败与拒绝（不得静默）

```text
⇒ 承 §0 S5（失败关闭）与 P4-4.3（STOPPED 条件）。
```

| 情形 | 处置 | 不得 |
|---|---|---|
| 内核互斥已被持有 | STOPPED（本进程不取得资格） | 不得等待后"顺手接管" |
| 互斥创建失败 | STOPPED | 不得改名重试 |
| 无法跨会话互斥 | STOPPED | 不得退化为会话内互斥后继续 |
| 授予记录 epoch 不一致 | STOPPED（P4-4.3 第五条） | 不得用新 epoch 覆盖 |
| 旧持有者撤销不可确认 | STOPPED | 不得以"进程已死"替代 |
| epoch 是否已签发不可确认 | STOPPED | 不得假定尚未签发 |
| 授予记录半写/状态未知 | STOPPED，保留证据 | 不得截断后继续 |
| 两实例同时持有资格 | 双方均 STOPPED，保留证据 | 不得按"谁更早"裁决 |

```text
⇒ 【与 §3 的一致处】
   §3 的"多份冲突 ⇒ STOPPED"与本表的最后两行同形：
   冲突时【不选一个赢家】，而是双方都停。
   ⇒ 理由相同：选择规则一旦是"取最后一个/取最早一个"，
     就把"唯一性"交给了时序，而时序本身不受保护。
```

# 七 · 与相邻节的接口

```text
⇒ P2（§3）
   ⇒ §3 产出的 ATTESTATION 说明"谁提交了这次 attempt"，
     它【不】说明"谁有权签发"（§3 八①③）。
   ⇒ 本节不消费 ATTESTATION，也不修改其格式。
   ⇒ 写权边界（§3 5.1c）与资格判定（本节）是【不同机制】，
     不得互相替代（见 4.1 末段）。

⇒ P1（§2）
   ⇒ 本节新增的持久授予记录若需编码，
     应【另行声明 OBJECT_TYPE】，
     不得复用 §2 的 0x01/0x02/0x03，也不得复用 §3 的 0x04。
   ⇒ 本版【不】规定该编码（见第八节第 ④ 项）。

⇒ 持久化（§5）
   ⇒ 本节依赖持久 epoch 与持久授予记录，
     但【不主张】它们已可靠保存（§0 D-1：无 fsync）。

⇒ P4（恢复）
   ⇒ 本节是 P4-5.2a 的机制落实，
     不是 P4 的替代或放宽。
   ⇒ 恢复判定仍由 P4-2.5 / P4-3.1..3.3 决定。
```
