**裁定性质：** 申请编制边界裁定
**适用基线：** P4 最终设计基线 / 事件时序协议 v0.2
**当前权限：** DESIGN_BASELINE 已接受；原型实施尚未授权
**日期：** 2026-11-04

### 一、关于最小原型的范围

**裁定：P5 最小独占执行机制必须纳入范围，不构成越界。**

原因：

恢复路径不仅需要判断历史记录是否完整，还需要在决定恢复后，保证不会同时出现两个拥有执行权限的主体。

如果没有 P5，恢复路径只能持续进入 `STOPPED`，无法检验其完整的安全执行闭环。

因此，最小原型的范围定义为：

**必须包含：**

1. P4 已定版的恢复身份与 epoch 判定路径，包括首次身份登记条件。
2. P1 最小引用完整性编码与验证。
3. P2 最小身份凭证格式、可信来源验证及绑定检查。
4. P5 本机、单一权限域内的独占执行机制。
5. epoch 分配、身份登记与持久化提交的明确边界。
6. 完整的 `STOPPED` 失败关闭路径，以及可观测测试证据。

**明确排除：**

- 分布式多节点一致性；
- 高可用与自动故障转移；
- 网络租约与跨主机独占；
- 多个合法活动写入者；
- 生产密钥与真实生产签名；
- 冻结 Q3 RC11 的任何修改。

这里必须区分：

**不支持多实例运行，不等于不测试多实例竞争。**

至少要能够启动两个本机测试进程进行竞争验证。成功条件不是两个进程协同工作，而是任何时刻都不能同时获得有效执行权限。

P5 可以采用受限的 Windows 本机原语，但不能只声明“理论上独占”。申请必须说明权限边界、锁或令牌的可信来源、异常退出后的处理、与 epoch 持久化状态的关系，以及失效时的 `STOPPED` 行为。

异常退出或独占状态丢失，不能直接等同于恢复签名权限。

**范围结论：**

`MINIMAL_SCOPE = P4_RECOVERY + P1_MIN + P2_MIN + P5_LOCAL_EXCLUSIVITY + EPOCH_DURABILITY + FAULT_INJECTION`

### 二、关于 P1 编码方案的决策权

**裁定：由 Coder 提出具体技术方案，由凌翼裁定设计边界，睫与知微进行独立复核。**

我给出的技术偏好是：

- 编码必须是唯一、确定、可跨进程复现的规范字节表示。
- 每条被验证的引用都必须明确对象类型、协议版本和完整的字节范围。
- 多字节整数优先采用固定的大端字节序。
- 采用显式长度、严格字段顺序与边界检查；拒绝歧义编码、重复字段及未定义的扩展内容。
- 完整性摘要优先采用 SHA-256，并为不同对象类型建立明确的域分离。
- 必须提供规范编码样例、预期摘要及非法编码反例。

Coder 可以提出更简单且同样满足这些性质的编码方案。上述偏好不是在看到字节布局和反例之前预先冻结实现。

**特别强调两条边界：**

**第一，完整性不等于可信身份。**
SHA-256 能够验证所读取字节与指定摘要是否一致，但无法独自证明摘要来源可信，也不能代替 P2 的身份凭证与授权链。

**第二，规范编码不等于原子持久化。**
编码、校验与持久化提交是不同问题。Windows 文件替换、缓冲区刷新、崩溃后的落盘状态以及 epoch 分配原子性，必须分别说明，不能因为采用了一种文件写入方式就宣称已经证明崩溃一致性。

Coder 下一次提交必须包含：

1. 一套首选方案及选择理由。
2. 完整的字节布局、端序、长度约束和版本规则。
3. 至少一组可独立复算的规范测试向量。
4. 非法输入和对象替换的验证反例。
5. 与 P2 可信凭证及持久化机制的接口边界。
6. 哪些性质仍未被证明。

**P1 技术定版权不下放给实现者独自行使。**

### 三、关于失败注入的覆盖与验收

**裁定：以安全不变量和故障覆盖为主要验收依据，以测试轮次作为最低工程证据。**

必须首先定义以下安全不变量：

- **S1：独占性。** 在受测的单机单权限域内，同一时刻最多一个主体拥有有效执行权限。
- **S2：epoch 不复用。** 已经持久分配的 epoch 不得再次分配；无法确认完整历史时必须 `STOPPED`。
- **S3：身份不重建越权。** 不能仅因历史缺失或身份不可读取就创建新身份，必须满足 P4-R1 全部首次创建前置条件。
- **S4：可信输入。** 引用完整性、身份来源与绑定验证未通过时，不得产生有效执行许可。
- **S5：失败关闭。** 崩溃、冲突、数据损坏或权限不确定时，不得绕过检查继续执行。

#### A. 必须覆盖的故障类别

| 故障类别 | 最低要求 |
|---|---|
| 半写或中断写入 | 覆盖各可达关键持久化边界的写入前、中、后 |
| epoch 冲突及历史缺失 | 冲突、重复、缺失、顺序不一致 |
| 双进程竞争 | 同时启动、竞争获取权限、异常退出后重新竞争 |
| P1/P2 完整性异常 | 字节篡改、截断、错误引用、错误身份绑定 |
| 崩溃后恢复 | 崩溃前后身份、epoch 与权限状态重新核验 |
| 首次身份登记 | 合法首次登记及三个前置条件分别不满足的反例 |

每个注入点必须定义明确的预期结果：允许安全恢复，或必须进入 `STOPPED`。

安全恢复只能发生在所有相关前置条件重新验证成功之后；不能把每次异常都简单归为成功或停止。

#### B. 最低执行轮次

以下数字是**原型验收测试底线，不是数学证明标准**：

- 每个确定性故障注入案例：至少 **30 次重复**，结果必须符合预期。
- 本机双进程竞争：至少 **1,000 组独立启动竞争测试**，包含不同调度与延迟。
- 崩溃后恢复：至少 **100 组跨进程重启测试**，覆盖不同的关键持久化阶段。
- 正常恢复闭环：至少 **30 次端到端成功执行**，确认原型并非只会停止。

全部测试要求：

- 安全不变量违反次数必须为 **0**。
- 每个失败都必须留下可复核的状态及事件证据。
- 故障注入位置、测试随机种子、执行命令、判定器与结果可复现。
- 所有未覆盖故障模型必须显式列出。
- 测试失败不得由自动重试掩盖。
- 不允许通过弱化 `STOPPED` 条件来提高通过率。

上述次数为首次实施申请的最低建议门槛。如测试架构显示不合理，Coder 可以提出有依据的调整申请，但不得未经批准自行降低门槛。

#### C. 什么才算通过

`TEST_GATE_PASS` 必须同时满足：

1. 指定安全不变量均有可执行断言。
2. 预定故障矩阵覆盖完成，无静默跳过项。
3. 最低轮次完成。
4. 安全不变量违反为零。
5. 预期 `STOPPED` 的路径全部真实停止。
6. 结果证据可独立复核。

即使全部满足，也只能写：

`BOUNDED_PROTOTYPE_TEST_GATE = PASS`

不能写：

`GENERAL_SAFETY_PROVEN = YES`

尤其不能把 1,000 次没有出现竞争失败等同于已经数学证明独占性。

设计层面的保证，还需要给出明确假设、状态转换推理、反例分析，以及机制与安全不变量之间的对应关系。
