# 一 · BD-56：凌翼的判断被证实 —— **代码是对的，MANIFEST 写错了**

## 凌翼的问题

RC5 §四 写：
```text
IDENTITY_ONLY_COMPONENTS = { literal.bin 16B, substrate.bin 8B }
```
按此字面执行，ΔS_identity_masked 与 ΔS_nonstorage 会同时把 literal 与 q 掩掉，
与同文件"唯一 nonstorage 数值 = q/2""D_NONSTORAGE_BASELINE over ΔS_nonstorage""h 依赖 literal 字节差"**全部矛盾**。
⇒ `executed semantics ≠ frozen binding semantics`。判定 BD-56 BLOCKING。

## 我查了实际代码（不猜）

```text
evaluate_basic_l1：h = literal 逐字节差异数（literal 可见）
evaluate_c2     ：T = Δz_C - Δz_B，只由 q 推出（literal 不参与）
```

⇒ **executed semantics 本来就是：**
```text
ΔS_identity_masked = literal + q（都可见）
ΔS_nonstorage      = q only（literal 被掩）
```
⇒ **凌翼的怀疑成立：代码是对的，是 RC5 §四 的 decomposition 写错了。**

## 修法（按凌翼最小修法）

```text
STATE_FIELDS                  = { literal.bin[16], substrate.bin[8] }
IDENTITY_ONLY_COMPONENTS      = EMPTY_SET     ← 本 harness STATE 里没有 identity-only content
LITERAL_STORAGE_COMPONENTS    = { literal.bin[0:16] }
NONSTORAGE_COMPONENT          = { substrate.bin q }   ← q 不放进任何 mask
NONSTATE_STORAGE_PIPELINE_NUISANCE_EXCLUSIONS = { filename, path, length, mtime, alloc, logs, container hash }

⇒ ΔS_registered      = literal change + q change
⇒ ΔS_identity_masked = ΔS_registered（identity mask 空 ⇒ literal 可见）
⇒ ΔS_nonstorage      = q change only（literal 被掩 ⇒ 只剩 q）
```

**为使"executed = frozen"可机器核验**，我把 decomposition 从"散文"提升为**代码里的具名单一真值**：
`afterglow_harness/harness_constants.py` 的 `DomainPartition`（`IDENTITY_ONLY_COMPONENTS` /
`LITERAL_STORAGE_COMPONENTS` / `NONSTORAGE_COMPONENT` / `NONSTATE_..._EXCLUSIONS`），并新增 `DOMAIN_PARTITION_HASH`。

```text
DOMAIN_PARTITION_HASH = 498ab252ed36f19cfdc0c1799af2651be9c2065e9f0e88b123fbdc16d40c3ea5
smoke_components 新增 5 条 BD-56 断言，全部 PASS（29/29）：
  identity_only == EMPTY / literal_storage == {literal} / nonstorage == {substrate}
  / ΔS_identity_masked includes literal / ΔS_nonstorage includes q
```

# 二 · CRLF -> LF（睫 建议乙）

```text
现状（睫实测）：RC5 MANIFEST = CRLF（CR=453, LF=453）
处置：转 LF。
结果：RC6 MANIFEST CR=0, LF=490；与 SPEC（LF）一致，canonical form 合规。
```

采睫建议乙的理由（同意）：1386ba22 vs b7ec1dca 那次混乱，根因正是"同一份文本在不同环节被序列化成不同字节"。
CRLF 就是那一类。现在改成本是一次重跑；冻结后改是一次重冻 + lineage 分叉。

**另（Git 传输层同名风险）：** 本地 clone 的 `core.autocrlf` 原为 `true`，
会在 checkout 时把冻结文本转成 CRLF、**破坏 hash**。已：
`git config core.autocrlf false` + 仓库根 `.gitattributes`（`spec/ prereg/ reports/ artifacts/` 标 `-text`）。
⇒ 从 GitHub clone 下来，冻结文件字节保持不变（已用 `git cat-file` 从远程 blob 复算验证）。
