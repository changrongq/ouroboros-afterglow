# 1 · 先定义记录者要保证的那件事

## 1.1 不是「有序」，是「可判定」

```text
凌翼 O-1 指出：记录接收顺序 ≠ 事件实际发生顺序（传输延迟）。
⇒ 所以记录者不能声称「我收到 A 再收到 B，所以 A 先发生」。
⇒ 记录者能声称的只有：
   「我以某个确定的顺序接收并持久化了这些事件，且这个顺序可恢复、可校验」。
```

## 1.2 记录的三个层次（须分开命名）

```text
L1 RECEIVED    记录者收到事件请求
L2 PERSISTED   记录者已落盘（含同步）
L3 ACKNOWLEDGED 记录者已向提交方确认 L2 完成

⇒ 凌翼提醒过：不能用一个名称假定四件事相等。
⇒ 这里同样：不能把 RECEIVED 当成 PERSISTED。
⇒ 只有 L3 才能作为【因果约束】的依据：
   例：WINDOW_CLOSE 必须达到 L3，才允许 SNAPSHOT_BEGIN。
   （这正是 O-1 要求的那条因果约束）
```

## 1.3 五类失败对应的层次

| 失败 | 击穿的层次 | 结果 |
|---|---|---|
| 记录者崩溃 | L2 可能未达成 | 状态未知 |
| 重复序号 | 编号唯一性 | 顺序不可判定 |
| 持久化失败 | L2 | 已确认但未落盘 |
| 重启 | 序号域 | 新旧序号不可比 |
| 未确认事件 | L3 | 提交方不知结果 |

# 2 · 失败模型一：记录者崩溃

## 2.1 崩溃发生的三个位置

```text
位置①  收到请求前崩溃
        ⇒ 事件【从未存在】。提交方会超时。
位置②  落盘中崩溃（写入磁盘但未返回）
        ⇒ 磁盘上可能有【半条记录】或【完整但无人知晓】的记录
位置③  落盘后、确认前崩溃
        ⇒ 记录存在，但提交方未收到 ACK
```

## 2.2 不可区分性（这是核心困难）

```text
对提交方而言，位置② 与 位置③ 【看起来一样】：都没收到 ACK。

⇒ 无法从提交方视角区分「写了但没确认」与「没写」。
⇒ 因此不能靠【提交方重试】来保证不重复：
   若位置③后提交方重试，可能产生两条记录指向同一事件。
```

## 2.3 本设计的处置（不代凌翼裁定）

```text
规则 F-1-a：
  记录者必须在【写入记录内容】中自带唯一事件 ID，
  该 ID 由【提交方】生成（不是记录者生成）。
  ⇒ 重试携带同一 ID ⇒ 记录者可以识别为重试而非新事件。

规则 F-1-b：
  记录者收到重复 ID 时：
    (i) 若已有该 ID 的 L2 记录 ⇒ 视为幂等，重发 ACK
    (ii) 若无   ⇒ 正常写入
  ⇒ 这是幂等提交，不是去重。
  ⇒ 不用「序号」做去重键（序号是记录者分配的，重试时还没有）。

规则 F-1-c：
  崩溃恢复时，记录者必须【扫描尾部】：
    若最后一条记录不完整 ⇒ 截断，并记一条 RECOVERY_TRUNCATED
    不得把不完整记录当作有效事件

规则 F-1-d：
  超时后仍未 ACK ⇒ 按 O-2 裁定处理：
    WINDOW_CLOSE missing + deadline exceeded → INVALID
  不得补造 WINDOW_CLOSE
```

## 2.4 一个必须承认的残余风险

```text
位置② 崩溃产生「磁盘上有完整记录，但提交方认为失败并重试」的情况。
⇒ F-1-a 的事件 ID 使重试幂等，故不会产生两条。
⇒ 但如果记录【已写而提交方判超时并放弃】，
   则存在一条「记录者认为已提交、提交方认为未提交」的记录。
⇒ 该状态【不可消除】，只能被【标记】：
   记录中保存 commit_state，CRASH_RECOVERED 时置为 UNKNOWN_ACK。
⇒ 该记录不得作为 positive 证据使用，
   但可用于说明「此处发生过分歧」。
```

# 3 · 失败模型二：重复序号

## 3.1 三种来源

```text
来源①  记录者重启后序号计数器回退（见失败模型四）
来源②  多个记录者实例并存（配置错误或多进程误启）
来源③  序号由非受信路径签发（绕过记录者）
```

## 3.2 检测规则

```text
规则 F-2-a：
  序号必须在【每条记录内】出现，且单调递增。
  发现 seq[i] <= seq[i-1] ⇒ ORDER_VIOLATION

规则 F-2-b：
  序号必须绑定记录者实例身份 (recorder_id, epoch)：
    完整键 = (recorder_id, epoch, seq)
  ⇒ 同一 epoch 内 seq 必须严格递增。
  ⇒ 不同 epoch 的 seq【不可直接比较】。

规则 F-2-c：
  若出现同一 (recorder_id, epoch, seq) 但内容不同
  ⇒ SEQ_REUSE_WITH_DIFFERENT_CONTENT → INVALID
  ⇒ 这是最严重的一种：无法判断哪一条是真相
```

## 3.3 处置

```text
重复序号 ⇒ 顺序不可判定。
⇒ 按 O-3 的同一逻辑：不制造冲突，但也不假装顺序成立。
⇒ 标记 ORDER_PROOF = NOT ESTABLISHED，并判 INVALID（若该顺序被用于科学判定）。
⇒ 不得「取先出现的」「取后出现的」或「取序号大的」。
```

# 4 · 失败模型三：持久化失败

## 4.1 四种失败点（对应第 1.2 节的层次）

```text
① write 抛异常        ⇒ 明确失败，可重试
② write 成功但未落盘   ⇒ 进程崩溃后丢失（当前 harness 无 fsync，属此类）
③ fsync 失败          ⇒ 部分平台不报（这是真实风险）
④ 磁盘满 / 只读挂载    ⇒ 可能延迟暴露
```

## 4.2 规则

```text
规则 F-3-a：
  「已持久化」必须以 fsync（或等价同步）返回为界，不是以 write 返回为界。
  ⇒ 直接后果：WRITE_COMMIT 的四候选里，(a)(b) 不能称持久化（见事件证据流 4.4b）。

规则 F-3-b：
  fsync 失败 ⇒ 记录者不得发送 ACK。
  ⇒ 提交方超时 ⇒ 按 O-2 处理 ⇒ INVALID。

规则 F-3-c（**2026-10-31 修正**，凌翼第五节）：
  不得在 fsync 失败后重试写【同一条记录】的修改版，
  因为无法确定原记录是否部分落盘。
  ⇒ 重试必须写【新记录】，引用同一 event_id，
     并标记 retry_of=<原 seq>。

修正说明：
  原规则「引用同一个 event_id」与「同一 event_id 只对应一个已确认事件」
  的幂等规则【冲突】—— 它会让一次逻辑事件产生多条都自称权威的记录。

  修正为两种身份分开：
    event_id    = 逻辑事件身份（一次逻辑事件只有一个）
    attempt_id  = 本次提交尝试身份（每次重试不同）

  ⇒ 恢复流程必须先检查已有记录及其可确认状态，
     不得因上一次 fsync 失败就自动制造另一个【权威事件】。
  ⇒ 若两条都达到 L3 ⇒ CONFLICTING_AUTHORITATIVE_RECORDS → INVALID。
```

## 4.3 一个必须写明的限制

```text
fsync 在部分文件系统（尤其网络盘、部分虚拟化磁盘）上
不保证真正持久化，只保证「已提交给设备」。

⇒ 本设计无法消除这一点。
⇒ 只能记录：fsync_returned = true / false
⇒ 并明确：PERSISTED 的定义是「fsync 返回成功」，不是「物理落盘」。
⇒ 这是定义层面的诚实，不是保障。
```

# 5 · 失败模型四：重启后序号域

## 5.1 核心问题

```text
记录者重启后，若简单地从 0 或「上次最后序号 +1」继续：
  · 从 0 继续 ⇒ 与旧记录序号冲突
  · 从 last+1 继续 ⇒ 若 last 读取本身来自不完整记录，会出错

⇒ 更根本：重启【本身】是一个需要被记录的事件。
```

## 5.2 规则

```text
规则 F-4-a：
  每次启动，记录者生成新的 epoch（单调递增，持久化）。
  序号域 = (recorder_id, epoch)。不同 epoch 序号不可比。

规则 F-4-b：
  epoch 必须【持久化】，且其分配本身必须原子
  （读-改-写，需锁或原子替换）。
  ⇒ 当前 harness 无此原语（见第 0 节）⇒ 属新增能力，不在本文范围。

规则 F-4-c：
  启动时必须写入一条 RECORDER_STARTED 记录，
  携带：新 epoch、上一次 epoch、上次最后完整 seq、恢复动作。

规则 F-4-d：
  跨 epoch 的顺序【不可推定】。
  ⇒ 若一次执行跨越了记录者重启，
     则该执行的 EVENT_ORDER_PROOF = NOT ESTABLISHED
  ⇒ 除非有其它独立见证（凌翼 O-1 提到 C 可实时参与）。
```

## 5.3 这条最容易被忽略

```text
大多数人会认为「重启后续号」是小事。
但 epoch 分割的价值在于：它让【不可比】变成【可识别】。

⇒ 若不分割：重启前后的序号看起来可比，实际不可比。
  这是【制造假顺序】。
⇒ 与 O-3 的判断一致：不对尚未证明可比较的数据制造冲突，
  反过来也不能制造顺序。
```

**2026-10-31 补记（凌翼第五节）：**

```text
⇒ epoch 切分是正确的【保守基线】，
   但不意味着所有跨重启顺序在原理上永远不可证明。
⇒ 若未来存在可信的跨 epoch 连续性见证，
   可以单独审查其证明能力。
⇒ 因此本项应写为：

   CROSS_EPOCH_ORDER_PROOF = NOT ESTABLISHED（当前）
   CROSS_EPOCH_ORDER_PROOF = 可在有连续性见证时单独审查（未来）

⇒ 不是「永远不可能」，是「当前未建立」。
```

# 6 · 失败模型五：未确认事件

## 6.1 三种未确认状态（必须分开）

```text
U-1  NOT_SENT      提交方确定未发送
U-2  SENT_NO_ACK   已发送，未收到 ACK，且记录者未崩溃
U-3  SENT_CRASHED  已发送，记录者崩溃，无法得知
```

## 6.2 规则

```text
规则 F-5-a：
  U-1 ⇒ 事件确定不存在。不得记入事件流。
  U-2 ⇒ 必须【保持未确认】直到超时，不得臆测成功。
  U-3 ⇒ 标记 UNKNOWN，不得判为成功，也不得判为失败。

规则 F-5-b：
  任何【用于因果约束】的事件（如 WINDOW_CLOSE）
  必须处于 CONFIRMED 状态。
  处于 U-2 / U-3 ⇒ 视为「缺必需关闭见证」⇒ 按 O-2 判 INVALID。

规则 F-5-c：
  允许记录 ABORT / RECORDER_FAILURE 作为终止原因，
  但【不能替代】正常关闭见证（凌翼 O-2 原话）。
```

## 6.3 一个反直觉的点

```text
「未确认」不是「失败」。
⇒ 把 U-2/U-3 写成 FAIL，等于把未知当成否定。
⇒ 这正是凌翼 D 项反复强调的那条：
   缺证是 INVALID，不是 FAIL。
⇒ 本设计的每一条失败规则都必须遵守这一点。
```

# 7 · 汇总：失败 → 状态 → 是否可作证据

| 失败 | 状态标记 | 可作 positive 证据？ | 判定 |
|---|---|---|---|
| 记录者崩溃（位置②③） | `UNKNOWN_ACK` | 否 | INVALID（若用于判定） |
| 重复序号 | `ORDER_VIOLATION` | 否 | INVALID |
| 同键不同内容 | `SEQ_REUSE_WITH_DIFFERENT_CONTENT` | 否 | INVALID |
| 持久化失败 | `fsync_returned=false` | 否 | INVALID |
| 跨 epoch | `ORDER_PROOF=NOT_ESTABLISHED` | 否 | INVALID |
| 未确认 U-2/U-3 | `UNCONFIRMED` | 否 | INVALID |

```text
⇒ 六种失败，无一种产生 FAIL。
⇒ 全部是 INVALID 或 NOT_ESTABLISHED。
⇒ 因为六种都是「证据不足」，不是「证据否定」。
```

# 10 · 一句

```text
五项失败里，四项的正确答案都是「不知道」。
而「不知道」在证据体系里有一个专门的名字：INVALID。

我原以为失败模型是用来防止出错的。
写完才明白，它们的真正作用是
让「我们不知道」这句话，也能被记录下来，
并且不会被下一个人读成「没问题」。
```
