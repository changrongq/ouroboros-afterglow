## 二、[P1] J 时点无效仍通过，执行 oracle 与冻结 oracle 不一致

位置：[fixtures.py:637](https://github.com/changrongq/ouroboros-afterglow/blob/63539abd9a3e13964230368d7fd7bf2b6aca01c5/afterglow_harness/fixtures.py#L637)、[fixtures.py:666](https://github.com/changrongq/ouroboros-afterglow/blob/63539abd9a3e13964230368d7fd7bf2b6aca01c5/afterglow_harness/fixtures.py#L666)、[manifest_bind.py:310](https://github.com/changrongq/ouroboros-afterglow/blob/63539abd9a3e13964230368d7fd7bf2b6aca01c5/afterglow_harness/manifest_bind.py#L310)。

`j_timing_ok` 被放入 actual，却不参与 INVALID 门禁。V5a/b/d/e/f 的 `FixtureResult.expected` 又删除了 `j_timing_ok=True`，但被 hash 绑定的 `FIXTURE_BUNDLES[...]['oracle']` 仍含此要求。

**反例：** 只让 `_apply_j_witnessed()` 返回的 J-after 与 handoff 见证不一致，不改变实际状态。结果：

```text
V5a.actual.j_timing_ok = false
V5a.actual.L2 = PASS
V5a.oracle_match = true
完整 13 项仍全部 oracle match
```

这是无效见证应触发拒绝的测试，不声称实际系统已经发生过非法 J 时序。它证明当前资格比较没有消费已冻结的要求。

**修复：** invalidity 优先于科学状态；任一 required J 时点见证无效必须按相应 scope INVALID。expected oracle 只保留一个冻结来源，由独立 comparator 消费；若实现需要另一份表示，启动前验证语义完全一致，不能分别手写后只校验各自文件 hash。

## 三、[P1] V5 未建立真实 pre-reset 门槛，并将失败回填为 C3

位置：[fixtures.py:600](https://github.com/changrongq/ouroboros-afterglow/blob/63539abd9a3e13964230368d7fd7bf2b6aca01c5/afterglow_harness/fixtures.py#L600)、[fixtures.py:626](https://github.com/changrongq/ouroboros-afterglow/blob/63539abd9a3e13964230368d7fd7bf2b6aca01c5/afterglow_harness/fixtures.py#L626)。

V5 主路径没有执行 Basic L1 / C1。其 pre C3 使用 `T_j_after`，并非原先 `S_write` 的 `T_write`；若 C3 判定不是 C1/C2/C3，又执行：

```python
pre_class = c3_pre['result'] if c3_pre['result'] in (C1, C2, C3) else C3
```

即失败时默认成 C3。

已复现两个反例：

1. storage writer 全部 no-op：V2/V3 已正确拒绝，但 **V5a 仍报 PRE C3 / POST C3 / L2 PASS / oracle match**，而 `post_C1_ok=false`。
2. 把内容相关 extra writer 换为恒定 extra，使 `T_write` 全为 +1、根本没有 pre C3：**V5b 仍报 PRE C3 / POST C2 / oracle match**。

**修复：** pre 证据从 `S_write` 计算，完整执行 Basic L1→class 判定，不通过就不提升层级。J-after 只记录中间状态，不能替代 pre 参照点。删除失败回填 C3。不要只在 V2/V3 helper 中执行这些门槛，V5 也必须复用相同 gate。

## 四、[P1] Ledger 把 B 的 J 见证与 C 的 reset 摘要接在一起

位置：[fixtures.py:282](https://github.com/changrongq/ouroboros-afterglow/blob/63539abd9a3e13964230368d7fd7bf2b6aca01c5/afterglow_harness/fixtures.py#L282)、[fixtures.py:310](https://github.com/changrongq/ouroboros-afterglow/blob/63539abd9a3e13964230368d7fd7bf2b6aca01c5/afterglow_harness/fixtures.py#L310)。

逐 member 的 `s_write/j_after` 取 B；reset 循环覆盖 `handoff_snap/restored_snap`，最终只留下 C。`_member_ledger_entry()` 把它们写成没有 arm 标识的一条摘要链。

**无故障注入的正常 V5a 就有：**

```text
四个 member 均：j_after_digest != handoff_digest
同一条记录又写：j_timing_valid = true
```

这不是 SHA-256 碰撞或真实时序非法，而是记录串错了对象。虽然内部逐臂比较可为真，外部审阅者拿到的证据链不能重建它。

RC7 增加了每 member 的 T 字符串，改善了可读性；但还没保存足够的逐臂原始观察来独立复算 T、验证 baseline 与 logical pair 的对应。全体 arm 的 reset outcome 也只保存为一个 member 布尔聚合。

**修复：** 使用 `member -> arm -> phase` 结构保存 A/B/C 各自的快照、digest、reset outcome；J 前后与 handoff 必须来自同一 arm。同一组 literal/q 原始观察应能重算 canonical digest 和 T，而不是只信计算后字符串。C2/C3 的稳定 logical identity / pre-post realization matching 仍须实例化；当前 PERSISTENCE_MATCH_RULE bundle 仍只显式写 C1。

## 五、[P1] 运行时绑定模块仍未受绑定保护

旧审阅已经指出 `manifest_bind.py` 在运行时参与资格决定，但 RC7 MANIFEST 仍把它列为“不因变动自动推翻 artifact”的 build provenance。

**独立复制目录中的反例：**

1. 给 `writers.py` 增加注释，造成真实的已绑定源码 hash 漂移。
2. 只在未被强制核验的 `manifest_bind.py` 末尾令 `COMPONENT_FILES={}`。
3. suite 得到空组件表，`all({}.values())` 为 True，**13/13、PASS、QUALIFYING RUN**。

这是受控的校验故障注入，不是针对实际仓库的恶意操作；原始文件未变。它直接表明“只核验代码清单给出的条目”无法发现清单本身漏项。

**修复：** 将运行时参与资格判定的全部模块纳入绑定，或从资格路径移除构建模块、读取不可变的声明数据。角色集合也必须非空且完整，逐个 role 对应固定文件/hash；不能把空表当作无漂移。

## 六、V4b 与 INVALID 传播仍有未闭合之处

### V4b wrapper 仍能选择 ON/OFF

位置：[fixtures.py:539](https://github.com/changrongq/ouroboros-afterglow/blob/63539abd9a3e13964230368d7fd7bf2b6aca01c5/afterglow_harness/fixtures.py#L539)。

新的 wrapper 公开：

```python
combined_write(payload, storage_mode, extra_mode)
```

使用相同 payload 和 STORE_FULL，一个实例传 EXTRA_OFF，另一个传 EXTRA_CONTENT，实测 literal 完全相同，q 分别为 0、2。**同一个公开入口的参数已经提供了反事实开关。** 是否恰好有名叫 `extra_on` 或 `set_extra_off` 的方法，不足以判断架构可识别性。该 fixture 仍输出 ARCHITECTURALLY_NOT_IDENTIFIABLE 并匹配 oracle。

应提供真正不暴露此选择的受测接口，且让 B/A 与能力检测指向同一个被测对象。无需靠不断增加方法名黑名单解决。

### V5f 把 reset INVALID 降为 L2 FAIL

位置：[fixtures.py:705](https://github.com/changrongq/ouroboros-afterglow/blob/63539abd9a3e13964230368d7fd7bf2b6aca01c5/afterglow_harness/fixtures.py#L705)。

令 `_reset_arm` 返回无效：V5a 正确给 INVALID，但 V5f 只令 `post_c1_ok=false`，随后走 `_l2_judge_simple()`，得到 **L2 FAIL**。此次 oracle 不匹配，所以不是假 PASS；但协议无效仍被错分成科学负向，旧问题没有在所有路径解决。

应共用 invalidity 优先的聚合入口，不在单个 fixture 重写简化版。

## 七、读路径修复的实际范围

V5 确实调用了 observer 和两条 reader，原“完全未调用”的问题已有进展。但现在 affine reader 只读 B 臂，B 的 q 在这些正常 fixture 中始终是零。

把 affine reader 替换成完全不读文件、只返回中性输入 u 的函数，suite 仍有 13/13 oracle match。组件 smoke 测试另外检查过非零状态，这点予以保留；这个反例说明的是资格 run 的读路径见证尚不足以证明目标 C 状态影响后续计算。

建议在目标 C 臂及合适对照上实际执行中性 probe，按冻结 reader 定义验证预期计算关系，并检查调用前后注册状态不变。该结果只作读路径见证，不充当 C2/C3 新 projection。
