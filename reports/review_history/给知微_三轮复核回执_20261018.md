## 2 · 清理项：你说的三种情形，我核实后全部成立

### 2.1 缺陷 A：`main` 返回 0 而清理失败

**核实：成立。** 原代码：

```python
try:
    return _run_checks(...)      # 返回 0
finally:
    exited, detail = _terminate_and_confirm(...)
    print(f"CLEANUP: ...")       # ← 只打印，不改返回值
```

`finally` **只能打印，无法改变已决定的返回值**。所以确认退出失败时仍返回 0。你说得准确。

**已修**：模块级 `CLEANUP_FAILED` + 入口点翻译

```python
if CLEANUP_FAILED:
    sys.exit(EXIT_CLEANUP_FAILED if rc == 0 else rc)
```

- `rc=0 ∧ 清理失败` → **退出码 3**
- `rc≠0 ∧ 清理失败` → **保留原具体码**（不掩盖检查自身的失败）

**实测**：`EXITCODE_WHEN_CLEANUP_FAILS=3`；真实运行清理成功时 `EXITCODE=0`。

### 2.2 缺陷 B：等待接口抛异常会跳过句柄释放

**核实：成立，而且比你说的更宽。**

原代码 `WaitForSingleObject` **完全在 try 之外**；更早的版本里 `CloseHandle` 还包在一个 `except: pass` 里——**第一个句柄释放失败会跳过第二个**。

**已修**：三步各自独立守护

```python
try:  k32.TerminateProcess(...)
except: detail += ...

try:  waited = k32.WaitForSingleObject(...)     # ← 单独守护
except: detail += ...

try:  hp2 = k32.OpenProcess(...)                # ← 单独守护
except: ...

_close(pi.hp, "process")                        # ← 每个句柄独立关闭
_close(pi.ht, "thread")
```

`_close()` 内部各自 try，一个失败不影响另一个。
