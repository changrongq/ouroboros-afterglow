## A.4b A-M3 的前提缺陷：先证 A-M2 指向的是【实际写入者】（知微 §4.1）

**⇒ 这是本文原先漏掉的一格，比 A-M3 本身更靠前。**

```text
反例：
  控制器按计划启动正确的 writer
  采集到正确的 token、程序摘要、启动信息
  然而实际写入目标文件的是【另一进程】
  ⇒ 只要 A-M2 记录的是那个合法进程 ⇒ A-M1 与 A-M2 完全可以相符
  ⇒ 于是 A-N1 的「A-M3 身份不一致」【并不必然触发】

⇒ 结论：
   必须先证明 A-M2 指向【实际写入者】，身份比较才有归属意义。
   增加 evaluator 参数或上游入口，只解决【证据送到哪里】；
   不解决【证据从哪里来】。
```

**⇒ 有限设计可任选其一，但须写清独立前提（知微建议）：**

```text
路线甲：可信采集路径把【实际写入操作】关联到被保留的进程实例及目标对象
路线乙：在受控写入阶段，以可核查的权限与资源约束，
        建立「只有注册 writer 能修改注册对象」的条件，
        再结合独立 before/after 与 write/no-write 对照归属变化
        ⇒ 须处理：注册范围内已有写句柄、内存映射、子进程、代理写入
        ⇒ 不能只写「该账户有权限」
```

**⇒ 若采用可信代理代写：**
```text
⇒ 必须明确真实写入角色【包含代理及其职责】
⇒ 不得把代理的实际写入冒称为业务进程直接写入
```

# 两链的交汇点

```text
链 A 输出：  这次写入是【谁】写到【哪个对象】的
链 B 输出：  这次写入属于【哪一次执行】

C1 的证明责任 ≠ A ∩ B。

本文承担的证明责任 = A ∩ B（即 R-7 / R-8 的展开）。
C1 的完整证明责任还含 R-1..R-6 与 §28.1 witness，不在本文范围；
不得因两条链建成而被认为 C1 已可签发。（睫 Q3）
  ⇒ 只有 A（谁写的）⇒ 不知道是哪一次 ⇒ 旧证据可冒充
  ⇒ 只有 B（哪一次）⇒ 不知道是谁写的 ⇒ 任意进程可冒充
  ⇒ 两者都不是充分条件，都只是必要条件
```

**⇒ 而 v0.3 的 R-1..R-10 中：**
```text
R-7（writer 关联）= 链 A 的 A-M3
R-8（execution 来源）= 链 B 的 B-M7（且 §31 L1948-1949 已要求，属 gate 5 具体化）
⇒ 两条链不是新规则，是把 R-7 / R-8 展开成可检验的流程
```

## 交汇点的一个硬问题：两链共用的主键还不存在（睫 NB-50）

**⇒ 这可能是整份文档最重的一格。**

```text
链 A 输出：谁、写到哪个对象
链 B 输出：哪一次执行
⇒ 二者要合成 A ∩ B，需要一个【共同主键】：execution_id

而字节事实：
  · grep execution_id 在 harness 代码里零命中（literal）
  · q3_qualify.py 有 run_id，但那是 Q3 运行标识，不是 C1 的 execution_id
  · fixtures.Ledger 有 fixture_id，但它 ≠ 每次运行唯一身份

⇒ 于是 A ∩ B 现在的真实形状是：【两个空集取交集】。
⇒ 而本文原先把交汇点画成「两条流程的接合处」——
   看起来只差把它们接起来。
⇒ 而实际是：连接点本身还不存在。

⇒ 因此：execution_id 的产生机制是【两链公共前置】，
   须先于两链各自实现，且【只建一次】。
⇒ 否则两链分头建，会长出两个不能互通的标识。
```

## A-G5 的准确说法：不是「没检查」，是「不可表达」（睫 NB-51）

# 六阶段执行时序（知微 §7）

> 知微建议：「下一步只补一条执行时序」。
> 本文补的是**时序**，不是机制、不是授权、不是结论。
> 每一阶段只回答三件事：**谁在动 / 动的是什么 / 落在哪一层证据上**。
> 凡标 `[冻结代码]` 者，均可在冻结件中逐字查到；凡标 `[缺口]` 者，
> 均为**当前不存在**的东西，本文**不**代为设计。

## 0 · 为什么必须有这张表

因为链 A 和链 B 现在**各自都不知道自己处在时序的哪一格**。

- 链 A 问「谁写的」——但「谁写的」只有在**写入窗口**这一个区间内才有意义；
- 链 B 问「这一次执行是哪一次」——但「这一次」只有在**身份先于产物**时才能绑定。

两条链缺的是同一个东西：**一个把「时刻」变成可判定对象的结构**。
没有这张表，A 与 B 只能各自描述，无法在同一时间轴上对齐（见 NB-50）。

## 1 · 表（六阶段）

| # | 阶段 | 谁在动 | 动的是什么 | 证据层 | 冻结代码位置 |
|---|---|---|---|---|---|
| ① | 事前计划 | 控制器（非被测系统） | run 身份、预期 payload、门集合 | META | `q3_qualify.py` L98-100 `[冻结代码]` |
| ② | 基线建立 | writer | `literal.bin` / `substrate.bin` 置零 | STATE | `storage.py` L54-57 `[冻结代码]` |
| ③ | 写入窗口 | writer（唯一持写权者） | registered state | STATE | `storage.py` L95-97, L112-124 `[冻结代码]` |
| ④ | 观测快照 | observer（非 writer） | STATE_FIELDS 独立重算 digest | STATE → META | `observer.py` L33-35, L44-57 `[冻结代码]` |

## 2 · 逐阶段的可否定点

时序表的价值不在「顺序」，在于**每一格都有独立的可否定点**。
一个阶段如果无法被单独否定，它就不是一个阶段，只是一句叙述。

### ① 事前计划 `[部分缺口]`

```text
存在：q3_qualify.py L98  run_id = uuid.uuid4().hex
      q3_qualify.py L100 child_env = {"AFTERGLOW_Q3_RUN_ID": run_id}
      ⇒ 身份【先于】任何产物产生，且经环境注入子进程

存在：q3_qualify.py L184-187
      if d.get("run_id") != run_id: return FAIL, "... stale artifact rejected"
      ⇒ 消费端【强制】比对身份，旧产物无法被冒充

存在：q3_qualify.py L49  FULL_VALID 门集合（exactly these keys, all True）
      ⇒ 门集合是【事前】固定的，不是事后补的

缺口：以上三者都只在 Q3 资格链上。
      C1 的 evaluator（L216-220 三输入）里【没有 run 身份】。
      ⇒ 链 A 与链 B 的公共主键此刻不存在（NB-50）。
```

**可否定点**：若某次执行的产物能被上一次的 run_id 消费成功，则 ① 失效。

### ② 基线建立 `[冻结代码]`

```text
storage.py L54-57  initialize_baseline()
  → literal.bin  写 LITERAL_ZERO
  → substrate.bin 写 SUBSTRATE_ZERO
```

**可否定点**：若基线不唯一（两次置零得到的字节不同），② 失效。

### ③ 写入窗口 `[冻结代码]`

```text
storage.py L95-97   _assert_write_open()
  if not self._write_open: raise HarnessError("attempted write outside an open write window")

storage.py L112-124 write_window() 上下文管理器
  L116-118 __enter__ → _open_write_window()
  L120-122 __exit__  → _close_write_window()
```

**这是本表最重要的一格。** 写入不是瞬时点，是一个**有开有关的区间**。
窗口的「开」与「关」是两个可被攻击的时刻：

- 窗口**开着**时，谁都能进来写（A.4b 说的就是这件事）；
- 窗口**关着**时，写入被 `_assert_write_open` 硬拒。

⇒ 所谓「谁写的」，在代码层面等价于 **「谁在窗口开着的那段时间里持有写权」**。
⇒ 这句话掩盖了一个空洞：**代码里没有任何东西记录「窗口开着时是谁」**。
   `_write_open` 只是一个布尔量，它知道自己**开着**，不知道**为谁开着**。

**可否定点**：若能在 `_assert_write_open` 通过的情况下由非预期方写入，③ 失效。
**当前状态**：`_write_open` 是进程内布尔量，跨进程无约束 ⇒ ③ 的隔离性
**未建立**（`BENIGN_CONTROL != ISOLATION_PROOF`）。

### ④ 观测快照 `[冻结代码]`，`[两个已知缺口]`

```text
observer.py L4-7   原文连续（L4 起，L7 止）：
  L4  "The observer is a read-only component that is NOT the write operator. It"
  L5  "collects registered state by reading STATE_FIELDS from the files directly and"
  L6  "computing state identities independently. Writer-reported digests are never"

  L47  "Useful when the observer runs in a separate process than the writer."
```

`snapshot_paths()` 的存在说明一件事：**observer 已经在设计上允许和 writer 不同进程。**
这是本表里唯一一处**隔离点已经写在冻结代码里**的地方。

但有两个缺口，必须同时说：

```text
缺口一（非原子）：storage.py L71-74 snapshot() 是【两次独立读】

  L74  sub = self.read_substrate_bytes()
  ⇒ 两次读之间若有写入，快照不是任何一个时刻的状态

```

**可否定点**：若在两次读之间插入一次写入而 digest 仍被接受，④ 失效。

