# 把 exp/v2-l1-verifier 纳入分支保护 · 操作步骤

日期：2026-11-17
背景：个人仓库协作者权限最低为 `write`，无法降为 read（GitHub 限制）。
      因此需靠分支保护使 write 权限【无法直接改分支】。
当前：`main` 已受保护；`exp/v2-l1-verifier` **未受保护**（漏洞点）。

---

## 现状（操作前）

```text
ruleset id=27252020  name=Protect  enforcement=active
  conditions  include = ["refs/heads/main"]        ← 只含 main
  bypass_actors = []                                ← 无豁免（好）
  rules:
    · deletion            （禁删）
    · non_fast_forward    （禁强推）
    · pull_request        （必须走 PR；approvals=0）
```

```text
⇒ 要做的只有一件事：把 `refs/heads/exp/v2-l1-verifier` 加进 include。
⇒ 【不需要新建规则集】，改现有的即可。
```

## 操作步骤

### 第 1 步 · 打开规则集

```text
1. 打开 https://github.com/changrongq/ouroboros-afterglow
2. 顶部点 Settings
3. 左侧栏找到 "Rules" → 点 "Rulesets"
   （若看不到，直接访问 https://github.com/changrongq/ouroboros-afterglow/rules）
4. 点击名为 "Protect" 的规则集
```

### 第 2 步 · 编辑目标分支

```text
1. 在规则集详情页，找到 "Target branches" 区块
2. 点右侧 "Edit"（或铅笔图标）
3. 在 "Add target" 下拉里选 "Include by pattern"
4. 输入框中【追加】下面这一行（原有的 refs/heads/main 保留，不要删）：

       refs/heads/exp/v2-l1-verifier

5. 点 "Add Inclusion"（或 Add）
6. 确认列表里现在有两行：
       refs/heads/main
       refs/heads/exp/v2-l1-verifier
```

```text
⇒ 【最容易出错的地方】：把 refs/heads/main 删掉了，只留 exp。
   ⇒ 那会让 main 失去保护。请确认【两行都在】。
```

### 第 3 步 · 确认其余设置不动

```text
⇒ 以下保持原样，不要改：

   Enforcement status : Active          （不要设成 Disabled）
   Bypass list        : 空              （不要加任何人）
   Rules 已勾选：
       ☑ Restrict deletions
       ☑ Block force pushes
       ☑ Require a pull request before merging

⇒ 【Bypass list 必须是空的】。
   如果这里加了 changrongq 或管理员，保护对我就失效了，
   前面所有验证都要重做。
```

### 第 4 步 · 保存

```text
点页面右下角 "Save changes"
```

### 第 5 步 · 把结果告诉我

```text
⇒ 只需说一句"保存好了"即可。我会用 API 核对实际生效情况。
```

## 这一步之后的影响

### 对我的影响

```text
⇒ 我不能再直接推 exp/v2-l1-verifier。
   每次提交需要：
     1. 在本地建临时分支（或继续在 exp 上提交后另推一个分支）
     2. 推该分支
     3. 开 PR 合并回 exp

⇒ 【这会变慢，但换来的是】：任何人的写入都必须留 PR 记录。
```

```text
⇒ 【一个重要提醒】：
```

## 一个诚实的说明

```text
⇒ 这个方案【不是真正的权限隔离】。
   它做的是：把"不能写"从【权限层】挪到【流程层】。

⇒ 区别在于：
   · 权限层隔离：即使绕过流程，也写不进去
   · 流程层隔离：必须先改规则集，才能写进去
   ⇒ 而改规则集的权限在船长手里 ——
     也就是说，这道墙的钥匙仍在同一个人手上。

⇒ 【这个边界已在 B_36 §五·丙 记录过】：
   邮箱 + owner 是最高控制点，无法通过仓库设置消除。

⇒ 但在当前架构下，这是能做到的最好状态：
   把"随时可以改"变成"改必须留下痕迹"。
```
