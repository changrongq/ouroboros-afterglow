## 一 · 点名的四问

**问 1 · Layer B 是真的"在冻结 Q3 计算前改输入"吗？答：不是。改的是输出。**
`ad = _base_adapter(tmp, chain_override=lambda a, _kw=kw: _FakeQ3Result(**_kw))`；seam 位置 `adapter._call_q3_chain = lambda: chain_override(adapter)`
⇒ 替换的是 `q3_reset_chain()` **返回的那个对象**，不是它**读进去的那些字节**。而那个类叫 `_FakeQ3Result`。
⇒ 第 188 句：不许靠篡改**结论**去证明一个检查会响。验的是比较器，不是推导器。
⇒ 测试 docstring 自写 "inject a REAL Q3 failure by changing INPUTS *before* the frozen chain computes" —— 与代码不符。一句与代码不符的 docstring 会被下一个人当成前提。
**真正输入侧注入**：让那 10 个冻结角色之一真的跑出失败（撤掉 forbidden 的 deny ACE 让其真读到、或让 worker 真起不来），再断言集成裁决 INVALID。

**问 2 · `r.valid is True` 合取不可绕吗？中间态 Q3_OK 被当成功消费吗？答：这一格修得比要求的更严。签。**
✅ `all(x is True …)`，不是独立赋值、不是 `all(gates)`（后者会把 "UNEVALUATED" 当 True）
✅ `real_reset_required` 做了 `is True`/`is False` 二值严判 ⇒ 三态哨兵在开关位也进不来
✅ 消费端 `r.valid is not True` 在入口，`real_reset_*` 另立三道门
✅ `TX_Q3_OK ∉ _TERMINAL` 且 `≠ TX_DONE`；`integration_valid=True` 全文件唯一一处

**问 3 · REAL_RESET 门禁挡住 FIRST_START 冒充了吗？（A2）答：源码有门，A2 没测到它。**
```python
if self._proving_real_replacement:
    if r.reset_mode != RESET_MODE_REAL_RESET: self._fail(...)
    if r.real_reset_required is not True:     self._fail(...)
    if r.real_reset_ok is not True:           self._fail(...)
```
⇒ 门是对的。而 A2 通过的原因与 `reset_mode` 无关（因 `_NullSupervisor` 恒 False）。

**问 4 · 对象绑定用 OS 文件身份而非字符串吗？答：是。B1+B2 合起来有真判别力。**
B1（内容大小相同、不同文件）期望拒绝 ⇒ 若是内容哈希则应接受 ⇒ 绿 ⇒ 排除内容哈希；
B2（硬链接别名，路径字符串不同）期望接受 ⇒ 若是路径字符串则应拒绝 ⇒ 绿 ⇒ 排除路径字符串。
⇒ 只剩 OS 文件身份能同时满足；实现侧正是 `file_identity`（卷序列号+文件索引）。两处一致。
**两点小保留**：① B1 断言过宽（`"SUBSTRATE" in str(e).upper() or ...` + `except Exception`）⇒ 改断言**异常类型**；② B2 依赖 `os.link`（Windows 需权限/开发者模式）⇒ 失败应 **SKIP**，勿伪装成"身份检查失败"。

## 二 · 睫发现的（按严重性）

⛔ **1 · 第 198 句：Layer A+B 的断言全部指向同一个结果。**
`_NullSupervisor.witness_ok()` / `.prove_persistent_isolation()` 恒 `False` ⇒ 六段流水线最多走到第 4 段 ⇒ 后两段从未进入。
B10 自证："even if Q3 valid" 仍 INVALID ⇒ valid=True 与 valid=False 得同一结果 ⇒ 所有"Q3 不合格"用例无法区分。
⇒ 推论：一个 `run_reset_transaction` 恒返回 False 的实现，会通过 Layer A+B 全部断言。**且没有任何一条断言 `integration_valid is True`** ⇒ 成功路径一次没走过。
另：七个 gate 里四个完全重复（`_FakeQ3Result` 无这些字段）⇒ 七个名字，一条用例。
另：A5 名不符实（`tuple[-1]` 只断言 state）。
**第 200 句（更该记 198）**：不许让一个测试套件里所有断言都指向同一个结果。判别力不来自断言数量，来自它们彼此不同。最常见的样子是有一个门永远失败，于是排在它后面的每一个门都从来没被走到。
**最小修法**：把 `_NullSupervisor` 做成可切换（恒 False + 恒 True），一个开关，最后两段就活了。

⛔ **2 · 第 200 句：隔离证明发生在 canary 上，RC11 保护的是另一对象。**
`forbidden ≠ protected`。而 `win32_isolation.py` scope 自写 "Q3 PASS does NOT prove a real Phase-B payload is isolated"；INDEX（Oct 11）明写 **STILL OPEN: real-object binding**。
⇒ 适配器接的正是那一格还开着的口子。用 canary 不是错的（科学上必须先用 canary），错的是那句没写出来的推论"因此真实对象也被隔离了"—— 由**参数传递**自动完成，中途无人问它从哪来。
⇒ 替身的诚实让它更危险：它真做了实验、真通过了，于是那个"因此"更像真的。
⇒ 同时回答凌翼第三问：Profile B 的有限声明**确实被扩大**，不是被谁说出来的，是被参数传递自动完成的。

⛔ **3 · 第 201 句：两次 deny，用的不是同一个 SID。**
`_stage_boundary` 用 `self._expected_sid`（**声称**）；`prove_persistent_isolation` 用 `self._witness.token_sid`（**实测**）。
而**没有任何一处检查二者相等**（`witness_ok()` 查了 `token_sid != current_process_sid`、查了存活，但**没查 `token_sid == expected_sid`**）。
⇒ 若 `expected_sid ≠ 真实 worker SID`：② 锁装别人身上 → ③ worker 起来（holding 期照样响应读）→ ④ 补装 deny 才被拒 ⇒ **③与④之间句柄已可开好**。
⇒ BD-62 "先开句柄后 deny" 的逃逸窗口没关掉，只是从"起进程之前"搬到"配置与实测之间"。
**第 201 句**：不许用一个"期望值"去建立防线。用声称去装锁，锁装好的那一刻没人知道它装在谁的门上。最毒的形状是：后面还有一次用实测值补装的锁，于是整体看起来安全 —— 而那第二次装锁，恰是作者自己不信任第一次的证据。
**最小修法（一行，同时治三格）**：`_stage_business_worker` 之后、`_stage_persistent_isolation` 之前：
```python
w = self._supervisor.witness()
if w is None or w.token_sid != self._expected_sid:
    self._fail(f"worker SID {w and w.token_sid} != expected {self._expected_sid}")
```
代价：一行。不动冻结源码、不改 digest、不要新 lineage。

⛔ **4 · 第 199 句：持久隔离取信于 worker 自报。**
`prove_persistent_isolation` 的 `result` 来自 worker 自写 `.afterglow_access_response.json` ⇒ 被隔离者可**不去读，直接写 "DENIED"**。
而 `win32_isolation.py` 第一句即 "A recorded denial is not a denial that happened"；`probe_read_access`（唯一能产封条见证者）在 adapter 里调用 **0 次**。
**第 199 句**：不许在系统下游，重新引入上游已经消灭掉的那种弱证据。最过不去的一格：下游声称自己"包含在"上游那个合取里（`V_Q3 ∧ V_isolation`），而后一项证据等级比前一项低一档。
**修法（仓库里都有）**：① controller 侧封条见证（`probe_read_access`）∧ worker 自报 DENIED，两者都要，自报留作一致性对照；② `q3_handle_audit.audit_process_handles_for_target(w.pid, forbidden_path)` 由 controller 枚举 worker 句柄表，证明其**不持有**指向该对象的句柄（Q3 链那条 `handle_ok` 管的是 Q3 自己的 probe，管不到这个持续业务 worker，必须单独做）。

⚠️ **5 · 第 186 句第二半：`access_side_ok` 恒真。** `rc11_access_ok = (self._state == TX_ISOLATION_OK)` ⇒ 能走到这行前提是前面没 `_fail` ⇒ state 恒等 `TX_ISOLATION_OK` ⇒ 常量穿检查外衣。今天无害，危险在"有人给隔离段加 warning 分支"那天。修法：把见证对象直接传进去，不从状态导出布尔。

⚠️ **6 · 三个死 import —— 不要删。**
`probe_read_access` / `bind_object_identity` / `identity_still_matches` 各 0 次。它们精确指向一处"该做而未做"：`identity_still_matches`（该用于 `_stage_bind` 复查）、`probe_read_access`（该用于持久隔离）、`bind_object_identity`（带 size+sha256，`file_identity` 只有卷序列号+索引 ⇒ 现能抓"换文件"，抓不住"内容被改"）。一个死 import 是"本打算做、后来没做"的化石。删掉它，那件事就再也没人知道。**处置：改 TODO 警报。**

⚠️ **7 · `_stage_bind` 的指纹：该在的不在。** 记了 protected/substrate/literal，**唯独没有 forbidden** —— 而证明恰恰发生在 forbidden。比死 import 更隐蔽（连名字都没留）。**修法**：补 `forbidden_path` + `forbidden_os_identity`。

⚠️ **8 · `proving_real_replacement` 记账（不阻塞）。** 一按此开关，real_reset 三道门全消失。合理于"首次启动"场景，但如今只是构造参数，谁都能传 False。应绑到"当前确为首次启动"这个**事实**。
