# 一 · 范围（照录裁定，不改写）

⇒ 裁定第一节原文：

                 + P1_MIN

```text
⇒ 逐项含义（本节的解读，若与裁定原文有出入以裁定为准）：

① P4_RECOVERY
   P4 已定版的恢复身份与 epoch 判定路径，
   包括【首次身份登记条件】（P4-1.2 / P4-1.2a 的三条件合取）。

② P1_MIN
   最小引用完整性编码与验证。
   ⇒ 只覆盖【引用记录】（AttemptRecord / ReceiptRecord）对本节所涉对象的引用，
     不覆盖任意文件格式。

③ P2_MIN
   最小身份凭证格式、可信来源验证与绑定检查。
   ⇒ 只覆盖【本次原型注册范围内的提交者身份】，
     不覆盖生产级密钥体系。

④ P5_LOCAL_EXCLUSIVITY
   本机、单一权限域内的独占执行机制。
   ⇒ 见第三节「关于 P5：不支持的与必须测的」（裁定原文：
     「不支持多实例运行，不等于不测试多实例竞争」）。

⑤ EPOCH_DURABILITY
   epoch 分配、身份登记与持久化提交的明确边界。
   ⇒ 只要求【边界明确】，不要求崩溃一致性已证明（见 §0 A-2）。

⑥ FAULT_INJECTION
   故障注入与可观测证据。

⇒ 【不包含】任何与生产部署、跨主机、高可用相关的内容。
```

# 二 · 排除（照录裁定，逐条）

```text
⇒ 裁定第一节「明确排除」六项：
   ① 分布式多节点一致性
   ② 高可用与自动故障转移
   ③ 网络租约与跨主机独占
   ④ 多个合法活动写入者
   ⑤ 生产密钥与真实生产签名
   ⑥ 冻结 Q3 RC11 的任何修改
```

```text
⇒ 【第④项须与「多实例竞争测试」分开读（裁定原文强调）】
   ⇒ 排除的是：允许【多个合法活动写入者同时有效】。
   ⇒ 不排除的是：启动两个进程【抢】，验证任何时刻不能同时持有。

⇒ 裁定原文（照录，本节不改写）：
   「这里必须区分：
     不支持多实例运行，不等于不测试多实例竞争。
     至少要能够启动两个本机测试进程进行竞争验证。
     成功条件不是两个进程协同工作，
     而是任何时刻都不能同时获得有效执行权限。」

⇒ 即：不支持多实例运行，≠ 不测试多实例竞争。
   ⇒ 但本节【不得】把 ≠ 当作对原文的替代 ——
     原文见上方照录，以原文为准。
```

```text
⇒ 本节另加三项排除（§0 C 类已列，此处给出与主体相关的界定）：
   ⑦ 恶意对抗模型 —— 见第四节「范围外 ≠ 不需要防」
   ⑧ 长时间运行（数月级泄漏/漂移）
   ⑨ 多用户并发（同一时刻只有同一身份）
```

# 三 · 关于 P5：不支持的与必须测的

```text
⇒ 这是裁定第一节里最容易读反的一段，故单列。

【不支持的】
  · 两个实例【同时有效】地签发权威事件
  · 任何选举机制
  · 跨主机 / 跨会话的独占
  ⇒ CONCURRENT_AUTHORITY_INSTANCES = NOT SUPPORTED

【必须测的】
  · 同时启动两个本机进程，竞争获取执行权限
  · 任一进程异常退出后，另一进程重新竞争
  · 进程未终止但被判定为已终止（挂起 / 分区 / 饥饿，见 §0 A-2c）
  ⇒ 成功条件不是「两个进程协同工作」，
    而是「任何时刻都不能同时获得有效执行权限」。

【申请必须说明的五件事（裁定原文）】
  ① 权限边界
  ② 锁或令牌的可信来源
  ③ 异常退出后的处理
  ④ 与 epoch 持久化状态的关系
  ⑤ 失效时的 STOPPED 行为
⇒ 具体方案见 §4（P5）。

【一条裁定明写的禁止推论】
  异常退出或独占状态丢失
  ≠ 恢复签发权限。
  ⇒ 见 P4-5.3 与 §0 A-2c。
```

# 四 · 主体与对象：信任边界（知微 Z0-02 要求）

## 4.1 本原型内的四类主体

```text
⇒ 【写法说明】以下主体名称取自【现有 harness 的实际实现】，
   不是新造的角色。
   依据：afterglow_harness/q3_business_worker_entry.py 的文件头与协议描述。
   ⇒ 该文件自述「INTEGRATION-layer test scaffolding; it is NOT a frozen role」。
   ⇒ 故本节只把【它实际在做的事】写进边界，不把它升格为冻结角色。
```

| # | 主体 | 是否受信 | 它做什么（现状） | 在原型中的位置 |
|---|---|---|---|---|
| S | supervisor / 测试驱动程序 | **受信**（本原型内的测试控制方） | 发起 worker、下达 release / stop、发起 access 请求、收集证据 | 测试控制方 |
| W | business worker | **非受信**（就身份真实性而言） | 长驻业务进程；写状态、应答 access 请求 | 被测对象 |
| R | recorder（拟建，尚不存在） | **拟受信** | 签发权威 EventRecord、产生 authority_record_key | §4 待建 |
| C | controller（拟建，尚不存在） | **拟受信** | 依 P2 核验提交方身份并绑定到 AttemptRecord | §3 待建 |

```text
⇒ 【必须说清的一件事实】
   R（recorder）与 C（controller）【当前都不存在】。
   依据：D1-1 / D2 已确认「记录者不存在」「ReceiptRecord 不存在」。
   ⇒ 故本原型内，R 与 C 是【要造出来的东西】，
     不能把它们当作既有的可信主体来引用。
```

## 4.2 哪类记录由谁写、谁核验

```text
⇒ 【对照表：谁能写、谁能核验、谁不能】
   「写」= 创建该记录；「核验」= 独立确认其成立。
```

| 记录 | 由谁写 | 由谁核验 | 禁止 |
|---|---|---|---|
| `EventRecord`（权威） | **R**（记录者） | 消费者读取其 digest 与键；来源真实性需另证（§0 A-3） | W 【不得】写权威 EventRecord |
| `AttemptRecord` | **W**（提交方侧） | R 侧独立观测（P4-5 要求） | W 【不得】自行宣告其可信 |
| `SUBMITTER_IDENTITY_ATTESTATION` | **C**（控制主体） | 消费者按 P2 五判据核（§0 引 D2 §4.3） | W 【不得】自己写自己的核验结果 |
| `ReceiptRecord` | **W**（收据方） | 与 AttemptRecord 交叉核对（c1–c7） | W 【不得】只凭自填成立 |
| `RECORDER_STARTED` / 恢复诊断 | **R** | 恢复流程消费 | 不得作为恢复完成依据（§0 已列） |
| 独占资格 | **P5 机制**（拟建） | 见 §4 | W 【不得】自行宣布持有 |

```text
⇒ 【一条通则（与 §0 红线④同形）】
   凡是【由 W 自己写】的记录，
   【不得仅凭其自身内容】被记为成立。
   ⇒ 必须有【另一个主体】的独立观测，或 P2 的核验结果。
```

## 4.3 范围外的对抗：范围外 ≠ 不需要防

```text
⇒ 裁定排除第④项是「多个【合法】活动写入者」，
   本节排除第⑦项是「写入者具有【改字节并重算摘要】的意图与权限」。
   ⇒ 前者是并发，后者是对抗。两者不同。

⇒ 【关键】
   ⇒ 它只表示【本原型不防】，不表示生产里不存在，
     也【不表示不必由别的机制承担】。

⇒ 【归属】
   ⇒ 若 W 能重写本应独立可信的身份依据（例如伪造 ATTESTATION、
     或改写 AttemptRecord 的 submitter_id 并重算摘要），
     则相关保证【未建立】，必要条件【未满足】，不得放行。
   ⇒ 该责任须在【本原型的 P2 / 权限边界设计】中落实
     ——【不得】以「归 P2 负责」为由移出原型范围。
   ⇒ 范围外的恶意管理员等破坏可信前提者，按排除项另行记录。

⇒ 【这里不要求新增攻击实验，也不要求生产级密钥系统。】
```
