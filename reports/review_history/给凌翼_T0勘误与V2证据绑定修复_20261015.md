## 2. V2 证据绑定修复（CLEAN_EVIDENCE_BINDING = STILL OPEN → 已补）

**你指出的问题**：`EnumeratorEvidence.trusted` 只检查 pid/create_time/非空/all_verified_seen —— **这些字段调用者可自行构造**；且 `audit_business_worker_handles` 只查 `trusted` 属性 + pid 相等，**没有**把证据的 create_time 与本次 OS 实测值比较，也**没有**独立复核那些句柄值确实被枚举过。⇒ 过去那个"调用者传 True"，**部分变成了"调用者可构造的数据对象"**。

**修复（仅 V2 新增层）**——三点：

1. **封条（seal）**：镜像冻结 `AccessWitness` 的做法 —— 模块持有**每进程秘密** `_ENUM_SECRET`；**只有受信生产者** `build_enumerator_evidence(...)` 能算出并写入 `seal`（HMAC-SHA256 覆盖 pid/create_time/句柄值列表/all_verified_seen/method/raw_ref）。
   - **手工构造的 `EnumeratorEvidence` 无法产生有效 seal ⇒ `trusted=False`。**
2. **审计器独立复核 create_time**：CLEAN 前，审计器**自己**用 `_process_create_time(pid)`（OS `GetProcessTimes`）取本次进程创建时间，与证据里的 `create_time` 比较（容差 1e-3）。
3. **审计器独立复核句柄确实被枚举**：审计器用**本次枚举返回的句柄集合** `seen_handles`，要求证据里的每个 `verified_handle_values` 都**在本轮被枚举到**。

⇒ CLEAN 现在**必须**：`trusted（seal 有效）∧ pid 相等 ∧ create_time 与 OS 实测一致 ∧ 证据句柄值在本轮枚举中被看见`。否则 **UNRESOLVED**。

**实测（真跨账户 worker，5 例）**：
| 用例 | 期望 | 实测 |
|---|---|---|
| 无证据 | UNRESOLVED | ✅ UNRESOLVED |
| **手工构造（无 seal）** | UNRESOLVED | ✅ UNRESOLVED |
| sealed 但 create_time 错 | UNRESOLVED | ✅ UNRESOLVED |
| sealed 但句柄未被本轮枚举 | UNRESOLVED | ✅ UNRESOLVED |
| sealed + 正确 | 过证据门（仍未 CLEAN，因句柄不可分类） | ✅ UNRESOLVED-by-handles |

⇒ **构造者无法再伪造 CLEAN 的证据来源。**
