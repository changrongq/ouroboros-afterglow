## 一 · 现有类型与新增类型的分界

```text
⇒ 【§2 已占用】（不得复用，也不得改语义）：
   0x01  ATTEMPT_REF   发送侧引用
   0x02  RECEIPT_REF   收据侧引用
   0x03  KEY_TRIPLE    (recorder_id, epoch, seq)

⇒ 【B2-2 需要的五类对象】——它们【都不是引用】，是【实体记录】。
   ⇒ 故必须新编号，不得借 0x01–0x03 表达。

   | # | 对象 | 为什么不能复用现有类型 |
   |---|---|---|
   | N1 | 身份登记 | 它是持久实体，不是对别的记录的引用 |
   | N2 | epoch 分配 | 同上；且它是 C2 的期望来源之一 |
   | N3 | 授予 / 撤销 | 同上；且带有效区间语义 |
   | N4 | 准备记录 / 结案记录 | §5 要求二者可分别标识（PENDING vs COMMITTED） |
   | N5 | 可信历史范围承诺 | **不属于业务历史**（B2-3），必须可区分 |

⇒ 【建议编号（提案，非定版）】：
   N1 = 0x81  IDENTITY_REGISTRATION
   N2 = 0x82  EPOCH_ASSIGNMENT
   N3 = 0x83  GRANT_RECORD
   N4a= 0x84  PREPARE_RECORD      （对应 PENDING_*）
   N4b= 0x85  CLOSURE_RECORD      （对应 COMMITTED 结案）
   N5 = 0x86  HISTORY_COMMITMENT  （受信承诺，非业务历史）
   ⇒ 【为什么从 0x81 起】：§2 已声明 0x80–0xFF 保留给后续版本。
     从 0x81 开始可保留 0x80 作为"已定义但不得使用"的哨兵。
```

## 二 · 公共要求（五类共用，写一次）

```text
⇒ (G1) 协议版本：沿用 §2 的 FORMAT_VER（本文提案仍为 0x0001）。
   ⇒ 若某类对象未来改字段，须升 FORMAT_VER，不得原地改。

⇒ (G2) 字段顺序：固定，不得重排。字段顺序是摘要的一部分（§2 2.4）。

⇒ (G3) 整数：一律大端无符号定宽。不使用原生端序、不使用变长整数。

⇒ (G4) 字符串：UTF-8，带 2 字节 LEN 前缀；**不含终止符**；
   不得含 NUL 以外的控制字符（NUL 本身也禁止）。
   ⇒ 理由：避免"看起来相同、字节不同"的两个标识符。

⇒ (G5) 摘要输入：严格按 §2 2.4 ——
   `SHA-256( OBJECT_TYPE ‖ FORMAT_VER ‖ OBJECT_TYPE ‖ RESERVED ‖ FIELD_COUNT ‖ FIELDS )`
   ⇒ 新类型【必须】让 OBJECT_TYPE 参与，从而天然域分离。

⇒ (G6) 每个对象必须含 `authority_domain` 与 `generation`。
   ⇒ 依据 `§5 二 (r3)`「显式绑定」：登记项须写明
     「哪个对象、哪个版本、哪个权威域/世代」。

⇒ (G7) 每个对象必须含 `predecessor_digest`（可为全零 = 无前驱）。
   ⇒ 依据 C5；且全零必须与"缺失该字段"区分（长度不同）。
```

## 三 · 五类对象的最小字段契约

> 说明：下列 `TAG` 为字段标签建议值，仅为在本提案内可读；
> 正式 TAG 分配须在复核后统一。

### N1 · 身份登记 `IDENTITY_REGISTRATION` (0x81)

| 字段 | 类型 | 说明 |
|---|---|---|
| `recorder_id` | bytes[16] | 身份标识，定长 |
| `authority_domain` | str | 权威域 |
| `generation` | u32 | 世代 |
| `root_ref` | bytes[32] | 指向信任根的摘要 |
| `registered_commitment` | bytes[32] | 登记项自身的承诺摘要 |
| `predecessor_digest` | bytes[32] | 前一登记的摘要，或全零 |
| `order_evidence_ref` | bytes[32] | **登记侧顺序**依据（见 §5 二 (r1)） |

```text
⇒ 【要点】：`order_evidence_ref` 是 (r1)「预先登记」的落地。
   ⇒ §5 二 (r1) 明写：`clock_ns` 不参与排序，
     "预先"的顺序须由【登记侧自己的顺序】判定。
   ⇒ 故本字段【必须】指向登记侧证据，不得填记录自带时间戳。
```

### N2 · epoch 分配 `EPOCH_ASSIGNMENT` (0x82)

| 字段 | 类型 | 说明 |
|---|---|---|
| `recorder_id` | bytes[16] | 归属身份 |
| `authority_domain` | str | 权威域 |
| `generation` | u32 | 世代 |
| `epoch` | u64 | 分配的 epoch 值 |
| `assigned_from_max` | u64 | 计算时所依据的 max |
| `max_scope_digest` | bytes[32] | **max 取值集合**的摘要（见下） |
| `predecessor_digest` | bytes[32] | 前一分配 |

```text
⇒ 【`max_scope_digest` 为什么必要】：
   B2-2 要求"摘要输入"明确。只写 `assigned_from_max` 不够 ——
   同一个 max 值可来自不同操作数集合（这正是 99b7481 复核时
   知微 N99-01 指出的问题）。
   ⇒ 故必须绑定"当时认为的最大集合是什么"，
     使"算对了但来源错"可被识别。
```

### N3 · 授予 / 撤销 `GRANT_RECORD` (0x83)

| 字段 | 类型 | 说明 |
|---|---|---|
| `recorder_id` | bytes[16] | 被授予者 |
| `authority_domain` | str | 权威域 |
| `generation` | u32 | 世代 |
| `grant_epoch` | u64 | 授予开始生效的 epoch |
| `revoke_epoch` | u64 | 撤销 epoch；`0xFFFFFFFFFFFFFFFF` = 仍有效 |
| `grant_kind` | u8 | 1=授予 2=撤销 |
| `predecessor_digest` | bytes[32] | 前一授予/撤销 |

```text
⇒ 【撤销为什么也是 GRANT_RECORD】：
   §5 2.1 要求"保留 PENDING、追加提交记录"，
   撤销同理是【追加一条新记录】，不是删改旧的。
   ⇒ 故用同一对象类型 + `grant_kind` 区分，
     而非定义两个类型 —— 但【这需要复核确认】：
     若复核认为授予与撤销应当域分离（不同 TYPE），
     则应拆成 0x83 / 0x87。见第七节 Q2。

⇒ 【非法反例】：`revoke_epoch < grant_epoch` ⇒ 整条记录非法，
   不得"取绝对值"或"视为立即撤销"。
```

### N4a · 准备记录 `PREPARE_RECORD` (0x84)

| 字段 | 类型 | 说明 |
|---|---|---|
| `recorder_id` | bytes[16] | 归属 |
| `authority_domain` | str | 权威域 |
| `generation` | u32 | 世代 |
| `intent_kind` | u8 | 1=epoch 2=身份 3=授予 |
| `intent_payload_digest` | bytes[32] | 拟写入内容的摘要（**不写内容本身**） |
| `attempt_nonce` | bytes[16] | 本次尝试标识 |
| `predecessor_digest` | bytes[32] | 前一 COMMITTED |

```text
⇒ 【关键】：准备记录【不进入 C5 的前驱链】——
   承 §5 L248-250：「准备记录（attempt）= 同一次尝试留下的 PENDING，
   它不参与 C5 的前驱链」。
⇒ 故其 `predecessor_digest` 指向【前一 COMMITTED】，
  但它自己【不是】别人的前驱。
```

### N4b · 结案记录 `CLOSURE_RECORD` (0x85)

| 字段 | 类型 | 说明 |
|---|---|---|
| `recorder_id` | bytes[16] | 归属 |
| `authority_domain` | str | 权威域 |
| `generation` | u32 | 世代 |
| `attempt_ref` | bytes[32] | 指向被结案的 PREPARE_RECORD 摘要 |
| `closure_result` | u8 | 1=成功 2=放弃 3=失败保留 |
| `result_payload_digest` | bytes[32] | 结案后实际写入内容的摘要 |
| `predecessor_digest` | bytes[32] | 前一 COMMITTED |

```text
⇒ 【这张表与 F-1-2 的五个分支直接对应】：
   · B1 未结案 ⇒ 只有 N4a，无 N4b
   · B2 唯一合法结案 ⇒ 恰一条 N4b 且 attempt_ref 匹配
   · B3 结案冲突 ⇒ 多条 N4b 指向同一 N4a
   · B4 结案不可验证 ⇒ attempt_ref 指向不存在的摘要
   · B6 关联错配 ⇒ N4b 存在且可读，但 attempt_ref 指向
     **另一个** N4a
   ⇒ 故 §5 六 (c) 的「身份或关联不匹配」在本编码下是
     【可机械判定】的：比对 attempt_ref 与目标 N4a 的摘要。
```

### N5 · 可信历史范围承诺 `HISTORY_COMMITMENT` (0x86)

| 字段 | 类型 | 说明 |
|---|---|---|
| `authority_domain` | str | 承其所覆盖的域 |
| `generation` | u32 | 世代 |
| `range_start_seq` | u64 | 覆盖起点（含） |
| `range_end_seq` | u64 | 覆盖终点（含） |
| `head_digest` | bytes[32] | 至 `range_end_seq` 为止的历史链摘要 |
| `commitment_seq` | u64 | **登记侧**单调序号 |
| `predecessor_digest` | bytes[32] | 前一承诺 |

```text
⇒ 【N5 与前五类的根本区别】：
   它不是业务历史的一部分，而是【关于业务历史该有多长】的独立声明。
   ⇒ 依据凌翼 B2-3：「受信承诺：提供该历史应覆盖什么范围、
     哪个版本、哪个权威域，以及应该满足什么摘要和顺序关系的独立依据」。

⇒ 【N5 不得由 W 或被侧业务写入路径创建】（凌翼 B2-3 原文）。
   ⇒ 故其写入主体与 N1–N4 不同 —— 这决定了它必须在
     【不同的权限边界】内（见 B2-1 2.3）。
```

## 四 · 非法反例（每类至少一条）

| 对象 | 非法情形 | 判定 |
|---|---|---|
| N1 | `root_ref` 指向的根不存在或未预先登记 | 整条无效 ⇒ STOPPED |
| N1 | `order_evidence_ref` 填了记录自带时间戳 | **违规**：违反 §5 二 (r1) |
| N2 | `epoch ≤ assigned_from_max` | 非法：分配值必须大于其依据的 max |
| N2 | `max_scope_digest` 全零 | 非法：max 来源不可为空 |
| N3 | `revoke_epoch < grant_epoch` | 非法 |
| N3 | `grant_kind = 2` 但 `revoke_epoch` 为全 `FF` | 非法：撤销必须有撤销点 |
| N4a | 存在两条 `attempt_nonce` 相同但字段不同的 N4a | 非法：nonce 必须唯一 |
| N4b | `attempt_ref` 指向不存在的 N4a | 结案不可验证 ⇒ STOPPED（对应 B4） |
| N4b | `attempt_ref` 指向**另一个** recorder 的 N4a | 关联错配 ⇒ STOPPED（对应 B6） |
| N5 | `range_end_seq < range_start_seq` | 非法 |
| N5 | `commitment_seq` 非单调 | 非法 ⇒ 历史不可信 |
| 全部 | `FIELD_COUNT` 与实际字段数不符 | 解析失败 ⇒ NOT_COMMITTED（不进 C2） |
| 全部 | `TOTAL_LEN` 与实读字节数不符 | 解析失败 ⇒ NOT_COMMITTED |
| 全部 | 同一逻辑记录算出两个不同摘要 | 非法：§2 单射性被破坏 |

## 五 · 前驱关系（C5 的落地）

```text
⇒ 【两类引用，务必分清】（承 §5 L247-254）：

   | 引用 | 指向 | 是否参与 C5 |
   |---|---|---|
   | `predecessor_digest` | 上一条 **COMMITTED** 记录 | **是** |
   | `attempt_ref` | 同一尝试的 **PREPARE_RECORD** | **否** |

   ⇒ 【若混读】：把 PENDING 当前驱 ⇒ 它过不了 C4 ⇒ 新记录过不了 C5
     ⇒ 永远无法 COMMITTED（§5 L237-240 已写明这个坑）。

⇒ 【前驱链形态】：
   N1 → N2 → N3 → N4b → N4b → … → N5
   ⇒ N4a（准备记录）【挂在链外】，只被 N4b 的 attempt_ref 指向。
   ⇒ N5 虽是新类型，但其 `predecessor_digest` 指向
     【前一 N5】，不是业务链 —— 因为它是另一个存储边界。
```

## 七 · 待独立复核的问题

```text
⇒ (Q1) 五类对象是否遗漏了"该有但没写"的对象？
   ⇒ 我能想到的两个候选：
     · 撤销**确认**记录（区别于撤销意图）
     · 历史**封存**记录（把一段历史标记为不可再追加）
   ⇒ 未纳入，因为凌翼 B2-2 的清单未列。请裁定是否补。

⇒ (Q2) 授予与撤销应否域分离（0x83 / 0x87 两个类型）？
   ⇒ 当前提案合为一个类型 + `grant_kind`。

⇒ (Q3) N5 的存储边界：是否必须与 N1–N4 **异构**（不同引擎/不同介质）？
   ⇒ 若允许同引擎不同库，则"独立"只剩权限层面的意思。
   ⇒ 我倾向必须异构，但这是安全判断，不由我定。

⇒ (Q4) `max_scope_digest` 所摘要的"最大集合"，
   其元素顺序是否也须纳入？若不纳入，集合相同则摘要相同，
   但遍历顺序不同可能掩盖"读到了不同范围的记录"。
   ⇒ 我倾向纳入（有序），请裁定。

⇒ (Q5) N4a 的 `intent_payload_digest` 只存摘要、不存内容，
   是否足够支撑 F-1-2/B2 的"排除效果"判定？
   ⇒ 若不足，则需存内容或存其可重建依据。请裁定。
```
