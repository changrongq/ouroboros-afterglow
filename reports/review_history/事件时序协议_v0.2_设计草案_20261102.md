# 一 · 规范基础与继承关系

## 1.1 三份文档的关系

```text
v0.1（历史协议，事件时序第一版）

    epoch/seq 序号域、幂等提交、失败处置总表。
  ⇒ 其【已被 D1/D2 推翻】的部分失效：
    commit_state 在 EventRecord 内、WRITE_COMMIT 含糊语义。

D1-1（记录不可变性）+ D1-2（WRITE_COMMIT 语义边界）
  ⇒ 已接受为设计基线。
  ⇒ v0.2 的 EventRecord / StateTransition / AttemptRecord /
    ReceiptRecord 结构【以这两份为准】。

D2（接口契约）
  ⇒ 已 DESIGN_CLOSED。
  ⇒ v0.2 的字段绑定与阶段放行条件【以 D2 为准】。

v0.2（本文件）
  ⇒ 在上述基础上【合流】，并补 D1 未定义的两个字段。
```

## 1.2 现行 EventRecord 结构（以 D1-1 为准，非 v0.1）

```text
EventRecord {
    # ── 定位键（凌翼 T-1：这三项即权威记录定位键）──
    recorder_id    记录者实例身份
    epoch          记录者启动世代
    seq            该 epoch 内单调序号

    # ── 业务字段 ──
    event_id       提交方生成的唯一标识（重试时复用）
    attempt_id     本次提交尝试身份（每次重试不同）
    execution_id   执行身份
    object_id      对象身份
    event_type     WINDOW_OPEN | WINDOW_CLOSE | SNAP_BEGIN | SNAP_END
                 | HANDOFF | J_APPLIED | RECORDER_STARTED
                 | RECOVERY_TRUNCATED | STATE_WRITE_COMPLETED
    clock_ns       perf_counter_ns（辅助，不参与排序）
    state_digest   附加字段（不参与排序）
    producer_id    记录者签名/身份

    # ── 已移出（D1-1 L52）──
    # commit_state  【不在 EventRecord 内】
    # ⇒ 改由 StateTransition 记录承载
}
```

```text
⇒ 【与 v0.1 §3.1 的差异，逐条列明】

⇒ 除此之外，EventRecord 字段集合与 v0.1 一致。

⇒ 【关键】authority_record_key 【不】进入 EventRecord。
   理由见 §二（凌翼 T-1）。
```

# 二 · T-1 · 引用的完整性保护

**裁定：`REFERENCE_INTEGRITY_REQUIRED`；禁止不必要的自引用结构。**

## 2.1 接受的一个概念纠正

```text
⇒ 我在初稿里担心「authority_record_key 进摘要 ⇒ 自引用递归」。
⇒ 凌翼指出：这个担心基于错误的 key 定义。

⇒ authority_record_key = (recorder_id, epoch, seq)
   ⇒ 这是【记录定位键】，由三个既有字段构成。
   ⇒ 对一个固定键的字节计算摘要，不构成密码学递归。
   ⇒ 只有把 key 定义成【依赖其自身摘要】的值，才形成循环依赖。

⇒ 我接受这个纠正。初稿的担心是错的。
```

## 2.2 落实的设计

```text
① 权威 EventRecord 的定位键由既有 recorder_id / epoch / seq 构成。
② 这三个字段继续纳入 EventRecord.content_digest。
③ AttemptRecord 与 ReceiptRecord 保存对权威记录的【引用】。
④ 两种引用记录【各自】有完整性覆盖规则，
   将 authority_record_key 及对应 event_id / attempt_id 纳入保护。
⑤ 【不】以修改既有 EventRecord.content_digest 字段清单的方式，
   解决其他记录类型的完整性问题。
```

```text
AUTHORITY_RECORD_KEY_IN_EVENT
    = DERIVED_FROM_EXISTING_IDENTITY_FIELDS

AUTHORITY_REFERENCE_IN_ATTEMPT
    = INTEGRITY_COVERAGE_REQUIRED

AUTHORITY_REFERENCE_IN_RECEIPT
    = INTEGRITY_COVERAGE_REQUIRED

EVENT_CONTENT_DIGEST_LEGACY_SCOPE
    = PRESERVED_FOR_EXISTING_FIELDS
```

## 2.3 完整性覆盖的边界（凌翼特别强调）

```text
⇒ 摘要校验只能证明【内容与摘要相符】。
⇒ 摘要校验【不能】单独证明：
     · 来源真实
     · 抵御能同时改写记录及摘要的攻击者

⇒ 可信来源、追加式存储、写权隔离仍须【独立建立】。
⇒ 因此：
     DIGEST_MATCH           ≠ SOURCE_TRUSTED
     DIGEST_MATCH           ≠ TAMPER_PROOF
```

```text
⇒ 【未规范化的部分，显式列前置条件】
⇒ 引用记录完整性编码（具体用什么算法、覆盖哪些字节序）
   本版【未规范化】。
⇒ ⇒ 列为原型实施前置条件 P-1，不得凭「已有摘要字段」默认具备。
   → 见 §七。
```

# 三 · T-2 · 权威域范围

**裁定：`SINGLE_LOGICAL_AUTHORITY`。当前设计只支持单一逻辑权威域。**

```text
⇒ 同一被管理的执行及对象范围内，
   同一时刻只允许【一个】权威记录者具有绑定写入权。

⇒ 允许以后讨论重启恢复，
   但恢复后的记录者必须【继承原权威域的持久化身份与绑定历史】，
   并保持 epoch 语义一致。

⇒ 禁止在没有协调机制的情况下启动两个可独立签发权威事件的实例。
```

```text
AUTHORITY_SCOPE
    = SINGLE_LOGICAL_AUTHORITY

CONCURRENT_AUTHORITY_INSTANCES
    = NOT SUPPORTED

CROSS_AUTHORITY_ELECTION
    = NOT DEFINED

AUTHORITY_EXCLUSIVITY_ENFORCEMENT
    = NOT ESTABLISHED
```

```text
⇒ 若无法证明当前只有一个合法权威写入者，
   则【不得宣布权威映射成立】。

⇒ 这是一项【设计限制】，不是已实现的互斥保证。
   ⇒ AUTHORITY_SCOPE = SINGLE_LOGICAL_AUTHORITY（设计）
   ⇒ AUTHORITY_EXCLUSIVITY_ENFORCEMENT = NOT ESTABLISHED（现状）
   ⇒ 两者【不可互相推出】。

⇒ 未来如需多实例/高可用/自动选举，
   应【另立扩展设计】，不得偷偷带入 v0.2。
```

```text
⇒ 【对本草案前文的修正】
⇒ 初稿写 AUTHORITY_UNIQUENESS_CROSS_INST = NOT ESTABLISHED。
⇒ 那是【含糊的】—— 只说了「没建立」，没说「不支持」。
⇒ 本版改为：CONCURRENT_AUTHORITY_INSTANCES = NOT SUPPORTED（设计禁止）。
⇒ 区别：前者是「不知道」，后者是「设计上不允许」。
```

# 四 · T-3 · 提交方身份的可信路径

**裁定：`TRUSTED_CONTROLLER`（受信控制主体核验并绑定到 AttemptRecord）。**

## 4.1 为什么选 C

```text
⇒ D2 已要求存在控制主体，负责依据收件证据决定是否放行后继阶段。
⇒ 对最小原型：把身份核验职责【明确纳入这一受信控制边界】，
   避免同时引入新的密码学信任根，
   也避免要求尚不存在的记录者独立完成全部身份鉴定。

⇒ A（记录者侧观测）作为未来替代方案。
⇒ B（密码学绑定）暂不进入最小原型范围。
```

## 4.2 五个必须满足的条件

```text
① 控制主体须有【独立于提交方自填字符串】的身份依据，
   例如经验证的进程或受控通信通道身份。
② 核验结果必须绑定到具体 (event_id, attempt_id)，
   【不得仅凭 submitter_id 文本匹配】。
③ 该绑定须具有可追踪的记录来源及完整性要求，
   并能被记录者和后续验证过程消费。
④ 控制主体【不能仅以其自身声称「可信」作为可信依据】；
   其启动、权限与写入边界须在原型信任模型中说明。
⑤ 核验失败或证据缺失时，
   SUBMITTER_IDENTITY = NOT ESTABLISHED，
   不得进入依赖它的正式放行路径。
```

## 4.3 建议的身份核验记录（设计示意）

```text
SUBMITTER_IDENTITY_ATTESTATION {
    event_id
    attempt_id
    verified_submitter_id
    verifier_id
    verification_source
    verification_result
    evidence_reference
}
```

```text
⇒ 这是【设计示意】，不是要求立即增加实现。
⇒ 本版不定义其序列化格式（列为前置条件 P-2，见 §七）。
```

## 4.4 必须区分的一件事

```text
⇒ 核验谁【提交】了事件
   ≠ 已证明谁【实际写入】了目标状态文件。

⇒ 因此：
SUBMITTER_IDENTITY_TRUST_PATH
    = TRUSTED_CONTROLLER

SUBMITTER_IDENTITY_VERIFIED
    = NOT ESTABLISHED

WRITER_ATTRIBUTION_CHAIN
    = NOT ESTABLISHED
```

```text
⇒ 【这是本协议最关键的一处 N O T】
⇒ 即使 4.2 五条全部做到，
   也只解决了「谁提交」，
   没有解决「谁写入目标文件」。
⇒ 两者的证据不通用。
```

# 七 · 失败与拒绝规则（T-4 要求项）

```text
⇒ 本节按 T-4 第 6 项「失败及拒绝规则」要求补齐。
⇒ 只写规范语义，不写实现。
```

## 7.1 引用完整性失败

```text
情形：AttemptRecord 或 ReceiptRecord 的 authority_record_key
     与其完整性覆盖不符（被篡改）

判定：INVALID_REFERENCE_INTEGRITY
处置：该记录【不得】参与 c1..c7 的判定
      SUBMITTER_IDENTITY 相关放行路径【不启动】
```

## 7.2 引用解析失败

```text
情形：authority_record_key 解析不到任何 EventRecord

判定：REFERENCE_UNRESOLVED
处置：不放行；记录该失败（不得静默丢弃）
注意：UNRESOLVED ≠ CLEAN，也 ≠ 已证明不存在
```

## 7.3 多权威实例（T-2 违反）

```text
情形：检测到两个可独立签发权威事件的实例
     （注意：AUTHORITY_EXCLUSIVITY_ENFORCEMENT = NOT ESTABLISHED，
      故本情形【可能无法被检测】）

判定：若检测到 ⇒ AUTHORITY_SCOPE_VIOLATED ⇒ 不得宣布权威映射成立
     若未检测到 ⇒ 【不得据此宣布权威映射成立】——
       未检测 ≠ 不存在（PROBE_CLEAN ≠ BUSINESS_CLEAN）
```

## 7.4 身份核验失败

```text
情形：SUBMITTER_IDENTITY_ATTESTATION 缺失、失败或无法绑定到
     (event_id, attempt_id)

判定：SUBMITTER_IDENTITY = NOT ESTABLISHED
处置：不得进入依赖该身份的正式放行路径
```

## 7.5 四类反例（凌翼第八节第 4 项要求检查）

```text
【反例 1 · 正常重试】
  首次 attempt=A1，建立权威记录 K。
  ACK 丢失。重试 attempt=A2（≠A1），仍引用 K。
  ⇒ 期望：A2 合法，c1 通过（比较的是键是否就是该 event 的唯一权威绑定，
    不要求 attempt 相等）。
  ⇒ 若 c1 判 A2 失败 ⇒ 实现违反 D2 IC-1。

【反例 2 · 重复 ACK】
  同一 (event_id, attempt_id) 收到两次 ACK。
  ⇒ 期望：第二次不新建权威记录，不改变 K；
    重复收据不得产生第二个 ReceiptRecord 的独立语义，
    除非 receipt_seq 明确区分。
  ⇒ 若第二次覆盖了第一次 ⇒ 违反记录不可变性。

【反例 3 · 错误引用】
  AttemptRecord 的 authority_record_key 指向另一 event 的记录。
  ⇒ 期望：c1 的 A.event_id == E.event_id 判据命中 ⇒ 拒绝。
  ⇒ 不得因「键能解析」而通过。

【反例 4 · 双记录者】
  两个实例同时签发权威事件。
  ⇒ 期望：按 T-2，CONCURRENT_AUTHORITY_INSTANCES = NOT SUPPORTED。
  ⇒ 但 AUTHORITY_EXCLUSIVITY_ENFORCEMENT = NOT ESTABLISHED，
    故【当前无机制阻止】，只能声明不支持。
  ⇒ 【不得】因声明了「不支持」就认为已经防住了。
```
