# 二 · T-1 · 引用的完整性保护

**裁定：`REFERENCE_INTEGRITY_REQUIRED`；禁止不必要的自引用结构。**

## 2.1 接受的一个概念纠正

```text
⇒ 我在初稿里担心「authority_record_key 进摘要 ⇒ 自引用递归」。
⇒ 凌翼指出：这个担心基于错误的 key 定义。

⇒ authority_record_key = (recorder_id, epoch, seq)
   ⇒ 这是【记录定位键】，由三个既有字段构成。
   ⇒ 对一个固定键的字节计算摘要，不构成密码学递归。
   ⇒ 只有把 key 定义成【依赖其自身摘要】的值，才形成循环依赖。

⇒ 我接受这个纠正。初稿的担心是错的。
```

## 2.2 落实的设计

```text
① 权威 EventRecord 的定位键由既有 recorder_id / epoch / seq 构成。
② 这三个字段继续纳入 EventRecord.content_digest。
③ AttemptRecord 与 ReceiptRecord 保存对权威记录的【引用】。
④ 两种引用记录【各自】有完整性覆盖规则，
   将 authority_record_key 及对应 event_id / attempt_id 纳入保护。
⑤ 【不】以修改既有 EventRecord.content_digest 字段清单的方式，
   解决其他记录类型的完整性问题。
```

## 2.2c 单射性要求（属「范围」侧，不属编码债务）

```text
⇒ 【2026-11-02 二次修正（睫 ③）：单射性不属于 P-1，属「范围」这一侧】

⇒ authority_record_key = (recorder_id, epoch, seq) 是【三元组】。
⇒ 若编码是【无分隔拼接】：
     (recorder_id="A", epoch="1",  seq="23") → "A123"
     (recorder_id="A", epoch="12", seq="3" ) → "A123"
⇒ 两个【不同】的键拼出【相同】字节 ⇒ 摘要相同。

⇒ 于是「覆盖 authority_record_key」这个声明，
   在编码不保证单射时，【无法唯一确定它保护的是哪一个取值组合】。
⇒ 也就是说：范围并没有被完整地定下来。
   它定住了「覆盖哪些字段」，
   而没定住「覆盖这些字段的哪一个取值组合」。

⇒ 【单射性不是实现细节】
⇒ 一个实现细节换一种做法，规范仍然成立；
   而一个非单射的编码，会让【规范本身失去确定含义】。
⇒ 故本版把它从 P1_ENCODING 提出来，留在「范围」这一侧：

   覆盖编码【须为单射且无歧义可解析】
   —— 不同字段取值组合 ⇒ 不同字节。
   复合键须显式定义分隔符或长度前缀。

⇒ 剩下的（用什么算法、字节序、拼接顺序）继续留在 P1_ENCODING。
⇒ 于是切分仍然成立，而「范围已定」这一句才真的站得住。
```

## 2.3 完整性覆盖的边界（凌翼特别强调）

```text
⇒ 摘要校验只能证明【内容与摘要相符】。
⇒ 摘要校验【不能】单独证明：
     · 来源真实
     · 抵御能同时改写记录及摘要的攻击者

⇒ 可信来源、追加式存储、写权隔离仍须【独立建立】。
⇒ 因此：
     DIGEST_MATCH           ≠ SOURCE_TRUSTED
     DIGEST_MATCH           ≠ TAMPER_PROOF
```

```text
⇒ 【未规范化的部分，显式列前置条件】
⇒ 引用记录完整性编码（具体用什么算法、覆盖哪些字节序）
   本版【未规范化】。
⇒ ⇒ 列为原型实施前置条件 P1_ENCODING，不得凭「已有摘要字段」默认具备。
   → 见 §七。
```

# 三 · T-2 · 权威域范围

**裁定：`SINGLE_LOGICAL_AUTHORITY`。当前设计只支持单一逻辑权威域。**

```text
⇒ 同一被管理的执行及对象范围内，
   同一时刻只允许【一个】权威记录者具有绑定写入权。

⇒ 允许以后讨论重启恢复，
   但恢复后的记录者必须【继承原权威域的持久化身份与绑定历史】，
   并保持 epoch 语义一致。

⇒ 禁止在没有协调机制的情况下启动两个可独立签发权威事件的实例。
```

```text
AUTHORITY_SCOPE
    = SINGLE_LOGICAL_AUTHORITY

CONCURRENT_AUTHORITY_INSTANCES
    = NOT SUPPORTED

CROSS_AUTHORITY_ELECTION
    = NOT DEFINED

AUTHORITY_EXCLUSIVITY_ENFORCEMENT
    = NOT ESTABLISHED
```

# 四 · T-3 · 提交方身份的可信路径

**裁定：`TRUSTED_CONTROLLER`（受信控制主体核验并绑定到 AttemptRecord）。**

## 4.1 为什么选 C

```text
⇒ D2 已要求存在控制主体，负责依据收件证据决定是否放行后继阶段。
⇒ 对最小原型：把身份核验职责【明确纳入这一受信控制边界】，
   避免同时引入新的密码学信任根，
   也避免要求尚不存在的记录者独立完成全部身份鉴定。

⇒ A（记录者侧观测）作为未来替代方案。
⇒ B（密码学绑定）暂不进入最小原型范围。
```

## 4.2 五个必须满足的条件

```text
① 控制主体须有【独立于提交方自填字符串】的身份依据，
   例如经验证的进程或受控通信通道身份。
② 核验结果必须绑定到具体 (event_id, attempt_id)，
   【不得仅凭 submitter_id 文本匹配】。
③ 该绑定须具有可追踪的记录来源及完整性要求，
   并能被记录者和后续验证过程消费。
④ 控制主体【不能仅以其自身声称「可信」作为可信依据】；
   其启动、权限与写入边界须在原型信任模型中说明。
⑤ 核验失败或证据缺失时，
   SUBMITTER_IDENTITY = NOT ESTABLISHED，
   不得进入依赖它的正式放行路径。
```

```text
⇒ 【2026-11-02 二次修正（知微 V02-Z-01）：① 不够，须绑到实际来源】

⇒ 反例：业务进程 P 在请求里填入另一个进程 Q 的标识。
   控制主体独立查询，确认 Q 确实存在且身份合法，
   然后把 Q 的身份记为这次提交者。
⇒ 查询本身是真实的，结果不是复制字符串，
   但它【没有证明这条请求来自 Q】。
⇒ 把该查询结果绑定到 event/attempt 也补不出缺失的来源关系。

⇒ 故 ① 须加强为规范句：
   可信观察必须建立
   「实际提交端点／进程实例 — 这次请求 — event/attempt」
   的关系，
   【不能仅验证请求里点名的身份确实存在】。

⇒ 身份的有效时间与实例范围也须明确，
   避免把旧实例的观察用于新实例。
⇒ 具体用何种系统接口可以后续选择；
   「这个关系本身」属设计语义，不可后置。

⇒ ④ 并非天然不可证伪，但须列明证据入口：
   事前登记控制主体 / 受信启动者 / 允许权限 / 输入端点 /
   核验结果的写入与消费权限边界；
   消费者核验实际实例符合该登记。
⇒ 登记及核验依据【不得】由被核验业务方随意改写，
   也【不得】仅来自控制主体的 trusted=True 自报。
⇒ 可接受公开的受信宿主或管理员前提，
   不需要为验证控制主体无限新增验证者。
⇒ 有限信任模型须说明【信任在哪里停止】。

⇒ 最小负向场景（文档推演，未执行）：
   · 请求自报另一个合法进程，独立查询成功但来源不匹配 ⇒ 拒绝身份成立。
   · 非指定组件产生同格式核验记录 ⇒ 不得因格式与结果值正确而接受。
   · 合法组件从不符合登记的启动/权限边界运行 ⇒ 前提未建立，不放行。
```
