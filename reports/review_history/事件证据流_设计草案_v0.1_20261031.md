# 2 · 第一个硬发现：有不留痕迹的合法情形（不止一种）

## 2.1 代码

`perturbation_j.py` L61-69：

```python
if mode not in J_MODES:
    raise HarnessError(f"unknown J mode: {mode!r}")

snap = state.snapshot()
q = snap.q
lit = snap.literal

if mode == IDENTITY:
    return
```

`perturbation_j.py` L44：

```python
IDENTITY = "IDENTITY"
```

`perturbation_j.py` L49：

```python
J_MODES = (IDENTITY, COLLAPSE_SIGN, ERASE_EFFECT, HALVE_AND_ERASE_LITERAL)
```

`perturbation_j.py` L22 注释：

```text
IDENTITY                : literal unchanged ; q unchanged
```

## 2.2 这意味着什么

```text
J 被执行了。J 走完了 apply_j。J 没有报错。
但 J 在 literal.bin 和 substrate.bin 上【什么也没改】。

⇒ 任何基于"比较前后摘要"的时序机制，
   对 IDENTITY 模式【结构上不可见】。
⇒ 不是难以检测，是不可能检测：
   摘要前后相等，因为没有变化。
```

## 2.3 实测（不是推理，是跑出来的）

```text
baseline literal = 16 个 \x00, q = 0
baseline digest  = 9d908ecfb6b256def8b49a7c…

在写入窗口内 apply_j(state, IDENTITY) 之后：
after digest     = 9d908ecfb6b256def8b49a7c…
digest equal?    True
literal equal?   True
q equal?         True
```

```text
⇒ J 被调用了、执行了、没报错，摘要一个字节没变。
⇒ 摘要层【结构上】无法观测到这次 J。
```

## 2.3b 更一般的发现：幂等写入同样不留痕

实测（同一环境，`tempfile` 沙箱，不改任何文件）：

```text
COLLAPSE_SIGN  on q=2 : 845c35898d2c -> 845c35898d2c   changed=False
COLLAPSE_SIGN  on q=0 : 9d908ecfb6b2 -> 9d908ecfb6b2   changed=False
ERASE_EFFECT   on 零基线: 9d908ecfb6b2 -> 9d908ecfb6b2   changed=False
ERASE_EFFECT   on q=2 : 845c35898d2c -> 9d908ecfb6b2   changed=True  ← 对照
```

```text
⇒ 不留痕的不是只有 IDENTITY 一种模式。
⇒ 任何"写入值等于当前值"的调用，摘要都不变。
   COLLAPSE_SIGN 的语义就是 q->+2，若 q 已是 +2，则写入幂等。
   ERASE_EFFECT 在零基线上写零，同样幂等。
⇒ 准确说法：
   摘要不变 ⇏ 该操作没有执行
   摘要不变 ⇏ 该写入没有发生
⇒ 这才是完整的边界。
   IDENTITY 只是它的最纯粹形态（连写都不写，直接 return）。
```

```text
⇒ 这条比我原报告强得多。
   我原报告只论证了"== 分不清早晚"（比较方法的问题）。
   实测显示还有更根本的一层：
   被比较的东西在某些合法情形下【根本不发生变化】，
   于是"比较方法够不够强"已经不构成问题。
```

## 2.4 这与凌翼的理由第 5 条完全对应

凌翼 A 项理由：

```text
"等值检查并未覆盖『相同状态被重复使用』或『J 未改变摘要』等反例。"
```

```text
⇒ 我在原报告里只举了对称性（alpha/beta），
   没有意识到"J 未改变摘要"不是假想反例，
   而是冻结代码里【已经存在】的情形，且不止一种模式。
⇒ 凌翼这一条比我原报告更根本：
   即使把 == 换成有序列的 <，
   摘要层的比较仍然看不见幂等写入与 IDENTITY。
```

## 2.5 由此得到的结论

```text
时序证据【不能建立在状态摘要上】。
不是"摘要不够好"，是摘要回答的是另一个问题：
  摘要回答："状态变了吗"
  时序需要："这个事件发生了吗，什么时候"
⇒ 这两件事在 IDENTITY 和幂等写入下明确分离。
⇒ 整个设计的存在性证明：
   状态未变 ⇏ 事件未发生。
```

# 3 · 第二个发现：写入方自己读了快照

## 3.1 代码

`writers.py` L110-115：

```python
    # SET semantics precondition: q must be at the frozen precondition value.
    snap = state.snapshot()
    if snap.q != WRITE_PRECONDITION_Q:
        raise HarnessError(
            f"extra write requires q == {WRITE_PRECONDITION_Q}, got {snap.q}"
        )
```

`perturbation_j.py` L64-66：

```python
    snap = state.snapshot()
    q = snap.q
    lit = snap.literal
```

## 3.2 两处问题

```text
问题一（角色冲突）：
  observer.py L4-7 声明 "The observer is a read-only component that is
  NOT the write operator."
  但 extra_write 和 apply_j —— 两个都是写入方 —— 各自调用了 state.snapshot()。
  ⇒ 写入方读了状态。虽然只用于前置条件检查、不产出证据，
    但这使得"写入方读到的状态"与"observer 看到的状态"是两条独立路径，
    彼此之间没有任何一致性保证。

问题二（非原子，且发生在写入路径内）：
  storage.py L71-83 的 snapshot() 是两次独立读（L73 literal，L74 substrate）。
  ⇒ writers.py L111 / perturbation_j.py L64 取到的 snap，
    可能是一个【从未真实存在过】的组合状态。
  ⇒ 而它被用来做前置条件判定（q != WRITE_PRECONDITION_Q 就报错）。
  ⇒ 即：一次合法写入可能因为非原子快照而被误判为非法。
```

## 3.3 这一条我要标成"本文最不确定的判断"

```text
我确认事实：两处调用 snapshot()，且 snapshot() 是两次独立读。
我不确认后果：是否【已经】发生过误判，我没有证据。
⇒ 准确说法：这是【结构性风险】，不是【已发生的缺陷】。
⇒ 若凌翼认为需要，可另开一项核查；本文不宣称它是 bug。
```

# 4 · 设计：事件记录，不依赖摘要

## 4.1 基本原则

```text
一条事件记录回答四个问题，每个都必须独立成立：

  WHO     —— 哪个对象（arm / episode / 文件身份）
  WHAT    —— 哪类事件（OPEN / COMMIT / CLOSE / SNAP_BEGIN / SNAP_END）
  WHEN    —— 有序位置（序号，不是摘要，不是裸时间戳）
  BY      —— 哪个执行主体（execution 身份）

⇒ 摘要只作为【附加】字段记录状态，【不参与】排序。
```

## 4.2 为什么必须有 BY，而没有 BY 就不能定序

```text
若事件记录里没有"谁记录的"，
那么两个进程可以各自写序号 1、2、3 …
⇒ 合并后无法排序，因为序号空间不共享。
⇒ 这【正是】NB-50 说的问题：主键不存在。
⇒ 所以 execution 身份不是锦上添花，是排序的前提。
```

## 4.3 结构（设计草案，非实现）

```text
EventRecord {
    seq            : 序号（由可信记录路径分配，全局单调）
    execution_id   : 执行身份（必须先于任何事件产生）
    object_id      : 对象身份（arm + 文件身份）
    event_type     : WINDOW_OPEN | WRITE_COMMIT | WINDOW_CLOSE
                   | SNAP_BEGIN  | SNAP_END     | HANDOFF
    clock_ns       : perf_counter_ns（辅助，非判据）
    state_digest   : 附加字段，不参与排序
    producer_id    : 记录者身份
}
```

## 4.4 四条 precedes 如何被判定

```text
WRITE_COMMIT 的 seq  <  WINDOW_CLOSE 的 seq
⇒ 判定依据是【序号】，不是摘要，不是时钟。

⇒ 因此 IDENTITY 模式的 J 也能被看见：
   它不产生 WRITE_COMMIT（因为没有写入），
   但它【可以】产生一条 J_APPLIED 事件。
⇒ 关键设计点：事件记录必须记录【调用】，
   而不只是记录【效果】。
```

## 4.4b 凌翼提醒：WRITE_COMMIT 这个词本身还没有定义

凌翼原文：

```text
第二，WRITE_COMMIT 必须定义清楚。
函数返回、数据进入缓存、系统确认写入以及持久化完成，
不一定是同一个事件。
设计不能仅通过一个名称就假定这些语义相等。
```

```text
⇒ 这是本文一个实质缺陷，我必须承认：
   我在 4.4 里直接使用了 WRITE_COMMIT，
   却从未定义它指四者中的哪一个。

⇒ 更要紧的是：这四个时刻在本实现里【分得开】：

  (1) 函数返回        storage.py L99 write_literal 返回
  (2) 数据进入缓存     Python 文件对象缓冲（_write_bytes 用 open(...,"wb") + f.write）
  (3) 系统确认写入     OS 收到 write() 调用
  (4) 持久化完成       fsync / 关文件后落盘

⇒ 我核过 storage.py L59-61 的 _write_bytes：

    def _write_bytes(self, path: Path, data: bytes) -> None:
        with open(path, "wb") as f:
            f.write(data)

   ⇒ 无 flush()、无 os.fsync()。
   ⇒ with 退出时只保证【文件对象关闭】，不保证【持久化】。
   ⇒ 因此 (1)(2) 与 (4) 之间【没有强制同步点】。
   ⇒ 全仓库检索 fsync / flush() ：仅 q3_business_worker_entry.py L63、L85
     两处 sys.stdout.flush()，与文件持久化无关。零处文件级同步。

⇒ 后果：若 WRITE_COMMIT 取 (1)，则崩溃可能丢数据，
   而事件流已经记录了"已提交"。
⇒ 这不是命名问题，是【崩溃语义】问题。
```

**需要明确的定义（本文不代定，列出四种候选）：**

```text
WRITE_COMMIT 定义为：
  (a) write_literal/write_substrate 返回
      ⇒ 最弱。崩溃可丢。但与本实现现状一致（无 fsync）。
  (b) 文件对象 close 完成（with 退出）
      ⇒ 中等。仍无持久化保证。
  (c) os.fsync() 返回
      ⇒ 强。需新增同步点 ⇒ 属 CODE_CHANGE。
  (d) 外部记录者确认收到提交回执
      ⇒ 最强，且与 O-1「事件记录者统一分配序号」天然对齐
        （凌翼 O-1 已要求：只有记录者确认 WINDOW_CLOSE 有效提交后，
          才允许进入 SNAPSHOT_BEGIN）。

⇒ 本文倾向 (d)，因为它与 O-1 的裁定结构一致 ——
   但"倾向"二字我已在 5.1 撤回过一次，
   因此这里只【指出 (d) 与 O-1 一致】，不代为选择。
⇒ 请凌翼在 O-1 的因果约束落地时一并确定。
```

**在定义明确前：**

```text
WRITE_COMMIT 在本文中仅为【占位符】，
不得用于任何判定，不得填入证据矩阵（O-6 要求五段式）。
```

## 4.5 这一条是与 BD-52 的根本区别

```text
BD-52    : 记录效果（摘要），因此看不见无效果的事件
本文提议 : 记录调用（事件），效果作为附加字段

⇒ 前者无法表达"发生了但没改变"
⇒ 后者可以
⇒ 幂等写入是检验该设计是否成立的最小测试用例
  （IDENTITY 更极端：连写都不写）。
```

# 5 · 设计中的三处未决点（我不自决）

## 5.1 序号由谁分配

```text
候选 A：单一记录进程（独立于 writer）
  ✓ 序号天然全局有序
  ✗ 该进程成为单点；它崩了就没有见证
候选 B：文件锁 + 递增计数
  ✓ 无单点
  ✗ 锁的语义跨平台不同；崩溃时锁可能残留
候选 C：外部见证者（阶段⑥同源）
  ✗ 事后，不能用于事前判定（凌翼已指出这一点）
⇒ 三条各有不可消除的缺口。
⇒ 【修订 2026-10-31】原文此处写「我倾向 A 或 B」，该表述已撤回：
   在需要裁定的地方给出倾向，等于替裁定者预选。
   选哪个取决于哪种失效更可接受 —— 这是凌翼的判断，不是我的。
```

## 5.2 崩溃时事件流的完整性

```text
凌翼反例 #1：写入窗口尚未关闭，writer 进程崩溃。

若事件记录与 writer 同进程：
  ⇒ 崩溃时 WINDOW_CLOSE 永不产生
  ⇒ 而"窗口没关"与"窗口关了但没记录"无法区分
⇒ 因此记录者必须独立于 writer（凌翼 C 项已明确要求）
⇒ 但即使如此，"记录者也崩了"仍需处理：
   ⇒ 必须有【超时后判定为 INVALID】的规则，
     而不是补造一个 CLOSE。
```

## 5.3 时钟的角色

```text
按凌翼 C 项：
  · 时钟值可作为【辅助】时间证据
  · 不得将记录顺序无条件等同于实际发生顺序

⇒ 因此 clock_ns 不进排序键，只用于：
   · 检测明显不可能的顺序（记录延迟过大）
   · 事后审计
⇒ 【修订 2026-10-31】原文此处写「若 clock_ns 与 seq 矛盾，应当报 INVALID，
   而不是自动相信其中一个」。该表述已撤回为【三个并列选项】，不再预选：
     (a) 以 seq 为准，clock_ns 仅告警
     (b) 以 clock_ns 为准，seq 仅计数
     (c) 一律 INVALID，不自动仲裁
   ⇒ 原文的「应当报 INVALID」实际上就是 (c)，即我替裁定者选了 (c)。
   ⇒ 请凌翼裁定；在此之前本规则不成立。
```
