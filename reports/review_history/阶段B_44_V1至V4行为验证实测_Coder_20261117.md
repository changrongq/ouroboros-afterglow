## 四 · 遗留：probe-v4 分支无法删除

```text
⇒ 合并后尝试删除远端 probe-v4：
     DELETE /git/refs/heads/probe-v4  → 422
     {"message":"Repository rule violations found\n\n
                Cannot delete this branch"}

⇒ 【原因】：`~ALL` 规则含 `deletion`，禁止删除分支 —— 包括探针分支。
   ⇒ 这不是错误，是保护生效的副作用。

⇒ 【待处理】（需船长在界面操作或决定）：
   方案 a：界面 Settings → Branches 中删除 probe-v4
           （若界面也被规则拦住，需临时调整 ruleset）
   方案 b：保留该分支，在台账中注明"V-4 探针分支，已合并，非工作分支"
   ⇒ 我倾向 b：它不影响安全，且删除它会留下"规则可以临时放宽"的先例。
```

## 五 · 这次验证改了什么

### 5.1 事实层面的改变

```text
之前                         现在
─────────────────────────────────────────────────
main 受保护，exp 不受保护      两者均受保护，且新分支自动受保护
Mion 的 write 权限可直推 exp   推 exp 被拒（V-3 实测）
只能靠"约定"不推               靠规则集拦（bypass_actors = []）
```

### 5.2 对 Mion 的实际影响

```text
⇒ 她的 `write` 权限仍在（个人仓库无法降低），
   但：
     · 推 main → 被拒（已实测，B-1）
     · 推 exp  → 被拒（本次 V-3 实测）
     · 新分支  → 可推（V-4 实测），但分支受保护无法删除
   ⇒ 实际效果 = "可以提 PR，不能直接改受保护分支"。

⇒ 加上她的 token 本身是 Contents: Read-only，
   等于【两条路都堵住了】：
     · 用 token：权限不够
     · 用账号密码：规则集不许
```

### 5.3 对我的实际影响

```text
⇒ 我以后每次提交都需要：
     建分支 → 推分支 → 开 PR → 合并
   ⇒ 本次 V-4 已完整走通该流程（PR #2），
     所以这条路是【验证过的】，不是推测的。
```
