# 一 · 裁定 2：HWM 追加式历史表

## 1.1 裁定内容

```text
⇒ 「选择方案 (a)，保留追加式 HWM 历史记录。」

⇒ 建议 TSU 结构：
   | 对象 | 职责 |
   |---|---|
   | `commitment` | 追加 N5 |
   | `hwm_history` | 追加每次 HWM 变更记录 |
   | `hwm_current`（可选） | 当前高水位的派生投影，**非独立信任根** |

⇒ 「恢复时不得仅依赖 `hwm_current`。」
⇒ 「同一受信事务允许多个对象同时提交；
    不得把对象数量与逻辑原子性混为一谈。」
⇒ 「追加历史可支持留痕分叉检测，
    但不能自行证明整个 TSU 没有被回滚。」
```

## 1.2 我原来的矛盾与修正

```text
⇒ 【我的矛盾】（我已经在阶段B_3 Q3 里自己标出）：
   一边说"hwm 表恒 1 行"，
   一边设计"两条同 counter 的记录 ⇒ 分叉"。
   ⇒ 单行表不可能有两条记录 ⇒ 该检测是空的。

⇒ 【裁定选择 (a) 之后，矛盾消除】：
   · `hwm_history` 追加 ⇒ 可以有多条 ⇒ 分叉检测有意义
   · `hwm_current` 是投影 ⇒ 单行，但不是信任根

⇒ 【一个新的要求出现了】：恢复时必须读 `hwm_history`，
   而不是读 `hwm_current`。
   ⇒ 因为 `hwm_current` 是【派生】的，若它与 history 不一致，
     以 history 为准；若不一致 ⇒ 判为缺陷。
```

## 1.3 修订后的 TSU 结构

| 表 | 行数 | 约束 | 职责 |
|---|---|---|---|
| `commitment` | 无上限 | 只追加；禁 UPDATE/DELETE | N5 记录 |
| `hwm_history` | 无上限 | 只追加；禁 UPDATE/DELETE | 每次 HWM 变更 |
| `hwm_current` | 恒 1 行 | 可由 history 重建；**非信任根** | 派生投影（可选） |

```text
⇒ 【hwm_current 的三个限定】：
   ① 不可作为恢复依据
   ② 不可作为"当前高水位"的权威来源
   ③ 若与 hwm_history 推算值不一致 ⇒ 判缺陷，不是"以它为准"
```

## 1.4 恢复时的读取顺序（修订）

```text
⇒ STEP R1′（修订）：
   ① 读 `hwm_history` 全部记录
   ② 验证链：`predecessor_hwm_digest` 连续
   ③ 验证 `hwm_epoch_counter` 严格 +1 递增，无重复
      ⇒ 若有重复 ⇒ 分叉 ⇒ STOPPED 并保留证据
   ④ 取最后一条作为当前可信高水位 H
   ⑤ 【若存在 hwm_current】：
      计算 history 推算的期望值
      ⇒ 与 hwm_current 比对
      ⇒ 不一致 ⇒ 判缺陷（STOPPED），【不得】以 hwm_current 覆盖

   ⇒ 【绝不】先读 hwm_current 再用它去解释 history：
     那等于让投影定义事实。
```

## 1.5 分叉检测的含义与边界

```text
⇒ 【能检出的分叉】：
   两条 `hwm_epoch_counter` 相同的记录被【同时保留】在 history 里。

⇒ 【检不出的】：
   · 分叉的一条被【删除】了（虽然禁止删除，但越权者可为之）
   · 整个 TSU 被回滚（承裁定：追加历史不能自证未被回滚）

⇒ 【故】：分叉检测支持"留痕分叉"，
   【不支持】"无痕篡改"与"整体回滚"。
   ⇒ 后者仍依赖介质独立性（阶段B_2），仍为 0/6 已测。
```

# 二 · 裁定 3：N3 重复撤销的三类情形

## 2.1 裁定内容

```text
⇒ 「区分重复记录与重复请求。

    · 对同一有效授予重复创建新的撤销效果：**拒绝**。
    · 对完全相同、具有同一幂等标识且能够独立验证的重试请求：
      允许返回此前结果，但不得追加第二次撤销，
      也不得产生第二次资格状态跃迁。
    · 请求标识相同但内容不一致，或者此前撤销是否生效无法确定：
      不得当作合法幂等请求处理；按既有冲突或未知状态规则拒绝或停止。

    须将这三类情形分别写成测试反例。」
```

## 2.2 三类情形之一的判定表

| # | 情形 | 判定 | 期望行为 | 证据要求 |
|---|---|---|---|---|
| **N3-A** | 对同一有效授予，**新建一个撤销效果**（不同请求标识）| **拒绝** | 不写入；不产生第二次状态跃迁 | 已有 REVOCATION 记录 + 新请求标识不同 |
| **N3-B** | **完全相同**的重试：同请求标识、同内容、可独立验证 | **允许返回旧结果** | 返回此前结果；不追加记录；不跃迁 | 旧 REVOCATION 记录 + 请求标识匹配 + 内容摘要匹配 |
| **N3-C1** | 请求标识相同但**内容不一致** | **拒绝**（冲突）| 不写入；报冲突 | 旧记录摘要 ≠ 新请求内容摘要 |
| **N3-C2** | 此前撤销**是否生效无法确定** | **STOPPED** | 不写入；保留证据 | 旧记录状态 = UNKNOWN |

```text
⇒ 【A 与 B 的分界是"请求标识"】：
   标识相同 ⇒ 视为同一次请求的重试
   标识不同 ⇒ 视为两次独立请求，第二次必须拒绝

⇒ 【B 与 C1 的分界是"内容是否一致"】：
   标识相同 + 内容相同 ⇒ 幂等
   标识相同 + 内容不同 ⇒ 冲突（不是幂等）

⇒ 【C2 为什么要单独】：
   若连"此前是否生效"都不知道，
   就不能判断新请求是"重复"还是"补充"。
   ⇒ 按 UNKNOWN 处置，不归类（承 S5 的"UNKNOWN 不归类"）。
```

## 2.3 幂等标识的设计要求

```text
⇒ 【幂等标识是什么】：
   由调用方提供，用于声明"这是同一次请求"。
   ⇒ 必须在 REVOCATION 记录中持久化。

⇒ 【必需字段（增补）】：
   | 字段 | 类型 | 说明 |
   |---|---|---|
   | `idempotency_key` | bytes[16] | 请求标识 |
   | `request_digest` | bytes[32] | 请求内容的规范化摘要 |

⇒ 【为什么需要两个】：
   只有 key ⇒ 无法区分"同请求重试"与"同 key 不同内容"
   ⇒ 两者同时存在才能实现 A/B/C1 的区分。

⇒ 【key 的唯一性范围】：
   ⇒ 建议：(authority_domain, generation, idempotency_key) 唯一
   ⇒ 跨域重用同一 key 不应被视为同一请求
```

## 2.4 测试反例（凌翼要求分别写）

```text
TV-N3-A  重复创建新撤销效果
  前置：GRANT G1 已存在且有效；REVOCATION R1 已存在指向 G1
  注入：提交 R2，指向 G1，idempotency_key ≠ R1 的 key
  期望：拒绝写入；状态不变；返回冲突错误
  若未拒绝 ⇒ FAIL_IMPLEMENTATION

TV-N3-B  完全相同重试
  前置：同 TV-N3-A 的前置
  注入：提交 R2，指向 G1，idempotency_key == R1 的 key
        且 request_digest == R1 的 request_digest

TV-N3-C1  同 key 异内容

```

# 三 · 裁定 4：S1 独立观测者接口

## 3.1 裁定内容

```text
⇒ 「允许暂时停留在 DESIGNED_NOT_IMPLEMENTED，
    但不得因此获得验证通过资格。」

⇒ 「单进程内的自报、两个进程各自输出的日志，
    以及未验证的时间戳，均不能单独证明
    可签发资格区间不存在重叠。」

⇒ 下一版应提出【独立于被测 W 和 S 决策路径】的观察者接口，明确五项：
   ① 观察者如何获得实际持锁和资格状态证据
   ② 如何确定观察区间的起点与终点
   ③ 如何发现观测缺口
   ④ 如何注入双持有者、挂起和异常退出情形
   ⑤ 何种证据足以判定 VIOLATED 或在有限覆盖区间内判定 HOLDS

⇒ 「在没有独立观察证据时，S1 不能宣告 HOLDS，L3 不得 PASS。」
```

## 3.2 观察者接口设计

```text
⇒ 【核心原则】：观察者【不得】读取 W 或 S 的自报状态。
   ⇒ 它必须读【操作系统层面的可观测事实】。

⇒ 【可用的观测源】：
   | 观测源 | 能证明什么 | 局限 |
   |---|---|---|
   | 内核 mutex 句柄归属 | 谁真正持有互斥对象 | 需要能枚举句柄 |
   | 进程/线程存在性 | 实例是否活着 | 不代表持有资格 |
   | 文件锁状态 | 独占是否成立 | 依实现 |
   | 授予记录的可读状态 | 谁被授予 | 只是声明，非执行 |
```

### 3.2.1 五项要求的逐项回答

```text
⇒ 【① 如何获得实际持锁和资格状态证据】
   方案：观察者独立打开【同一命名 mutex】，
         尝试 `OpenMutex` + 检查是否可获取。
   ⇒ 若能获取 ⇒ 说明当前无人持有
   ⇒ 若返回 ALREADY_EXISTS 且无法获取 ⇒ 有人持有
   ⇒ 【但"谁持有"操作系统不直接告诉外部进程】
     ⇒ 需辅以句柄枚举（`NtQuerySystemInformation` 类）
   ⇒ 【这是关键限制】：见 3.3 的不可得性说明。

⇒ 【② 如何确定观察区间起止】
   区间 = [首个实例获得资格, 最后一个实例释放资格]
   ⇒ 起点：由观察者轮询检测到"有实例持有时"标记
   ⇒ 终点：观察者检测到"无实例持有"时标记
   ⇒ 【不得用被测方报告的启动/停止时间】
   ⇒ 时间基准：观察者的单调计数器，非墙上时钟
     （承 §0 B-3：clock_ns 不参与排序）

⇒ 【③ 如何发现观测缺口】
   观察者必须【连续轮询】并记录每次采样的时刻。
   ⇒ 缺口 = 两个相邻采样之间的间隔 > 预设上限
   ⇒ 有缺口 ⇒ 该段区间为 UNKNOWN ⇒ 不得判 HOLDS
   ⇒ 【采样间隔直接决定可信度】：间隔越大，漏检越容易。

⇒ 【④ 如何注入双持有者/挂起/异常退出】
   | 注入 | 方法 | 观察者应看到 |
   |---|---|---|
   | 双持有者 | 强制两个实例都进入"声称持有"状态 | 同时存在两个持有者 ⇒ VIOLATED |
   | 挂起 | `SuspendThread` 持有者 | 持有区间变长，但基数仍为 1 |
   | 异常退出 | `TerminateProcess` 持有者 | 持有突然结束，另一实例可能接手 |

⇒ 【⑤ 何种证据足以判定】
   | 结论 | 需要 |
   |---|---|
   | VIOLATED | 在某一采样点上，观察者独立确认存在 2 个持有者 |
   | HOLDS | 全区间无缺口 + 每个采样点基数 ≤ 1 |
   | UNKNOWN | 有任一缺口 |
   | INCONCLUSIVE | 资源耗尽未采完 |
```

## 3.3 一个我必须承认的不可得性

```text
⇒ 【要害】：在 Windows 上，【另一个进程】无法可靠地把
   "持有一个命名 mutex 的线程属于哪个进程"告诉外部观察者。
   ⇒ mutex 是线程所有；句柄表是进程私有。
   ⇒ 枚举系统句柄需要【特权】（如 SeDebugPrivilege），
     且结果本身可能被规避。

⇒ 【故】：观察者能可靠回答的是：
   · "当前是否有人持有"（可）
   · "某一时刻有几个人声称持有"（只能靠各自的证据）
   ⇒ 【不能】可靠回答"谁持有"。

⇒ 【这对 S1 意味着什么】：
   S1 要判的是【基数 ≤ 1】。
   ⇒ 若只能观测"是否有人持有"，则无法数出基数 2。
   ⇒ 【基数 2 的唯一可靠证据】，是观察到
     "两个实例在同一区间内都完成了签发动作"
     → 这依赖签发记录，而签发记录可能被回滚/删除。

⇒ 【结论】：S1 的独立观测在本机范围内【不可完全建立】。
   ⇒ 我按裁定登记：
     `S1_INDEPENDENT_OBSERVER = NOT ESTABLISHED`
   ⇒ 并给出【部分可行的替代】：见 3.4。
```

## 3.4 部分可行的替代（明确标注为不足）

```text
⇒ 【替代方案 O1】：观察者 + 内核对象存活检测
   · 观察者轮询命名 mutex 是否存在且被持有
   · 若同时存在【两个不同名称】的 mutex 被各自持有
     ⇒ 说明互斥机制被绕过 ⇒ VIOLATED
   · 【局限】：只能发现"用了两个 mutex"，不能发现
     "两个实例共用一个 mutex 但都认为持有"

⇒ 【替代方案 O2】：签发记录交叉比对
   · 收集两个实例各自的签发记录
   · 若存在两条签发记录的 epoch/seq 冲突
     ⇒ 说明并发成立 ⇒ VIOLATED
   · 【局限】：这是【事后】检测，不是区间内观测；
     且依赖记录未被删除

⇒ 【两者都不是完整的 S1 观测】。
   ⇒ 【不得】用它们宣告 S1 HOLDS。
```

## 5.2 裁定 5：第⑦栏不变，另设完成性字段

```text
⇒ 「不改变第⑦栏的既有语义。」
⇒ 「第⑦栏仍表示【事前登记的预期 L2 判定】；
    不得为了反映运行时未完成，而把既定预期结果改成 `—`。」

⇒ 【这否定了我上一轮的提议】：
   我想在 ⑦ 栏加 `—（未完成）`。⇒ 被否定，正确。
   ⇒ 因为 ⑦ 栏是【事前预期】，不是【事后结果】。
     把结果写进预期栏，会让"预期"与"实际"混在一起。

⇒ 【正确做法】：另设完成性与实际判定字段：
   | 情况 | 完成性 | 实际 L2 |
   |---|---|---|
   | L1 未达 | NOT_ELIGIBLE | 不进入 |
   | 验证资源耗尽 | INCONCLUSIVE | 尚未产生 |
   | 验证完成 | COMPLETE | L2 三值之一 |
   | 尚未执行 | NOT_RUN | 无结果 |

⇒ 【现有绑定表不改动】。
   先在【专项结果表】加入这些列，待独立复核后再定正式格式。
```
