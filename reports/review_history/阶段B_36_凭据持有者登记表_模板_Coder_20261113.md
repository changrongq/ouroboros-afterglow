## 零 · 这份表是什么、不是什么

```text
⇒ 【是】：一份【事实清单】——现在谁手上有什么凭据、能改什么。
⇒ 【不是】：一份【信任声明】。填满这张表，也不等于 S2 已经建立。

⇒ 【为什么先要有这张表】：
   裁定 A.3 第 2 条要求「权限持有者名单完整、可审计，并在变更后重新核验」。
   ⇒ 而"谁有资格当 CUSTODIAN"这个问题，真正的答案不在人选的德行或身份，
     而在【谁与记录写权真的没有路径重叠】。
   ⇒ 要把这件事说清楚，必须先知道【现在谁手上有什么】。
     这份清单就是那个前提。
```

```text
⇒ 【本表此刻全空】。空白不是遗漏，是【诚实的起点】：
   在我们没有真实盘点之前，任何填进去的名字都是虚构。
   ⇒ 裁定 A.2 原话：「可信摘要保管者的人选及实际凭据持有者，目前不作虚构指定。」
```

## 一 · 先填什么（两条线，分开填）

```text
⇒ 【重要】：本表有两条记录线，不要混填。

   线 1 · 凭据现状（WHO HAS WHAT）—— 这是【事实盘点】，全部靠核对
   线 2 · 角色指派（WHO PLAYS WHAT）—— 这是【治理决定】，由船长批准

⇒ 【顺序不能颠倒】：
   先有事实盘点，才谈得上指派。反过来先指派再补盘点，
   等于用决定去迁就事实 —— 那样填出来的名单一定是"刚好合适"的，
   而"刚好合适的名单"没有证明力。
```

## 二 · 凭据持有者条目（A3-2 前置）

```text
⇒ 每个持有人一条。字段定义来自 B_32 §2.8.4，此处给填写说明。
```

| 字段 | 填什么 | 怎么核实 |
|---|---|---|
| `holder_id` | 持有人标识（可与署名不同，但须能对应到人） | 由本人确认 |
| `credential_kind` | 凭据种类（GitHub 账号 / SSH 密钥 / 部署密钥 / Token / 管理员权限 / 其他） | 看实际配置，不凭记忆 |
| `credential_scope` | 该凭据**能改哪些路径或仓库** | 逐条列，写"全部"要有依据 |
| `can_modify_record_side` | 能否修改**待验证记录**及其产生代码 | 是 / 否 / 不确定 |
| `can_modify_digest_side` | 能否修改**预期摘要**及其存储 | 是 / 否 / 不确定 |
| `third_party_paths` | 是否有间接路径（代管、代办、脚本、CI 密钥） | 写清路径；无则写"无" |
| `evidence_ref` | 支撑以上判断的事实来源（截图 / 配置 / 记录） | 可被第三方复查 |
| `as_of` | 以上信息对应的时间点 | 凭据会变，必须有时间戳 |

```text
⇒ 【`不确定` 是一个合法答案，而且是重要的答案。】
   ⇒ 不知道就说不知道。写成"否"会让整张表的独立性论证凭空成立。
   ⇒ §2.3 的 WE-1 判据是「交集为空」。若有人填"不确定"，
     则交集是否为空【无法判定】⇒ 独立性判定必须是 UNDETERMINABLE。
```

## 三 · 角色指派条目（治理线）

```text
⇒ 字段与 B_32 §2.8.1 的三职责对应。本表只留位置，由船长批准后填写。
```

| 字段 | 说明 |
|---|---|
| `role` | `RECORD_WRITER` / `EXPECTED_DIGEST_CUSTODIAN` / `INDEPENDENT_REVIEWER` |
| `assignee` | 承担者 |
| `approved_by` | 批准者（按裁定 A.2，为船长） |
| `approved_at` | 批准时间 |
| `basis` | 批准依据（**必须指向本表第二节的事实条目**） |
| `accepted_at` | 承担者明确接受的时间 |
| `scope_accepted` | 明确接受的审查/职责范围 |
| `revoked_at` / `reason` | 撤销时间与原因 |

```text
⇒ 【`basis` 是关键字段】：不许写"因为他合适"。
   必须写成"其 `can_modify_record_side = 否`（见第 N 条，证据 E-xx）"。
   ⇒ 即：【指派必须建立在事实条目上，而不是印象上】。
```

## 四 · CUSTODIAN 资格的判定条件（供船长批准时对照）

```text
⇒ 本表不提名，只给判定条件。条件是【可核对的】，不是主观评价。

  条件 C-1  与记录写权分离
    要求：`can_modify_record_side = 否`，且 `third_party_paths` 无通往记录侧的路
    核对：第二节对应条目的证件
    ⇒ 这是 WE-1「交集为空」能否成立的根本。

  条件 C-2  不决定摘要校验逻辑
    要求：未参与定义"怎样算摘要正确"
    ⇒ 否则"判定标准"与"预期值"由同一人掌握，独立性成空话。

  条件 C-3  持独立凭据
    要求：写入预期摘要所用凭据，不与其他角色共享
    ⇒ 注意：共享同一账号 ≠ 共享凭据。要看的是【凭据】不是【账号】。

  条件 C-4  能维护四项产出（裁定 A.1）
    要求：能实际维护
          ① 预期摘要存储 ② 凭据持有者名单
          ③ 凭据变更记录 ④ 写入权限证明
    ⇒ 这四项缺一不可。只维护存储不维护名单 ⇒ 无法支撑 WE-1。

⇒ 【三条都不满足就直接不合格】。若 C-1 无法判定（填了"不确定"），
  则只能记 UNDETERMINABLE，不能记合格。
```

```text
⇒ 【关于"船长"身份的纪律（裁定 A.2 原话）】：
   「船长负责治理层面的角色指定和批准，
     但不得因为是船长，就自动被认定为独立可信根。」
   ⇒ 也就是说：船长可以【当】CUSTODIAN，但理由必须是
     条件 C-1 成立，而【不是】"因为他是船长"。
   ⇒ 这两句必须分开写，否则判定就退化成身份认定。
```

## 五 · 知晓但未参与者（本表附注，不是缺陷记录）

```text
⇒ 项目中有成员尚未完全参与。这不影响本表的有效性，但必须记录，
   否则"名单完整"这个说法就没有意义。

  记录方式：列出已知存在但尚未取得凭据 / 尚未参与审查的人，
  并注明其【当前是否持有任何可影响两侧的凭据】。

⇒ 【为什么要记】：WE-1 判的是"谁能改"，不是"谁在参与"。
   一个不参与项目但持有管理员凭据的人，恰恰是 WE-1 最该关心的对象。
   ⇒ 所以"未参与者"这一节不是礼貌性的，是安全性的。
```

## 六 · 范围说明：本系统对谁负责

```text
⇒ 船长 2026-11-13 说明：本系统为千年舟服务，只对千年舟负责。
⇒ 【这条对 S2 论证的影响，如实写在这里】：

   · 若【不对外提供、不引入外部审计方】：
     ⇒ 裁定 A.3 的六条证据仍然是必要条件，但"谁有权审这份名单"
       可以收敛在千年舟内部。CUSTODIAN 人选的治理摩擦更小。

   · 【但有一条不因此消失】：
     "保管者与批准者是同一人"这件事，即便在内部，
     仍然使 S2 的独立性论证【只能靠自证】。
     ⇒ 不是违规，是【论证强度较低】。
     ⇒ 内部使用可以接受这个强度，但要【写在明处】，
       而不是等将来有人说"当初没讲"。

⇒ 【我不把"内部使用"理解为"可以降低证据要求"】。
   证据要求不降，只是【谁来看证据】可以变简单。
```

## 七 · 填完之后能得出什么

```text
⇒ 全表填完，可以严格回答三个问题：

  ① 现在谁能同时改两侧？（WE-1 的交集是否为空）
  ② 谁有资格当 CUSTODIAN？（第四节的四条）
  ③ 还差哪些证据？（A3-1..A3-6 的分项）

⇒ 【不能得出】：S2 已建立。
   因为还缺实际配置、权限测试（失败注入）与独立复核签署。
   ⇒ 本表只解决"人"这一层，不解决"机制"与"证据"两层。
```

## 八 · 一句

```text
⇒ 这张表现在是全空的，这是它最诚实的状态。
⇒ 填它的过程中，很可能会发现某个"不应该能改"的人其实能改，
   或者某个"应该管"的人其实从未持有凭据。
⇒ 【那才是这张表真正的用处】—— 不是记录我们以为的样子，
   而是暴露我们以为错了的地方。
```
