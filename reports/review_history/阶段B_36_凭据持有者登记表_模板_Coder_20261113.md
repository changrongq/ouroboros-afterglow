```text
⇒ 【是】：一份【事实清单】——现在谁手上有什么凭据、能改什么。
```

## 二 · 凭据持有者条目（A3-2 前置）

```text
⇒ 每个持有人一条。字段定义来自 B_32 §2.8.4，此处给填写说明。
```

| 字段 | 填什么 | 怎么核实 |
|---|---|---|
| `holder_id` | 持有人标识（可与署名不同，但须能对应到人） | 由本人确认 |
| `credential_kind` | 凭据种类（GitHub 账号 / SSH 密钥 / 部署密钥 / Token / 管理员权限 / 其他） | 看实际配置，不凭记忆 |
| `credential_scope` | 该凭据**能改哪些路径或仓库** | 逐条列，写"全部"要有依据 |
| `can_modify_record_side` | 能否修改**待验证记录**及其产生代码 | 是 / 否 / 不确定 |
| `can_modify_digest_side` | 能否修改**预期摘要**及其存储 | 是 / 否 / 不确定 |
| `third_party_paths` | 是否有间接路径（代管、代办、脚本、CI 密钥） | 写清路径；无则写"无" |
| `evidence_ref` | 支撑以上判断的事实来源（截图 / 配置 / 记录） | 可被第三方复查 |
| `as_of` | 以上信息对应的时间点 | 凭据会变，必须有时间戳 |

```text
⇒ 【`不确定` 是一个合法答案，而且是重要的答案。】
   ⇒ 不知道就说不知道。写成"否"会让整张表的独立性论证凭空成立。
   ⇒ §2.3 的 WE-1 判据是「交集为空」。若有人填"不确定"，
     则交集是否为空【无法判定】⇒ 独立性判定必须是 UNDETERMINABLE。
```

```text
⇒ 【由实测得出的判定（这条比口述重要）】：

        "未授予写权" 在仓库转为公开/接受外部 PR 时可能改变；
        "明确只读角色 + 分支保护" 才是主动设定的边界。

   ② 【main 无分支保护】这一条要单独指出：
      ⇒ 任何有写权的凭据都可以直接推 main。
      ⇒ 这与 A3-1「记录写入者无法通过间接路径同时修改两侧」直接相关：
        没有分支保护时，连"提交必须经审查"这一层都不存在。

      ⇒ 我不仅能推，还能改协作者、改分支保护、删分支、改仓库设置。

```

## 四 · CUSTODIAN 资格的判定条件（供船长批准时对照）

```text
⇒ 本表不提名，只给判定条件。条件是【可核对的】，不是主观评价。

  条件 C-1  与记录写权分离
    要求：`can_modify_record_side = 否`，且 `third_party_paths` 无通往记录侧的路
    核对：第二节对应条目的证件
    ⇒ 这是 WE-1「交集为空」能否成立的根本。

  条件 C-2  不决定摘要校验逻辑
    要求：未参与定义"怎样算摘要正确"
    ⇒ 否则"判定标准"与"预期值"由同一人掌握，独立性成空话。

  条件 C-3  持独立凭据
    要求：写入预期摘要所用凭据，不与其他角色共享
    ⇒ 注意：共享同一账号 ≠ 共享凭据。要看的是【凭据】不是【账号】。

  条件 C-4  能维护四项产出（裁定 A.1）
    要求：能实际维护
          ① 预期摘要存储 ② 凭据持有者名单
          ③ 凭据变更记录 ④ 写入权限证明
    ⇒ 这四项缺一不可。只维护存储不维护名单 ⇒ 无法支撑 WE-1。

⇒ 【三条都不满足就直接不合格】。若 C-1 无法判定（填了"不确定"），
  则只能记 UNDETERMINABLE，不能记合格。
```

```text
⇒ 【关于"船长"身份的纪律（裁定 A.2 原话）】：

   ⇒ 也就是说：船长可以【当】CUSTODIAN，但理由必须是

   ⇒ 这两句必须分开写，否则判定就退化成身份认定。
```

## 五·乙 · 无账号不影响复核能力（必须写下来，防下一轮误读）

```text
⇒ 2026-11-14 船长决定：凌翼 / 钳星 / 知微 / 睫 暂不给 GitHub 账号。
⇒ 【这个决定不影响任何正在进行的工作】。逐项对照：

   他们要做的        | 是否需要 GitHub 账号 | 说明
   ------------------|---------------------|---------------------------
   读文档 / 审设计    | 【不需要】           | 仓库 private=false，
                     |                     | 任何人无需账号即可读
   出审查意见         | 【不需要】           | 意见是文书，不是仓库操作
   签署复核结论       | 【不需要】           | 签署是文书行为
   推送代码           | 不需要（本就不该）   | 他们不需要写权限
   查权限配置         | 【本来就查不到】     | 普通成员读保护接口得 403

⇒ 【唯一受影响的情形】：若将来仓库转为私有，无账号者将无法读取。
   ⇒ 现状 private = False，故当前不受影响。
   ⇒ 若转为私有，必须【同时】解决这四人的读取问题，
     否则复核链会断在第一环（看不到就没法审）。
```

```text
⇒ 【特别提醒下一轮的我 / 任何读这份表的人】：

   「台账里写着无账号」≠「无法复核」。
   ⇒ 这两件事在 B_36 里分属不同字段：
     · 能否持凭据 → 记在 §二 的 holder 条目
     · 能否复核   → 记在本节

   ⇒ 【不要把"没有 GitHub 账号"写成"复核尚未开始"】。
     前者是权限事实，后者是工作进度，两者无关。
```

```text
⇒ 【还有一个反向的坑，一并写明】：
   也不能因为"他们不需要账号"，就认为
   「所以共享一个只读账号也无所谓」。

   ⇒ 共享只读账号在能力上确实无害（Read 无法推送），
     但它会破坏【签署可归因性】：
      四人共用一个账号时，"钳星签署了"无法被证实。
   ⇒ 所以本轮结论是：【不共享，也不发账号】。
     复核靠文书 + 各自的署名，不靠 GitHub 身份。
   ⇒ 将来若确实需要仓库内身份（例如分支权限分级），再单独处理。
```

## 五·丙 · 保障的边界：能力边界也是边界

```text
⇒ 船长 2026-11-14 原话：
   「我们这个项目只要诚实就行了，有些边界是我们能力的边界，
     那也是边界了，我们知道边界在哪就行了。」

⇒ 我按这句话把边界【显式写下来】，而不是继续追求一个做不到的"绝对保障"。
```

### 5.4.1 一条无法消除的事实

```text
⇒ 【事实】：所有账号最终都由船长持有。
   原因不是谁不小心，而是：
     · 邮箱能找回密码
     · 仓库 owner 唯一
     · 新账号（如 millennialboattech）也是船长注册的

⇒ 【所以"绝对隔离"不存在】。
   ⇒ 任何"独立写权"的论证，最终都会停在【船长本人】这一层。
   ⇒ 这不是我们这个项目的疏忽，是单人持有型仓库的固有边界。
```

```text
⇒ 【这条边界并不意味着 S2 没有意义，但改变了它能证明什么】：

   可以证明：  · 我与记录侧在【操作层面】分离
               · 推 main 会被挡住（可行为验证）
               · 权限变更有记录

   不能证明：  · 谁【都不可能】与记录侧合一
               · 掌控邮箱的人不会恢复某个旧账号
               · 没有"幽灵"凭据存在于视野之外

⇒ 【把这两栏分开写，比含糊地说"我们尽量独立"有用得多。】
```

### 5.4.2 哪些是我们能力的边界（明确列出）

```text
  B-1  邮箱控制权
       能力边界：无法在技术上阻止邮箱持有者恢复任何以该邮箱注册的账号
       应对：只能靠【记录】—— 记录该邮箱属于谁，并承认它是最高控制点

  B-2  仓库 owner 的不可分割性
       能力边界：GitHub 单人仓库的 owner 无法被"分开"
       应对：用分支保护 + include administrators 限制其【常规】操作，
             但无法限制其修改保护规则本身

  B-3  平台行为的不透明
       能力边界：无法确认 GitHub 侧是否存在我们看不到的凭据
       应对：只能记录"我们查了什么、查到了什么"，不能宣称"已穷尽"

  B-4  API 与界面不一致
       实例：millennialboattech 已从界面移除，但单用户权限接口仍返回 read
       应对：以界面为准并留痕矛盾，不当成"一定没问题"

  B-5  未来的未知
       能力边界：现在无账号的人将来可能被授予
       应对：台账的 as_of 字段 —— 记录的是【某个时刻的状态】，不是永久结论
```

### 5.4.3 那么这份台账到底能证明什么

```text
⇒ 【能证明】（因为可被独立核对）：
   · 在 as_of 这个时刻，协作者全集是什么
   · 谁持有什么级别的权限
   · 某些操作会被拒绝（行为证明）

⇒ 【不能证明】（因为超出能力）：
   · 未来不会变化
   · 视野之外没有别的凭据
   · 最高控制点（邮箱 / owner）不会自行行动

⇒ 【正确的表述方式】：
     "截至 2026-11-14，按协作者全集与界面核对，写权仅 Coder 一人持有；
      最高控制点为船长（邮箱 + owner），此点无法通过技术手段隔离。"
   ⇒ 而不是："权限已隔离，独立性已建立。"

⇒ 前者是【可核对的事实 + 明确的边界】，
   后者是【一个我们无法兑现的承诺】。
```

### 5.4.4 这条边界对 S2 结论的影响

```text
⇒ L2_TRUST_ROOT = NOT_ESTABLISHED —— 【这条边界是原因之一】，且不会消失。
⇒ 但这不等于"什么都不用做"：
   ⇒ 把能做的做到（分支保护、台账、行为证明），
     并【如实标出做不到的部分】，这本身就是一种诚实的状态。

⇒ 【一个写着"保障到此为止"的文档，比一个暗示"已经安全"的文档可靠。】
   因为前者可以被继续推进，后者会让人停止追问。
```
