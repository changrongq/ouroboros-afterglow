## 2 · 剩余缺陷二：`CloseHandle` 的 FALSE 返回被忽略 — 成立，且你指出的是一个概念错误

**核实：成立。** `_close` 原来只 catch Python 异常，**Win32 返回 0 完全不记录**。

**但你这条里最重要的一句不是这个**：

> **不要用一个"exited"字段同时承诺进程退出和资源释放都已完成。**
> 需要区分 `worker_exit_confirmed` 与 `controller_resources_released`，分别报告。

**这是一个真实的概念缺陷，我接受。** 我把两件不同的事压进了一个返回值。

### 已改：返回值拆成两个独立事实

```python
return {
    "worker_exit_confirmed": ...,          # OS 是否确认进程退出
    "controller_resources_released": ...,  # 我们拥有的每个句柄是否都真的关掉了
    "detail": ...,
}
```

### `_close` 现在检查 BOOL 并取 GetLastError

```python
ok = bool(k32.CloseHandle(h))
if not ok:
    err = k32.GetLastError()
    detail += f"; CloseHandle({label}) returned FALSE err={err} (NOT released)"
```

### 你要求的那条边界，我写进了注释和输出

> A worker can be confirmed exited while a CloseHandle fails; that is a RESOURCE RELEASE problem and is **NOT evidence the worker is still alive**.

**实测**（你给的场景：等待已确认退出、关闭 `pi.hp` 返回 0）：

```text

  PASS  controller_resources_released is FALSE                        [False]
  PASS  CloseHandle FALSE is recorded with an error code
```

