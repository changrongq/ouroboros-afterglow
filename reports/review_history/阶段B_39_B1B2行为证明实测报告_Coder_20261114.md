## 一 · 保护配置的实际形态（先记录，再谈结论）

```text
⇒ 船长开启保护后，我核对到的实际形态是【规则集（ruleset）】，
   不是传统的 branch protection。

   GET /repos/.../branches            → main: protected = True
   GET /repos/.../branches/main/protection → 404（传统接口未使用）
   GET /repos/.../rulesets            → 1 条

   ruleset id=27252020  name=Protect  enforcement=active
     target              = branch
     conditions.ref_name = include ["refs/heads/main"], exclude []
     bypass_actors       = []          ← 【关键】
     rules:
       · deletion            （禁止删除）
       · non_fast_forward    （禁止强推）
       · pull_request        required_approving_review_count = 0
                             require_extra_approval_for_unattributed_changes = true
```

```text
⇒ 【bypass_actors = [] 是这次保护真正生效的原因】。
   ⇒ 它意味着【没有任何主体】被允许绕过规则 —— 包括 admin（我）。
   ⇒ 这等价于传统保护里的 "Do not allow bypassing the above settings"。

⇒ 【但要注意一处不完整】：required_approving_review_count = 0。
   ⇒ 即：必须走 PR，但 PR 【不要求任何批准】。
   ⇒ 这意味着我能自己开 PR 自己合并。
   ⇒ 详见 §四 的边界说明。
```

   required_approving_review_count 提到 1，并且
   PR 作者不能自批（GitHub 本身不允许自批，但批准人需要真实存在）。

⇒ 【后者在当前架构下做不到】：仓库只有我一个能写的人。
   ⇒ 这就是 §五·丙 说的能力边界 —— 不是配置问题，是"没有第二个人"。
