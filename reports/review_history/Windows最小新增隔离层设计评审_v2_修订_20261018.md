# W-BD1 · 进程创建接口

## 1.1 三个 API 的实际差异（官方文档核对）

| 项目 | `CreateProcessWithLogonW` | `CreateProcessAsUserW` | 受限令牌 |
|---|---|---|---|
| 所属 DLL | `Advapi32.dll`（`winbase.h`） | `Advapi32.dll`（`processthreadsapi.h`） | `CreateRestrictedToken`（`securitybaseapi`） |
| 输入身份 | **用户名 + 域 + 明文口令** | **`hToken`**（主令牌） | 由既有令牌派生新令牌 |
| **有无 `bInheritHandles`** | **无此参数** | **有** | N/A（令牌不涉及继承） |
| 调用者所需特权 | **无需特殊特权**；但目标账户须被允许**交互式登录** | 通常需 `SE_INCREASE_QUOTA`，非可分配令牌还需 `SE_ASSIGNPRIMARYTOKEN` | N/A |
| 登录会话 | **新建登录会话** | 复用 `hToken` 所属会话 | 继承源令牌会话 |
| 失败时可改用 | — | 若报 `ERROR_PRIVILEGE_NOT_HELD (1314)`，官方建议改用 `CreateProcessWithLogonW` | — |

**官方原文（`CreateProcessWithLogonW`）**：参数表**没有** `bInheritHandles`。

**官方原文（`CreateProcessAsUserW`）**：

> `bInheritHandles` — If this parameter is TRUE, each inheritable handle in the calling process is inherited by the new process. If the parameter is FALSE, the handles are not inherited.

> Applications can use the `UpdateProcThreadAttributeList` function with the `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` parameter to provide a list of handles to be inherited by a particular process.

**官方原文（`CreateProcessAsUserW` → `hToken`）**：

> If `hToken` is a restricted version of the caller's primary token, the `SE_ASSIGNPRIMARYTOKEN_NAME` privilege is **not required**.

## 1.2 因此：我上一版那句话是**跨 API 混用**

我写：

```text
CreateProcess(..., bInheritHandles=FALSE, ...)
```

**但现有 Profile B 用的是 `CreateProcessWithLogonW`，该 API 没有这个参数。**

**这是错误的设计前提，不是措辞问题。** 修正如 §1.3。

## 1.3 两个可选实现路径（二者不可混用）

### 路径 A · 保持现有 `CreateProcessWithLogonW`

```text
身份建立：新建登录会话（afterglow_worker 账户）
继承控制：该 API 无 bInheritHandles 参数 ⇒ 不提供显式继承开关
受限令牌：CreateProcessWithLogonW 不接受 hToken ⇒ 无法直接注入受限令牌
```

**结论**：**路径 A 无法施加受限令牌，也无法显式声明继承白名单。**
它对继承的全部保证来自"新登录会话 + 无 bInheritHandles 参数"，**这已被现有 Profile B 的 `forbidden_handle_noninheritance_proven` 字段记录**（`win32_worker_process.py:227 REGISTERED_CREATION_API`）。

**优点**：不改动 Profile B 身份链，`win32_worker_process.py` 的既有验证全部保留。
**代价**：**受限令牌这一格拿不到。**

### 路径 B · 改为 `CreateProcessAsUserW` + 受限令牌

```text
步骤 1: LogonUser(afterglow_worker, ...) → hToken（主令牌）
步骤 2: CreateRestrictedToken(hToken, ...) → hRestricted
步骤 3: CreateProcessAsUserW(hRestricted, ..., bInheritHandles=FALSE, ...)
```

**优点**：**受限令牌 + 显式继承开关同时可得**；且官方明确"若 hToken 是 caller 主令牌的受限版本，则不需要 SE_ASSIGNPRIMARYTOKEN"——**降低了权限前提**。

**代价（必须记录）**：
- 需要 `LogonUser`（**明文口令仍在运行时使用**，与现状相同）
- 需 `SE_INCREASE_QUOTA`（通常普通账户可持有，**但我未实测**）
- `CreateProcessAsUser` **不加载用户 profile**（官方："does not load the specified user's profile into HKEY_USERS"），而现有链路用了 `LOGON_WITH_PROFILE`。**若 worker 依赖 profile，需额外 `LoadUserProfile`/`UnloadUserProfile`**
- **会话差异**：`CreateProcessWithLogonW` 新建会话，`CreateProcessAsUser` 复用 token 会话 ⇒ **行为不等价**

## 1.4 我的建议（供评审，非结论）

**不替换现有 Profile B，而是新增一条独立的创建路径作为新 lineage 的候选，两条并存对比。**

理由：Profile B 是**已冻结并已验证**的资产（`q3_provenance` 10 角色、`q3_contract.PROFILE_B_PROOF_FIELDS`）。**替换会使既有验证失效**，正是凌翼"不得修改冻结十角色"所防的。

**若评审认为必须二选一，则需要明确：选择路径 B 会导致 Profile B 的身份链重建，属实质合同变更。**

## 1.5 我**未**核实的事项（不能写成事实）

| 事项 | 状态 |
|---|---|
| `afterglow_worker` 是否具备 `SE_INCREASE_QUOTA` | **未核实** |
| `CreateRestrictedToken` 对 worker 现有功能的影响 | **未核实** |
| 路径 B 下 `LOGON_WITH_PROFILE` 的等价替代 | **未核实** |
| 跨账户下 `LogonUser` 的可用性 | **未核实**（现有 Profile B 用 `CreateProcessWithLogonW` 规避了这一步） |

# W-BD2 · 继承声明的**确切范围**

## 2.1 我上一版的错误

我写：**"worker 初始句柄集合为空"**。

**这是错的**，有四个来源使这句话不成立：

| 来源 | 说明 |
|---|---|
| **进程内在句柄** | 新进程创建后，加载器/运行时/DLL 初始化过程会自己打开句柄（`\KnownDlls`、注册表、事件等），**在 `CreateProcess` 返回前就已存在** |
| **`STARTUPINFO` 标准句柄** | 若 `STARTF_USESTDHANDLES`，`hStdInput/Output/Error` **被原样复制到子进程**（官方："copied unchanged to the child process without validation"） |
| **随后打开** | worker 运行中可自行 `CreateFile` 等 |
| **复制与代理** | `DuplicateHandle` 或请求对端代开 |

**"集合为空"是一个关于进程内部状态的强主张，任何 API 都不支持。**

## 2.2 修正后的声明（这是我要给评审的**确切**保证）

```text
非继承保证（Non-Inheritance Guarantee）
  = 控制器在 CreateProcess 之前持有的任何句柄，都不会因继承而传到 worker
```

**这个保证的 API 依据分两种**：

| 路径 | 依据 |
|---|---|
| **A（`CreateProcessWithLogonW`）** | 该 API **无 `bInheritHandles` 参数**；且子进程在**新登录会话**中创建。已有 Profile B 字段 `forbidden_handle_noninheritance_proven` 记录此依据。**但这是"无继承开关"的推论，不是显式声明。** |
| **B（`CreateProcessAsUserW`）** | `bInheritHandles=FALSE` 明文："If the parameter is FALSE, the handles are not inherited."；或 `HANDLE_LIST` 精确白名单。**这是显式声明。** |

## 2.3 四类路径的**分别**声明（凌翼要求"区分"）

| 类别 | 本设计是否主张已控制 | 依据 | 剩余风险 |
|---|---|---|---|
| **① 初始继承** | **是**（路径 A 推论 / 路径 B 明文） | 见 2.2 | 路径 A 为推论，强度低于路径 B |
| **② 随后打开** | **部分** | `deny_read_for_sid`（已有）+ DACL 目标对象 | 依赖 DACL 覆盖全部访问路径；**`stat` 类元数据不在覆盖内** |
| **③ 复制（`DuplicateHandle`）** | **否** | — | worker 若能打开目标进程即可复制；**本设计未涉及** |
| **④ 代理授予** | **否** | — | 见 W-BD3 |

**明确：本设计只主张 ① 已被控制，② 部分，③④ 未控制。**

**"进程内可能持有某个句柄"不再被本设计声称可排空。** 这是与上一版最重要的差别。

# W-BD3 · 授权信息通道（不再把 `HANDLE_LIST` 当作信息流控制）

## 3.1 我上一版的错误

我把 `HANDLE_LIST` 白名单说成"合法通道注册表"，暗示它等于信息流控制。

**这是错的。** `HANDLE_LIST` 只控制**哪些句柄被继承**，它：

- **不控制**已继承句柄**承载的数据内容**
- **不控制**通过具名对象（命名管道名、共享内存名、motif）建立的新连接
- **不控制**通过文件系统路径的通信
- **不控制**时序/大小侧信道

## 3.2 修正：通道须逐条声明，且**每条都要有各自的可信依据**

凌翼要求："明确允许的通信主体、方向、数据类型、权限及其可信依据。"

| # | 通道 | 主体（两端） | 方向 | 数据类型 | 权限 | 可信依据 | 状态 |
|---|---|---|---|---|---|---|---|
| CH-1 | `hStdIn` | 控制器→worker | 单向 | 实验输入数据（预注册 schema） | 标准句柄复制 | `STARTF_USESTDHANDLES` 明文传递 | **需预注册** |
| CH-2 | `hStdOut` | worker→控制器 | 单向 | worker 输出（预注册 schema） | 同上 | 同上 | **需预注册** |
| CH-3 | 实验数据目录 | 文件系统 | worker 读 | 预注册实验数据 | DACL 允许读 | `q3_access_matrix` 行 | **需矩阵确认** |
| CH-4 | 结果写回目录 | 文件系统 | worker 写 | 结果文件 | DACL 允许写 | 同上 | **需矩阵确认** |

**未列入上表的通道 = 未授权。** 但**"未列入"不等于"不存在"**——本设计**不证明** worker 无法通过未声明路径通信（见 3.4）。

## 3.3 `HANDLE_LIST` 的正确位置

它只是**路径 B 下实现 CH-1/CH-2 的一个机制**，不是信息流控制的全部。

**它甚至不是必需的**：路径 A 无此参数，但标准句柄仍会传递。

## 3.4 明确未控制的信息通路（凌翼要求不得默认豁免）

| 通路 | 是否控制 | 影响 |
|---|---|---|
| 具名管道 / 共享内存（worker 自行 `CreateFile` 打开） | **未控制** | 若 DACL 不挡，可成为通道 |
| 文件系统临时文件 | **部分**（DACL 可挡已知路径） | 依赖路径枚举完整 |
| 网络（若 worker 有网络能力） | **未控制** | 需受限令牌去除网络能力，**未实测** |
| 时序 / 大小侧信道 | **未控制** | 见 G-2 |
| 同账户代理 | **未控制** | 见 G-1 |

**这些不是"已登记的非阻塞风险"，是"未控制"。** 分类权在睫，不在我。

# W-BD4 · Reset 与持久边界（三者必须分离）

## 4.1 我上一版的错误

我把"Reset 前后通路"当成一个整体来谈，**混淆了三个不同的时间边界**。

## 4.2 修正：三层分离

### 层一 · 冻结 Q3 的**临时**隔离（probe 路径）

```text
生命周期：短（probe worker 存在期间）
已有证据：frozen Q3 probe 路径达到过 HANDLE_AUDIT_CLEAN（pid 35048, 37200）
保证范围：仅该 probe 窗口
```

**不改动，不重开。** 它证明的是"仪器在短窗口内可达到 CLEAN"，**不证明持久 worker**。

### 层二 · 适配器的**独立持久**边界（本设计的对象）

```text
生命周期：整个 worker 存在期间（可能跨多个 episode）
本设计主张：仅 ① 初始继承受控（W-BD2）
未主张：② 部分、③④ 未控制
```

**这是 `PERSISTENT_WORKER_CLEAN_BLOCK = ACTIVE` 所指向的那一层，本设计不解除它。**

### 层三 · Reset 后的证据

| 责任 | 归属 | 现有组件 |
|---|---|---|
| 可信观察者 | **必须是独立主体** | `probe_read_access`（独立观察） |
| Reset 后目标仍被拒 | 由观察者提供 `access_ok` | `judge_reset(access_ok=...)` |
| DACL 还原验证 | 控制器 | `restore_sd` + `verify_sd_equal` |
| **信息残留**（缓存/临时/内存） | **未分配责任** | **无组件** ← 缺口 |
| worker release | 控制器 | `_process_is_gone` |
| 失败收敛 | 控制器 | 见 4.3 |

## 4.3 失败收敛：明确"不输出合格保证"的条件

按凌翼 `B-4`：`关键约束不成立、证据缺失或资源回收未完成时，不输出合格保证`。

```text
以下任一条成立 ⇒ 输出 INVALID / NOT ESTABLISHED，不得输出 PASS：
  1. 创建 API 与注册值不符
  2. 继承证明字段任一非 True
  3. DACL 还原验证失败
  4. 独立观察者未提供 access_ok
  5. worker release 未确认
  6. 任一预注册通道未登记
```

## 4.4 明确未解决

- **层三的"信息残留"我没有分配责任主体**——这是缺口，不是遗漏
- **三层之间的切换点（episode 边界）如何定义可信事件**——**未设计**
- **旧 episode 的能力是否可能被新 episode 复用**——**未设计**（这正是钳星要审的）

# 5 · 两处附带更正

## 5.1 AppContainer 对未打包应用的适用性

**我上一版写**："需要打包身份（package SID）、对无打包应用不适用"

**更正为更准确的说法**：

- AppContainer 要求进程运行在 **AppContainer 内**，通过 `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` 指定包 SID 与能力
- **"无打包应用不适用"这个说法过强**：技术上可以为未打包的可执行文件创建 AppContainer 配置文件，但需要额外配置文件与部署工作
- **准确表述**：**需要额外配置与部署成本，且其在无打包场景下的行为细节我未核实**

## 5.2 Job Object 的生命周期辅助价值

**我上一版写**："不需要，只管生命周期，已有 `_process_is_gone`"

**更正**：**这个判断低估了它。**

- `_process_is_gone` 是**事后检测**；`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 是**机制性保证**——控制器句柄一关，job 内进程被终止
- 对 `失败收敛`（4.3 第 5 条）有实质价值：**它把"release 未确认"从检测问题变成结构问题**
- **但仍不解决访问控制**

**更正结论**：**Job Object 应作为"生命周期辅助机制"保留在设计中，用于强化 release 与失败收敛；不是首版必需，但价值高于我上一版所述。**
