# 三 · 凭证格式

## 3.1 字段（承 v0.2 §4.3 示意，本节只补类型与约束）

```text
⇒ v0.2 §4.3 已给出示意：
     SUBMITTER_IDENTITY_ATTESTATION {
         event_id / attempt_id / verified_submitter_id /
         verifier_id / verification_source / verification_result /
         evidence_reference
     }
⇒ 本节【不增删字段】，只规定编码与约束。
```

| # | 字段 | 含义 | 约束 |
|---|---|---|---|
| 1 | `event_id` | 被核验的提交事件 | 1..255，须与 `AttemptRecord.event_id` 字面相等 |
| 2 | `attempt_id` | 被核验的那次尝试 | 1..255，须与 `AttemptRecord.attempt_id` 字面相等 |
| 3 | `verified_submitter_id` | C 认定的提交方 | 1..255 |
| 4 | `verifier_id` | 作出核验的 C 的标识 | 1..255，须在受信登记中 |
| 5 | `verification_source` | 核验所依据的来源类型 | 枚举，见 3.2 |
| 6 | `verification_result` | 核验结论 | 枚举，见 3.3 |
| 7 | `evidence_reference` | 指向核验证据的引用 | 1..255 |

```text
⇒ 【字段 3 与 7 的关系，必须说清】
   `verified_submitter_id` 是【结论】；
   `evidence_reference` 是【结论的依据指针】。
   ⇒ 若只有结论、没有可追的依据 ⇒ 该 ATTESTATION 不得被接受。
   ⇒ 这不是新增要求，是 v0.2 §4.3 判据①的落实：
     「来自登记的控制主体【及可信核验来源】」。
```

**`verified_submitter_id` 是【提交主体】，不是【记录者】（2026-11-05 修正，知微 Z-01）**

```text
⇒ 【本版原稿在此处写错过，先说错在哪】
   原稿写：「把这次 attempt 的提交端点【归入】已由 recorder_id
   确定的那个主体，不是在协议里新造一个身份」。
   ⇒ 这是错的。它把【提交主体】套进了【记录者身份体系】。

⇒ 反例（用本节自己的上游就能拆掉原写法）：
   W1 与 W2 向同一个记录者 R1 提交。
   两次提交都属 R1 的权威范围
   ⇒ 但【不等于】两个提交者都是 R1。
   ⇒ §2 4.1 的向量 V1 就是明证：
        authority_record_key = ("R1", 1, 1)   ← recorder_id = R1
        submitter_id         = "U1"           ← 提交者 = U1
      两个角色在 §2 里从一开始就是分开的。
   ⇒ 故「提交者 = recorder_id」与本项目已定的字节自相矛盾。
```

```text
⇒ 【修正后的语义】
   · `verified_submitter_id` 表示【受信核验所得的提交主体】，
     不自动等于 `recorder_id`，也不等于 `producer_id`。
   · `recorder_id` 的作用是【限定此次 attempt 所属的权威范围】，
     不是【提交者的身份】。
   · 二者之间须存在一条【授权关系】：
     该提交主体是否有权在该权威域内提交。
     这条关系【须被检查】，不能因为"在同一个域里"就默认成立。

⇒ 七字段不变：实例与来源关系由受保护的 `evidence_reference`
   所指证据承载，不需要为此立即增字段。
```

```text
⇒ 【提交主体的粒度，本版选定】
   ⇒ 选【稳定逻辑提交主体】（而非每次连接一个身份）。
   ⇒ 但"稳定"这件事【不能靠援引 P4-1.4 得到】——
     P4-1.4 规范的对象是 `producer_id` / `recorder_id`，是记录者身份，
     【不是】提交者身份。
   ⇒ 故须【单独定义】提交主体与以下四者的映射：
     (a) 实际的 W 进程实例
     (b) 当前连接
     (c) 当前请求（event_id / attempt_id）
     (d) 该主体的有效区间
   ⇒ 这四者的组织方式属 §3 自身义务，不得转嫁给 P4。
```

| 字段 | 回答的问题 | 与提交主体的关系 |
|---|---|---|
| `recorder_id` | 哪个【权威域】（记录者身份，持久） | 限定本次 attempt 的范围；**不等于**提交者 |
| `producer_id` | 哪条记录【由哪个逻辑记录者产生】（与 `recorder_id` 同一主体） | 记录者侧，本节**不产出、不改写、不覆盖** |
| `instance_id` | 哪【一次进程实例】 | 表达实例层，不承担提交者身份语义 |
| `verified_submitter_id` | 【谁提交了这次请求】（本节产出） | 独立的提交主体，须与上述三者显式映射 |

```text
⇒ 三条禁止（修正后）：
   ① 不得让 `verified_submitter_id` 承担「哪一次进程」的语义（那是 `instance_id`）；
   ② 不得把 `verified_submitter_id` 当作 `recorder_id` 的同义词，
      也不得因二者"同域"就推定同一主体；
   ③ 不得用 `verified_submitter_id` 覆盖或替代 `producer_id`
      —— 后者签的是逻辑记录者，本节不触碰。

⇒ 【与 §2 V1 的一致】按上述语义，R1 / U1 的组合是合法的：
   提交者 U1 在记录者 R1 的权威域内提交。
⇒ 【不得】再把这种情形读成"提交者就是 R1"。
```

## 3.2 `verification_source` 取值

```text
⇒ 本版【只允许】以下取值（其余保留，实现不得自创）：

  0x01  OS_PROCESS_IDENTITY
        ⇒ C 观测到提交端的 OS 级进程身份
          （例如进程句柄 / SID / 会话），
          并与本次请求建立关联。

  0x02  CONTROLLED_CHANNEL_IDENTITY
        ⇒ C 通过受控通信通道自身获得的对端身份
          （通道身份由 C 侧建立，不由 W 申报）。

  0x03  TRUSTED_DEPLOYMENT_REGISTRY
        ⇒ C 依据部署期登记的主体清单核对。

⇒ 【三类都要求同一件事】
   该来源必须是 C【独立于 W 自填】取得的。
⇒ 【明确不允许】：
   · 由 W 在请求中提供的身份字符串（那只是被核验对象）
   · 由 W 提供的、声称"我已核验过自己"的任何记录
```

```text
⇒ 【本版不采用密码学身份绑定】
   ⇒ 裁定第一节已排除生产密钥与真实生产签名。
   ⇒ 故本节不定义签名式凭证；
     若将来引入，须新增 OBJECT/version 并另行授权。
```

## 3.3 `verification_result` 取值

```text
0x01  VERIFIED_MATCH
      ⇒ 核验成功，且来源与提交端点关联成立。

0x02  REJECTED_MISMATCH
      ⇒ C 观测到的实际提交端点与申报身份不一致。

0x03  REJECTED_SOURCE_UNAVAILABLE
      ⇒ C 无法取得独立来源（通道不可用、进程已退出等）。

0x04  REJECTED_NOT_REGISTERED
      ⇒ verifier_id 不在受信登记中，或来源类型不被允许。

⇒ 【只有 0x01 可用于建立身份。】
⇒ 0x02–0x04 均为【明确失败】，不得被消费方当作"未知"而放行。
   ⇒ 依据：§0 S5 失败关闭 / P4-4.3。
```

```text
⇒ 摘要、端序、长度检查、解析顺序【全部沿用 §2】：
   digest = SHA-256( OBJECT_TYPE(0x04) ‖ header_fixed ‖ fields_encoding )
   ⇒ 解析须按 §2 2.5 的步骤 0..9 执行。
⇒ 【本节不重复写一遍解析规则】，只声明沿用。
   ⇒ 若 §2 修订，本节自动跟随；由 §0 F 节的 CHECK_ALIGNMENT_WITH_S0 核对。

⇒ 【2026-11-06：§2 已受控修订，此处确认跟随无冲突】
   §2 依凌翼 R-1/R-2/R-3 修订了三处，本节逐条对照后【无需改字段表】：
   · MIN_FRAME_LEN 17 → 18：本节未硬写任何数值，只声明"沿用步骤 0..9"；
     故自动跟随，无残留旧值。
   · 摘要不覆盖 MAGIC / TOTAL_LEN（方案 A）：本节 L240 用的是
     `header_fixed` 简写，其定义在 §2 2.4，已随之修正；
     本节 digest 的实际输入区间即 §2 2.4 的展开式，
     `OBJECT_TYPE` 前缀取 0x04。既有 V1 向量不涉及本节类型，未受影响。
   · TOTAL_LEN 含自身 / 字段 LEN 不含自身：本节未自定义长度语义，随 §2。
   ⇒ 【本节 TAG 用 0x31–0x37、§2 用 0x01–0x07 / 0x11–0x16 / 0x21–0x23】
     错开理由：TAG 位于 FIELDS 内，按对象类型分段（承 §2 3.2 的同一原则）；
     误用他表时解析立即失败而非静默解出错误结构。

⇒ 【`header_fixed` 在本节的确切所指（2026-11-06 补，睫 ③）】
   §2 里存在【三个近名、三个数】，本节必须指明用哪一个：

   | §2 中的名称 | 字节数 | 含什么 |
   |---|---:|---|
   | `header_fixed`（2.4 摘要用） | **6** | `FORMAT_VER(2) ‖ OBJECT_TYPE(1) ‖ RESERVED(1) ‖ FIELD_COUNT(2)`，**不含 MAGIC、不含 TOTAL_LEN** |
   | `FIXED_HEADER_LEN`（2.1） | 14 | `MAGIC ‖ FORMAT_VER ‖ OBJECT_TYPE ‖ RESERVED ‖ FIELD_COUNT`，**含 MAGIC** |
   | 「固定框架最小长度」（N16 / 步骤 0） | 18 | 上面 14 + 尾部 `TOTAL_LEN(4)` |

   ⇒ **本节 L240 的 `header_fixed` 特指【6 字节】那一个。**
   ⇒ 【不得】按 14 或 18 去理解本节的摘要输入区间 ——
     那会多算 MAGIC（8）乃至 TOTAL_LEN（4），
     得到一个完全不同、而且【自洽】的散列（正是 A-6 立的判据）。
   ⇒ 【两处 OBJECT_TYPE 都必须是 0x04】：
     · 前缀那次（域分离） = 0x04
     · `header_fixed` 内那次（编码自描述） = 0x04
     ⇒ 若沿用 V1 的 0x01 填入任一位置，结果会算错而自己看不出来。
```

# 四 · 可信来源：C 自身的边界

```text
⇒ 判据①要求「来自登记的控制主体及可信核验来源」。
⇒ ⇒ 那么「C 本身凭什么可信」？本节必须回答，否则判据①悬空。
```

## 4.1 `verifier_id` 的受信登记（规范下限）

```text
⇒ 一个 `verifier_id` 算「已登记」【至少】须满足四项：
   (i)   其身份记录在【业务进程不可写】的地方
         （W 只能读，不能改该登记）；
   (ii)  登记项包含：主体标识、允许的动作（仅限"产出
         SUBMITTER_IDENTITY_ATTESTATION"）、生效范围；
   (iii) 登记变更本身可追溯（谁在何时改了什么）；
   (iv)  该 verifier 【不得】是 W 自身，也不得由 W 启动。

⇒ 具体形式（受信清单 / 配置 / 存储前提）本版不选定，
  但必须满足上述四项。
⇒ 【不得】因「形式未定」而把「任何会写这个格式的进程」认作已登记主体。
```

## 4.2 与 §0 B 类的关系

```text
⇒ 「OS / 通道遵守其接口契约」属【外部前提】（§0 B 类左列）。
⇒ 「C 确实使用了该机制、且命名空间/作用域/生命周期处理正确」
   属【本地核验义务】（§0 B 类右列）。
⇒ 本节不把后者豁免。
```

# 五 · 消费契约（落实 v0.2 §4.3 五判据）

```text
⇒ v0.2 §4.3 已定五条，本节【照录】并给出每条的判定依据与失败出口。
```

| # | 判据（v0.2 原文） | 本节给出的判定依据 | 不满足时 |
|---|---|---|---|
| ① | 选定 ATTESTATION 来自登记的控制主体及可信核验来源 | **须同时满足四层**（见下方"判据①的落实"）：<br>(a) `verifier_id` 在 4.1 受信登记中<br>(b) `verification_source` ∈ 3.2 允许集<br>(c) 该凭证确由**符合登记的当前 C 实例**产生<br>(d) 该实例的证据把**实际的 W 实例/连接/本次请求**关联到 event/attempt | 不建立身份 |
| ② | 核验结果为协议明确允许的成功值 | `verification_result == 0x01` | 不建立身份 |
| ③ | `ATTESTATION.(event_id, attempt_id)` == 本次 `AttemptRecord` 的对应键 | 两者字面相等 | 不建立身份 |
| ④ | `AttemptRecord.submitter_id` == `ATTESTATION.verified_submitter_id` | 字面相等；**且两侧须不同源**（见下方方向说明） | 不建立身份 |
| ⑤ | 该引用、结果、主体及身份值的关联受既定完整性／写权边界保护 | 见 5.1 | 不建立身份 |

```text
⇒ 【判据①的落实：四层，缺一不建立身份（2026-11-06 补，知微 1）】

⇒ 【为什么必须补这一层】
   原判据①的依据只写了两项：verifier_id 在登记中、来源枚举合法。
   ⇒ 这【弱于】被照录的上游要求。
   ⇒ v0.2 L543-545 原文要求：
     「事前登记控制主体 / 受信启动者 / 允许权限 / 输入端点 /
       核验结果的写入与消费权限边界；
       消费者核验【实际实例符合该登记】。」
   ⇒ 即：不能只查"这个名字登记过"，须核"这一份凭证确由
     符合登记的那个实际实例产生"。

⇒ 【纸面反例（原写法挡不住）】
   保留合法的稳定 C 标识 + 合法的来源枚举 + 一份【旧实例】的证据。
   核验时发现：实际生产实例、或本次请求所属的连接，与证据对不上。
   ⇒ 原表格的两项字面检查【仍然全部通过】。
   ⇒ §3 第二节的总原则要求拒绝，但没有落到消费行上。

⇒ 【四层检查】
   (a) `verifier_id` 在 4.1 受信登记中；
   (b) `verification_source` ∈ 3.2 允许集；
   (c) 该凭证确由【符合登记的当前 C 实例】产生
       ⇒ 沿受保护的 `evidence_reference` 确认：
         实际 C 实例符合登记的【受信启动、允许权限、生效范围】；
   (d) 该实例的证据把【实际 W 实例 / 连接 / 本次请求】
       关联到 event_id / attempt_id。
   ⇒ 缺少其中任一环 ⇒ 本次身份【保持未建立】。

⇒ 【来源类型 0x03 的特别要求】
   `TRUSTED_DEPLOYMENT_REGISTRY` 只说明"某主体被登记"。
   ⇒ 若没有【实际提交端点到登记主体】的受保护映射，
     它【不能单独】证明本次消息来自该主体。
   ⇒ 故 0x03 同样须提供 (d) 的端点映射。

⇒ 【本版不选定的部分】
   登记载体与具体 Windows 接口留待实施申请。
   ⇒ 例如 `GetNamedPipeClientProcessId` 可取得客户端 PID，
     但【单独一个 PID 不是完整绑定方案】，
     还须说明实例生命周期、连接与请求的对应关系。
   ⇒ 这是候选，不是定版。
```

```text
⇒ 【判据 ④ 的方向与来源独立性（2026-11-05 补，睫 ② / 知微 Z-01）】
   ⇒ 等号本身是【对称】的：a == b 与 b == a 是同一个布尔值。
     故「双向验」不产生任何新信息，本版【不做】双向验。

   ⇒ 真正需要的不是方向，是【两侧来源是否独立】：
     · 左侧 `AttemptRecord.submitter_id`：W 的【主张】
     · 右侧 `ATTESTATION.verified_submitter_id`：C 核验后的【结论】

   ⇒ 【语义关系不是两个平等的值在比较，而是拿结论去核主张】
     - 主张方：AttemptRecord（W 填写）
     - 核验方：ATTESTATION（4.1 登记的 verifier 独立产出）
     - 核验方结论【优先】

   ⇒ 【一条硬约束：两侧不得由同一写入路径产生】
     若两侧都取自 W 的同一个自填字符串
     ⇒ 等号【恒真】⇒ 该判据等于不存在。
     ⇒ 这正是「两份错得一样」的情形，双向验也挡不住。

   ⇒ 来源独立性的依据已在本节其它位置写明，此处只是【接线】：
     · 本节「二 · 主体与职责」：W 不得自己写自己的 ATTESTATION
     · 本节 4.1(iv)：verifier 不得是 W，也不得由 W 启动
     · 本节 5.1(c)：能写 ATTESTATION 的集合 = 4.1 的登记集合
     · 本节判据①：verifier_id 须在受信登记中
   ⇒ 【只写节号，不写行号】
     —— 行号会随修订失效，而节号是稳定的。
     这是 §0 第三次复核的同一处理。
```

```text
⇒ 【判据 ③ 的一个易错点，须写明】
   ⇒ ③ 比的是【event_id 与 attempt_id 两个字面值】，
     不是「attempt 是否等于权威记录创建时的那次 attempt」。
   ⇒ 依据：P4-2.3 允许同一 event 的合法重试使用不同 attempt_id，
     且重试仍引用同一权威记录。
   ⇒ 若把 ③ 实现成「attempt 必须等于创建时那次」，
     【会误拒合法重试】。
```

## 5.1 判据⑤的落实：哪些关联须被保护

```text
⇒ 判据⑤是五条里最抽象的一条。本节把它拆成可核的三项：
   (a) ATTESTATION 自身的完整性
       ⇒ 按 3.4 编码并计算摘要；未经 §2 完整解析的字节不得使用。
   (b) ATTESTATION 与 AttemptRecord 的关联完整性
       ⇒ `AttemptRecord` 的完整性覆盖范围（v0.2 §2.2b）
         已含 `submitter_id`；
       ⇒ 若实现把 ATTESTATION 摘要另行保存，
         该摘要【须一并纳入】`AttemptRecord` 的覆盖，
         或通过不可替换的核验记录引用保护。
       ⇒ 二者择一，不得两者都无。
   (c) 写入权限边界
       ⇒ 能写 ATTESTATION 的主体集合，须与 4.1 的登记集合一致。
```

```text
⇒ 【明确禁止（承 §0 D-2）】
   ⇒ 不得以「内容未变」证明「只有 C 写过它」。
   ⇒ ObjectIdentity 式的相等检查不能替代写权边界。
```

## 5.2 多份 ATTESTATION 与晚到核验

```text
⇒ v0.2 §4.3 已定：
   · 若允许多份核验结果，须规定冲突处理或选择规则，
     不得各消费者自行取最后一条。
   · 晚到核验须用符合 D1 不可变性的【追加关联】或明确创建顺序，
     【不得默认为回填已持久化记录】。

⇒ 本节给出的最小规则（2026-11-06 补：先验来源，再比结果）：

⇒ 【第一步：先按来源筛选】（不能跳过）
   ⇒ 每份候选须【各自】先通过：
     · 来源核验（判据① 的 (a)(b)(c)(d) 四层）
     · 与本 AttemptRecord 的绑定（判据③）
     · 完整性（5.1(a)）
     · 有效区间（该 C 实例在本次请求时仍在授权范围内）
   ⇒ 【未经来源核验的记录不进入比较】。
   ⇒ 【禁止】：把来源不明的外来记录拿来参与"是否一致"的判断
     —— 它没有资格改写既有判定，只能被单独拒绝并留证。

⇒ 【第二步：在已通过筛选的可信记录集合内比较】
   · 同一 (event_id, attempt_id) 存在多份【已通过筛选】的 ATTESTATION 时：
       - 若全部为 0x01 且 verified_submitter_id 相同 ⇒ 视为一致。
         ⇒ 【但仍须指定选取规则】：按 (verifier_id, receipt_seq)
           的确定顺序取【第一份】，或取【其证据关联最完整】的一份。
         ⇒ 【不得】让不同消费者各取一份不同的。
       - 【身份相同 ≠ 证据可替换】：
         一份可能属于【旧实例】、另一份属于【当前实例】。
         二者不能只按身份字符串视为一致
         ⇒ 须各自通过第一步的有效区间检查。
       - 若 verified_submitter_id 不同，或含非 0x01，且【均通过来源核验】
         ⇒ 这是【真实冲突】⇒ 不建立身份，进入 STOPPED（见 §4 4.6）。
       - 【禁止】"取最后一份"或"取时间最新"作为选择规则。

⇒ 【第三步：留下本次消费的证据指针】
   ⇒ 本次消费【选中的那一份】，其 `evidence_reference`
     须一并纳入【消费记录】，否则依据指针会丢。
   ⇒ 只保证"可核"不够，须记录【本次实际核的是哪一份】。
   ⇒ 这与 3.1 「结论 + 依据指针」的要求同源。

⇒ 【第四步：晚到核验的处置范围】
   · 晚到核验：只能作为【追加记录】存在，
     不得修改既有 AttemptRecord。
   · 若晚到记录的来源未通过核验 ⇒ 【单独拒绝并留证】，
     【不使】既有结论失效（外来记录没有这个权威）。
   · 若晚到记录通过核验且结论与已消费的不同
     ⇒ 在该 event/attempt 范围内【使既有结论失效】
        ⇒ 阻止后续放行并进入 STOPPED。
```

# 六 · 失败与拒绝（不得静默）

```text
⇒ 承 §0 S5（失败关闭）与 P4-4.3（STOPPED 条件）。
```

| 情形 | 处置 | 不得 |
|---|---|---|
| ATTESTATION 缺失 | 本次身份**不成立，不放行** | 不得当作"默认可信" |
| 判据 ①–⑤ 任一不满足 | 同上 | 不得降级为"部分可信" |
| 多份冲突 | STOPPED | 不得取最后一份 |
| 晚到且结论不同 | STOPPED | 不得回填修改 |
| `verification_source` 不在 3.2 允许集 | 拒绝该 ATTESTATION | 不得"未知即通过" |
| `evidence_reference` 指不到可核证据 | 拒绝 | 不得只看结论不看依据 |

```text
⇒ 【与 §0 的一条对应】
   ⇒ 即使以上全部通过，也只能得到【一个受限结论】：
         「这次 attempt 的提交方身份已核实」
         （即 ESTABLISHED_FOR_THIS_ATTEMPT 这一限定形式）
   ⇒ 【不是】把状态键 SUBMITTER_IDENTITY 置为 ESTABLISHED。
     该键在全节的状态块中仍为 NOT ESTABLISHED
     —— 它描述的是【本原型尚未建立该能力】，不是某条记录的结论。
   ⇒ 两个层次，不要混读：
     · ESTABLISHED_FOR_THIS_ATTEMPT ⇒ 关于【一条记录】的判定
     · SUBMITTER_IDENTITY = NOT ESTABLISHED ⇒ 关于【本原型能力】的状态
   ⇒ 【不能】由前者推出后者，也不能由后者否证前者。
   ⇒ 并且，即使前者成立，也【不能】推出：
     · WRITER_ATTRIBUTION_CHAIN 已建立（§0 A-4）
     · 该提交方在生产环境中可信（§0 A-3）
     · P5 独占已满足（§0 D-2 / §4）
```
