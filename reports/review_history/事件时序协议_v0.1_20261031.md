# 一 · 协议要解决的问题

## 1.1 一句话

```text
让「窗口开 → 写入 → 窗口关 → 开始快照 → 快照结束 → 交接」
这五个先后关系，各自拥有【可判定、可否定】的证据。
```

## 1.2 当前材料状况 `[已实测]`

```text
harness 8 个核心文件 × 8 类原语
（fsync / flush / os.replace / os.rename / fcntl / flock / LockFile / msvcrt）

总计 = 0
```

```text
⇒ 没有同步、没有原子替换、没有文件锁、没有任何时间戳或序号原语。
⇒ 因此本协议不是在加固既有机制，是为一个【尚不存在】的记录者定义契约。
```

## 1.3 为什么不能建立在状态摘要上 `[已实测]`

```text
IDENTITY 模式：
  baseline digest 9d908ecfb6b256def8b49a7c…
  after IDENTITY  9d908ecfb6b256def8b49a7c…   equal

幂等写入（COLLAPSE_SIGN on q=+2 / ERASE_EFFECT on 零基线）：
  digest 同样不变

⇒ 摘要不变 ⇏ 该操作没有执行
⇒ 摘要不变 ⇏ 该写入没有发生
```

```text
⇒ 协议必须记录【调用】，不能只记录【效果】。
```

# 二 · 三个记录层次

## 2.1 定义

```text
L1 RECEIVED      记录者收到事件请求
L2 PERSISTED     记录者已落盘，且 fsync 返回成功
L3 ACKNOWLEDGED  记录者已向提交方确认 L2 完成
```

`[接受裁定]` 层次分离的依据是凌翼「附加审查提醒」第二條：
> 「函数返回、数据进入缓存、系统确认写入以及持久化完成，不一定是同一个事件。」

## 2.2 为什么必须分三层

```text
⇒ 只有 L3 可以作为【因果约束】的依据。
  例：WINDOW_CLOSE 必须达到 L3，才允许进入 SNAPSHOT_BEGIN。
      （这是凌翼 O-1 明确要求的因果约束）

⇒ 若把 L1 当 L3，则提交方在记录尚未落盘时就被放行，
   崩溃后出现「已放行但无记录」——正是最需要证据时刻的证据缺失。
```

## 2.3 PERSISTED 的准确含义 `[已核对源码]`

```text
storage.py L59-61:
    def _write_bytes(self, path, data):
        with open(path,"wb") as f:
            f.write(data)

⇒ 无 flush()、无 os.fsync()。
⇒ with 退出只保证文件对象关闭，不保证持久化。
⇒ 全仓库文件级同步：零处（仅两处 sys.stdout.flush()，无关）。
```

```text
⇒ 本协议定义：PERSISTED = fsync 返回成功，不是「物理落盘」。
⇒ 这是定义层面的诚实，不是保障。
⇒ 部分文件系统 / 虚拟化磁盘上 fsync 不保证物理持久化，本协议无法消除。
```

# 三 · 事件记录结构

## 3.1 字段

```text
EventRecord {
    event_id       提交方生成的唯一标识（重试时复用）
    recorder_id    记录者实例身份
    epoch          记录者启动世代（重启后递增）
    seq            该 epoch 内的单调序号
    execution_id   执行身份
    object_id      对象身份（arm + 文件身份）
    event_type     WINDOW_OPEN | WRITE_COMMIT | WINDOW_CLOSE
                 | SNAP_BEGIN  | SNAP_END     | HANDOFF
                 | J_APPLIED   | RECORDER_STARTED | RECOVERY_TRUNCATED
    commit_state   CONFIRMED | UNCONFIRMED | UNKNOWN_ACK
    clock_ns       perf_counter_ns（辅助，不参与排序）
    state_digest   附加字段（不参与排序）
    content_digest 覆盖以上全部语义字段（含 seq 与 epoch）
    producer_id    记录者签名/身份
}
```

## 3.2 三条硬约束

```text
C-1  event_id 由【提交方】生成，不由记录者生成。
     ⇒ 理由见 5.2：崩溃提交方不可区分，重试时记录者序号还不存在。

C-2  execution_id 与 object_id 必须出现在【每一条】记录上，
     不能只在头部出现一次。
     ⇒ 理由：否则无法检测部分重放（H-3）与身份冒充（J-1/J-2）。

C-3  content_digest 必须覆盖 seq 与 epoch。
     ⇒ 理由：否则重排序后改写 seq 可使记录自洽（I-2 无法检测）。
```

```text
C-3 的代价必须说明 `[接受裁定]`：
  摘要覆盖 seq 之后，「改 seq 而不破坏摘要」在不知道密钥的前提下不可行。
  但这只防【盲改】，不防【拿到内容后重算摘要并重排】。
  后者需要外部锚点（阶段⑥封存或头部摘要链）才能检测。
  ⇒ 无外部锚点时，正确的输出是 TAMPER_DETECTION = NOT ESTABLISHED，
     不是 PASS。
```

# 四 · 因果约束

## 4.1 五条 precedes（凌翼 O-1 / O-4 给定）

`[接受裁定]`

```text
WINDOW_OPEN   precedes WRITE_COMMIT
WRITE_COMMIT  precedes WINDOW_CLOSE
WINDOW_CLOSE  precedes SNAP_BEGIN
SNAP_END      precedes HANDOFF
```

## 4.2 precedes 的判定方式

```text
若 a precedes b，则：
  (i)  a 与 b 的 commit_state 均为 CONFIRMED
  (ii) a.recorder_id == b.recorder_id 且 a.epoch == b.epoch
  (iii)a.seq < b.seq

⇒ 三条同时成立，才可判 precedes 成立。
⇒ 任一不成立 ⇒ ORDER_PROOF = NOT ESTABLISHED（不是 FAIL）。
```

## 4.3 为什么必须同 epoch

`[接受裁定]`

```text
跨 epoch 的 seq 不可比。
⇒ 若一次执行跨越了记录者重启，该执行的 EVENT_ORDER_PROOF = NOT ESTABLISHED
  （除非有其它独立见证，见 4.4）
```

## 4.4 时钟的角色

`[已实测]` + `[接受裁定]`

```text
[已实测] perf_counter_ns 在 win32/CPython 3.11 上由 QueryPerformanceCounter()
        提供，跨进程同源：
        parent window [3335198510456300, 3335198552131200]
          child0 3335198538371400  inside=True
          child1 3335198542480400  inside=True
          child2 3335198548142500  inside=True

[接受裁定] 同源 ≠ 可用于排序。
          clock_ns 只作辅助，不参与 precedes 判定。
```

## 4.5 冲突与不可比较必须分开

`[接受裁定]` — 凌翼 O-3

```text
情形甲：两来源均已证明适用于同一事件顺序判断，且矛盾不可调和
        ⇒ TRUSTED_ORDER_CONFLICT → INVALID

情形乙：两来源没有相同可信来源 / 采样边界 / 可比较性保证
        ⇒ CLOCK_COMPARABILITY = NOT ESTABLISHED
        ⇒ 【不是冲突】，不得凭此推翻可信顺序
```

```text
⇒ 不得凭时钟倒退单独推翻 seq。
⇒ 不得用时钟值自行建立顺序。
⇒ 不得对尚未证明可比较的数据制造冲突。
```

## 4.6 时刻相等不作为判据

`[接受裁定]` — 凌翼 O-4

```text
SAME_CLOCK_TICK != SAME_EVENT
SAME_CLOCK_TICK != ORDER_PROOF

⇒ 窗口合法性由 4.2 的 precedes 判定，不由时刻相等判定。
⇒ 若同一 clock_ns 但 seq 已证关闭先于读取 ⇒ 不因此判快照无效。
⇒ 若无法证明先后 ⇒ 不得接受为合格快照。
```

# 五 · 提交与确认

## 5.1 提交时序

```text
提交方                        记录者
  |-- SUBMIT(event_id, ...) --->|
  |                             | L1 RECEIVED
  |                             | L2 write + fsync
  |<-- ACK(event_id, seq) ------| L3 ACKNOWLEDGED
  |
  记录者为该 event_id 绑定 seq
```

## 5.2 幂等提交（核心）

```text
⇒ 记录者崩溃的三个位置：
   ① 收到请求前        ⇒ 事件从未存在，提交方超时
   ② 落盘中            ⇒ 磁盘可能半条或完整记录，提交方未收 ACK
   ③ 落盘后、确认前     ⇒ 记录存在，提交方未收 ACK

⇒ 对提交方而言，② ③ 看起来【完全一样】：都没收到 ACK。
⇒ 因此不能靠提交方「重试即可」，否则可能重复。
⇒ 也不能靠记录者序号去重，因为重试时序号尚未分配。
```

```text
规则 SUBMIT-IDEMPOTENT：
  提交方重试时复用【同一 event_id】。
  记录者收到已存在 event_id 时：
    · 若已有该 event_id 的 L2 记录 ⇒ 幂等，重发 ACK
    · 若无                         ⇒ 正常写入
```

```text
⇒ 这是幂等提交，不是记录者去重。
⇒ 重试与重放的区别：
   幂等重试 = 同一 event_id 的重新提交（协议内，合法）
   重放攻击 = 同一 event_id 在已持久化流中出现两次（协议外，INVALID）
```

## 5.3 未确认状态

`[接受裁定]`

```text
U-1 NOT_SENT       提交方确定未发送      ⇒ 事件不存在，不得记入流
U-2 SENT_NO_ACK    已发送未收到 ACK       ⇒ 保持 UNCONFIRMED 至超时
U-3 SENT_CRASHED   已发送，记录者崩溃      ⇒ 标记 UNKNOWN_ACK

⇒ U-2/U-3 不得臆测成功，不得判为失败。
⇒ 用于因果约束的事件（如 WINDOW_CLOSE）必须为 CONFIRMED，
  否则视为「缺必需关闭见证」⇒ 按 O-2 判 INVALID。
```

## 5.4 一处必须承认的残余风险

```text
位置②产生「磁盘有完整记录，但提交方判超时并放弃」。
⇒ SUBMIT-IDEMPOTENT 使重试不产生重复。
⇒ 但若提交方【不再重试】，则存在一条
   「记录者认为已提交、提交方认为未提交」的记录。

⇒ 该状态不可消除，只能被【标记】：
   commit_state = UNKNOWN_ACK
⇒ 该记录不得作为 positive 证据，
   但可用于说明「此处发生过分歧」。
```

# 六 · 序号域与重启

## 6.1 epoch 切分

```text
序号域 = (recorder_id, epoch, seq)

规则 EPOCH-1：
  每次启动生成新的 epoch（单调递增）。
  同一 epoch 内 seq 严格递增。
  不同 epoch 的 seq 【不可直接比较】。
```

## 6.2 为什么必须切分

```text
若重启后接着编号：
  重启前后的 seq 看起来可比，实际不可比。
⇒ 这是【制造假顺序】。
⇒ 与 O-3「不对尚未证明可比较的数据制造冲突」是同一原则的反面。
```

## 6.3 重启记录

```text
规则 EPOCH-2：
  启动时必须写入 RECORDER_STARTED，携带：
    新 epoch、上一 epoch、上次最后【完整】 seq、恢复动作
```

```text
规则 EPOCH-3：
  恢复时扫描尾部：
    若最后一条记录不完整 ⇒ 截断，记 RECOVERY_TRUNCATED
    不得把不完整记录当作有效事件
```

## 6.4 一个本协议无法解决的依赖

```text
epoch 分配本身必须原子（读-改-写）。
⇒ 当前 harness 无锁、无原子替换（见 1.2）。
⇒ 因此 EPOCH-1 的【实现前提尚不存在】。
⇒ 本协议只定义规则，不声称可实施。
```

# 七 · 写入提交的语义（WRITE_COMMIT）

## 7.1 问题是它从未被定义

`[接受裁定]` — 凌翼附加审查提醒第二条

```text
四个可能的时刻：
  (a) write_literal / write_substrate 返回
  (b) 文件对象 close 完成（with 退出）
  (c) os.fsync() 返回
  (d) 受信记录者确认收到提交回执
```

## 7.2 本协议的处理

```text
⇒ 本协议【不选】。
⇒ 因为选哪个取决于崩溃语义的取舍，而那是裁定范围。
⇒ 在选定前：WRITE_COMMIT 仅为占位符，
   不得用于任何判定，不得进入证据矩阵（O-6 要求五段式）。
```

## 7.3 但可以说明三件事

```text
[已核对源码] (a)(b) 在本实现中【不保证持久化】——无 fsync（见 2.3）。

[接受裁定]  (c) 比 (a)(b) 强，但 fsync 仍不等于物理落盘（见 2.3）。

[推论]      (d) 与 O-1 的因果约束天然一致：
            若 WINDOW_CLOSE 必须达到 L3 才允许 SNAP_BEGIN，
            则同一逻辑下 WRITE_COMMIT 也应取「记录者确认」。
            ⇒ 这只是结构一致的观察，不是建议。
```

# 八 · 失败处置总表

| 失败 | 状态标记 | 期望判定 |
|---|---|---|
| 记录者崩溃（②③） | `UNKNOWN_ACK` | INVALID（若用于判定） |
| 重复序号 | `ORDER_VIOLATION` | INVALID |
| 同键不同内容 | `SEQ_REUSE_WITH_DIFFERENT_CONTENT` | INVALID |
| 持久化失败（fsync 失败） | `fsync_returned=false` | INVALID |
| 跨 epoch | `ORDER_PROOF=NOT_ESTABLISHED` | INVALID |
| 未确认 U-2/U-3 | `UNCONFIRMED` | INVALID |
| 必需关闭见证缺失 | `WINDOW_CLOSE missing` | INVALID（O-2） |
| 时钟不可比较 | `CLOCK_COMPARABILITY=NOT_ESTABLISHED` | 不是冲突，不判 INVALID |
| 无外部锚点的篡改/重排 | `TAMPER/REORDER_DETECTION=NOT_ESTABLISHED` | NOT_ESTABLISHED |

```text
⇒ 表中无一项为 FAIL。
⇒ 全部为「证据不足」而非「证据否定」。
⇒ 凌翼 D 项：缺证 ⇒ INVALID；实测否定 ⇒ FAIL。二者不得合并。
```

# 九 · 本协议明确不成立的六件事

```text
1. 本协议不能建立 EVENT_ORDER_PROOF —— 它只定义可被否定的结构
2. 本协议不能被实施 —— 依赖不存在的锁/同步/原子替换
3. 本协议不能声称 WRITE_COMMIT 已定义 —— 7.2 明确留空
4. 本协议不能消除「提交方认为失败、记录者认为成功」的分歧
5. 本协议不能防住拿到内容后重算摘要的攻击（需外部锚点）
6. 本协议不替代未来规范审查（O-5 三层归属）
```

```text
这份协议最重要的部分不是它定义了什么，
而是它给四种情况各自取了名字：

  不知道     -> NOT ESTABLISHED
  不可比     -> CLOCK_COMPARABILITY = NOT ESTABLISHED
  没落盘     -> fsync 未返回

有了名字，它们才不会在下一个人手里
```
