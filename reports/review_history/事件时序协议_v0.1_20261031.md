# 一 · 协议要解决的问题

## 1.1 一句话

```text
让「窗口开 → 写入 → 窗口关 → 开始快照 → 快照结束 → 交接」
这五个先后关系，各自拥有【可判定、可否定】的证据。
```

## 1.2 当前材料状况 `[已实测]`

```text
harness 8 个核心文件 × 8 类原语
（fsync / flush / os.replace / os.rename / fcntl / flock / LockFile / msvcrt）

总计 = 0
```

```text
⇒ 没有同步、没有原子替换、没有文件锁、没有任何时间戳或序号原语。
⇒ 因此本协议不是在加固既有机制，是为一个【尚不存在】的记录者定义契约。
```

## 1.3 为什么不能建立在状态摘要上 `[已实测]`

```text
IDENTITY 模式：
  baseline digest 9d908ecfb6b256def8b49a7c…
  after IDENTITY  9d908ecfb6b256def8b49a7c…   equal

幂等写入（COLLAPSE_SIGN on q=+2 / ERASE_EFFECT on 零基线）：
  digest 同样不变

⇒ 摘要不变 ⇏ 该操作没有执行
⇒ 摘要不变 ⇏ 该写入没有发生
```

```text
⇒ 协议必须记录【调用】，不能只记录【效果】。
```

# 二 · 三个记录层次

## 2.1 定义

```text
L1 RECEIVED      记录者收到事件请求
L2 PERSISTED     记录者已落盘，且 fsync 返回成功
L3 ACKNOWLEDGED  记录者已向提交方确认 L2 完成
```

`[接受裁定]` 层次分离的依据是凌翼「附加审查提醒」第二條：
> 「函数返回、数据进入缓存、系统确认写入以及持久化完成，不一定是同一个事件。」

## 2.2 为什么必须分三层

```text
⇒ 只有 L3 可以作为【因果约束】的依据。
  例：WINDOW_CLOSE 必须达到 L3，才允许进入 SNAPSHOT_BEGIN。
      （这是凌翼 O-1 明确要求的因果约束）

⇒ 若把 L1 当 L3，则提交方在记录尚未落盘时就被放行，
   崩溃后出现「已放行但无记录」——正是最需要证据时刻的证据缺失。
```

## 2.3 PERSISTED 的准确含义 `[已核对源码]`

```text
storage.py L59-61:
    def _write_bytes(self, path, data):
        with open(path,"wb") as f:
            f.write(data)

⇒ 无 flush()、无 os.fsync()。
⇒ with 退出只保证文件对象关闭，不保证持久化。
⇒ 全仓库文件级同步：零处（仅两处 sys.stdout.flush()，无关）。
```

```text
⇒ 本协议定义：PERSISTED = fsync 返回成功，不是「物理落盘」。
⇒ 这是定义层面的诚实，不是保障。
⇒ 部分文件系统 / 虚拟化磁盘上 fsync 不保证物理持久化，本协议无法消除。
```

# 三 · 事件记录结构

## 3.1 字段

```text
EventRecord {
    event_id       提交方生成的唯一标识（重试时复用）
    attempt_id     本次提交尝试身份（每次重试不同）
    recorder_id    记录者实例身份
    epoch          记录者启动世代（重启后递增）
    seq            该 epoch 内的单调序号
    execution_id   执行身份
    object_id      对象身份（arm + 文件身份）
    event_type     WINDOW_OPEN | WRITE_COMMIT | WINDOW_CLOSE
                 | SNAP_BEGIN  | SNAP_END     | HANDOFF
                 | J_APPLIED   | RECORDER_STARTED | RECOVERY_TRUNCATED
    clock_ns       perf_counter_ns（辅助，不参与排序）
    state_digest   附加字段（不参与排序）
    producer_id    记录者签名/身份

    ── 以下为【状态字段】，不属 content_digest 覆盖范围 ──
    commit_state   CONFIRMED | UNCONFIRMED | UNKNOWN_ACK
}
```

## 3.1b content_digest 的覆盖范围（2026-10-31 修正，凌翼 R-2）

> **原文问题：** §3.1 曾写「content_digest 覆盖以上**全部**语义字段」，
> 而 §3.3 规定 commit_state 不属覆盖范围。二者矛盾。
> 已取消「全部语义字段」这一概括表述，改为明确清单。

**纳入 content_digest 的字段（含清单）：**

```text
COVERED_BY_CONTENT_DIGEST = [
    event_id,
    attempt_id,
    recorder_id,
    epoch,
    seq,
    execution_id,
    object_id,
    event_type,
    clock_ns,
    state_digest,
    producer_id,
]
```

**排除在外（排除清单）：**

```text
EXCLUDED_FROM_CONTENT_DIGEST = [
    commit_state,        # 理由见 §3.3：状态可变
    content_digest,      # 自引用，必须排除自身
]
```

**稳定序列化要求：**

```text
⇒ 为保证不同实现可复算同一摘要，须规定稳定序列化方式：
   · 字段按上方清单【固定顺序】拼接
   · 字符串用 UTF-8 编码
   · 长度前缀或明确分隔符，避免拼接歧义
   · 不得依赖 dict 迭代顺序或平台默认行为

⇒ 具体编码格式【本协议未定】。
   SERIALIZATION_FORMAT = OPEN
⇒ 未定之前，跨实现复算同一 content_digest【不成立】。
```

```text
⚠ 在 RECORD_IMMUTABILITY_DECISION = OPEN 的情况下，
   本节的字段清单属【暂行描述】，
   不得读成已完成的记录完整性协议。
```

## 3.2 三条硬约束

```text
C-1  event_id 由【提交方】生成，不由记录者生成。
     ⇒ 理由见 5.2：崩溃提交方不可区分，重试时记录者序号还不存在。

C-2  execution_id 与 object_id 必须出现在【每一条】记录上，
     不能只在头部出现一次。
     ⇒ 理由：否则无法检测部分重放（H-3）与身份冒充（J-1/J-2）。

C-3  content_digest 必须覆盖 seq 与 epoch。
     ⇒ 理由：否则重排序后改写 seq 可使记录自洽（I-2 无法检测）。
     ⇒ 且 content_digest 的计算输入【必须排除自身】，否则自引用。
```

## 3.2b C-3 的保证范围（2026-10-31 修正，凌翼 P0-1）

**原文错误：** 我此前写「改 seq 而不破坏摘要，在不知道**密钥**的前提下不可行」。

```text
⇒ 这是错的，且错在两处：
   ① 协议里从未定义任何【密钥】—— 我引入了一个不存在的概念
   ② 普通 SHA-256 无密钥；任何能改内容的人通常也能重算摘要
```

**修正后的准确分层：**

```text
[已核对源码] 本协议未定义密钥、未定义 MAC、未定义签名。
             因此 content_digest 只能是普通摘要，不能是认证码。

普通摘要        检测【未同步更新摘要】的损坏或篡改
                ⇒ 攻击者重算摘要即可绕过
MAC / 数字签名   在密钥与信任根受保护时可验证来源与完整性
                ⇒ 本协议【没有】这一层
外部可信锚点     可识别历史记录的替换、截断、整体重写
                ⇒ 本协议【没有】这一层
```

```text
HASH_COVERS_SEQ_AND_EPOCH
    = VALID DESIGN CONSISTENCY RULE

HASH_AUTHENTICATES_EVENT_ORIGIN
    = NOT ESTABLISHED

HASH_PREVENTS_ADVERSARIAL_REORDERING
    = NOT ESTABLISHED
```

```text
⇒ C-3 不是「已闭合的防篡改约束」，只是字段一致性规则。
⇒ 没有可信锚点时，摘要链整体也可能被重写。
```

## 3.3 记录不可变性（2026-10-31 新增，凌翼 P0-3）

**问题：** §3.1 的 `commit_state` 会在重试、确认、恢复时变化，
而 §3.2 C-3 要求 `content_digest` 覆盖全部语义字段。

```text
⇒ 若 commit_state 属于「语义字段」并被摘要覆盖，
   则每次状态变化都要改摘要 ⇒ 记录被修改 ⇒ 摘要失去意义。
⇒ 若 commit_state 不被摘要覆盖，
   则它可被任意改写而不被发现。
⇒ 二者不可兼得。这是原协议【未解决】的冲突。
```

**候选方向（凌翼建议优先采用 A，但明确说这不是实施授权）：**

```text
方向 A：不可变事件记录 + 独立状态转换记录
  事件记录只写一次，永不变更。
  commit_state 的每次变化，写一条独立的状态转换记录：
    StateTransition { event_id, from, to, reason, transition_seq }
  ⇒ 事件记录 digest 不覆盖 commit_state
  ⇒ 当前状态 = 该 event_id 所有转换记录折叠所得
  ⇒ 好处：事件真实性可校验；状态演变可追溯
  ⇒ 代价：读取需折叠，复杂度上升

方向 B：记录可变，摘要在每次修改后重算
  ⇒ 无法区分「合法状态更新」与「篡改」
  ⇒ 不推荐

方向 C：拆成两条记录（事件记录 + 确认记录），互不覆盖
  ⇒ 与 A 接近，但把状态直接分成两类记录
```

```text
⇒ 本协议【不选】。理由：这是协议结构选择，不是文字修正。
⇒ 在选定前：
   · commit_state 标注为【状态字段，不属 content_digest 覆盖范围】
   · content_digest 覆盖范围 = 除 commit_state 外的全部语义字段
   · 且 commit_state 的任何变化【必须】有独立记录，否则不成立

RECORD_IMMUTABILITY_DECISION = OPEN
```

## 3.4 日志持久化 ≠ 业务持久化（2026-10-31 新增，凌翼 P0-3）

```text
⇒ 记录者确认【日志已保存】，不等于业务写入已经提交或持久化。

两者是不同保证：
  事件日志 fsync        ⇒ 该条记录已落盘
  目标 STATE 文件持久化  ⇒ literal.bin / substrate.bin 已落盘
                        ⇒ 当前 harness【没有任何 fsync】（见 §2.3）

⇒ 因此不能从 EVENT_RECORD_ACKNOWLEDGED 推出 STATE 已持久化。
⇒ 也不能把「记录者确认某条 WRITE_COMMIT 报告」
   等同于「独立证明数据真正写入注册对象」。
```

# 四 · 因果约束

## 4.1 五条 precedes（凌翼 O-1 / O-4 给定）

`[接受裁定]`

```text
(1) WINDOW_OPEN   precedes WRITE_COMMIT
(2) WRITE_COMMIT  precedes WINDOW_CLOSE
(3) WINDOW_CLOSE  precedes SNAP_BEGIN
(4) SNAP_BEGIN    precedes SNAP_END
(5) SNAP_END      precedes HANDOFF
```

> **2026-10-31 修正（凌翼 P0-2）**
> 本节原文标题写「五条」，正文只列了 4 行——
> 漏掉 `SNAP_BEGIN precedes SNAP_END`。
> 标题声明 5 条而内容 4 条，我没有核对自己写的数量。
> 已补齐为 (1)..(5)。

**适用条件（同样须明确）：**

```text
五条关系各自限定在同一
  · 事件范围（涉及的 event_type）
  · 对象范围（object_id 相同）
  · execution 范围（execution_id 相同）
  · epoch 范围（recorder_id 与 epoch 相同）
内。

⇒ 跨对象 / 跨执行 / 跨 epoch 的五条关系【不成立】，须另行举证。
```

## 4.2 记录层排序的必要条件（2026-10-31 修正，凌翼 R-1）

> **本节的地位已收窄。**
> 原 §4.2 把下列三项写成【独立充分条件】，与 §4.2b 冲突。已修正。

```text
若 a precedes b，则【必须】满足：
  (i)  a 与 b 的 commit_state 均为 CONFIRMED
  (ii) a.recorder_id == b.recorder_id 且 a.epoch == b.epoch
  (iii)a.seq < b.seq

⇒ 这三条是【必要条件】，不是充分条件。
⇒ 满足它们只说明「记录层顺序成立」，【不】说明 precedes 成立。
⇒ 要判 precedes，必须【另外】满足 §4.2b 的三项。
```

```text
⇒ 因此正确的推理方向是：
   precedes 成立  ⇒  (i)(ii)(iii) 成立
   (i)(ii)(iii) 成立  ⇏  precedes 成立
```

**跨对象 / 跨 epoch 的处置（已修正措辞）：**

```text
若 a 与 b 跨对象（object_id 不同）或跨 epoch：
  ⇒ 应记为：当前规则【不适用】，顺序【未建立】
  ⇒ 不得写成「先后关系不成立」

⇒ 差别：
   「不适用 / 未建立」 = 本规则无法判定，可能另有证据
   「不成立」          = 已判定为假
⇒ 本协议没有能力判定后者，故只能用前者。
```

## 4.2b precedes 的充分条件（凌翼 P0-2）

**原文不足：** 我此前写「三条同时成立，才可判 precedes 成立」。
这暗示记录顺序即可建立因果顺序。**不成立。**

```text
[接受裁定] 严格递增的 seq 只证明【记录者接收并持久化的次序】，
           不证明【事件实际发生的次序】，因为：
           · 传输延迟可使后发生的事件先被记录
           · 若无阶段依赖强制，后续阶段可在前一阶段未确认时开始
```

**修正后的判定式：**

```text
TRUSTED_SEQ_ORDER
  AND ENFORCED_STAGE_DEPENDENCY
  AND BOUND_EVENT_IDENTITY
=> ELIGIBLE_ORDER_EVIDENCE
```

```text
三项含义：
  TRUSTED_SEQ_ORDER          序号由受信记录者分配且未被重排
  ENFORCED_STAGE_DEPENDENCY  后续阶段【在机制上】不能在前一阶段必要确认之前启动
                             ⇒ 这不是声明，是必须被强制的约束
  BOUND_EVENT_IDENTITY       事件身份（object / execution / event）绑定完整
```

```text
⇒ 缺任一项 ⇒ ELIGIBLE_ORDER_EVIDENCE = NOT ESTABLISHED
⇒ 不得仅凭 seq 严格递增建立事件发生顺序。
```

## 4.3 为什么必须同 epoch

`[接受裁定]`

```text
跨 epoch 的 seq 不可比。
⇒ 若一次执行跨越了记录者重启，该执行的 EVENT_ORDER_PROOF = NOT ESTABLISHED
  （除非有其它独立见证，见 4.4）
```

## 4.4 时钟的角色

`[已实测]` + `[接受裁定]`

```text
[已实测] perf_counter_ns 在 win32/CPython 3.11 上由 QueryPerformanceCounter()
        提供，跨进程同源：
        parent window [3335198510456300, 3335198552131200]
          child0 3335198538371400  inside=True
          child1 3335198542480400  inside=True
          child2 3335198548142500  inside=True

[接受裁定] 同源 ≠ 可用于排序。
          clock_ns 只作辅助，不参与 precedes 判定。
```

## 4.5 冲突与不可比较必须分开

`[接受裁定]` — 凌翼 O-3

```text
情形甲：两来源均已证明适用于同一事件顺序判断，且矛盾不可调和
        ⇒ TRUSTED_ORDER_CONFLICT → INVALID

情形乙：两来源没有相同可信来源 / 采样边界 / 可比较性保证
        ⇒ CLOCK_COMPARABILITY = NOT ESTABLISHED
        ⇒ 【不是冲突】，不得凭此推翻可信顺序
```

```text
⇒ 不得凭时钟倒退单独推翻 seq。
⇒ 不得用时钟值自行建立顺序。
⇒ 不得对尚未证明可比较的数据制造冲突。
```

## 4.6 时刻相等不作为判据

`[接受裁定]` — 凌翼 O-4

```text
SAME_CLOCK_TICK != SAME_EVENT
SAME_CLOCK_TICK != ORDER_PROOF

⇒ 窗口合法性由 4.2 的 precedes 判定，不由时刻相等判定。
⇒ 若同一 clock_ns 但 seq 已证关闭先于读取 ⇒ 不因此判快照无效。
⇒ 若无法证明先后 ⇒ 不得接受为合格快照。
```

# 五 · 提交与确认

## 5.1 提交时序

> **2026-10-31 修正（凌翼 P0-3）**
> 原示意图把「为 event_id 绑定 seq」画在 ACK 之后，
> 会被读成「先确认、再分配序号」。**顺序是反的。**

```text
提交方                                记录者
  |-- SUBMIT(event_id, attempt_id, ...) -->|
  |                                        | (1) 接收 event_id
  |                                        | (2) 校验提交身份与绑定对象
  |                                        | (3) 分配 seq
  |                                        | (4) 持久化 event_id ↔ seq ↔ 内容 的绑定
  |                                        | (5) 同步成功（fsync 返回）
  |<-- ACK(event_id, attempt_id, seq) -----| (6) 发送 ACK
  |                                        |
  | (7) 提交方【实际收到】有效 ACK
  | (8) 后继阶段【才】获得执行许可
```

```text
⇒ 顺序要点：seq 在 ACK 【之前】分配并持久化。
⇒ 原图把它画在 ACK 之后，语义错误，已改。
```

## 5.1b 三个必须分开的状态（凌翼 P0-3）

```text
S1 ACK_SENT          记录者已发送 ACK
S2 ACK_RECEIVED      提交方确实收到有效 ACK
S3 STAGE_RELEASED    后继阶段因 S2 而获得执行许可

⇒ 三者不能合并。
⇒ 只到 S1 时：ACK 可能丢失在传输中，提交方仍处于 U-2 未确认。
⇒ 只到 S2 时：若记录者崩溃且 S2 的证据未留存，仍无法证明。
⇒ 只有 S3 才是「允许下一阶段开始」的实际依据。
```

## 5.2 幂等提交（核心）

```text
⇒ 记录者崩溃的三个位置：
   ① 收到请求前        ⇒ 事件从未存在，提交方超时
   ② 落盘中            ⇒ 磁盘可能半条或完整记录，提交方未收 ACK
   ③ 落盘后、确认前     ⇒ 记录存在，提交方未收 ACK

⇒ 对提交方而言，② ③ 看起来【完全一样】：都没收到 ACK。
⇒ 因此不能靠提交方「重试即可」，否则可能重复。
⇒ 也不能靠记录者序号去重，因为重试时序号尚未分配。
```

```text
规则 SUBMIT-IDEMPOTENT：
  提交方重试时复用【同一 event_id】，但使用【新的 attempt_id】。
  记录者收到已存在 event_id 时：
    · 若已有该 event_id 的 L2 记录 ⇒ 幂等，重发 ACK
    · 若无                         ⇒ 正常写入
```

**2026-10-31 新增：逻辑事件身份 vs 提交尝试身份（凌翼第五节）**

```text
问题：原规则 §4.2「fsync 失败后重试必须写新记录，引用同一 event_id」
      与「同一 event_id 只对应一个已确认事件」的幂等规则冲突。

⇒ 因为它会让【同一次逻辑事件】产生多条都自称权威的记录。

修正：两种身份必须分开。

  event_id    = 逻辑事件身份（一次逻辑事件只有一个）
  attempt_id  = 本次提交尝试身份（每次重试不同）

⇒ 恢复流程必须先检查已有记录及其可确认状态，
   不得因为上一次 fsync 失败，就自动制造另一个【权威事件】。
```

```text
⇒ 因此重试写新记录时：
   新记录的 event_id 与旧记录【相同】，attempt_id【不同】，
   并标记 supersedes_attempt=<旧 attempt_id>。
```

**2026-10-31 修正：权威记录选择规则（凌翼 R-3）**

> **原规则作废：** 我曾写「以最终达到 L3 且未标记 fsync 失败的那条为准；
> 若两条都达到 L3 ⇒ INVALID」。
> **这个规则有两处错误：**

```text
错误一：重复 ACK ≠ 两条冲突的权威事件
  同一 event_id 的合法重试，可能使记录者【多次发送 ACK】。
  ⇒ 但这只是重复确认同一个逻辑事件，
     不是出现了两个互相冲突的权威事件。

错误二：后一次成功不能自动取代先前已确认的逻辑事件
  ⇒ 若事件 A 已被确认，重试成功【不应】让新记录成为权威。
  ⇒ 「选择最后成功者」等于用时间先后消解歧义，
     而歧义恰恰可能就出在时间不可靠上。
```

**修正后的规则：以 event_id 的唯一权威映射为核心**

```text
核心原则：
  event_id → 权威记录  的映射在【首次确认时建立】，此后不再变更。

三种情形必须分开：

  情形甲：同一权威事件的重复确认
    ⇒ 多条记录指向同一 event_id 且内容一致
    ⇒ 不是冲突。保留首次确认的映射，重复 ACK 视为幂等
    ⇒ 不判 INVALID

  情形乙：未确认尝试的恢复与重试
    ⇒ 先前 attempt 未达 L3
    ⇒ 若此时映射尚未建立 ⇒ 新 attempt 可建立映射
    ⇒ 若映射已建立（先前其实已确认，只是 ACK 丢失）
      ⇒ 保持原映射不变，新 attempt 视为同一事件的重复确认

  情形丙：真正存在两个互相冲突的权威事件绑定
    ⇒ 同一 event_id 出现【内容不同】且【都声称已确认】的记录
    ⇒ 这才是真冲突 ⇒ INVALID

⇒ 判定顺序：先看映射是否已建立，再看内容是否一致，
   而不是看谁最后成功。
```

```text
⇒ 发生不确定恢复时（无法确定映射是否已建立）：
   ⇒ 必须【暂停判定】，标记 AUTHORITY_MAPPING_UNDETERMINED
   ⇒ 不得通过「选择最后成功者」消除歧义
```

```text
AUTHORITY_RULE = EVENT_ID_UNIQUE_MAPPING_AT_FIRST_CONFIRMATION
IDEMPOTENT_AUTHORITY_RULE = REVISED（凌翼 R-3）
```

```text
⇒ 这是幂等提交，不是记录者去重。
⇒ 重试与重放的区别：
   幂等重试 = 同一 event_id 的重新提交（协议内，合法）
   重放攻击 = 同一 event_id 在已持久化流中出现两次（协议外，INVALID）
```

## 5.3 未确认状态

`[接受裁定]`

```text
U-1 NOT_SENT       提交方确定未发送      ⇒ 事件不存在，不得记入流
U-2 SENT_NO_ACK    已发送未收到 ACK       ⇒ 保持 UNCONFIRMED 至超时
U-3 SENT_CRASHED   已发送，记录者崩溃      ⇒ 标记 UNKNOWN_ACK

⇒ U-2/U-3 不得臆测成功，不得判为失败。
⇒ 用于因果约束的事件（如 WINDOW_CLOSE）必须为 CONFIRMED，
  否则视为「缺必需关闭见证」⇒ 按 O-2 判 INVALID。
```

## 5.4 一处必须承认的残余风险

```text
位置②产生「磁盘有完整记录，但提交方判超时并放弃」。
⇒ SUBMIT-IDEMPOTENT 使重试不产生重复。
⇒ 但若提交方【不再重试】，则存在一条
   「记录者认为已提交、提交方认为未提交」的记录。

⇒ 该状态不可消除，只能被【标记】：
   commit_state = UNKNOWN_ACK
⇒ 该记录不得作为 positive 证据，
   但可用于说明「此处发生过分歧」。
```

# 六 · 序号域与重启

## 6.1 epoch 切分

```text
序号域 = (recorder_id, epoch, seq)

规则 EPOCH-1：
  每次启动生成新的 epoch（单调递增）。
  同一 epoch 内 seq 严格递增。
  不同 epoch 的 seq 【不可直接比较】。
```

## 6.2 为什么必须切分

```text
若重启后接着编号：
  重启前后的 seq 看起来可比，实际不可比。
⇒ 这是【制造假顺序】。
⇒ 与 O-3「不对尚未证明可比较的数据制造冲突」是同一原则的反面。
```

## 6.3 重启记录

```text
规则 EPOCH-2：
  启动时必须写入 RECORDER_STARTED，携带：
    新 epoch、上一 epoch、上次最后【完整】 seq、恢复动作
```

```text
规则 EPOCH-3：
  恢复时扫描尾部：
    若最后一条记录不完整 ⇒ 截断，记 RECOVERY_TRUNCATED
    不得把不完整记录当作有效事件
```

## 6.4 一个本协议无法解决的依赖

```text
epoch 分配本身必须原子（读-改-写）。
⇒ 当前 harness 无锁、无原子替换（见 1.2）。
⇒ 因此 EPOCH-1 的【实现前提尚不存在】。
⇒ 本协议只定义规则，不声称可实施。
```
