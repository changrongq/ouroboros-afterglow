## 1 · 现状缺口：为什么现在做不到（精确位置）

我们此前所有努力都在**进程已经跑起来之后**：

```text
spawn worker → worker 已持有它继承/拿到的全部句柄 → 枚举 → 逐个证明"不是目标"
```

而 `win32_worker_process.py` / `spawn_worker_tracked` 的创建路径里，**继承控制是被动的**：进程继承我们给的默认继承集。

**缺口不在"证明得不够仔细"，在"创建的瞬间我们没把集合定死"。**

---

## 2 · 最小新增：**创建时点的一次显式继承裁决**

### 2.1 设计原则

**只加一个决策点，不加一整套新框架。**

```
现有:  CreateProcess(..., bInheritHandles=<默认>, ...)
新增:  CreateProcess(..., bInheritHandles=FALSE, ...)          ← 配置 (a)
     或 CreateProcess(..., bInheritHandles=TRUE,
                        PROC_THREAD_ATTRIBUTE_HANDLE_LIST=[白名单], ...)  ← 配置 (b)
```

**配置 (a)/(b) 的区别已实测过**（`c_verify_m1_inherit_premise.py`，`8acc27c`）：

| 配置 | 结果 |
|---|---|
| `inherit=FALSE`，无列表 | `err=0` 有效 |
| `inherit=TRUE` + `HANDLE_LIST` | `err=0` 有效 |
| `inherit=FALSE` + `HANDLE_LIST` | **`err=87` 不合法** |

**默认建议用 (a)**：`inherit=FALSE`，worker 初始句柄集合为**空**。
理由：**空集合是唯一不需要证明的集合。** (b) 需要证明"列表外的确实没继承"，(a) 不需要。

> **⚠️ 该实测是在 `8acc27c` 中进行的，当时已登记为执行范围越界。本轮引用的是它的记录，不重新执行。**

### 2.2 这一格解决什么

| 路径 | 是否解决 |
|---|---|
| 继承带来的不当能力 | **是**（集合为空） |
| 创建前父进程持有的句柄 | **是**（不继承即不传递） |
| worker 新开受保护对象 | 否 → 由 `deny_read_for_sid` + DACL 回答（已有组件） |

### 2.3 这一格**不**解决什么（必须写明）

- **不解决** worker 通过 IPC 请求他人代读（见 §3）
- **不解决** `stat` 类元数据探测（Windows DACL 可挡读，但对象存在性可能可见）
- **不解决** 边界在创建后是否被修改（需 §4）

## 3 · 三件事逐条回答

### ① 业务 worker 的直接访问限制

**已有可复用**：`q3_access_matrix` 定义矩阵 + `deny_read_for_sid` 施加 + `probe_read_access` 独立观察。

**最小新增**：

1. worker 以**受限令牌**创建（去除非必需 SID / 降低完整性级别）——`CreateRestrictedToken`，**现有代码未使用**
2. `inherit=FALSE`（§2）

**这两项相加，直接访问限制从"事后枚举证明"变成"创建时不可得"。**

**未证明事项**：受限令牌下 worker 是否仍可通过某种既有 API 取得 $P$ 的句柄——**需实测，本轮不测**。

### ② 控制器与 worker 之间的合法信息通道

凌翼 §3 要求：**允许通信，但每条通道事前声明端点、方向、数据类别、权限与证据记录**。

**最小设计**：**用 `HANDLE_LIST` 显式白名单，替代"全开/全关"二分**。

```text
worker 只能持有:
  - stdin / stdout（实验协议通道，方向与内容预注册）
  - 一个命名管道或共享内存句柄（若实验需要）
  - 无其他
```

**这是本设计里唯一"新增机制"的地方**，且它复用 §2 的同一个 API。

**关键优势**：**通道清单本身就是注册表。** 白名单即"预注册允许流动的信息"，与凌翼 §3 的表述直接对应。

**未证明事项**：白名单内的通道是否会被用作**隐蔽通道**（例如 stdout 的时序、管道缓冲区大小）。**这是剩余风险，不是已解决项。**

### ③ Reset 前后禁止信息是否可能回流

**已有可复用**：`judge_reset(clear_ok, preserve_ok, access_ok)` + `q3_dacl.restore_sd` + `verify_sd_equal`。

**现有能力的边界**：

| 问题 | 现有组件能否回答 |
|---|---|
| Reset 后受保护对象是否仍被拒 | **能**（`probe_read_access` 再观察一次） |
| DACL 是否被还原 | **能**（`verify_sd_equal`） |
| worker 是否残留状态在**其他位置**（缓存、临时目录、内存） | **不能** ← 缺口 |

**最小新增**：**Reset 后的"再观察"必须由独立主体执行**，而非 worker 自报。

**这一点 `judge_reset` 的签名已经支持**（`access_ok` 是入参），**但需要明确"谁提供 `access_ok`"**——建议由 `probe_read_access` 的独立观察者提供。

**明确未解决**：**缓存 / 临时文件 / 内存残留。** 我不声称本设计能覆盖它。

## 4 · 哪些"看似需要"的机制其实**不需要**新增

凌翼说"如果现有组件足以支撑，就不需要重造 RC11 和 Q3"。我据此逐项排除：

| 候选 | 结论 | 理由 |
|---|---|---|
| AppContainer / LPAC | **不建议首版采用** | 需要打包身份（package SID）、对无打包应用不适用；收益主要在"默认拒绝"，而 `inherit=FALSE` + DACL 已能给首版提供足够边界。**列为备选。** |
| Job Object | **不需要** | 它只解决生命周期（$t_{end}$ 可信化），不涉及访问控制；现有 `_process_is_gone` 已足够 |
| 内核驱动 / ETW | **不需要** | 超出威胁模型（凌翼 §2 已排除内核被攻破） |
| 重写句柄枚举 | **不需要** | Option C 已归档；新路线**不依赖枚举** |
| Hypervisor 隔离 | **不需要** | 代价远超收益，且首版目标不含该威胁 |

## 5 · 缺口清单：本设计**不能**覆盖的（精确指出，不无限加功能）

凌翼要求"如果仍存在足以影响科学归因的缺口，就精确指出缺口，进入独立评审"。

| # | 缺口 | 是否影响科学归因 | 我的判断 |
|---|---|---|---|
| G-1 | **同账户代理**：worker 若与某对端同安全主体，可请求其代读 $P$ | **取决于 attempted claim** | **需睫裁定** |
| G-2 | **隐蔽通道**：白名单通道的时序/大小侧信道 | 取决于 claim 精度要求 | **需睫裁定** |
| G-3 | **Reset 后的第三方残留**（系统缓存、文件系统日志） | 可能影响 L2 | **未解决，需独立评审** |
| G-4 | **元数据可见性**：`stat` 类探测即使不能读内容也可能泄漏"存在" | 取决于 claim | **需睫裁定** |
| G-5 | **受限令牌的实际强度**：未实测 | 未知 | **需实测，本轮不测** |

**这五项我一个都不声称已解决。** 其中 G-1 与 G-3 是**与 Linux 分析中同名的两个缺口**——换个平台，它们没有消失。

## 6 · 与 G-2 三段结论的对应

```text
G2_DIRECT_BOUNDARY          = CANDIDATE IDENTIFIED（本设计给出了具体候选：inherit=FALSE + 受限令牌 + DACL）
G2_INDIRECT_CHANNEL_CONTROL = NOT ESTABLISHED（白名单缩小了面，但 G-1/G-2 未解决）
G2_END_TO_END               = NOT ESTABLISHED（不变）
```

**本设计改善的是第一段，不改善第二段。** 我不把"通道白名单"说成"间接通路已控制"——白名单**限制了已声明的通道**，但没有证明**不存在其他通路**。

## 10 · 一句话总结

**最小新增只有两处**：创建时 `inherit=FALSE`（或显式白名单），以及 worker 受限令牌。

**其余全部复用现有组件。** 不需要重造 RC11 和 Q3。

**但 G-1（同账户代理）与 G-3（Reset 后第三方残留）两个缺口仍在，且与 Linux 分析中的同名缺口一致——换平台不会让它们消失。**
