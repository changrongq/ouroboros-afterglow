## 一 · 方案定位：SQLite 承担什么、不承担什么

```text
⇒ 【核心区分，先写在最前】：

   | 层面 | 由谁承担 | 是否等于 P4 的 COMMITTED |
   |---|---|---|
   | 单条记录的物理落盘 | SQLite 事务 | **否** |
   | 多条写入的原子性 | SQLite 事务 | **否** |
   | 崩溃后数据库可打开 | SQLite 恢复 | **否** |
   | 记录按 §2 可完整解析 | §2 编码校验 | C1 |
   | 摘要可被独立重算一致 | 独立期望来源 | C2 |
   | 另一次启动可再读到 | C3 | C3 |
   | 无 PENDING_* 标记 | C4 | C4 |
   | 前驱满足 C1–C4 | C5 | C5 |
   | **历史范围未被截断** | **受信承诺（B2-3）** | **不在 C1–C5 内** |

   ⇒ 【结论】：SQLite 事务提交解决的是**前五行**，
     而 P4 的 `COMMITTED` 是**六行到八行**的事。
   ⇒ 两者【不同层面】，不得互相替代。
```

### 1.1 为什么这里必须写清"不等于"

```text
⇒ 凌翼原文的三条边界，我逐条接受并落到判定上：

   (1)「SQLite 事务提交不自动等于 P4 定义的可信 COMMITTED」
       ⇒ 采纳。本文所有判据【均不引用】SQLite 事务成功作为 C1–C5 依据。

   (2)「数据库能够恢复，不等于权威绑定历史完整」
       ⇒ 采纳。数据库能打开只说明"文件还在"，
         不说明"该有的记录一条不少"。
       ⇒ 完整性由 B2-3 的受信承诺回答，不由数据库自答。

   (3)「不得把数据库自身的最后一条记录，
       直接当作证明历史没有被截断的独立依据」
       ⇒ 采纳，且这条与我已有的 P4-2.5(b)(iv) 完全同形：
         「不被被恢复对象单独改写：即不能只由同一个待验证的
          历史文件自称完整」。
       ⇒ 故 `SELECT max(seq) FROM records` 【不得】作为完整性依据。
```

## 二 · Windows 适用性分析

### 2.1 为什么 SQLite 在 Windows 单机范围内可用

| 需求 | SQLite（WAL + FULL）的对应能力 | 局限 |
|---|---|---|
| 多条写入的原子提交 | `BEGIN IMMEDIATE … COMMIT` 单事务 | 仅限单连接/单进程语义 |
| 崩溃后一致性 | WAL 恢复，未提交事务不生效 | **依赖底层文件系统与磁盘** |
| 单合法写入者 | 见 2.2 | SQLite 本身允许多连接，须额外约束 |
| 追加式语义 | 用表约束 + 禁止 UPDATE/DELETE 表达 | **SQLite 不强制**，须由应用层或触发器保证 |
| 不引入分布式选举 | 无网络、无多主 | 符合 |

```text
⇒ 【结论】：在本机范围内，SQLite 能承担"原子性 + 可恢复"这两件事，
   且【不需要我重造事务与崩溃恢复机制】——这正是凌翼要求的第 1 条。
```

### 2.2 单合法写入者：这是约束，不是 SQLite 的默认行为

```text
⇒ 【必须写明】：SQLite 允许多个连接同时写（WAL 下写者互斥但仍可多连接）。
   ⇒ 它【不提供】"只有一个合法业务写入者"的保证。
   ⇒ 该保证必须由【外部机制】提供：

   | 层 | 机制 | 对应既有条款 |
   |---|---|---|
   | 进程级 | 单实例锁（§4 的 P5 独占） | `§4 4.4` |
   | 线程级 | mutex 所有权 ≠ 签发资格 | `§4 4.4` 事实 1 / T1 |
   | 文件级 | 数据库文件与 -wal / -shm 的 ACL | 见 2.3 |
   | 应用级 | 只开放一个写连接；只追加 | 见第三节 |

   ⇒ 【顺序不能颠倒】：P5 的独占必须先成立，
     否则 SQLite 的多连接能力会【削弱】而非增强"单一权威"。
```

### 2.3 需要进入权限与恢复边界的文件（凌翼边界第 3 条）

```text
⇒ 【WAL 模式不只一个文件】。至少这些都要进同一权限边界：

   | 文件 | 作用 | 丢失后果 |
   |---|---|---|
   | `<db>` | 主库 | 全部丢失 |
   | `<db>-wal` | 未合并的已提交页 | **已 COMMIT 但未 checkpoint 的记录会消失** |
   | `<db>-shm` | 共享内存索引 | 可重建，但读写期间必须一致 |
   | `<db>-journal` | 回滚日志（非 WAL 模式时） | 回滚失败 |

   ⇒ 【要害】：**WAL 文件是已提交数据的载体之一**。
     只备份主库、丢下 -wal，会得到一个"看起来正常但少了尾部"的库。
   ⇒ 这正是凌翼第 3 条要防的情形，也是我把"范围完整性"
     交给 B2-3 而不是交给数据库自答的原因。

   ⇒ 【Windows ACL 要求】：
     · 整个目录（含 -wal / -shm）对业务写入者只给"追加记录所需"的最小权限；
     · 对受信承诺登记（B2-3）的存储【另设边界】，业务写入者不可写；
     · 二者不得放在同一可写目录下。
```

## 三 · 原子事务边界

### 3.1 一个事务 = 一个逻辑提交单元

```text
⇒ 【定义】：一个 SQLite 事务【至多】对应一个逻辑提交单元。
   ⇒ 不得把"分配 epoch + 登记身份 + 授予资格"塞进同一事务后
     宣称"它们一起成立了"。它们是**三个不同对象**，
     各有自己的 C1–C5 判定。

⇒ 【允许的形态】：
   · 一条记录 + 它的准备记录结案标记 ⇒ 同一事务
     （因为它们描述同一次尝试的结局）
   · 跨对象的多条记录 ⇒ 【分开事务】，各自 COMMITTED 或各自 NOT

⇒ 【理由】：把多对象打包进一个事务，会让"部分成功"变得不可表达，
   而 §5 恰恰要求能在半写状态【保留证据并 STOPPED】。
   ⇒ 打包会把"可观测的失败"变成"不可观测的消失"。
```

### 3.2 三条禁止

```text
⇒ (P1) 禁止在事务内做【跨对象】的读取后写入决策。
   ⇒ 例："在事务里算出 max(epoch) 然后插入" ——
     这依赖事务内可见的历史，而历史的完整性由 B2-3 判，不由事务判。
   ⇒ 正确做法：先按 §5 六 (a)(b)(c)(d) 判结案与 max，【再】进入写事务。

⇒ (P2) 禁止用 `INSERT OR REPLACE` / `ON CONFLICT DO UPDATE`。
   ⇒ 历史是追加式的；替换会使 C5（前驱链）失去意义。
   ⇒ 需要"纠正"时，追加新记录，不覆盖旧记录（承 §5 L223-226）。

⇒ (P3) 禁止把 `PRAGMA integrity_check` 的结果当作范围完整性依据。
   ⇒ 它说明"页结构没坏"，不说明"记录没少"。
   ⇒ 这是凌翼第 3 条的同一形状：【结构完好 ≠ 内容未被截断】。
```

## 四 · 失败时序分析

```text
⇒ 【方法】：对每个时点假设"在此处断电/崩溃"，问两件事：
   (i) SQLite 恢复后看到什么？
   (ii) §5 的判定器应当得出什么结论？

⇒ 记 T0 = 事务开始，T1 = COMMIT 返回，T2 = checkpoint 完成。
```

### 4.1 逐时点

| 时点 | 崩溃后 SQLite 所见 | 记录状态 | 判定器应得结论 |
|---|---|---|---|
| T0 之前 | 无该记录 | 不存在 | 该次尝试无痕迹 ⇒ 不得据此签发 |
| T0..T1 之间 | 事务未提交 ⇒ 回滚 | **不存在** | 无记录 ⇒ **NOT_COMMITTED** |
| 恰在 T1 前后（**原子点**） | 要么全有、要么全无 | 二值 | 全有 ⇒ 进入 C1 校验；全无 ⇒ NOT_COMMITTED |
| T1 之后、T2 之前 | 记录在 **-wal** 中 | 存在（未 checkpoint） | 可读 ⇒ 走 C1–C5 |
| T2 之后 | 记录入主库 | 存在 | 同 T1 之后 |

```text
⇒ 【关键结论 1】：T0..T1 之间崩溃 ⇒ 记录【完全不存在】。
   ⇒ 这不是"写了一半的坏记录"，是"什么都没有"。
   ⇒ 故 §5 的 PENDING 状态【不是】由崩溃产生的 ——
     它必须由实现【显式写入】一条 PENDING 记录才存在。
   ⇒ 【这条很重要】：它意味着"崩溃 ⇒ PENDING"是错的推理。
     要么什么都没留下（NOT_COMMITTED），
     要么留下一条显式 PENDING（可观测、可 STOPPED）。
```

```text
⇒ 【关键结论 2】：T1 之后、T2 之前崩溃 ⇒ 记录在 WAL 里。
   ⇒ 若只恢复主库，这条记录【看起来从未存在】。
   ⇒ 【这正是"范围完整性"必须独立于数据库的证据】：
     数据库自己无法区分"从未写过"与"写过但 WAL 丢了"。
   ⇒ 故 B2-3 的受信承诺必须能回答：
     "至 seq=N 为止应当存在"，从而暴露 N 之后的缺失。
```

### 4.2 一类特殊失败：COMMIT 返回了，但落盘未完成

```text
⇒ 【这是凌翼那条技术依据直接指向的情形】：
   synchronous=FULL 在提交时做额外同步以增强持久性，
   但这依赖于【实际文件系统与底层存储行为】。
   ⇒ 意味着：COMMIT 返回成功 ⇒ 逻辑提交成立；
     但【不保证】断电后它一定还在（取决于磁盘缓存是否真的落盘）。

⇒ 【本设计的态度】：不试图证明这一层，而是【让它可被发现】。
   ⇒ 即：若该记录实际丢失，B2-3 的受信承诺会显示缺口 ⇒ STOPPED。
   ⇒ 【不主张】"已经解决断电安全"。
     这句话我写在这里，也写进 §0 的未证明清单（见第六节）。
```

## 八 · 一句

```text
⇒ 这个方案最容易被我写成的样子是：
   "用了 SQLite，所以原子性和崩溃恢复有了"。
   ⇒ 那句话把【工具能力】当成了【我们的保证】。

⇒ 实际上 SQLite 给我的只有一件事：
   多条写入要么都发生要么都不发生，且崩溃后不会留下半条。
   ⇒ 而 P4 要的 COMMITTED 里，有一半（C2 的独立期望来源、
     范围完整性）【完全不在数据库能回答的范围内】。
   ⇒ 这也是为什么 B2-3 不是"配置问题"，是必须要独立成立的东西。
```
