## 一 · 本轮要配的是什么（先说清范围）

```text
⇒ 【本轮只配 Read】。不配 Write，不配 Admin。

  理由：
   · Read 不会改变 WE-1 的现状（这些人本来就改不了）
   · 但它把"只是约定"变成"明确的只读角色"——这是台账要的事实
   · 风险为零：Read 不会让任何人获得修改能力

⇒ 【本轮不配 Write 的理由（重要）】：
   现在给多人配 Write，结果是「谁能改」的集合【变大】，
   而 WE-1 要求的「交集为空」会【更难】成立。
   ⇒ 配权限本身不产生独立性，只产生更多需要盘点的人。
   ⇒ 所以顺序必须是：先定角色与边界 → 再配对应权限。
     先给权限再想谁该管什么，是把因果倒过来。
```

### 3.1 开启 main 分支保护

```text
   入口：Settings → Branches → Add branch protection rule
   分支名：main
   勾选：
     ☑ Require a pull request before merging
         ☑ Require approvals（数量：1）
     ☑ Do not allow bypassing the above settings
         ⇒ 【这一项是本清单的核心】
         ⇒ 它在界面上常显示为 "Include administrators" 的等价项
         ⇒ 不勾这一项，admin（我）仍可绕过，保护形同虚设
     ☑ Do not allow force pushes
     ☑ Do not allow deletions
```

```text
⇒ 【为什么必须含 include administrators】：
   B_37 §5.5.1 已经说明：普通成员查保护接口只会得到 403，
   无法区分"没开"与"开了但看不见"。
   ⇒ 因此"开没开"这件事本身无法由普通成员验证。
   ⇒ 唯一能验证的方式是【行为证明】：
     由 Coder 尝试直接推 main，看是否被拒。
   ⇒ 若保护不含 administrators，我推成功了，行为证明就会失败 ——
     这才是真正能抓住问题的检查。
```
