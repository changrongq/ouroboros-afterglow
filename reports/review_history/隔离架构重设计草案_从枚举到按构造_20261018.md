## 1 · 为什么换路线（不是因为我们失败了）

### 1.1 旧路线（Option C）：**事后枚举证明**

```text
进程已运行 → 枚举它持有的每个句柄 → 逐一证明"这个不是受保护对象" → 证明枚举覆盖完整
```

**卡死点是一个结构性矛盾**，不是工程细节：

> 要证明 $\forall h \in E,\ \neg T(h)$ 等价于"不存在目标句柄"，必须同时证明 $E = H$（观测集 = 全部持有集）。
> 而 $H$ 在枚举过程中**会变**。

我在草案里给过反例 A：枚举器越过某索引后 worker 新取得的目标句柄不在 $E$ 内，而它**是**目标。**这不能靠"枚举更仔细"消除**——它是枚举动作本身的非原子性。

### 1.2 新路线：**按构造建立边界**

```text
进程创建之前/创建瞬间 → 限制它能获得什么 → 证明该限制在要求的时间窗内持续成立
```

**关键区别**：

| | 事后枚举 | 按构造 |
|---|---|---|
| 需要证明 | $E = H$（观测完备性） | 边界持续有效（能力可授予性） |
| 时间性质 | 需要"某一瞬间的完备快照" | 可以是一个**区间性质** |
| 失败模式 | 未知即不可判 | 越界即拒绝 |

**这不是说新路线更容易。而是它把一个"时间点完备性"问题换成了一个"时间区间不变性"问题**——后者在操作系统里有既有机制可依托。

## 2 · 威胁模型（必须先写清，否则后面全是空话）

### 2.1 我们要防的是什么

| 编号 | 威胁 | 说明 |
|---|---|---|
| **T-1** | 业务 worker 持有受保护对象的可读句柄 | 它能读取/写入本应被隔离的数据 |
| **T-2** | 业务 worker 获得**继承来的**不当能力 | 从父进程继承 |
| **T-3** | 业务 worker 在运行期间**新取得**受保护对象访问 | 通过已知路径（文件系统、共享内存、命名管道等） |
| **T-4** | 业务 worker 通过**通信通道**让别的进程替它取得 | 代理攻击 |
| **T-5** | 对象替换 / 符号链接 / 重解析点绕过 | 名字没变，对象变了 |

### 2.2 我们不在此声称能防的

- **不防**：恶意内核代码、驱动、调试器附加（需更高权限假设，另议）
- **不防**：物理访问
- **不声称**：本草案能证明"用户态永远不可能做到"，那是另一类主张

## 3 · 候选机制（全部是候选，不是已成立的安全保证）

凌翼明确要求：**Windows 的句柄继承限制、访问控制或受限令牌，单独任何一项都不足以自动证明持久隔离。**

### M-1 · 显式句柄继承控制

> **勘误（2026-10-18，凌翼要求修订，已实测）：** 本节原标题写作
> `bInheritHandles=FALSE + PROC_THREAD_ATTRIBUTE_HANDLE_LIST`，**这是一个不存在的配置**。
> 驱动 `afterglow_harness/c_verify_m1_inherit_premise.py` 实测本机：
>
> | 配置 | 结果 |
> |---|---|
> | `inherit=FALSE`，无列表 | `ok=True err=0` 有效 |
> | `inherit=TRUE` + `HANDLE_LIST` | `ok=True err=0` 有效 |
> | **`inherit=FALSE` + `HANDLE_LIST`** | **`err=87`（`ERROR_INVALID_PARAMETER`）不合法** |
>
> 正确表述只有两种：
> **(a)** `inherit=FALSE`，不给列表 ⇒ **什么都不继承**；
> **(b)** `inherit=TRUE` + `HANDLE_LIST` ⇒ **只有列出的句柄继承**。

- **能回答**：T-2（继承）——配置 (a) 全部切断，(b) 精确白名单
- **不能回答**：T-1/T-3/T-4/T-5
- **前提**：(a) 无需列表；(b) 必须显式列出允许继承的句柄
- **已实测**：三种组合的实际行为见上表（本机验证，非读文档）
- **未证明事项**：配置 (b) 下列表外的句柄是否**绝无**继承路径（实测仅证明了配置合法性，未证明内核的完备性）

### M-2 · 受限令牌（Restricted Token / `CreateRestrictedToken`）

- **能回答**：部分 T-1/T-3（降低能力上限）
- **不能回答**：时间区间内的不变性；且受限令牌**不等于**不能通过共享通道
- **前提**：显式禁用组、降低完整性级别
- **未证明事项**：受限令牌下是否仍可通过某种 IPC 取得目标访问

### M-3 · 强制完整性控制（MIC，低/中完整性级别）

- **能回答**：写入类威胁；读取类取决于标签
- **不能回答**：低完整性进程仍可读未标记对象
- **未证明事项**：`NO_WRITE_UP` 对目标对象的实际效果

### M-4 · DACL 显式拒绝（已有 Q3 组件 `q3_dacl.py`）

- **能回答**：T-1/T-3（对特定路径）
- **不能回答**：T-5（对象替换）、T-4（代理）
- **未证明事项**：ACL 在**整个 worker 生命周期**内不被改动

### M-5 · 受限执行环境（Job Object + UI 限制 + 必要时容器）

- **能回答**：更宽范围
- **不能回答**：需要明确"更强环境"的边界在哪
- **注意**：**成本与可复核性**——越强的环境，越难向评审者证明其性质

## 4 · 新路线仍需回答的三个问题（**与 Option C 同样的三问，不再回避**）

凌翼在 Option C 裁决里要求定义三件事。**新路线同样要定义，只是含义变了**：

| 问题 | Option C 下的含义（未能定义） | 新路线下的含义 |
|---|---|---|
| **完整性 / OBSERVATION_BOUNDARY** | 枚举是否覆盖全部句柄 | **边界是否覆盖全部能力授予路径** |
| **可信执行主体 / SNAPSHOT_COVERAGE** | 快照是否原子 | **谁在施加边界？施加者本身是否可信？** |
| **时间范围 / TIME_SCOPE** | 快照何时有效 | **边界从何时生效到何时失效，期间通过什么机制保证不变** |

### 4.1 我认为最可能卡住的地方（提前说，不等到实现阶段）

**卡点候选 1：启动前的既有能力**
在施加边界**之前**，进程可能已经持有能力。要证明"创建即刻生效"，必须证明存在一个 $t_0$ 使得边界在 $t_0$ 之前就已生效，而进程在 $t_0$ 之后才获得任何能力。

**这在 Windows 上是否可达，我不知道。** 若不可达，**新路线也会卡在这里**。

**卡点候选 2：施加者可信性**
若边界由本账户施加，则本账户可撤销它。那么"持续成立"依赖于**本账户不会撤销**——这是一个**策略假设**，不是技术保证。

**若设计只能到"策略假设"，必须明说，不能包装成技术隔离。**

**卡点候选 3：整个有效时间窗**
worker 是**持久**的。若它运行 24 小时，边界要成立 24 小时。任何时刻的一次越界都使保证失效。

**这与"某一时刻枚举干净"是完全不同的强度要求。**
