## 0. 为什么这不是"再多写点代码"

Phase A 的 reset 层是**逻辑层**：`reset.py` 的 `restart_worker()` / `access_probe()` 显式 `raise NotIsolatedError`——它**诚实拒绝假装已完成隔离**。SPEC §16.1.1 的原话是：

```text
记账隔离 ≠ 眼睛隔离。
不许把"没写进账本"，当成"没看见"。
```

Phase A 冻结的是**尺子（reference harness）**，且授权范围 = `HARNESS_VALIDATION`（逻辑层）。现在的 Q3 要把"眼睛隔离"真正落地：**一个被禁止的访问，必须被操作系统真正拒绝，并被独立观察到。**

## 1. 本机环境实测（先说约束）

```text
python 3.11.15 / Windows 10
has os.fork            = False        （无 fork）
has os.chmod           = True 但…
advapi32/kernel32      = via ctypes 可用（CreateRestrictedToken / SetSecurityInfo / CreateFileW）
pywin32                = 未安装
icacls                 = 可用（内置）
```

**关键实测（这条很重要）：**

```text
os.chmod(file, 0) 之后：
  st_mode 变为 0o100444（看起来"只读"）
  但 file.read_text() 仍然成功 —— payload 照读
⇒ 在 Windows 上，POSIX 风格的 chmod 是【装样子】：
  代码里看起来隔离了，眼睛其实没被挡住。
```

这正是 §16.1.1 要防的陷阱。**如果我们用 `chmod(0)` 当隔离机制，我们会重犯"记账隔离当眼睛隔离"**。所以机制必须换。

**真实拒绝实测（可用的机制）：**

```text
icacls <file> /deny <USER>:(R)
⇒ 之后 read 抛 PermissionError [Errno 13] Permission denied
⇒ 即使是 owner，deny ACE 依然生效（deny 优先于 allow）
```

即：**Windows 上，"眼睛隔离"要落成真实 DACL deny ACE（或受限 token）**，而不是 chmod。

## 2. 提案：三层隔离 + 三向 witness

### 2.1 三个隔离面（对应 SPEC 的三条 NO_ACCESS）

```text
I-1  episode isolation     : 新 worker 进程 NO_ACCESS 真实 episode payload
I-2  substrate isolation   : 新 worker 进程 NO_ACCESS 真实 registered substrate
I-3  reset isolation       : 新 worker 进程 NO_ACCESS 真实 reset（历史/ledger/oracle）
```

### 2.2 "真实"vs"沙箱"的判据

Phase A 跑在 `tempfile.mkdtemp()` 沙箱里，那些**不是**真实 substrate/episode。Q3 的隔离对象是**真实对象**（未来 Phase B 会用到的、被授权的真实 literal store / AFTERGLOW_SUBSTRATE / episode）。

冻结前必须钉死：

```text
REAL_OBJECT_SET = { 真实 literal store, 真实 substrate, 真实 episode payload, 真实 reset 产物 }
判据             : 任何对 REAL_OBJECT_SET 成员的访问尝试
证据             : 该尝试被 OS 拒绝（PermissionError / ERRNO 13），由【独立观察者】记录
```

### 2.3 进程替换（真·fresh worker）

`PROCESS_REPLACE_PRESERVE_FILES_V1` 的"进程替换"要求：新 worker 是**真正的新进程**，且**能力被削减**。落法（Windows）：

```text
1. 父进程（controller）在受控目录创建真实对象，并对新 worker 的访问【deny】。
2. 父进程 spawn 一个【全新子进程】worker（subprocess，独立 PID）。
3. worker 尝试访问真实对象：
      - 成功 -> 隔离失败（FAIL CLOSED）
      - PermissionError -> 该访问被 OS 拒绝（witness）
4. 父进程独立记录 worker PID、启动时间、访问尝试、拒绝结果。
```

**"fresh process"的机器证据**：worker 报告自己的 PID，父进程核对 `pid != parent_pid` 且 `pid` 在父进程 spawn 之前不存在。

### 2.4 三向 witness（结构化、fail-closed）

```text
clear-side   : 声明的 counterfeit signal 确实被【移除】（不是"没人看"，是"没了"）
preserve-side: 声明的 registered substrate 确实【存活】（字节级 handoff == restored）
access-side  : 一个真实 forbidden access 确实被【拒绝】（OS errno 证据，非"没试"）
```

三向**任一**不是"跑过且通过" => RESET = INVALID。三态语义沿用 RC11 铁律：

```text
True        = 跑过且通过
False       = 跑过且失败
UNEVALUATED = 未到达（前序已失败）—— 绝不默认 True
```

### 2.5 access-side 必须区分三种状态（防"没试"冒充"被拒"）

这是本层最容易再犯的错。access-side witness 必须区分：

```text
ACCESS_DENIED     : 尝试了，OS 拒绝   -> 隔离成立 ✅
ACCESS_GRANTED    : 尝试了，OS 放行   -> 隔离失败 ❌（FAIL CLOSED）
ACCESS_NOT_ATTEMPTED : 没试          -> 未评估，绝不算通过 ❌
```

`ACCESS_NOT_ATTEMPTED` 与 `ACCESS_GRANTED` 都不得被当成"隔离成功"。

### 6.1 PoC 实测暴露的两条真实 OS 性质（重要，写进契约）

**性质 A：`os.chmod(0)` 在 Windows 上【不拒绝】。**
```
chmod(file, 0) -> st_mode=0o100444（看起来只读），但 read 仍成功。
```
⇒ 若用 chmod 当隔离，就是重犯"记账隔离 ≠ 眼睛隔离"。**必须用 DACL deny ACE。**

**性质 B：deny ACE 是【粘性】的——连 owner 都无法再改 ACL 或读回。**
```
icacls <f> /deny USER:(R)
  -> read 抛 PermissionError
  -> 之后 icacls <f> /remove:d USER 也失败（rc=5 拒绝访问）
  -> 再 deny 也失败
```
⇒ 这**更强**：真隔离不是可随手撤销的 flag。代价是——**控制器必须"先读、后上锁"**：
```
capture_handoff（读字节）-> deny（上锁）-> spawn fresh worker（被拒）-> capture_restored
（restored 从已捕获的 handoff 字节核对，不再依赖事后读被锁文件）
```
这与 reset 协议天然吻合。

### 6.2 契约新增：access-side 三态（防"没试"冒充"被拒"）

```text
ACCESS_DENIED        : 尝试了，OS 拒绝   -> 隔离成立 ✅
ACCESS_GRANTED       : 尝试了，OS 放行   -> 隔离失败 ❌（FAIL CLOSED）
ACCESS_NOT_ATTEMPTED : 没试 / 非干净拒绝 -> 未评估，绝不算通过 ❌
```

只有 `ACCESS_DENIED` 属 `ACCESS_ISOLATION_OK`。任何其他结果（含 `OSError` 非权限错误）都**不是通过**。
