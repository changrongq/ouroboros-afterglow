## 零 · 这份表要解决的问题

```text
⇒ 【旧做法的问题（睫 格一）】：
   每份文档在自己正文里写「固定点 = 某 blob」。
   ⇒ 但文档一改，它写的那个 blob 立刻失效。
   ⇒ 于是出现「两份文档各自写了固定点，而两份文档都不在自己写的固定点里」。
   ⇒ 这不是谁抄错，是【自指结构必然失败】：
     任何自称固定点的文档，都晚一步。
```

```text
⇒ 【本表的做法】：
   ⇒ 值【只在这一次集中】。
   ⇒ 被登记的文件【不写自己的 hash】。
   ⇒ 三方核对文件，就来读这张表。
   ⇒ 【表自己的 hash 无法写在表里】——自指环依然存在，
     所以表的 blob 只能由 Coder 计算后【通过消息】报给三方。
```

## 一 · 值的语义（必须先读这一节）

```text
⇒ 本表的 hash 一律是 【git blob SHA-1】：

     git rev-parse <commit>:<path>

⇒ 【不是】文件系统 sha256
⇒ 【不是】commit sha
⇒ 【不是】目录树 sha

⇒ 取值为：commit a5a9b67 那棵树里的每个文件。
⇒ 若你手上的 blob 与本表不一致，【先查你读的是哪个 commit】。
```

```text
⇒ 【与旧文书的兼容】：
   旧文书里出现的 `blob d4c7ce05…` 之类，也是同一口径（git blob）。
   ⇒ 可以直接与本表对照，无需换算。
```

## 三 · 本表自己的 blob（不能写在本表内）

```text
⇒ 【这一格必须由 Coder 用消息报给三方】，因为：
   表算自己的 blob ⇒ 算之前要先把 blob 写进表 ⇒ 写进去后 blob 又变。
   ⇒ 自指环无法在文件内部闭合。
```

```text
⇒ 【所以本文件【不含】自己的 blob，这是【故意留空】，不是遗漏】。

⇒ 表的当前 blob 由 Coder 在交付消息里给出，形如：
     FILE_REGISTRY_BLOB = <git rev-parse <commit>:reports/review_history/阶段B_30_文件版本登记表_Coder_20261111.md>

⇒ 三方核对时：
   ① 先用消息里的 blob 核对表本身
   ② 再用表内的值核对各文件
   ③ 两步都过，才等价于「这批文件在该 commit 上彼此自洽」
```

```text
⇒ 【必须说清的限制】：
   消息里的 blob 与表内的值，【都来自 Coder 本地的那棵树】。
   ⇒ 如果 Coder 算错，两张表会一起错，且彼此自洽。
   ⇒ 所以【核对仍须三方独立从远端跑一遍】，
     不能以「表内自洽」替代「独立复现」。
   ⇒ 自洽 ≠ 正确。
```

## 四 · 更新规则（写给下一个我）

| 规则 | 内容 |
|---|---|
| R1 | **被登记文件内不得再写自己的 blob/sha**。已写的按「历史保持它是历史」处理：保留原句，但加一行指向本表。 |
| R2 | 任何文件改动后，**同一提交内**更新本表该行（blob ＋ 变动历史追加）。 |
| R3 | 变动历史**只追加不删除**，用 `→` 分隔。 |
| R4 | 新增文件 → 新增一行；删除文件 → 该行保留，变动历史写「已删除（保留历史）」。 |
| R5 | 本表 blob **永远不进本表**，只走消息。 |
| R6 | 本表值一律 `git rev-parse <commit>:<path>`，措辞不得简写为「hash」而不注明口径。 |
