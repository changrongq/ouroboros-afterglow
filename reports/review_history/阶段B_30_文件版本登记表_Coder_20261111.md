## 零 · 这份表要解决的问题

```text
⇒ 【旧做法的问题（睫 格一）】：
   每份文档在自己正文里写「固定点 = 某 blob」。
   ⇒ 但文档一改，它写的那个 blob 立刻失效。
   ⇒ 于是出现「两份文档各自写了固定点，而两份文档都不在自己写的固定点里」。
   ⇒ 这不是谁抄错，是【自指结构必然失败】：
     任何自称固定点的文档，都晚一步。
```

```text
⇒ 【本表的做法】：
   ⇒ 值【只在这一次集中】。
   ⇒ 被登记的文件【不写自己的 hash】。
   ⇒ 三方核对文件，就来读这张表。
   ⇒ 【表自己的 hash 无法写在表里】——自指环依然存在，
     所以表的 blob 只能由 Coder 计算后【通过消息】报给三方。
```

## 一 · 值的语义（必须先读这一节）

```text
⇒ 本表的 hash 一律是 【git blob SHA-1】：

     git rev-parse <commit>:<path>

⇒ 【不是】文件系统 sha256
⇒ 【不是】commit sha
⇒ 【不是】目录树 sha

⇒ 若你手上的 blob 与本表不一致，【先查你读的是哪个 commit】。
```

## 三 · 本表自己的 blob（不能写在本表内）

```text
⇒ 【这一格必须由 Coder 用消息报给三方】，因为：
   表算自己的 blob ⇒ 算之前要先把 blob 写进表 ⇒ 写进去后 blob 又变。
   ⇒ 自指环无法在文件内部闭合。
```

```text
⇒ 【所以本文件【不含】自己的 blob，这是【故意留空】，不是遗漏】。

⇒ 表的当前 blob 由 Coder 在交付消息里给出，形如：
     FILE_REGISTRY_BLOB = <git rev-parse <commit>:reports/review_history/阶段B_30_文件版本登记表_Coder_20261111.md>

⇒ 三方核对时：
   ① 先用消息里的 blob 核对表本身
   ② 再用表内的值核对各文件
   ③ 两步都过，才等价于「这批文件在该 commit 上彼此自洽」
```

```text
⇒ 【必须说清的限制】：
   消息里的 blob 与表内的值，【都来自 Coder 本地的那棵树】。
   ⇒ 如果 Coder 算错，两张表会一起错，且彼此自洽。
   ⇒ 所以【核对仍须三方独立从远端跑一遍】，
     不能以「表内自洽」替代「独立复现」。
   ⇒ 自洽 ≠ 正确。
```

```text
⇒ 【知微 5.3 澄清，我照录并采纳】：
   ① 「不把文件的完整自身 hash 写进被哈希的原文」是合理的，
      但【不要推广成「凡是引用固定点都矛盾」】。
   ② `l1_parser.py` 引用 B_23 规范 blob、`run_a16.py` 引用 B_24 证据 blob，
      都是【引用另一个对象】，不构成自身哈希循环。
      ⇒ 这些必要的固定依赖绑定【不应为了消自指而一并移除】。
   ③ 后续报告可以引用此前的固定实现；只需分清
      「【实现固定点】」与「【报告自身版本】」，前者照常可写。
   ④ 文件在首次提交前【可以】计算 Git blob（按 .gitattributes 的 clean 规则），
      并非「未提交就无法知道 blob」——
      我上一轮写的 `PENDING_FIRST_COMMIT` 措辞过强，此处更正为
      「首次提交前无法确认该 blob 与最终入库对象一致」，故仍以占位待回填。
   ⑤ 本检查器用 `git hash-object`，其「与工作树一致」的准确含义是
      【经仓库属性处理后的 Git 对象一致】，不等于原始磁盘字节逐字节相等。
      若某项测试要求原始字节身份，须另外核对（B_24 运行时另有固定 blob 检查）。
```
