## 剩余维护缺陷：控制器资源释放

### P2 — GetExitCodeProcess 抛异常时，新增查询句柄未被释放

在 `_terminate_and_confirm` 中，OpenProcess 成功取得 hp2 后，GetExitCodeProcess 和 `_close(hp2, "query")` 顺序放在同一 try 中。前者一旦抛异常，后者被跳过；外层 except 会记录错误并继续关闭原进程/线程句柄，却没有释放 hp2。

替身复现：OpenProcess 返回 0x3333；GetExitCodeProcess 抛 RuntimeError；最终成功关闭列表只有 [0x1111, 0x2222]，缺少已获得的 0x3333。退出未确认这一结论仍正确，缺陷是资源泄漏。

建议为成功取得的 hp2 设置自身 try/finally，确保查询失败或抛异常也会尝试释放；或者直接用 spawn 返回的稳定进程句柄完成所需查询，取消这个额外拥有的查询句柄。

### P2 — CloseHandle 的 FALSE 返回被忽略

`_close` 只处理 Python 异常，没有检查 CloseHandle 返回 BOOL。普通 Win32 失败返回 0 时，代码不记录错误码，也不记录释放失败。

替身复现：worker 的等待已确认退出，关闭 pi.hp 返回 0，其余调用成功；函数仍返回 `(True, "; exit code 0x1")`，没有任何释放失败记录。**不能据此说 worker 尚存活**：等待证据已经确认退出。需要区分 `worker_exit_confirmed` 与 `controller_resources_released`，分别报告；若整体成功要求完整清理，则资源释放失败也必须影响整体结果。

建议检查 BOOL 并立即记录 GetLastError，保留逐句柄失败信息，保证一个失败不跳过另一个。CloseHandle 抛异常时同样应进入资源释放失败状态。不要用一个“exited”字段同时承诺进程退出和资源释放都已完成。
