## 零 · HWM 为什么需要"独立记录编码"

```text
⇒ 【它本来只是一个数字】。为什么还要编码？

⇒ 因为一个裸数字无法回答三件事：
   ① 它属于哪个权威域、哪个世代？
   ② 它是谁写的？
   ③ 它有没有被改成另一个"看起来合法"的数？

⇒ 若 HWM 只是 `hwm = 42`，那么把 42 改成 41 或 43
   在数据层面【完全合法】——没有校验，没有归属，没有来源。
   ⇒ 而 HWM 的全部价值就是"它不能随便变"。
```

## 一 · HWM 记录编码

```text
⇒ 【沿用 §2 的编码框架】，与 B2-2 的五类对象同一套规则。
   【新增候选类型】：0x89  TRUSTED_HWM
   （接在 0x87 REVOCATION / 0x88 MAX_SCOPE_SET 之后）
```

### 1.1 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `authority_domain` | str | 所属权威域 |
| `generation` | u32 | 世代 |
| `hwm_value` | u64 | 高水位值 = 已被承诺覆盖的最大 seq |
| `last_commitment_digest` | bytes[32] | 最后一次推进 HWM 的那条 N5 的摘要 |
| `last_commitment_seq` | u64 | 该 N5 的 `commitment_seq` |
| `root_ref` | bytes[32] | 指向信任根（承 §5 二 (r1)(r3)） |
| `hwm_epoch_counter` | u64 | **HWM 自身的推进次数**（从 0 起，每次 +1） |

```text
⇒ 【`hwm_epoch_counter` 为什么必要】：
   若 HWM 只记 `hwm_value`，
   则"回退到同一 range_end 但不同提交历史"无法区分。
   ⇒ 加计数器后，每次推进都留下一个单调递增的痕迹。
   ⇒ 【但它仍然不能防"整个记录一起回滚"】——
     那需要介质独立性（见阶段B_2）。
   ⇒ 它只防"同值不同史"这一种。
```

### 1.2 摘要输入

```text
⇒ 【严格按 §2 2.4】：
   SHA-256( OBJECT_TYPE ‖ FORMAT_VER ‖ OBJECT_TYPE ‖ RESERVED
            ‖ FIELD_COUNT ‖ FIELDS )

   ⇒ OBJECT_TYPE = 0x89（域分离：HWM 摘要不可能与 N5 摘要互换）
   ⇒ FIELDS 顺序即 1.1 表序，不得重排
```

### 1.3 非法反例

| 情形 | 判定 |
|---|---|
| `hwm_value` 小于上一版本 | 非法（违反单调性 D2）|
| `hwm_epoch_counter` 未递增 | 非法 |
| `last_commitment_digest` 不对应任何已存 N5 | 非法 ⇒ `STOPPED` |
| `last_commitment_seq` 与对应 N5 的 `commitment_seq` 不符 | 非法 |
| `hwm_value` > 对应 N5 的 `range_end_seq` | 非法（HWM 不能超过承诺）|
| `root_ref` 无法解析 | 非法 ⇒ `STOPPED` |
| 存在两条 `hwm_epoch_counter` 相同的 HWM 记录 | 非法（分叉）|

```text
⇒ 【最后一条 —— 分叉检测】：
   若出现两条 counter 相同的 HWM 记录，说明有分叉写入。
   ⇒ 这是【唯一能检出"两个 S 同时写"】的信号。
   ⇒ 但它只能检出【留痕的分叉】；若一份被删掉则检不出。
```

## 二 · 提交时序（按凌翼第四节修订）

```text
⇒ 【裁定原文】：
   「S 根据旧可信状态计算新的承诺与高水位；
    在同一受信事务中提交 N5 和 HWM；
    只有该事务完成并通过核验，二者才共同成为新的可信状态。
    不得把同一事务内部的写入顺序描述成两个已经分别生效的提交事件。」
```

### 2.1 我原来错在哪

```text
⇒ 【我原 H3 写的】：
   「HWM 只在【N5 成功提交之后】推进
    顺序：业务 COMMIT → N5 写入 → N5 提交成功 → HWM 推进」

⇒ 【错在哪】：
   这句话描述的是【两个提交事件】。
   而设计里它们是【同一个事务里的两次写】。
   ⇒ 同一个事务里不存在"N5 先提交成功、然后 HWM 推进"这种时序。
   ⇒ 我把【事务内的写顺序】写成了【提交顺序】。
   ⇒ 若有人按我的原文实现，会真的做成两个事务 ——
     而那正是会产生"HWM 已推、N5 未写"或反向窗口的原因。
```

### 2.2 修正后的时序

```text
⇒ 【正确表述】：

   T0  读取旧可信状态（旧 HWM 记录 H_old，最新 N5 记录 C_old）
   T1  根据旧状态计算新承诺 C_new 与新高水位 H_new
   T2  ┌─ 单一受信事务 BEGIN IMMEDIATE
       │   INSERT commitment (C_new)
       │   UPDATE hwm SET ... (H_new)
       └─ COMMIT
   T3  事务完成后，回读并核验 C_new 与 H_new 是否一致绑定
   T4  核验通过 ⇒ 二者【共同】成为新的可信状态
```

```text
⇒ 【T2 的关键】：
   两次写【在同一个事务内】，不存在"哪一个先生效"。
   ⇒ 事务提交前：两次写都不可见
   ⇒ 事务提交后：两次写同时可见
   ⇒ 【中间没有第三个状态】。

⇒ 【T3 为什么还需要回读】：
   因为"事务提交成功"不等于"内容正确"。
   ⇒ 回读是 C3（另一次读取）的应用，也是对
     "写进去的和算出来的是否一致"的独立检查。
```

### 2.3 三处必须禁止的表述

```text
⇒ 以下三种说法【都不得】出现在任何实现说明或文档里：

   ✗ "先写 N5，再推进 HWM"
     ⇒ 暗示两个提交事件
   ✗ "N5 提交成功后 HWM 随之推进"
     ⇒ 同上，且暗示有中间态
   ✗ "若 HWM 推进失败则回滚 N5"
     ⇒ 同一事务不可能只失败一半；
       若整个事务失败则两者都没写，不需要"回滚 N5"

   ⇒ 【正确说法】：「在同一受信事务中提交 N5 与 HWM；
     事务成功则二者共同生效，失败则二者均未生效。」
```

### 2.4 事务失败后的状态

```text
⇒ 【事务失败】（磁盘满、进程退出、约束冲突等）：
   | 事实 | 判定 |
   |---|---|
   | C_new 未写入 | 承诺未扩展 |
   | H_new 未写入 | HWM 未推进 |
   | 二者均不可见 | 可信状态 = 旧状态（H_old, C_old）|

   ⇒ 此时【不需要任何补偿动作】——
     状态就是"什么都没发生"。
   ⇒ 业务侧可能已有提交但未锚定 ⇒ `COMMITTED_BUT_UNANCHORED`
     （RE-1），按该情形处置。
```

```text

    则必须另行提交跨介质一致性方案。
```

## 四 · HWM 与 N5 的绑定关系（跨记录一致性）

```text
⇒ 【双向绑定，两侧都要能验】：

   | 方向 | 检查 | 失败判定 |
   |---|---|---|
   | HWM → N5 | `last_commitment_digest` 能解析到一条存在的 N5，且该 N5 的 `commitment_seq == last_commitment_seq` | 非法 ⇒ STOPPED |
   | N5 → HWM | 该 N5 的 `hwm_value` 与当时 HWM 记录一致（由 `hwm_epoch_counter` 定位）| 非法 ⇒ STOPPED |

   ⇒ 【为什么要双向】：
     只查一个方向，可以构造"指向一条旧 N5 的新 HWM"而不被发现。
```

## 六 · 待独立复核的问题

```text
⇒ (Q1) 0x89 是否应作为独立类型，还是归入 0x86 的一个变体？
   ⇒ 我倾向独立，因为 HWM 与 N5 是【不同对象】：
     N5 是"关于历史有多长"的声明，
     HWM 是"我确认过到哪了"的状态。
     ⇒ 而且它们的摘要域必须分离。

⇒ (Q2) `hwm_epoch_counter` 与 N5 的 `commitment_seq`
   是否重复？能否只保留一个？
   ⇒ 它们不同：`commitment_seq` 是 N5 的序号，
     `hwm_epoch_counter` 是 HWM 的推进次数。
     若一次事务推进一次，两者应同步增长 ——
     ⇒ 若是这样，是否就冗余了？请裁定。

⇒ (Q3) 1.3 的"分叉检测"要求扫描全部 HWM 记录，
   但第二节说 hwm 表恒 1 行。
   ⇒ 矛盾：若只有 1 行，如何有两条 counter 相同？
   ⇒ 【我承认这是设计不闭合】。
     可能解法：(a) hwm 表保留历史行（放弃单行）
               (b) 分叉检测另设审计表
   ⇒ 请裁定采用哪个。

⇒ (Q4) T3 回读失败时，事务已提交，
   此时是否要追加 CONTRADICTED 记录？
   ⇒ 见 TSU 架构 3.2，逻辑一致，但需确认适用范围。
```
