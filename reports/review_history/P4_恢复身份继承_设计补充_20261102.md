# 一 · P4-1 · 身份继承

## 1.1 必须显式处理的语义变更

```text
⇒ 凌翼要求：
   「优先采用一个持久的逻辑记录者身份，通过不同 epoch 区分重启世代。
     Coder 必须明确 recorder_id 是否承担这一持久身份。
     如果是，就须在 v0.2 中显式调整原先 '实例身份' 的语义，
     而不能悄悄改变定义。」

⇒ 【核实结果】v0.2 L91 现写：
     recorder_id    记录者实例身份

⇒ 这一语义与 P4-1 不兼容：
   若 recorder_id 是【实例身份】，则重启后新实例必须换新 id，
   于是 authority_record_key = (recorder_id, epoch, seq) 在重启后
   指向【另一个记录者】，而 T-2 要求恢复后的实例
   继承原权威域的持久化身份。

⇒ 因此：本补充【显式】把 recorder_id 的语义从「实例身份」
   调整为「持久逻辑记录者身份」，并引入新的实例标识。
```

## 1.2 调整后的定义（显式，不悄悄改）

```text
EventRecord 定位键仍为三元组，但三项语义调整如下：

  recorder_id    持久【逻辑记录者身份】
                 ⇒ 跨重启【保持不变】。
                 ⇒ 代表「这是哪一个权威域」。
                 ⇒ 不再是「哪一次进程实例」。

  epoch          记录者【启动世代】（重启后递增）
                 ⇒ 语义不变（沿用 v0.1 EPOCH-1）。
                 ⇒ 代表「同一逻辑记录者内的第几次启动」。

  seq            该 epoch 内的单调序号
                 ⇒ 语义不变。
```

```text
⇒ 【新增】实例标识（不进入定位键）

  instance_id    本次进程实例的身份
                 ⇒ 每次启动【必然不同】。
                 ⇒ 【不】进入 authority_record_key。
                 ⇒ 用途：在 RECORDER_STARTED 与诊断中区分实例，
                    但【不】用于构造记录定位键。

⇒ 为什么不让 instance_id 进定位键：
   若它进键，则同一逻辑记录者在不同世代的记录会落到不同键域，
   恢复后无法用同一键语义定位历史记录 —— 与 P4-2 冲突。
```

```text
⇒ 【语义变更的后果，必须写明】
⇒ 旧语义下：recorder_id 变 ⇒ 是另一个记录者。
⇒ 新语义下：recorder_id 不变 ⇒ 仍是同一逻辑记录者，
             即使进程重启、instance_id 改变。
⇒ 因此 v0.2 中凡提到「记录者实例身份」之处，均须改为
   「持久逻辑记录者身份」，并另用 instance_id 表达实例。
⇒ 这不是措辞润色，是【定义变更】。
```

## 1.3 明确不做的事

```text
⇒ 不引入多实例选举（CROSS_AUTHORITY_ELECTION 仍 = NOT DEFINED）。
⇒ 不定义「多个逻辑记录者」之间如何选择权威。
⇒ 同一时刻仍只允许一个逻辑记录者持有绑定写入权（T-2）。
```

# 二 · P4-2 · 历史恢复

## 2.1 恢复依据

```text
⇒ 凌翼要求：
   「最小设计以完整、可验证的持久化事件历史重放为基础，
     恢复 event_id 到权威记录键的既有映射。
     不得以 '最后成功的一次提交' 为规则重选权威记录。
     检查点与增量恢复暂不纳入本版。」

⇒ 本补充据此定义：
```

```text
规则 P4-2.1 · 恢复的输入
  恢复者必须读取【完整的持久化事件历史】，
  并按 (recorder_id, epoch, seq) 排序。

规则 P4-2.2 · 恢复的目标
  从历史中重建 event_id → authority_record_key 的映射。
  ⇒ 该映射必须与崩溃前的映射【逐条一致】。
  ⇒ 不得新增、删除或改写任何一条绑定。

规则 P4-2.3 · 权威记录的判定
  某条 EventRecord 是 event_id 的权威记录 ⟺
     它是历史上【首次】为该 event_id 建立绑定的那条
     （即 BINDING_CONFIRMED 的第一次出现）。
  ⇒ 【禁止】以「最后成功的一次提交」重选权威记录。
  ⇒ 【禁止】以「最新 epoch」重选权威记录。

规则 P4-2.4 · 历史不完整时的处置
  若历史存在缺口、截断或无法验证的段
  ⇒ 视为【恢复失败】，进入停止状态（见 §四）。
  ⇒ 不得用「跳过残缺段继续」消除歧义。
```

## 2.2 为什么禁止「最后成功者」

```text
⇒ 「最后成功的一次提交」是【提交方视角】的说法。
⇒ 它假设：后提交的一定更新、一定更权威。
⇒ 而 D1-1 已定记录不可变：权威记录一旦建立【不可替换】。
⇒ 若允许用「最后一次」重选，等于允许回溯性地改写历史绑定 ——
   直接违反记录不可变性。
⇒ 故本补充明确禁止。
```

# 三 · P4-3 · epoch 继承

```text
⇒ 凌翼要求：
   「恢复后签发新权威事件前，必须建立一个不与历史 epoch 冲突的
     新世代。新世代身份的持久化、唯一性和恢复失败处置，
     都必须有明确规范。不得仅凭进程启动次数或内存计数推断
     持久化 epoch。」
```

```text
规则 P4-3.1 · 新世代的来源
  新 epoch 必须【从持久化的历史中推导】：
     new_epoch = max(历史中该 recorder_id 的所有 epoch) + 1
  ⇒ 必须读取持久化历史，不得用内存计数器。
  ⇒ 不得用「进程启动次数」推断。

规则 P4-3.2 · 唯一性
  同一 recorder_id 下，epoch 值【不得复用】。
  ⇒ 若推导出的 new_epoch 与任一历史 epoch 相同 ⇒ 冲突 ⇒ 恢复失败。

规则 P4-3.3 · 新世代的持久化
  新 epoch 必须先【持久化】并【可验证】，
  之后才允许签发该世代的第一条权威事件。
  ⇒ 顺序不可颠倒。

规则 P4-3.4 · 恢复失败的处置
  若无法确定 max(epoch)，或无法验证新 epoch 未被使用
  ⇒ 恢复失败 ⇒ 进入停止状态（§四）。
  ⇒ 不得「猜一个新 epoch」继续。
```

```text
⇒ 【必须承认的残余】
⇒ v0.1 §6.4 已写明：epoch 分配本身必须原子（读-改-写），
  而当前 harness 无锁、无原子替换。
⇒ ⇒ 因此 EPOCH-1 与本节 P4-3 的【实现前提尚不存在】。
⇒ 本补充只定义规则，不声称可实施。
⇒ 这一条必须保留，不得因为「P-4 补齐了」就当作已具备。
```

# 四 · P4-4 · 恢复期禁止签发

```text
⇒ 凌翼要求：
   「恢复完成前，不得签发新的权威事件。
     恢复所需的记录完整性、身份、历史绑定或独占权若不可确认，
     则进入停止状态。不允许通过猜测或选择最后成功者消除歧义。」
```

```text
规则 P4-4.1 · 恢复期定义
  恢复期 = 从进程启动到【恢复完成】**之前**的全部时间。
  恢复完成的判据（三者全部满足）：
     (a) 历史已完整读取并验证（P4-2.1）
     (b) event_id → authority_record_key 映射已重建并校验一致（P4-2.2）
     (c) 新 epoch 已持久化且可验证唯一（P4-3.1..3.3）

规则 P4-4.2 · 恢复期禁止
  恢复期内【不得】签发任何新的权威 EventRecord。
  ⇒ 包括 WINDOW_CLOSE 等本可作为权威记录的 event_type。

规则 P4-4.3 · 停止状态
  下列任一不可确认 ⇒ 进入 STOPPED：
     · 记录完整性（历史有缺口/截断/无法验证）
     · 身份（无法确定 recorder_id 的持久身份）
     · 历史绑定（映射无法重建或校验不一致）
     · 独占权（无法确认无其他实例在签发，见 §五）
  ⇒ STOPPED 状态下【不得】签发。
  ⇒ STOPPED 状态下【不得】自动恢复为 RUNNING；
     须由外部显式处置。

规则 P4-4.4 · 禁止消除歧义的手段
  【禁止】通过以下任一方式让恢复「成功」：
     · 猜测缺失的历史
     · 选择「最后成功」的记录作为权威
     · 跳过残缺段继续
     · 用新 epoch 覆盖冲突的旧 epoch
```

# 五 · P4-5 · 单一权威写入者

```text
⇒ 凌翼要求：
   「重启恢复不得绕开 T-2 的单一逻辑权威域约束。
     即使恢复者认为原实例已经终止，也不能仅凭这一判断
     宣布互斥成立。缺乏可验证的独占条件时，
     新的权威签发不得开始。
     这一条是规范要求；实际独占强制机制仍属于 P5，
     不因本裁定而宣称已建立。」
```

```text
规则 P4-5.1 · 恢复不豁免 T-2
  恢复者【不因】「我是重启后的实例」而获得独占权。
  ⇒ CONCURRENT_AUTHORITY_INSTANCES = NOT SUPPORTED 仍然适用。

规则 P4-5.2 · 「原实例已终止」不是证据
  恢复者认为原实例已终止 ⇒ 【不构成】独占成立的依据。
  ⇒ 须有可验证的独占条件（例如持久化的独占租约、
     原实例的终止凭证等），本补充【不定义】其形式。

规则 P4-5.3 · 缺乏独占条件时的处置
  若无法确认独占 ⇒ 不得开始新的权威签发 ⇒ 进入 STOPPED。

⇒ 【关键边界】
⇒ AUTHORITY_EXCLUSIVITY_ENFORCEMENT = NOT ESTABLISHED（现状不变）。
⇒ 本补充定义的是【规范要求】（没有独占就不许签发），
   不是【已实现的强制机制】。
⇒ 两者不可互相推出。
```

## 反例 1 · ACK 丢失后重启，恢复者错误重建权威映射

```text
输入状态：
  event_id = E1，首次 attempt A1 已建立权威记录 K1。
  ACK 丢失（提交方不知道已成功）。
  进程崩溃。提交方以 attempt A2 重试，得到新权威记录 K2。
  ⇒ 此时 E1 有两条「看似权威」的记录。

错误路径：
  恢复者按「最后成功」重选 ⇒ 认定 K2 为权威。
  ⇒ 而 K1 才是首次绑定。

期望拒绝结果：
  ⇒ 依 P4-2.3，权威记录 = 首次绑定 K1，【不是】K2。
  ⇒ A2 应作为同一 event 的合法重试【引用】K1，
    而不是新建 K2。
  ⇒ 若实现产生了两条独立权威记录 ⇒ 违反 P4-2.2/P4-2.3 ⇒ 拒绝该实现。
```

## 反例 2 · 重启后 epoch 被复用，造成记录键碰撞

```text
输入状态：
  历史上 recorder_id = R，已用 epoch = {1, 2, 3}。
  进程重启，实现用【内存计数器】推断新 epoch，重新从 1 开始。

错误路径：
  新纪元用 epoch = 1 ⇒ (R, 1, seq=1) 与历史记录键【完全相同】。
  ⇒ 两条不同的记录得到同一个 authority_record_key。

期望拒绝结果：
  ⇒ 依 P4-3.1，new_epoch 必须从持久化历史推导 = 4。
  ⇒ 用内存计数得 1 ⇒ 与历史冲突 ⇒ P4-3.2 命中 ⇒ 恢复失败 ⇒ STOPPED。
```

## 反例 3 · 恢复历史不完整，却允许新事件签发

```text
输入状态：
  持久化历史尾部有一条记录不完整（写入中断）。
  恢复者按「截断后继续」，认为剩下的部分「够用」。

错误路径：
  截断后直接进入 RUNNING，开始签发新的权威事件。
  ⇒ 而被截断的那条可能正是某个 event_id 的首次绑定。
  ⇒ 于是该 event 的权威映射永久丢失，且无人知道。

期望拒绝结果：
  ⇒ 依 P4-2.4，历史不完整 ⇒ 恢复失败。
  ⇒ 依 P4-4.3，进入 STOPPED，不得签发。
  ⇒ 「截断后继续」只能用于【记录】RECOVERY_TRUNCATED（v0.1 EPOCH-3），
    不能用于【放行签发】。
```

## 反例 4 · 旧记录者仍可能签发，而新记录者已开始签发

```text
输入状态：
  旧实例实际未终止（例如只是网络分区 / 挂起），仍在运行。
  新实例重启，认为「旧实例已结束」，开始签发。

错误路径：
  两个实例同时签发权威事件 ⇒ 违反 T-2 单一逻辑权威域。
  ⇒ 且两边的 epoch 可能都合法（若旧实例未重启），
    故 epoch 检查【无法】检出。

期望拒绝结果：
  ⇒ 依 P4-5.2，「原实例已终止」的判断本身不是证据。
  ⇒ 依 P4-5.3，缺乏可验证独占条件 ⇒ 新实例不得开始签发 ⇒ STOPPED。
  ⇒ 【注意】此反例在当前无强制机制时【可能无法被系统检出】——
     AUTH EXCLUSIVITY_ENFORCEMENT = NOT ESTABLISHED。
  ⇒ 故本反例的「期望拒绝」是【规范要求】，
    不是【当前能自动检测到的】。
  ⇒ 不得因规范写了「拒绝」就认为已经防住了。
```
