```text
⇒ 【所以我只提供方案与验证命令，不提供执行】。
```

## 五·乙 · 本方案的权限模型缺陷（凌翼 2026-11-14 指出，已修正）

```text
⇒ 凌翼复核后指出三点，我逐条核对，【全部属实】，而且其中一条是我方案的方法论错误：

   ① 两个分支 protected 均为 false
      ⇒ 我实测：main = False，exp/v2-l1-verifier = False   ✅ 一致

   ② 仓库规则集列表为空
      ⇒ 我实测：GET /rulesets → 200，条目数 = 0            ✅ 一致

   ③ 单独访问保护配置接口返回 403（他那边）
      ⇒ 【这是最关键的一条】。我这边对同样的接口得到的是 404。
```

### 5.5.1 404 与 403 不是一回事（我原方案的错误）

```text
   我这边：  GET /branches/main/protection → 404 "Branch not protected"
   他那边：  GET /branches/main/protection → 403 权限不足

⇒ 【两种结果，我原方案把它们当成了同一个结论】。
   · 404 = 【确实没有保护配置】（配置不存在）
   · 403 = 【无权查看是否存在保护】（配置可能有，也可能没有）

⇒ 【我方案的错】：§六 的 V-1 写"任何人可跑，结果应可复现"。
   ⇒ 这是错的。普通成员跑这条命令只会拿到 403，
     而 403 无法区分"没配保护"和"配了但我看不见"。
   ⇒ 我以自己的 admin 视角写验证方法，等于把
     【只有我能看到的证据】当成了【公共可验证的证据】。
```

```text
⇒ 【更麻烦的推论】：
   假设将来 M-1 真的执行、main 开了保护，
   凌翼再去查，仍然会拿到 403 ——
   他会看到一个【和现在完全相同】的结果，
   因此无法判断改造是否真的发生。

   ⇒ 也就是说：按我原来写的验证方法，
     【改造前和改造后，在普通成员眼里长得一样】。
   ⇒ 这样的验证方法【没有证明力】，写它等于没写。
```

### 5.5.2 修正后的权限模型（三层，必须分开陈述）

```text
  L-层 1 · 配置事实（Configuration Fact）
    "仓库是否真的开启了保护"
    ⇒ 只能由【管理员视角】读取，或由【界面截图 + 操作记录】佐证
    ⇒ 普通成员无法独立核实 —— 这是 GitHub 权限模型的限制，不是我方疏忽

  L-层 2 · 可见证据（Observable Evidence）
    "普通成员能看到什么"
    ⇒ 普通成员能看到：protected: false 标记、尝试直接推送是否被拒
    ⇒ 【关键】："推送被拒"是可被普通成员独立验证的信号，
      而它比"读保护配置"更接近我们要证明的东西

  L-层 3 · 行为证明（Behavioral Proof）
    "能不能绕过"
    ⇒ 唯一可信的方式是【实际尝试并失败】：
      由 Coder 尝试直接 push main → 应被拒绝
    ⇒ 这一次尝试【本身】就是证据，且【任何人都能看见结果】
```

```text
⇒ 【结论：验证必须用行为证明，不能用配置读取】。
   因为行为证明的结果对所有人可见，
   而配置读取的结果【取决于你是谁】。
```

### 5.5.3 因此 M-1 的验收标准要改

```text
  原写法（错）：
    "GET /protection 应返回 200，enforce_admins.enabled = true"

  现写法（对）：
    B-1  由 Coder 用推送凭据尝试直接 push 到 main
         ⇒ 期望：被拒绝（非快进/受保护分支）
         ⇒ 记录：完整命令与错误输出
    B-2  由 Coder 尝试 force push 到 main
         ⇒ 期望：被拒绝
    B-3  由仓库所有者通过 PR 合并一次
         ⇒ 期望：成功
         ⇒ 三者合起来才能说明"保护生效且未完全堵死"

  ⇒ 【B-3 不能省】：只证明"推不进去"，也可能是因为保护配错成了
     谁都推不进去（包括 owner）。那不是保护，是锁死。
```

### 5.5.4 一处必须承认的局限

```text
⇒ 【我的盘点能力本身就是特权】。
   我能读到 collaborators 列表、rulesets、permissions，
   是因为我是 admin。
   ⇒ 普通成员读不到这些，因此【我提供的盘点无法被他们独立复核】。

⇒ 这一条我也写进 B_36 的修订要求里（见该文件 §二·乙（7））。
```

## 六 · 验证方法（2026-11-14 已按凌翼意见重写）

```text
⇒ 【先说结论】：原来的"跑几条 API 命令看返回值"【不能用】。
   理由见 §五·乙：同一检查在不同身份下会得到
   404（配置不存在）/ 403（无权查看）两种结果，
   而两者在"是否已保护"这个问题上【不能区分】。
⇒ 所以验证改为【行为证明】：让动作去撞保护，看它是否被挡住。
```

```text
  B-1  直接推送 main
       执行者：Coder（用其推送凭据）

       期望：  被拒绝
       记录：  完整命令 + 完整错误输出（不是摘要）
       ⇒ 若成功，说明保护未生效或未含 include administrators

  B-2  强制推送 main
       命令：  git push --force origin main
       期望：  被拒绝
       ⇒ 这一条专门验 allow_force_pushes = false

  B-3  所有者经 PR 合并一次
       期望：  成功
       ⇒ 【不能省】：只证明"推不进去"，可能是保护配成锁死（连 owner 也进不去）。
          B-1+B-2+B-3 合起来才说明"保护生效且未堵死正常通道"。

  B-4  两侧同时修改的尝试
       执行者：Coder
       动作：  在一次提交里同时改记录侧与摘要侧文件

       ⇒ 这一条对应 WE-2。

⇒ 【B-1~B-4 的共同优点】：结果【对所有人可见】。
   无论谁去看 PR 列表、commit 历史、CI 日志，都能看到同样的东西。
   ⇒ 不需要 admin 权限，也不需要相信我。
```

### 6.2 仍需管理员视角的部分（必须标明来源）

```text
⇒ 有些事实【确实只能由管理员读】：
   · 协作者全集与各自权限级别
   · ruleset 的具体规则内容
   · 谁在什么时候改过设置（audit log）

⇒ 【处理方式】：不把它当成"公共证据"，而是标成
   `EVIDENCE_CLASS = ADMIN_VIEW`，并附上：
     · 读取时间
     · 读取所用凭据的身份
     · 若可能，附带界面截图（截图比 API 输出更容易被第三方核对）

⇒ 【纪律】：凡是 `ADMIN_VIEW` 类证据，
   都必须【另有行为证据与之交叉】，否则不单独采信。
   ⇒ 例如：台账说"Coder 已被降为 Write"（admin 视角）
      ⇒ 必须再用 B-4 的行为证明来交叉验证。
```
