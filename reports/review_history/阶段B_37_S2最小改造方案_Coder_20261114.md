## 二 · 改造清单（按"必须做"与"可选"分开）

### 2.1 必须做（M-1 ～ M-5）

```text
  M-1  main 分支保护
       改什么：对 main 启用 Branch protection

                       Require approvals（≥1）
                       Do not allow bypassing the above settings
                       （即 include administrators）
       为什么：当前 main 无保护，任何写权凭据可直接推。

             enforce_admins.enabled = true
       ⇒ 【注意】：若不开 include administrators，admin 仍可绕过，
          G-2 依然不成立。这一项是本方案的核心。

  M-2  降低 Coder 的仓库权限
       改什么：把 Coder 从 admin 降为「只能通过 PR 贡献」的级别

               选项 b：取消协作者，改为 fork + PR（最强，但流程变重）
       为什么：A3-1 要求"无法通过管理员权限……同时修改两侧"。
               admin 天然可改保护规则，因此 admin 与 G-2 不可共存。
       谁能改：仓库 owner
       验证：GET /repos/.../collaborators/coder/permission
             应不含 admin；且 M-1 的 enforce_admins = true

  M-3  建立 CUSTODIAN 的独立写入路径
       改什么：给 CUSTODIAN 一个【自己实际能用】的写入方式
               候选 a：独立 GitHub 账号 + 对摘要存储仓库的 Write
               候选 b：CUSTODIAN 作为 PR 的【唯一批准人】
       为什么：§二·乙（4）已指出 —— 若由 Coder 代为执行，
               B 路径实质不存在，WE-1 仍不成立。

       验证：CUSTODIAN 能实际完成一次写入，且该次写入【不经过 Coder】

  M-4  摘要存储与记录存储分离到两个受保护单元
       改什么：预期摘要不得与记录处于"同一个可被单人同时修改"的位置
               候选 a：两个独立仓库（最强）

       为什么：§2.2.2 的 S1（同仓库不同文件）必然 WE-2 不通过。
       谁能改：仓库 owner
       验证：存在一条命令/一次提交能同时改两侧吗？若存在 → 不通过

  M-5  凭据台账落地
       改什么：把 B_36 二·乙的口述条目逐条取证（协作者列表截图/API 结果、
               分支保护设置、每个成员的实际权限级别）

       谁能改：CUSTODIAN（台账维护者）
```

### 2.2 建议做（S-1 ～ S-3，不阻断 G-1～G-4，但降低风险）

```text
  S-1  仓库转为私有
       现状 private = False（公开）。
       ⇒ 公开本身不等于不安全，但它意味着：
         · 任何人可 fork、可看到全部设计
         · 未来若接受外部 PR，只读边界会变化
       ⇒ 是否转私有属治理决定，不是技术必需。

  S-2  CODEOWNERS
       给 .github/ 与摘要存储路径设必需审查人。
       好处：即使有写权，也不能单方面改保护相关文件。

  S-3  凭据轮换记录
       记录何时换过凭据、换了谁的、旧凭据何时失效。
       ⇒ 裁定 A.3 第 2 条提到"变更后重新核验"，需要这条记录才有对象。
```

### 2.2·附带 · 一条【已经成立】的正面事实（不必改造）

```text
⇒ 盘点时顺手核对了 CI 侧凭据面，结论是【这一块目前是干净的】：

   .github/workflows/v2_l1_verifier.yml 已声明
     permissions:
       contents: read

   ⇒ 即：CI 只读仓库内容，没有 contents: write，
     也就【不能】用工作流去改记录或改摘要。

⇒ 【为什么这条值得单独写】：
   如果 workflow 拥有写权限，那么它就构成 A3-1 所说的
   「自动化流程」这条间接双侧路径 —— 而它是【不需要知道任何人密码】就能改东西的路径。
   ⇒ 目前没有这个风险，这是现状里少有的、不需要改造就满足条件的一项。

⇒ 【但我只写"当前是干净的"，不写"以后也是"】：
   任何后续修改 workflow 的提交都可能把 permissions 放宽，
   而【放宽本身很难被注意到】—— 因为它只是一个 yml 里的几行。
   ⇒ 建议在复核清单里加一条：每次改 workflow 都要确认 permissions 未被放宽。
```

## 五 · 为什么我不自行执行

```text
⇒ 我技术上能做到 M-1~M-5 的全部（admin 权限仍在）。
⇒ 但我【不会】自己做，有三个理由：

  ① 【自证无效】
     一个被约束的人自行设置约束，无法向任何人证明
     "我在设置时没有留下绕过路径"。
     ⇒ 这正是 §2.5.1 TR-1 要防的那种"无法检验的信任假设"。

  ② 【顺序悖论】
     M-2 是降低我自己的权限。若由我执行，
     则"我有权降低我自己的权"这件事本身，证明了 WE-1 仍不成立。
     ⇒ 必须由他人执行，WE-1 才有意义。

  ③ 【记录价值】
     由 owner 执行、我旁观并记录，这份操作记录【本身】就是 A3-1 的证据。
     由我执行，这份记录无法被别人采信。

⇒ 【所以我只提供方案与验证命令，不提供执行】。
   执行后我可以跑验证，并把结果写成记录 —— 但"改"这一步不是我做。
```
