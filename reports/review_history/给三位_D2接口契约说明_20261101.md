# 二 · IC-1 · 来源可信性

## 凌翼的要求

```text
"仅有提交方自行填写的 ACK_RECEIVED，
 不能自动满足可靠证据的要求。"
```

## 当前缺口的准确形态

```text
ReceiptRecord {
    event_id
    attempt_id
    authority_record_key
    receipt_fact            ACK_RECEIVED
    received_by             提交方身份      ← 自填，无校验
    receipt_seq
}
```

```text
⇒ received_by 与 receipt_fact 都由提交方自己写。
⇒ 任何进程都能写这一行"我收到 ACK 了"。
```

## 契约的四要素

| # | 要素 | 契约要求 |
|---|---|---|
| 0 | 收据可引用 | `receipt_record_key = (event_id, attempt_id, receipt_seq)` |
| 1 | 提交方身份 | 须 (a) 记录者 ACK 回显的 submitter_id / (b) 控制主体核验 / (c) 否则 NOT ESTABLISHED |
| 2 | 收件事实来源 | 须**两侧对得上**：记录者 `ACK_SENT` + 提交方 `ACK_RECEIVED` |
| 3 | 持久化位置 | 须与 `EventRecord` **不同位置**，写权不得同一主体 |
| 4 | 独立校验 | c1–c4 四项由控制主体**分别读取两侧** |

**c1–c4 清单：**

```text
c1  EventRecord 流中存在 ACK_SENT，attempt 匹配
c2  ReceiptRecord 流中存在 ACK_RECEIVED，authority_record_key 匹配
c3  两侧 event_id / attempt_id 一致
c4  两侧均达 L3

c1–c4 全过 ⇒ RECEIPT_VERIFIED
任一不过 ⇒ NOT ESTABLISHED（不是 INVALID）
c1 c2 都存在但互相矛盾 ⇒ INVALID
```

```text
⇒ 最后一行是知微您那套区分的直接应用：
   缺证据 = NOT ESTABLISHED；观察到矛盾 = INVALID。
```

# 四 · IC-3 · 版本一致性（两子项）

## IC-3a · 映射与弃用

| 旧 | 新 | 弃用规则 |
|---|---|---|
| `EventRecord.commit_state` | 独立 `StateTransition` 流 | 旧字段失效；不得从旧记录读状态 |
| `WRITE_COMMIT` | 四事件分开 | 名称弃用；旧文档出现处不得解释为已证明的写入提交 |
| 单一 `confirmed` 布尔 | `BINDING_CONFIRMED` / `ACK_CONFIRMED` | 旧布尔无法表达两者之分，不得迁移 |

```text
⇒ 历史文档与冻结规格【不自动改写】（凌翼明令）。
```

## IC-3b · 事件粒度（这是我做的唯一一个判断）

**凌翼要求固定：一次底层文件写入，还是整个干预动作？**

```text
⇒ 本契约固定为【一次底层文件写入】。
```

**理由（有源码依据）：**

```
storage.py L99-105   write_literal    → 写 literal.bin
storage.py L107-109  write_substrate  → 写 substrate.bin
```

```text
⇒ 两次独立写入，之间【无原子提交】。
⇒ 若定为「整个干预动作」，等于定义一条
   在这台 harness 上【永假】的规则。
```

**直接后果（我认为这是本契约最重要的一句）：**

```text
CROSS_FILE_ATOMICITY = NOT ESTABLISHED

⇒ "literal 与 substrate 同时处于某状态"这件事，
   无法由写入事件推出。
⇒ 只能由快照观测，而快照本身非原子（B-1 已诊断）。
```
