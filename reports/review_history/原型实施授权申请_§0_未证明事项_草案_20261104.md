# A · 测试通过也不能推出的结论

```text
⇒ 以下每一条，即使 TEST_GATE_PASS 全部满足，
   也【不得】在任何文档、报告、结论中出现为已成立。

A-1  独占性被数学证明
     ⇒ 1,000 组双进程竞争无失败
       ≠ 「任意调度、任意时序下都独占」
     ⇒ 只能写：在此测试配置下未观察到竞争失败。
     ⇒ 原因：有限次采样不覆盖全部交错；调度由 OS 决定，
       测试无法穷举。
       ［2026-11-04 二次修正（睫）：原写「这是归纳，不是归纳证明」，
         措辞绕。改为：这是【有限次观察】，不是【数学归纳法证明】。］

     ⇒ 【增加轮次不改变结论的性质，仍为「未观察到」】
       ［睫第一处 a：读者可能误以为「多加轮次就能证明」。
         轮次是工程置信度，不是逻辑上的充分性。］

     ⇒ 【「同一测试配置」里，一词又承担了两件事】
       ［睫第一处 b：这是我在 A-2 刚修掉的同一个毛病，在 A-1 又犯一次。］
       配置相同  ≠  交错相同
       ⇒ 配置（进程数、启动时机、延迟参数、随机种子）是【能固定的】；
       ⇒ 而调度交错由 OS 决定，【不保证每次相同】。
         ［知微：原写「每次都不同」过强；有限采样结论不需要这个断言。］
       ⇒ 故禁止写「同一配置下重复通过 ⇒ 该配置是稳定的」——
         这句话把【配置】与【交错】合成了一个词。
       ⇒ 可以说：在同一配置下重复执行 N 次，均未观察到违规。
         不能说：该配置下已稳定。

     ⇒ 【本节不展开该论证；但本申请必须给出它】
       ［2026-11-04 三次修正（知微 R1 末段）：
         原写「本原型【不提供、也不产生】该论证路径」——
         会把本申请【必须交付】的内容反而排除掉。已改为分工表述。］
       ⇒ 本节不展开设计层论证；
         本申请【必须由 §6 / §7 给出】有界的
         「前提—状态转换—机制—不变量—失效后果」论证。
       ⇒ 原型测试结果仅作为该论证的【独立支持】，不替代它。
       ⇒ 本节只负责【指出它必须存在】，不负责声称它已完成。

A-2  崩溃一致性已被证明 —— 【本条须拆为两种，不许合称】
     ［自查：初稿把「进程崩溃」与「系统断电」都写作「崩溃」，
       这是一个词承担两件事，已拆。这两者的保证完全不同。］

     A-2a 进程级中止（进程被杀 / 异常退出，OS 仍在运行）
          ⇒ 本原型【可以】在可控点中止进程并观察结果。
          ⇒ 【进程中止矩阵须覆盖各可达关键持久化边界的写入前/中/后】
            ［2026-11-04 三次修正（知微 R3）：
              上一轮写「中止点必须落在写入过程中」，
              会把裁定明确要求的写入前/后场景一并排除。已收窄。］

          ⇒ 【半写用例的触达条件（单独成立，不外推）】
            storage.py L59-61：
                def _write_bytes(self, path, data):
                    with open(path, "wb") as f:
                        f.write(data)
            ⇒ with 退出会 close；close 把 Python 用户态缓冲交给 OS，
              但【不 fsync】。
            ⇒ 若用例声称覆盖"半写"，而中止点落在【close 之后】：
              文件在 OS 页缓存中可能是完整的，
              该用例【不能】充当半写证据。
            ⇒ 而 D-1 自己就写着「它们会让『看起来通过』变成『其实没测到』」。
              ⇒ 那一句警告，原先没有接到半写用例的触达条件上。
            ⇒ 故：半写用例须证明【触达预定的不完整写入状态或等效故障模型】，
              不能用「全部写入成功后的终止」代替；
              并须留下「中止点位置」的证据。

          ⇒ 【但 close 后的终止 ≠ 无效测试（知微 R3）】
            ⇒ 它【不计作半写覆盖】，但仍可能检验
              「已写文件与后续提交/身份登记/epoch/签发权限的关联恢复」。
            ⇒ 例（举例，不预设方案）：若实现把状态文件与提交记录分步完成，
              在【前一个文件关闭之后、提交记录完成之前】终止，
              是有意义的恢复边界 —— 文件内容完整【不等于】整个协议已提交。
            ⇒ 故：【close 后的终止不计作半写覆盖，也不能一概判为无效测试。】
            ⇒ 每个中止点按其【测量目标】判定。

          ⇒ 但即使观察到预期，也只能写：
            「在本测试点中止进程后，未观察到违规状态」。
          ⇒ 不能推出「任意中止时刻都不产生半写」。
          ⇒ 原因：中止时刻不可穷举。

          ⇒ 【写入层次（知微 R5 修正后）】
            ⇒ f.write() 【成功返回并不保证】数据已离开 Python 缓冲；
              它【也可能已写入底层流】（缓冲不足等条件下会直接刷）。
            ⇒ 正常成功的 close 【会刷新流缓冲】，
              但 close 本身【不提供本协议所需的完整持久化保证】。
            ⇒ 【OS 可能后台写回】；未显式 fsync 不代表数据一定尚未落盘。
            ⇒ 需要明确持久化边界时，应使用选定的同步机制，
              处理其返回值并说明存储栈前提。
            ⇒ 【是否实际落盘不能只从「调用/未调用 fsync」反推。】
            ［原写「f.write() 返回只在 Python 缓冲层 / close 后在此但未落盘 /
              需 fsync 才可能到达 / 只有 fsync 才处理」——
              这四句把「可能已发生」写成了「肯定未发生」。已改。］

            ⇒ 故「仅凭 OS 仍运行的进程中止试验」，
              不能建立断电持久性，
              也不能据此认定同步持久化不必要。

          ⇒ 【与 D-1 互引】
            若按 D-1 先补 fsync / 原子替换，A-2a 测的是【补过的实现】，
            结论【不能回推】原 harness。
            ⇒ D-1 与 A-2a / A-2b 须相互引用，不得各说各的。

     A-2b 系统级断电 / 掉电（缓存可能丢失）
          ⇒ 本原型【不测试】真实断电。
          ⇒ 任何「进程中止测试」都不能替代它。
          ⇒ 因此本节不主张任何断电一致性结论。
          ⇒ 【修正（知微 Z0-03 第 4 条）】
            原写「只有 fsync 过的才安全」——撤回。
            ⇒ 它把一种操作写成完整安全判据，并排除了其他可能机制。
            ⇒ 改为：
              「断电保证需要【明确的持久化协议】及【存储栈前提】；
               本轮不建立此保证。」
            ⇒ 刷新（flush）与原子替换（atomic replace）

            虚拟机强制断电或存储故障注入只是各自的故障模型，
            不能未经论证就代表宿主机 / 物理存储掉电。
            当前【不开展】这些测试，无需扩张工作范围。

     A-2c 【进程未终止，但被判定为已终止】
          ［2026-11-04 二次修正（睫第二处 b）：本节原先只分了
            「进程中止」与「系统断电」两类，漏了第三类。
            而这一条【设计基线里已经写过】——P4 §六 反例 4。］
          ⇒ 情形：挂起 / 网络分区 / 长时间暂停 / 调度饥饿。
            进程【仍然活着】，但恢复者认为它已结束。
          ⇒ 为何单列：它不是「进程中止」（进程还在），
            也不是「系统断电」（系统正常运行）。
            用前两类中任何一个去套，都会描述错。
          ⇒ 与 P5 独占直接相关，且是【这台机器上最容易发生的一类】。
          ⇒ 本原型【能测】：启动两个进程，其一挂起或暂停，
            观察另一进程是否被允许取得独占。
          ⇒ 但结论仍受 A-1 限制：未观察到 ≠ 已证明。
          ⇒ 【设计基线已知，故本条不是新发现，而是补位】：
            P4 反例 4 已承认该故障模型，
```

# B · 外部前提与必须落实的本地核验义务

```text
⇒ 本节分两列：
     左列 = 【外部前提】：可声明为假设，本原型不自行证明；
     右列 = 【本地核验义务】：原型【必须落实】的实现核验。
⇒ 混淆两者，会让一个实现借"相信内核"来逃避"核验自己用得对不对"。
```

```text
⇒ 左列的前提若【不成立】，设计层结论会失效；
   但本原型【无法】证明它们成立。
⇒ 右列的义务若【未落实】，相应条件不得记为通过。
```

```text
⇒ 【2026-11-04 二次修正（知微 Z0-01）：B 类必须拆成两列】
   ⇒ 原写法把「可声明的外部前提」与「原型自身必须核验的实现义务」
     混在一起，导致一个依赖墙上时间排序的实现可以借
     「不验证实现是否真的没用它」避开核验。
   ⇒ 这不对：相信内核，与核验自己是否正确使用内核，是两层。
```

| 可声明的外部前提 | 后续申请必须落实的本地核验义务 |
|---|---|
| 注册版本的 OS / 文件系统遵守所引用的接口契约 | 所有相关访问路径确实使用选定机制；对象名称、作用域、返回值与生命周期对应正确 |
| 注册测试环境不受范围外主体主动破坏 | 记录测试范围、参与者与控制依据；已知范围内干扰不得用此外部假设豁免 |
| 无需自行证明内核调度器正确 | 核对 epoch/seq 的实现与证据，不让 clock_ns 参与权威排序 |
| 存储栈满足明确列出的保证前提 | 核对写入、刷新、发布、恢复的实际顺序及错误处理；不得把「调用了 API」当作成功 |

```text
   ⇒ 该项写入 §7 的验收判据，不留在本节作意图。
   ⇒ 本节只负责【指定它存在】，不负责保证它被执行。
```
