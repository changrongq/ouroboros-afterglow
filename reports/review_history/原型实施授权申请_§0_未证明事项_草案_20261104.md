# 零 · 这一节回答什么

```text
⇒ 凌翼在裁定第三节 C 项明写：
   「即使全部满足，也只能写：
      BOUNDED_PROTOTYPE_TEST_GATE = PASS
    不能写：
      GENERAL_SAFETY_PROVEN = YES
    尤其不能把 1,000 次没有出现竞争失败
    等同于已经数学证明独占性。」

⇒ 所以本节的任务是：在动手之前，先列出
   【这个原型即使全部通过，也不能证明什么】。

⇒ 分四类：
   A. 测试通过也不能推出的结论
   B. 设计层声明成立所需的前提（本原型不验证）
   C. 本原型明确不覆盖的范围
   D. 已知的实现级缺陷（当前 harness 的事实）
```

# A · 测试通过也不能推出的结论

```text
⇒ 以下每一条，即使 TEST_GATE_PASS 全部满足，
   也【不得】在任何文档、报告、结论中出现为已成立。

A-1  独占性被数学证明
     ⇒ 1,000 组双进程竞争无失败
       ≠ 「任意调度、任意时序下都独占」
     ⇒ 只能写：在此测试配置下未观察到竞争失败。
     ⇒ 原因：有限次采样不覆盖全部交错；调度由 OS 决定，
       测试无法穷举。这是归纳，不是归纳证明。

A-2  崩溃一致性已被证明 —— 【本条须拆为两种，不许合称】
     ［自查：初稿把「进程崩溃」与「系统断电」都写作「崩溃」，
       这是一个词承担两件事，已拆。这两者的保证完全不同。］

     A-2a 进程级中止（进程被杀 / 异常退出，OS 仍在运行）
          ⇒ 本原型【可以】在可控点中止进程并观察结果。
          ⇒ 但即使观察到预期，也只能写：
            「在本测试点中止进程后，未观察到违规状态」。
          ⇒ 不能推出「任意中止时刻都不产生半写」。
          ⇒ 原因：中止时刻不可穷举。
          ⇒ 【注意】这种情况下 write() 已返回的字节通常仍在页缓存中，
            所以它【不能】用来检验 fsync 的必要性。

     A-2b 系统级断电 / 掉电（缓存可能丢失）
          ⇒ 本原型【不测试】真实断电。
          ⇒ 任何「崩溃测试」都不能替代它。
          ⇒ 因此本节不主张任何断电一致性结论。
          ⇒ 若将来要测，须另有手段（例如虚拟机强制断电、
            或使用可注入故障的存储层），且仍属有限采样。

A-3  来源真实性
     ⇒ SHA-256 摘要匹配
       ≠ 「这份字节来自某个可信主体」。
     ⇒ 这是凌翼裁定第二节「完整性不等于可信身份」的直接后果。
     ⇒ 本原型能验证的只有：读到的字节与给定摘要一致。

A-4  写入归属
     ⇒ 即便身份核验通过、绑定正确，
       ≠ 「某进程确实写入了目标文件」。
     ⇒ 依据：D2 §IC-1 与 P4 §4.4 已确立
       SUBMITTER_IDENTITY_VERIFIED 与 WRITER_ATTRIBUTION_CHAIN 是两件事。
     ⇒ 本原型不建立 WRITER_ATTRIBUTION_CHAIN。

A-5  生产环境适用性
     ⇒ 原型在本机沙箱通过
       ≠ 「可部署到生产」。
     ⇒ 沙箱与生产的差异（权限模型、并发规模、存储介质、
       运维流程）本原型一概不覆盖。

A-6  科学资格
     ⇒ 原型跑通
       ≠ C1_MEASUREMENT_CHAIN 已具备资格。
     ⇒ 科学执行门禁在本阶段完全不触及。
```

# B · 设计层声明成立所需的前提（本原型不验证）

```text
⇒ 以下前提若【不成立】，设计层结论会失效；
   但本原型【无法】验证它们是否成立。
⇒ 故它们只能作为【外部假设】列出，不得当作已获支持。
```

```text
B-1  OS 调度器与文件系统的行为
     P5 独占依赖 Windows 本机原语（拟用命名互斥体或等效物）。
     ⇒ 假设：该原语在同一登录会话内确实提供内核级互斥。
     ⇒ 本原型能观察到的只是【行为】，不是【内核保证】。
     ⇒ 若该假设不成立，本原型的所有独占测试都只是巧合。

B-2  测试进程未被外部干扰
     ⇒ 假设：测试期间无第三方进程以相同身份访问被测路径。
     ⇒ 若存在，测试结果不可解释（既不能判定通过，也不能判定失败）。
     ⇒ 本原型【不检测】外部干扰（检测它需要更宽的观测面）。

B-3  时钟与序号语义
     ⇒ epoch/seq 的推导不依赖墙上时钟（v0.2 已定 clock_ns 不参与排序）。
     ⇒ 但「不参与排序」是规范声明，本原型不验证
       实现是否真的没用它。

B-4  持久化原语的实际语义
     ⇒ 若本原型改用 fsync 或原子替换，
       假设该原语在本机文件系统上确实提供声称的保证。
     ⇒ 原型不验证文件系统内部实现。
```

# C · 本原型明确不覆盖的范围

```text
⇒ 照录凌翼裁定第一节「明确排除」：
   · 分布式多节点一致性
   · 高可用与自动故障转移
   · 网络租约与跨主机独占
   · 多个合法活动写入者
   · 生产密钥与真实生产签名
   · 冻结 Q3 RC11 的任何修改

⇒ 补充本拟稿认为同样不覆盖、且容易被误读为已覆盖的：
   · 恶意攻击者（本原型测试的是【故障】，不是【对抗】）
     ⇒ 故障注入 ≠ 攻击模拟。
     ⇒ 若被测进程有足够权限直接改字节并重算摘要，
       本原型的完整性检查【拦不住】——这不是缺陷，是范围外。
   · 长时间运行（本原型是短时测试，不含数月级泄漏/漂移）
   · 多用户并发（同一时刻只有同一身份）
   · 系统级断电 / 掉电（本原型只做进程级中止，见 A-2a / A-2b 的区别）
```

# D · 已知的实现级缺陷（当前 harness 的事实）

```text
⇒ 以下【不是】本原型的缺陷，是【现状】。
⇒ 列出是因为它们会让「看起来通过」变成「其实没测到」。
```

```text
D-1  _write_bytes 无 flush / 无 fsync / 无原子替换
     ⇒ 依据：storage.py L59-61
         def _write_bytes(self, path, data):
             with open(path, "wb") as f:
                 f.write(data)
     ⇒ 全仓 .py 中 fsync 零命中；
        flush 仅两处且均为 sys.stdout（与持久化无关）。
     ⇒ 后果：「半写」在当前实现下【必然可能】。
     ⇒ 本原型若依赖持久化，必须【先补】或【显式声明不补】。
     ⇒ 不得因为「用了文件写入」就声称任何一致性
       —— 无论是进程级中止后的（A-2a）还是系统断电后的（A-2b）。

D-2  ObjectIdentity 是【内容摘要身份】，不是【独占凭证】
     ⇒ 依据：win32_isolation.py L205-229
         ObjectIdentity = (object_id, abs_path, size, sha256)
         identity_still_matches() 比对 size + sha256
     ⇒ 它能证明：「这个文件现在的内容与我记录时一致」。
     ⇒ 它【不能】证明：「只有我在写这个文件」。
     ⇒ 【陷阱】：若把「身份未变」读作「我持有独占」，
       就会在双进程竞争时两边都判通过。
     ⇒ 本原型【禁止】把 ObjectIdentity 用作 P5 独占判据。
     ⇒ 若需内容一致性检查，可复用；若需独占，必须另建。

D-3  无现成的 OS 级独占原语
     ⇒ 全仓无 LockFileEx / CreateMutex / 命名 mutex。
     ⇒ 有 msvcrt.get_osfhandle（可取 OS 句柄），但未在其上建锁。
     ⇒ 后果：P5 独占机制【必须新建】，不能宣称复用现有代码。

D-4  epoch 分配无原子性
     ⇒ 依据：v0.1 §6.4 原文「epoch 分配本身必须原子（读-改-写），
       而当前 harness 无锁、无原子替换」。
     ⇒ EPOCH_ALLOCATION_ATOMICITY = NOT ESTABLISHED（现状未变）。
     ⇒ P4-3 的 max(epoch)+1 规则【实现前提尚不存在】。
```
