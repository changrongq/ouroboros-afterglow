# 零 · 这一节回答什么
```text
⇒ 凌翼在裁定第三节 C 项明写：
   「即使全部满足，也只能写：
      BOUNDED_PROTOTYPE_TEST_GATE = PASS
    不能写：
      GENERAL_SAFETY_PROVEN = YES
    尤其不能把 1,000 次没有出现竞争失败
    等同于已经数学证明独占性。」

⇒ 所以本节的任务是：在动手之前，先列出
   【这个原型即使全部通过，也不能证明什么】。

⇒ 分四类：
   A. 测试通过也不能推出的结论
   B. 设计层声明成立所需的前提（本原型不验证）
   C. 本原型明确不覆盖的范围
   D. 已知的实现级缺陷（当前 harness 的事实）
```

# A · 测试通过也不能推出的结论

```text
⇒ 以下每一条，即使 TEST_GATE_PASS 全部满足，
   也【不得】在任何文档、报告、结论中出现为已成立。

A-1  独占性被数学证明
     ⇒ 1,000 组双进程竞争无失败
       ≠ 「任意调度、任意时序下都独占」
     ⇒ 只能写：在此测试配置下未观察到竞争失败。
     ⇒ 原因：有限次采样不覆盖全部交错；调度由 OS 决定，
       测试无法穷举。
       ［2026-11-04 二次修正（睫）：原写「这是归纳，不是归纳证明」，
         措辞绕。改为：这是【有限次观察】，不是【数学归纳法证明】。］

     ⇒ 【增加轮次不改变结论的性质，仍为「未观察到」】
       ［睫第一处 a：读者可能误以为「多加轮次就能证明」。
         轮次是工程置信度，不是逻辑上的充分性。］

     ⇒ 【「同一测试配置」里，一词又承担了两件事】
       ［睫第一处 b：这是我在 A-2 刚修掉的同一个毛病，在 A-1 又犯一次。］
       配置相同  ≠  交错相同
       ⇒ 配置（进程数、启动时机、延迟参数、随机种子）是【能固定的】；
       ⇒ 而调度交错由 OS 决定，【每次都不同】。
       ⇒ 故禁止写「同一配置下重复通过 ⇒ 该配置是稳定的」——
         这句话把【配置】与【交错】合成了一个词。
       ⇒ 可以说：在同一配置下重复执行 N 次，均未观察到违规。
         不能说：该配置下已稳定。

     ⇒ 【本原型不提供「设计层论证路径」】
       ［睫第一处 c：凌翼裁定第三节 C 要求「设计层面的保证，
         还需要给出明确假设、状态转换推理、反例分析，
         以及机制与安全不变量之间的对应关系」。那是【另一份产出】。］
       ⇒ A 类整节只做否定。若不写明这一点，读者会以为
         「只要不吹牛，就满足了该要求」。
       ⇒ 故此明确：本原型【不提供、也不产生】该论证路径。
       ⇒ 归属：该论证属【§6 安全不变量与故障矩阵】连同
         【§7 验收判定器】的共同产出，应在那两节给出
         「前提—状态转换—机制—不变量—失效后果」的有界论证。
       ⇒ 本原型只提供测试结果作为【独立支持】，不替代该论证。
       ［知微 Z0-01 同条：不要求全系统形式化证明，
         但要求有界的上述论证，§0 不得预先排除。］

A-2  崩溃一致性已被证明 —— 【本条须拆为两种，不许合称】
     ［自查：初稿把「进程崩溃」与「系统断电」都写作「崩溃」，
       这是一个词承担两件事，已拆。这两者的保证完全不同。］

     A-2a 进程级中止（进程被杀 / 异常退出，OS 仍在运行）
          ⇒ 本原型【可以】在可控点中止进程并观察结果。
          ⇒ 【但中止点必须落在写入过程中】
            ［2026-11-04 二次修正（睫，本轮最重的一格）］
            storage.py L59-61：
                def _write_bytes(self, path, data):
                    with open(path, "wb") as f:
                        f.write(data)
            ⇒ with 退出会 close；close 把 Python 用户态缓冲交给 OS，
              但【不 fsync】。
            ⇒ 若中止点落在【close 之后】：
              文件在 OS 页缓存中【是完整的】，
              测试会「通过」，而【什么都没测到】。
            ⇒ 而 D-1 自己就写着「它们会让『看起来通过』变成『其实没测到』」。
              ⇒ 那一句警告，原先没有接到 A-2a 自己的测试点上。
            ⇒ 故：中止点须【明确落在写入过程中】，
              并留下「中止点位置」的证据；否则本条测的不是半写。

          ⇒ 但即使观察到预期，也只能写：
            「在本测试点中止进程后，未观察到违规状态」。
          ⇒ 不能推出「任意中止时刻都不产生半写」。
          ⇒ 原因：中止时刻不可穷举。

          ⇒ 【写入层次：三层必须分开（知微 Z0-03）】
            ① Python 用户态缓冲：f.write() 返回 ≠ 已进 OS 页缓存
            ② OS 页缓存：close 后在此，但未落盘
            ③ 持久介质：需 fsync / _commit 才可能到达
            ⇒ f.write() 返回只在 ① 层；
              with 正常退出 close 会刷新 ① → ②；
              只有 fsync 才处理 → ③ 的提交请求。
            ⇒ 故「仅凭 OS 仍运行的进程中止试验」，
              不能建立断电持久性，
              也不能据此认定同步持久化不必要。

          ⇒ 【与 D-1 互引】
            若按 D-1 先补 fsync / 原子替换，A-2a 测的是【补过的实现】，
            结论【不能回推】原 harness。
            ⇒ D-1 与 A-2a / A-2b 须相互引用，不得各说各的。

     A-2b 系统级断电 / 掉电（缓存可能丢失）
          ⇒ 本原型【不测试】真实断电。
          ⇒ 任何「进程中止测试」都不能替代它。
          ⇒ 因此本节不主张任何断电一致性结论。
          ⇒ 【修正（知微 Z0-03 第 4 条）】
            原写「只有 fsync 过的才安全」——撤回。
            ⇒ 它把一种操作写成完整安全判据，并排除了其他可能机制。
            ⇒ 改为：
              「断电保证需要【明确的持久化协议】及【存储栈前提】；
               本轮不建立此保证。」
            ⇒ 刷新（flush）与原子替换（atomic replace）
              也不能被当作可相互替代的同一保证。
          ⇒ 【关于测试手段（知微 Z0-03 第 5 条）】
            虚拟机强制断电或存储故障注入只是各自的故障模型，
            不能未经论证就代表宿主机 / 物理存储掉电。
            当前【不开展】这些测试，无需扩张工作范围。

     A-2c 【进程未终止，但被判定为已终止】
          ［2026-11-04 二次修正（睫第二处 b）：本节原先只分了
            「进程中止」与「系统断电」两类，漏了第三类。
            而这一条【设计基线里已经写过】——P4 §六 反例 4。］
          ⇒ 情形：挂起 / 网络分区 / 长时间暂停 / 调度饥饿。
            进程【仍然活着】，但恢复者认为它已结束。
          ⇒ 为何单列：它不是「进程中止」（进程还在），
            也不是「系统断电」（系统正常运行）。
            用前两类中任何一个去套，都会描述错。
          ⇒ 与 P5 独占直接相关，且是【这台机器上最容易发生的一类】。
          ⇒ 本原型【能测】：启动两个进程，其一挂起或暂停，
            观察另一进程是否被允许取得独占。
          ⇒ 但结论仍受 A-1 限制：未观察到 ≠ 已证明。
          ⇒ 【设计基线已知，故本条不是新发现，而是补位】：
            P4 反例 4 已承认该故障模型，
            它在「未证明事项 / 故障分类」里原先没有位置。
```

# B · 设计层声明成立所需的前提（本原型不验证）

```text
⇒ 以下前提若【不成立】，设计层结论会失效；
   但本原型【无法】验证它们是否成立。
⇒ 故它们只能作为【外部假设】列出，不得当作已获支持。
```

```text
⇒ 【2026-11-04 二次修正（知微 Z0-01）：B 类必须拆成两列】
   ⇒ 原写法把「可声明的外部前提」与「原型自身必须核验的实现义务」
     混在一起，导致一个依赖墙上时间排序的实现可以借
     「不验证实现是否真的没用它」避开核验。
   ⇒ 这不对：相信内核，与核验自己是否正确使用内核，是两层。
```

| 可声明的外部前提 | 后续申请必须落实的本地核验义务 |
|---|---|
| 注册版本的 OS / 文件系统遵守所引用的接口契约 | 所有相关访问路径确实使用选定机制；对象名称、作用域、返回值与生命周期对应正确 |
| 注册测试环境不受范围外主体主动破坏 | 记录测试范围、参与者与控制依据；已知范围内干扰不得用此外部假设豁免 |
| 无需自行证明内核调度器正确 | 核对 epoch/seq 的实现与证据，不让 clock_ns 参与权威排序 |
| 存储栈满足明确列出的保证前提 | 核对写入、刷新、发布、恢复的实际顺序及错误处理；不得把「调用了 API」当作成功 |

```text
⇒ 【关于 Windows mutex 的两点提示（知微提供，不进方案，只防误读）】
   ① mutex 的所有者是【线程】。取得同一 mutex 可以作为条件论证的一环，
      但【不会】自动覆盖绕过该 mutex 的文件访问；
      线程死亡后的 WAIT_ABANDONED 也【不证明】共享状态一致。
   ② 同一用户身份 ≠ 同一会话命名空间。
      原型可以限定单会话，只需把该限制与实际对象绑定对应起来，
      【不必】扩大到跨会话验证。
⇒ 这两点只是说明为什么集成义务不能归为「内核无法验证」，
   不替 P5 定方案。
```

```text
B-1  OS 调度器与文件系统的行为
     P5 独占依赖 Windows 本机原语（拟用命名互斥体或等效物）。
     ⇒ 外部前提：该原语在同一登录会话内确实提供内核级互斥。
     ⇒ 本地义务：核验实现确实在所有访问路径上使用它、
       命名空间与作用域对应正确、生命周期与返回值处理正确。
     ⇒ 本原型能观察到的只是【行为】，不是【内核保证】。
     ⇒ 若外部前提不成立，本原型的所有独占测试都只是巧合。

B-2  测试进程未被外部干扰
     ⇒ 外部前提：测试期间无第三方进程以相同身份访问被测路径。
     ⇒ 本地义务：记录测试范围、参与者与控制依据；
       已知范围内干扰不得用此外部假设豁免。
     ⇒ 若存在范围外干扰，测试结果不可解释（既不能判通过，也不能判失败）。
     ⇒ 本原型【不检测】外部干扰，也【不检测自身观测失效】（见 E⑤）。

B-3  时钟与序号语义
     ⇒ 外部前提：无需自行证明内核调度器正确。
     ⇒ 本地义务：核对 epoch/seq 的实现与证据，
       【不让 clock_ns 参与权威排序】。
     ［知微 Z0-01 指出：原写「不验证实现是否真的没用它」，
```
