# 时序负向验证计划 v0.1

**依据**：凌翼 2026-10-31 裁定 F 项第 5 条
> "提出崩溃、重放、对象替换、非原子快照及非法写入的负向验证计划"

**性质**：**计划**。不实施、不改冻结件、不声称任何能力已建立。
只写「怎么证伪」，不写「结论是什么」。

# 0 · 采用的既有准则（不新造标准）

本文不发明验收标准，直接引用冻结体系内**已经存在**的准则。

## 0.1 字段成为证据的判据

`adversarial_regression.py` L5-7（凌翼 RC10 R2/R5 原文）：

```text
凌翼 RC10 R2/R5: a field only earns the name REQUIRED EVIDENCE if it is
    RECORDED  AND  CONSUMED  AND  NEGATIVE-TESTED
otherwise it is merely a log.
```

## 0.2 该准则的完整实现

`evidence_contract.py` 的 `REQUIRED_EVIDENCE_CONSUMPTION_MATRIX`
= **18 项**，每项五段式：

```text
field / recorded_in / prod_gate / replay_gate / negative_test
```

⇒ 本文的每一个新字段，都必须能被填进这个五段式，否则不算证据。

## 0.3 一个已经存在的重要事实

18 项中，**涉及时序语义的有 3 项**，且三者的门**全部是字节级等值**：

```text
[ 6] field      : reset_witness[arm].accepted_handoff
     prod_gate  : evidence_bundle._validate_handoff_continuity (byte-level)
     negative   : CE-R7 alter accepted_handoff byte -> INVALID

[ 7] field      : arms[arm].S_handoff / arms[arm].J_after
     prod_gate  : evidence_bundle._validate_j_witness (J_after == S_handoff byte-level)
     negative   : CE-R8 change J_after byte -> INVALID

[15] field      : reset preserve rule (accepted_handoff == verified_restored, raw bytes)
     prod_gate  : evidence_bundle._validate_reset_object_identity (recomputed)
     negative   : RC11 §7: handoff q != restored q w/ reset_valid=True -> INVALID
```

```text
⇒ 三项的门：两个 byte-level 比较 + 一个字节级重算。
⇒ 三项的 negative_test：改字节 / 改字节 / 令字节不等。
⇒ 全 18 项中，没有任何一项的 negative_test 检验【先后关系】。

⇒ 这不是我的推论，是矩阵本身的结构。
⇒ 「时序未被负向测试」在冻结证据契约里已是既成事实，
   且是以该体系自己的登记格式写明的。
```

# 1 · 计划的判定原则

## 1.1 每条用例必须是「可失败」的

```text
若一条负向用例在任何实现下都必然 PASS，它不是测试，是同义反复。
⇒ 每条用例必须能指明：什么样的错误实现会让它 FAIL。
⇒ 本文为每条用例注明「它杀死哪种错误实现」。
```

## 1.2 缺证与否定必须分开

凌翼 D 项已明确：

```text
缺少必需关闭见证或来源证据时：
  · 不得补造时间标记
  · 不得生成正向科学结论
  · 属实际执行必需证据缺失 ⇒ 按 invalidity 条款处理
  · 【不能】写成科学 FAIL
```

```text
⇒ 因此每条用例都必须标注期望结果是 INVALID 还是 FAIL。
⇒ 混淆这两者，等于把「没测成」写成「测出来不成立」。
```

## 1.3 不许用「通过」倒推能力

```text
若某用例 PASS，只能说「这一种攻击被拒绝」。
不能说「时序已建立」。
⇒ 本文每条用例都附「PASS 也不证明什么」一栏。
```

# 2 · 五组负向用例

## 组 A · 崩溃（凌翼反例 #1）

### A-1 窗口未关闭时 writer 崩溃

```text
构造：开启写窗口 → 执行一次部分写入 → 不调用 __exit__ 直接终止进程
目标：检测「窗口未关闭」

杀死哪种错误实现：
  任何把「进程退出」当成「窗口正常关闭」的实现。
  任何在崩溃后补造 WINDOW_CLOSE 的实现。

期望：INVALID（缺 WINDOW_CLOSE 见证）
不得：FAIL，不得生成 PASS

PASS 也不证明：不能证明正常路径下有窗口见证。
```

### A-2 记录者自身崩溃

```text
构造：事件记录进程在 WINDOW_CLOSE 之前被终止

杀死哪种错误实现：
  把「记录缺失」当成「事件未发生」的实现。

期望：INVALID
特别要求：必须有超时判定规则，而不是无限等待。
```

## 组 B · 非原子快照（凌翼反例 #5）

### B-1 两次读之间注入写入 ← 当前唯一「可构造且可验证」的用例

```text
事实依据：storage.py L71-83
  L73  lit = self.read_literal_bytes()
  L74  sub = self.read_substrate_bytes()
  两次独立读，中间无锁、无版本校验。

构造：在 L73 与 L74 之间插入一次 write_substrate()

杀死哪种错误实现：
  把两次读的结果当成「同一时刻的状态」的实现。
  即：任何直接 StateSnapshot(literal=lit, q_raw=sub) 而不记录读取区间的实现。

期望：INVALID（快照不属任何单一时刻）
不得：PASS

PASS 也不证明：不能证明不存在更隐蔽的撕裂。
```

### B-2 快照期间文件被替换（凌翼反例 #4）

```text
构造：快照读取期间用另一个文件原子替换 literal.bin

杀死哪种错误实现：
  只比较字节、不校验对象身份的实现。

期望：INVALID
现状：**不可能检测**（无 inode/句柄身份校验）
```

## 组 C · 非法写入（凌翼反例 #2 #3）

### C-1 窗口外写入（绕过 write_literal）

```text
构造：不进入 write_window，直接对 literal.bin 写字节

杀死哪种错误实现：
  认为 _assert_write_open 能挡住外部写入的实现。
  它只检查【本进程】布尔量（storage.py L95-97）。

期望：必须被检测为窗口外写入
现状：**不可能检测**
```

### C-2 继承写句柄 / 代理写入（凌翼反例 #3）

```text
构造：父进程开窗口，子进程通过继承的句柄写入

杀死哪种错误实现：
  把「同一进程」当成「同一权限主体」的实现。

期望：INVALID 或明确标记为不可归因
现状：**不可能检测**
```

## 组 D · 重放与幂等（本文第 2 节新增）

### D-1 IDENTITY 模式（已实测：摘要完全不变）

```text
实测依据（tempfile 沙箱，未改仓库文件）：
  baseline digest 9d908ecfb6b256def8b49a7c…
  after IDENTITY  9d908ecfb6b256def8b49a7c…   equal

构造：apply_j(state, IDENTITY)，全程

杀死哪种错误实现：
  任何以「摘要变化」作为「事件发生」判据的实现。
  包括：只记录 WRITE_COMMIT、不记录 J_APPLIED 的实现。

期望：必须留下事件记录（J_APPLIED），且无 WRITE_COMMIT
若某实现对它完全无记录 ⇒ 该实现不成立

PASS 也不证明：不能证明其它模式的记录完整。
```

### D-2 幂等写入（已实测）

```text
实测依据：
  COLLAPSE_SIGN on q=+2 : 845c35898d2c -> 845c35898d2c  changed=False
  COLLAPSE_SIGN on q=0  : 9d908ecfb6b2 -> 9d908ecfb6b2  changed=False
  ERASE_EFFECT  on 零基线: 9d908ecfb6b2 -> 9d908ecfb6b2  changed=False
  ERASE_EFFECT  on q=+2 : 845c35898d2c -> 9d908ecfb6b2  changed=True ← 对照

杀死哪种错误实现：
  认为「没有摘要变化就没有写入」的实现。

期望：幂等写入仍必须产生 WRITE_COMMIT 记录
不得：因为没有变化就省略记录
```

### D-3 相同摘要对应不同执行（凌翼反例 #6）

```text
构造：两次独立执行产生相同状态摘要

杀死哪种错误实现：
  用摘要充当执行身份的实现。
  这正是 NB-50 的形态：两链公共主键不存在。

期望：必须可区分（靠 execution_id，不靠 digest）
现状：**不可能检测**（execution_id 未进 C1 evaluator）
```

## 组 E · 记录顺序 ≠ 发生顺序（凌翼反例 #7）

### E-1 采集顺序与提交顺序不一致

```text
构造：事件采集者先看到写入 A 的完成通知，后看到写入 B，
      但 B 的提交实际早于 A（记录延迟）

杀死哪种错误实现：
  把「记录顺序」直接当成「发生顺序」的实现。

期望：INVALID（顺序证据自相矛盾）
或：明确降级为「顺序未建立」

PASS 也不证明：不能证明一般情况下记录顺序可信。
```

### E-2 clock_ns 与 seq 矛盾

```text
构造：人为使 seq 递增但 clock_ns 倒退

杀死哪种错误实现：
  默默采信其中一个、不报告矛盾的实现。

期望：INVALID（矛盾必须暴露，不得自动仲裁）
待裁定：矛盾时以谁为准（我不自决，见设计草案 5.3）
```

# 4 · 三组之外，本文新增的两条判定要求

## 4.1 每条新字段必须填满五段式

```text
任何新增的时序字段（seq / execution_id / event_type / ...）
若不能同时给出：
   recorded_in / prod_gate / replay_gate / negative_test
⇒ 它只是 log，不是证据（凌翼 RC10 R2/R5 原文）。
⇒ 不得进入 REQUIRED_EVIDENCE_CONSUMPTION_MATRIX。
```

## 4.2 replay 必须与 prod 用同一条门

```text
矩阵 18 项中，每一项的 replay_gate 都写着
"-> same gate" 或 "-> same ... 重算"。
⇒ 这是既有纪律：replay 不得走一条较弱的门。
⇒ 任何时序门若只在 prod 实现、replay 不复算，
   则该字段不满足 CONSUMED。
```

# 6 · 如果一个用例失败了，应当怎么记

```text
按凌翼 D 项：
  缺证 ⇒ INVALID
  实测否定 ⇒ FAIL

⇒ 若 B-1（非原子快照）跑出 PASS，说明当前实现把撕裂快照当成了合法快照。
   这【不是】FAIL，是「实现缺一个保护」⇒ 应按 invalidity 处置，
   而不是宣布「快照不可信」这一科学结论。
⇒ 这个区分是本文最重要的操作纪律。
```
