⇒ 【"三项合取"是最要紧的词】：

## 二 · P1 · 统一锁域与全部有效签发路径的结构约束

### 2.1 要证明什么

```text
⇒ 「所有能产生有效签发效果的路径，都经过同一锁域与同一资格判定」。
```

### 2.2 证据形式

| 证据项 | 内容 | 可验证方式 |
|---|---|---|
| P1-a | 代码中【唯一】的签发入口清单 | 静态：导出全部写 EventRecord 的调用点 |
| P1-b | 每个入口都调用同一 `acquire_lock_domain()` | 静态：调用图 |
| P1-c | `lock_domain_id` 的派生规则唯一 | 静态 + §4 4.2(v) |
| P1-d | 不存在旁路的写路径（直接构造记录、外部注入）| 静态：符号引用 + 运行时 API hook 证据 |
| P1-e | 授予/撤销写入也走同一受控路径 | 静态 |

```text
⇒ 【P1 的性质】：这是【结构证据】，不是行为证据。
   ⇒ 它能证明"按理只有一条路"，
     不能证明"运行时确实只走了这条路"。
   ⇒ 【故 P1 单独不能断 HOLDS】，这正是"三项合取"的意思。
```

### 2.3 P1 的盲区（必须登记）

```text
⇒ · 动态加载的代码（插件/DLL 注入）可能绕过静态清单
⇒ · 反射/动态调用可能隐藏调用点
⇒ · P1-d 的"运行时 API hook"本身是被测环境的一部分
⇒ 【故 P1-e 需要独立于被测进程的证据】，见 Q1。
```

## 三 · P2 · 生命周期与资格状态转换记录

### 3.1 要证明什么

```text
⇒ 「资格的有效区间可被重建，且区间之间不重叠」。
```

### 3.2 证据形式

```text
⇒ 【转换事件集】（最少必要）：
   | 事件 | 含义 |
   |---|---|
   | `GRANT_BECAME_EFFECTIVE` | 资格开始生效 |
   | `GRANT_CEASED` | 资格失效（撤销/过期/释放）|
   | `PROCESS_STARTED` / `PROCESS_EXITED` | 实例生命周期 |
   | `LOCK_ACQUIRED` / `LOCK_RELEASED` | 锁持有区间 |

⇒ 【区间重建规则】：
   有效资格区间 = [GRANT_BECAME_EFFECTIVE, GRANT_CEASED)
   ⇒ 两个区间重叠 ⇔ 存在时刻 t 同时属于两者。
```

### 3.3 独立证据的要求

```text
⇒ 【裁定原文】：「有独立证据支持的生命周期及资格状态转换记录」。

⇒ 【"独立"的含义】：记录不能由被测进程自己写并自己读。
   ⇒ 至少须满足：
     · 记录写入方 ≠ 被测签发进程
     · 或记录带不可伪造的时序依据（承 §0 B-3：clock_ns 不参与排序）
```

```text
⇒ 【我在这里遇到实际困难】：
   本机单进程原型中，谁来写这些转换记录？
   ⇒ 若还是被测进程自己写，就不是独立证据。
   ⇒ 【故 P2 在当前架构下最多做到"半独立"】。
   ⇒ 登记见第六节。
```

### 3.4 P2 的盲区

```text
⇒ · 记录可能丢失（尤其是进程崩溃时）
⇒ · 记录可能被截断（尾部缺失 ⇒ 无法知道区间终点）
⇒ · 若用时间戳排序，则同一时钟源 ⇒ 不可靠（§0 B-3）
⇒ 【故 P2 需要第四项：区间覆盖的完整性证据】。
   ⇒ 而完整性又回到受信承诺（HWM/N5）那一套。
```

## 四 · P3 · 定向违例注入

```text
⇒ 【裁定点名三类】：
   ① 错误锁域
   ② 绕过入口
   ③ 过期资格缓存
```

| 注入 | 构造 | 期望 | 检出依靠 |
|---|---|---|---|
| **I1 错误锁域** | 两个进程用【不同】 `lock_domain_id` 但同一权威域 | 必须被发现为违规 | P1-c（锁域唯一性）|
| **I2 绕过入口** | 直接调用底层写接口，不经统一入口 | 必须被拒绝或被发现 | P1-a/P1-d |
| **I3 过期资格缓存** | 撤销后进程仍用缓存资格签发 | 必须被拒绝 | P2（撤销事件）+ 缓存失效机制 |

```text
⇒ 【I1 的关键】：若两个进程用不同 lock_domain_id，
   它们会各拿各的锁，互不阻塞。
   ⇒ 这不是"锁失效"，是"锁域被分叉"。
   ⇒ 检出它【必须比对域身份】，不能靠"锁是否被抢"。
```

```text
⇒ 【P3 的性质】：这是【反例证据】，只能证明"某类违规可检出"，
   不能证明"无违规"。
   ⇒ 故 P3 通过 ≠ S1 成立。
```

## 五 · WCT 可行性评估（裁定要求登记五类事项）

```text
⇒ 【WCT = Wait Chain Traversal】。知微在上一轮指出它支持 mutex，
   等待链含对象及所属线程，节点含 ProcessId / ThreadId。
```

### 5.1 五项登记（裁定点名）

| # | 事项 | 说明 | 当前状态 |
|---|---|---|---|
| 1 | **权限要求** | 打开目标进程并遍历等待链通常需要 `PROCESS_QUERY_INFORMATION` 等权限；跨会话/跨完整性级别可能被拒 | **未验证** |
| 2 | **查询竞态** | 查询瞬间的快照，查询结束与"下一次查询开始"之间是盲区 | **未验证** |
| 3 | **未等待线程** | 若某线程持有 mutex 但【未处于等待状态】，等待链可能不包含它 | **未验证** |
| 4 | **跨进程可见性** | 能否看到其他会话/其他用户的进程的等待链 | **未验证** |
| 5 | **观测盲区** | 见 5.2 | 分析如下 |

### 5.2 WCT 的结构性盲区

```text
⇒ 【最要紧的一条】：
   WCT 回答的是"谁在等"，不是"谁持有"。
   ⇒ 持有者若不在等待任何东西，它可能不出现。
   ⇒ 故【WCT 不能直接数出"两个持有者"】。

⇒ 【它能做的】：发现"两个线程在等同一个人"，
   从而间接暴露"有一个人持有着"。
   ⇒ 若出现"两个都在等 X，同时又各自声称持有",
     那才构成双持有线索。
   ⇒ 【但这需要额外证据】证明"各自声称持有"，
     而那正是 P2 的事。
```

```text
⇒ 【结论】：WCT 是【辅助线索源】，
   不能作为"区间内无重叠"的证明。
   ⇒ 与裁定"不能以某次查询未发现等待关系来证明整个区间不存在双持有者"一致。
```

# 第二部分 · C3 跨启动观察方案

## 七 · 裁定给定（B-14）

```text
⇒ 「C3 的跨启动验证，采用【具有独立进程身份的操作系统终止证据】，
   加上【新进程重新打开与验证记录】。
   仅关闭文件句柄、超时或在同一进程重读均不足以证明。」

⇒ 「Windows 的进程对象在进程终止后会进入 signaled 状态。
   验证器可以持有目标进程的有效句柄，确认其退出，
   再由独立新进程进行冷启动读取。」

⇒ 「但必须防止 PID 重用、子进程继续持有相关资源及观察对象认错；
   进程终止也不能证明断电持久性。」
```

## 八 · C3 验证方案

### 8.1 三个阶段

```text
⇒ 【阶段 A：写入方身份固定】
   记录 W 的：
     · PID
     · 进程创建时间（`GetProcessTimes` 的 CreationTime，非 PID）
     · 进程句柄（验证器持有）
   ⇒ 【为什么必须用创建时间而非 PID】：
     裁定点名"防止 PID 重用"。
     ⇒ PID 可被复用，创建时间不会。

⇒ 【阶段 B：终止确认】
   验证器 `WaitForSingleObject(hProcess, timeout)`
   返回 `WAIT_OBJECT_0` ⇒ 进程对象 signaled ⇒ 已退出。
   ⇒ 【这比"句柄关闭"强】：句柄关闭只说明引用计数归零，
     不说明进程退出。
   ⇒ 【比"超时"强】：超时只说明"还没等到"。

⇒ 【阶段 C：新进程冷启动读取】
   由【另一个进程】（不同 PID、不同创建时间）读取目标记录，
   记录：读取者 PID、创建时间、启动序号、读到的字节摘要。
```

### 8.2 必须防的三项（裁定点名）

| 风险 | 防护 |
|---|---|
| **PID 重用** | 用 (PID, CreationTime) 双元组作身份，不用 PID |
| **子进程继续持有资源** | 须确认进程树全部退出，或证明子进程不持有目标资源 |
| **观察对象认错** | 读取前校验记录路径/域/世代，不只看文件存在 |

```text
⇒ 【"子进程继续持有"这一项我原来没想到】：
   即使父进程 signaled，子进程可能仍持有文件句柄或锁。
   ⇒ 故"进程退出"≠"资源释放"。
   ⇒ 需要一个【进程树遍历 + 逐个确认】的步骤。
```

### 8.3 不能证明的事

```text
⇒ 【裁定明写】：「进程终止也不能证明断电持久性」。

⇒ 【故 C3 与断电一致性是两件事】：
   · C3 = 重启后可再读并验证
   · 断电持久性 = 掉电后数据仍在
   ⇒ 【C3 通过不蕴含断电安全】。
   ⇒ 后者仍是 §6 U-10 未覆盖模型。
```
