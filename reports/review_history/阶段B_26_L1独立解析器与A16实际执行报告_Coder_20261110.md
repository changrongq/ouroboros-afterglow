### 2.1 预期来源与解析器实现【分离】

```text
⇒ 凌翼原文：「建议测试工具与受测解析器分别实现预期结果来源，
             避免两者复制同一错误。」

⇒ 【我的做法】：
   · expected.py 【不 import parser.py】，不共享任何常量
   · 每条预期手写，并附【依据条文】（如 "B_23 §3.2c / §2 N3"）
   · 解析器的 TAG 白名单、字段数【独立手抄】一遍
   ⇒ 两份独立手抄若不一致，测试会失败

⇒ 【但如上所述】：两份都抄错成同一个错，测试看不出。
   ⇒ 故第三节的变异测试是必要的补充，不是装饰。
```

### 2.2 解析器判定顺序（严格按 B_23 §3.1）

```text
统一分派器：
  ① L ≥ 18            → R-V2-07
  ② MAGIC              → R-V2-02a
  ③ 读 FORMAT_VER      → v1 / v2 / 其他(R-V2-03)
  ④ 转交专用入口

专用入口（v1 或 v2）：
  ① 版本自检           → R-V2-02b（版本不匹配）
  ② L ≥ 18 / MAGIC     → R-V2-07 / R-V2-02a
  ③ 类型判定：
     v1: otype>=0x80   → R-V2-02c（§2 N3）
     v2: 0x80           → R-V2-04
         0x01-0x03     → R-V2-02d
         白名单外       → R-V2-05
  ④ RESERVED != 0      → R-V2-06
  ⑤ TOTAL_LEN != L     → R-V2-08
  ⑥ FIELD_COUNT != 实读 → R-V2-09
  ⑦ 实读 != 规定字段数  → R-V2-10b
  ⑧ TAG 序列 != 规范    → R-V2-10
```

```text
⇒ 【顺序本身就是被测对象】：
   NEG-06 与 X2 就是靠"版本先于类型"才区分开的。
```

## 四 · 顺带发现的规范问题

```text
⇒ 【FIELD_COUNT 的判定需要区分两种情况】，这是实现时发现的。
```

```text
⇒ §2 步骤 9 原文：
   「FIELD_COUNT == 实际字段数 == 该对象类型的【规定字段数】」
   ⇒ 这是【三个值、两个约束】：
     (a) 声明数 == 实读数
     (b) 实读数 == 规定数
   ⇒ 原规范只给了一个规则号（R-V2-09）。
   ⇒ 【实现时发现】：两者是不同失败点：
     · (a) 失败 ⇒ 声明与实际不符 ⇒ 可能是构造错误
     · (b) 失败 ⇒ 内容与该类型要求不符 ⇒ 可能是冒充
```

```text
⇒ 【我在实现里拆成了两个码】：
   · R-V2-09   = 声明数 ≠ 实读数
   · R-V2-10b  = 实读数 ≠ 规定数（新增）
   ⇒ 【但这是我的实现选择，不是规范原文】。
   ⇒ 需要裁定：规范是否应把 R-V2-09 拆成两条？
   ⇒ 若不拆，验收时两种情形会得到同一个码，无法区分。
```
