```text
⇒ 【本节的性质】
   §6 定义【矩阵内容】，本节定义【如何判定】。
   ⇒ 本节【不是】判定器的实现，是判定器的【判据】。
   ⇒ 不运行任何测试；不产生任何 PASS。

⇒ 【本节要回答的核心问题】
   给定一次测试运行留下的证据，
   【凭什么】说它通过了 —— 以及【凭什么】说它不能算通过。
```

```text
⇒ 【一条必须先立的总则（承 §0 E ⑤ 与 B-2）】
   "没有出现违规"与"无法判断"，【不是同一件事】，而且后者更常见。
   ⇒ 判定器的第一职责不是判 PASS，
     而是【识别哪些用例根本没有资格被判定】。
```

# 一 · 判定器的三层职责

```text
⇒ 承 §0 L120-121：本申请必须给出有界的
   「前提—状态转换—机制—不变量—失效后果」论证。
   ⇒ 判定器是这套论证的【执行端】，不是它的替代品。
```

| 层 | 职责 | 输出 | 不许做 |
|---|---|---|---|
| L1 · 可判定性 | 该用例是否有足够证据被判定 | `ELIGIBLE` / `NOT_ELIGIBLE` | 不得对证据不足的用例输出 PASS 或 FAIL |
| L2 · 判定 | 对 `ELIGIBLE` 的用例比对预期 | `EXPECTED_PASS` / `EXPECTED_STOP` / `UNEXPECTED_BEHAVIOR` | 不得把 `UNEXPECTED_BEHAVIOR` 归入前两类 |
| L3 · 汇总 | 按裁定 C 节六项判定 Gate | `TEST_GATE_PASS` / `TEST_GATE_NOT_PASS` | 不得在任一用例 `NOT_ELIGIBLE` 时输出 PASS |

```text
⇒ 【三层必须分开】
   ⇒ 若把 L1 与 L2 合成一步，
     "证据不足"会被就近归入"没失败"，就变成 §0 E ⑤ 警告的那个洞。
   ⇒ 若把 L2 与 L3 合成一步，
     一个 `UNEXPECTED_BEHAVIOR` 会被"其余都通过"稀释掉 ——
     而裁定 C.4 要求不变量违反为【零】。
```

# 二 · L1 · 可判定性（本节最重要的一层）

```text
⇒ 【承 §0 B-2】
   「每个计入验收的用例，必须提供故障触达及关键观测完整性的依据。
     必要依据缺失或观察器失效时，该用例不能记 PASS，
     具体分类由 §7 规定。」
   ⇒ 本节规定的分类，就是下面这三问。
```

## 2.1 三问必须分别有答案

| 问 | 要证明的事 | 需要的证据 | 缺失时 |
|---|---|---|---|
| Q1 **触达** | 注入确实落在声明的那个点上 | 注入点标识 + 实际命中记录（哪条规则/哪个边界） | `NOT_ELIGIBLE` |
| Q2 **观测** | 观测面覆盖到该点的全部相关状态 | 观测点清单 + 每个观测点在本次运行中确实产出记录 | `NOT_ELIGIBLE` |
| Q3 **完整** | 证据在故障后仍可读、未被截断 | 证据存储位置独立于被测进程；完整性校验通过 | `NOT_ELIGIBLE` |

```text
⇒ 【三问的关系是"与"，不是"或"】
   ⇒ 任一为否 ⇒ `NOT_ELIGIBLE`。
   ⇒ 【不得】用"另两问都满足"弥补第三问。
```

## 2.2 「没有出现违规」的四种实际情形，必须能区分

```text
⇒ §0 E ⑤ 要求：
   「没有出现违规，必须能与 ①没有触达 ②没有观测 ③证据丢失 三者区分开。」
```

| 情形 | 判定 | 理由 |
|---|---|---|
| 真正执行了，且违反计数为 0 | `ELIGIBLE` → 可进 L2 | 这是唯一有资格谈"通过"的情形 |
| 注入没触达目标点 | `NOT_ELIGIBLE`（触达缺失） | 相当于这一格没测 |
| 触达了但观测面没覆盖 | `NOT_ELIGIBLE`（观测缺失） | 违反可能发生但看不见 |
| 触达且观测了，但证据丢失/被截断 | `NOT_ELIGIBLE`（证据不完整） | 无法回溯，等于没记 |

```text
⇒ 【一条硬规则】
   `NOT_ELIGIBLE` 的用例【不得】计入"通过数"，
   也【不得】计入"失败数" —— 它是第三类，必须单独计数并披露。
   ⇒ 三种计数必须在报告里【分列】，不得合并。
```

## 2.3 观察器自身失效的识别

```text
⇒ 【这一条是 §0 B-2 修正的直接落点】
   原文曾写「不检测自身观测失效」——若全面豁免，
   E⑤ 的验收义务就可被绕过：
   日志随进程死亡而丢失，判定器仍可能按"没有失败记录"放行。
```

```text
⇒ 【判定器必须能回答：观测器坏了没有？】
   (a) 观测器与被测进程【不同生命周期】
       ⇒ 若两者同时被中止，则 Q3 视为不满足；
   (b) 观测器产出【心跳/序号】
       ⇒ 缺失或回退 ⇒ 视为观测未覆盖该区间；
   (c) 每个注入点有【预期观测条目数】
       ⇒ 实际条目不足 ⇒ 视为 Q2 不满足。

⇒ 【不得】以"日志中没有错误行"作为观测正常的证据 ——
   日志本身可能就是那个失败的观测器。
```

# 三 · L2 · 判定（区分"预期停止"与"实现异常"）

```text
⇒ 【这是裁定最关心的一条】
   「不能把每次异常都简单归为成功或停止。」
   ⇒ 故每一格的结果必须落入三类之一，且第三类不得被吸收进前两类。
```

| 判定 | 含义 | 当 RULER 结论为"停止"时适用 |
|---|---|---|
| `EXPECTED_PASS` | 实际动作与**该格已登记的动作和后态**一致，且不属于 STOPPED | 不适用 |
| `EXPECTED_STOP` | 按 §6 该格预期为 STOPPED，实际也 STOPPED，**且命中规则与预期规则集合一致** | 须核 rule_id |
| `UNEXPECTED_BEHAVIOR` | 其余全部情形 | 包括"停了，但停的理由不对" |

```text
⇒ 【2026-11-06 修正：原词表装不下矩阵里的合法结果（知微 ③）】

⇒ 反例：F-4b-1（W 尝试写授予记录）
   正确结果是：**W 的写请求被拒、记录内容未变、R 继续工作**。
   ⇒ 这不是 STOPPED，也不是"安全恢复"。
   ⇒ 旧 `EXPECTED_PASS` 只指"安全恢复"，故这个【正确结果】
     会落入 `UNEXPECTED_BEHAVIOR`。

⇒ 同类：F-6-3（拒绝新建、读取既有身份）、F-2-4（正确计入 max）
   也都不是"安全恢复"，也不是 STOPPED。

⇒ 【改法：用"符合本格已登记的动作和后态"统一定义用例成功】
   把下列分别作为【可断言的动作】，而不是全部塞进两三类：
     · STOPPED（入口关闭、不再产生受禁操作）
     · 安全恢复到可签发
     · 单操作拒绝（写入/请求被拒，其余不受影响）
     · 复用既有身份（不新建）
     · 正确计入集合（如 epoch 进入 max）
   ⇒ 每格在运行【前】按前置条件选定【唯一】预期动作；
     若一格有多个合法分支（如 F-1-1"STOPPED 或按 P4 恢复判定"），
     【须拆成子格】，不得让"该格预期"本身不唯一。
```

```text
⇒ 【关键区分：停了 ≠ 停对了】
   ⇒ `EXPECTED_STOP` 要求两件事同时成立：
     (1) 该格预期结果确实是 STOPPED；
     (2) 实际停止所依据的规则【属于】该格"判定依据"所指的规则集合。
   ⇒ 若某格预期因 N16 拒绝，而实现因 N1 拒绝
     ⇒ 二者都是"拒绝"，但【不是同一件事】
     ⇒ 判 `UNEXPECTED_BEHAVIOR`。
```

```text
⇒ 【"等于"必须可执行：rule_id 规范化（2026-11-06 补，三人一致要求）】

   ⇒ 问题：§6「判定依据」列现在实录成多种形态——
     F-1-2  `§5 2.1 / 4.5(i) / §5 六`      ← 三条并列
     F-2-3  `P4-3.1 前置依赖`              ← 一条规则名
     F-5-6  `§4 4.5 五步 / 裁定 A 节末`     ← 正向格
   ⇒ 多规则并列时，"等于"是【命中任一】还是【全部】？未定。

   ⇒ 【本版规定：每个确定性格绑定一个规则 ID 集合】
     · 规则 ID 取稳定、可机器比对的标识（如 `N16` / `P4-3.1(d)` /
       `§5.C3` / `§4.4.WAIT_ABANDONED`），不用自然语言句子
     · 【集合语义】：预期为【命中任一】即合格，
       但实现须输出【实际命中的那个 ID】（不是"我命中了某条"）
     · 集合为空的正向格（如 F-5-6）须标明"正向"，不参与规则比对

   ⇒ 【停止理由不得采信被测方自报】
     若由被测实现报告"我因 N16 停止"，它可以是假的。
     ⇒ 判定器须能从【非被测方的证据】独立复算出命中哪条规则。
     ⇒ 这与 §2 的"规则性拒绝"（不得以语言层异常当拒绝路径）
       是同一精神：拒绝/停止必须带可核的规则标识。
   ⇒ 理由：若允许"任意拒绝都算通过"，
     那么一个把所有输入都拒绝的实现会拿满分 ——
     这正是"弱化 STOPPED 条件来提高通过率"的变体（裁定 B 节禁止）。
```

```text
⇒ 【`UNEXPECTED_BEHAVIOR` 的处置】
   · 记入不变量违反计数（裁定 C.4 要求为零）
   · 保留证据，不得重跑覆盖
   · 【不得】自动重试（裁定 B 节：测试失败不得由自动重试掩盖）
```

# 四 · L3 · 汇总（照录裁定 C 节六项）

```text
⇒ TEST_GATE_PASS 必须【同时】满足以下六项：
   1. 指定安全不变量均有可执行断言
   2. 预定故障矩阵覆盖完成，无静默跳过项
   3. 最低轮次完成
   4. 安全不变量违反为零
   5. 预期 STOPPED 的路径全部真实停止
   6. 结果证据可独立复核
```

```text
⇒ 【本节对六项的可执行化，逐项说明】
```

| # | 判定器如何核 | 不满足时 |
|---|---|---|
| 1 | §6 第一节 S1–S5 每条都有"可执行断言的形式"列且非空 | `NOT_PASS` |
| 2 | **逐格逐分支计数**（见下），不是"每格至少一条" | 任一必测格/分支未达标 ⇒ `NOT_PASS` |
| 3 | 四类轮次（30/1000/100/30）逐类计数达标 | 任一类不足 ⇒ `NOT_PASS` |
| 4 | `UNEXPECTED_BEHAVIOR` 计数 = 0 | >0 ⇒ `NOT_PASS` |
| 5 | 每个预期 STOPPED 的格，判定理由 = 预期规则（见第三节） | 任一不符 ⇒ `NOT_PASS` |
| 6 | 证据可由**非被测方**独立复核（见第五节） | 否则 ⇒ `NOT_PASS` |

```text
⇒ 【第 2 项的可执行化：逐格逐分支计数（2026-11-06 重写，知微 ③）】

   ⇒ 【原写法有漏洞】
     原文只要求"每格至少一条运行记录 + 披露 NE 数"。
     ⇒ 反例：某必测格（如 F-4b-1）只有 1 条记录且为 `NOT_ELIGIBLE`，
       其余格补足分类轮次，`UNEXPECTED_BEHAVIOR` 为零。
       只照原表写的汇总器【会放行】。

   ⇒ 【本版规定】
     (a) 每个【必测格】（§6 全部 55 格）都须独立计入；
         【不得】用其他格的记录补救。
     (b) 每个确定性格须满足【≥30 次合格记录】；
         该格的 `NOT_ELIGIBLE` 【不能】计入合格数。
     (c) 一格若有多个合法分支（如 F-1-1 的"STOPPED 或走恢复判定"），
         【每个分支分别计数】，不得合并。
     (d) `NOT_ELIGIBLE` 须【单独分列】并标明：
         该格是否因此【未达轮次】。
     (e) 【显式跳过、补跑、挪入 U 列表，均不能抵消原轮证据】。
         若某格最终无法达标 ⇒ Gate 不通过，
         且该缺口须按 §6 第六节列入未覆盖。

   ⇒ 【与第 3 项的区别】
     第 3 项是【分类总量】达标；本项是【逐格】达标。
     ⇒ 二者【都要满足】，不得用一个替代另一个。
```

```text
⇒ 【第 2 项的一条补充】
   "覆盖完成，无静默跳过项"不等于"每格都通过"。
   ⇒ 一格的 `NOT_ELIGIBLE` 是【显式披露的跳过】，不是静默跳过；
     但它【仍然不能】计入通过。
   ⇒ 若某格长期 `NOT_ELIGIBLE`，说明观测面或注入能力不足，
     该缺口须按 §6 第六节的方式【显式列入未覆盖】。
```

```text
⇒ 【即使六项全满足，也只能写】
     BOUNDED_PROTOTYPE_TEST_GATE = PASS
   【不能】写 GENERAL_SAFETY_PROVEN = YES。
```

# 五 · 证据的独立可复核性

```text
⇒ 裁定 C.6：「结果证据可独立复核」。
   ⇒ 本节给出它最小含义。
```

| 要求 | 具体 | 反面 |
|---|---|---|
| 证据由非被测方保存 | 测试控制方（S）侧，不随被测进程中止 | W 自己写的日志 |
| 可离线重算 | 输入字节 + 判定规则 ⇒ 结论可被第三方重算 | 只有"判定器说通过了" |
| 随机种子与命令留痕 | 种子、注入位置、执行命令、判定器版本 | 只留结果 |
| 失败证据保留 | 每次失败的状态与事件证据 | 只留通过数 |

```text
⇒ 【一条与 §5 同源的边界】
   ⇒ 证据哈希一致只能证明"你读到的是我看到的那一份字节"，
     【不能】证明内容正确。
   ⇒ 故证据的可复核性需要【可重算】，不只是【可对账】。
```

# 六 · `CHECK_ALIGNMENT_WITH_S0`（§0 F 节指定，落在此处）

```text
⇒ 【§0 原文】
   CHECK_ALIGNMENT_WITH_S0 =
       逐条取出本节 A/B/C/D 全部条目，
       对每一条回答两个问题：
         (i)  在 §1~§7 中，有没有任何结论或声明与它冲突？
         (ii) 若 §0 的某条被推翻或修订，
              §1~§7 中哪一节必须同步修改？
       任一条答不上来 ⇒ 不得提交定版。

   ⇒ 该项写入 §7 的验收判据，不留在本节作意图。
```

## 6.1 判定器如何执行它

```text
⇒ 【输入】§0 A/B/C/D 全部条目（不是抽样，是全部）
⇒ 【输出】每条一行，三列：
     §0 条目号 | (i) 结论 | (ii) 同步责任节
   ⇒ (i) 的取值只有三种：
       CONFLICT（有冲突，须指明 §x 的哪句）
       NO_CONFLICT（无冲突）
       UNANSWERABLE（答不上来）
   ⇒ (ii) 必须给出具体节号，不得写"N/A"除非该条被推翻的可能性为零
     且给出了理由。
```

```text
⇒ 【判据】
   · 存在任一 `CONFLICT` ⇒ 不得提交定版
   · 存在任一 `UNANSWERABLE` ⇒ 不得提交定版
   · 全部 `NO_CONFLICT` 且 (ii) 均已答 ⇒ 该检查项通过
```

```text
⇒ 【一条必须写明的限制】
   ⇒ 本节【只规定如何执行】，不规定执行结果。
   ⇒ `CHECK_ALIGNMENT_WITH_S0` 的实际执行
     须待 §7 完成后进行，本轮【未执行】。
   ⇒ 故 §0 的 `CROSS_CHECKED_WITH_FAULT_MATRIX` 仍为 NO，
     §6 状态中 `S0_BACKFILL_PENDING = YES` 仍成立。
```

## 6.2 为什么它不能是"意图"

```text
⇒ §0 自己承认过：
   「本节开头写『后面不得悄悄变成已证明』，
     结尾写『后面每写一节都要回头问』——
     两处都是【意图】，全文没有一个【可执行的检查点】。」
⇒ 故本节把它做成：
   · 输入被限定为"全部条目"（可清点，不可声称）
   · 输出被限定为三值（不存在"大概一致"）
   · 判据是存在性判定（有 CONFLICT/UNANSWERABLE 即不通过）
   ⇒ 于是"对齐"从一个态度，变成一个【会失败的检查】。
```

# 七 · 判定器自身的不可证性

```text
⇒ 【本节必须承认的元层残余】
   ⇒ 判定器本身也可能被错误实现。
   ⇒ 本原型【不证明】判定器正确。
   ⇒ 所能做的只是把它拆成三层，使每层可被分别质疑：
     · L1 可判定性：三问是否问全了（本文件可读、可争）
     · L2 判定：三类是否互斥且穷尽（本文件可读、可争）
     · L3 汇总：六项是否照录（可与裁定逐字比对）
   ⇒ 这与 §6 U-8「判定器自身被错误实现的可能」对应。
```

```text
⇒ 【因此判定器的结论也必须带边界】
   它可以输出 `BOUNDED_PROTOTYPE_TEST_GATE = PASS`。
   它【不能】输出 "判定器正确" 或 "结论无误差"。
```

## 一句

```text
⇒ 这一节最容易被写成"我们的判定器会检查这些"。
被写成那样时，它已经没用了 ——
因为判定器描述自己会检查什么，不产生任何约束。

⇒ 这一节能做的是把"通过"逼到只剩一条路：
   先证明这一格【值得一提】，
   再证明它【停对了】，
   最后才允许它计数。

⇒ 如果这一节只剩一句话，
   那应该是：
   判定器最大的功劳不是判出 PASS，
   而是把那些根本没测到的用例，
   从"通过"里挑出来，放到它自己那一栏。
```
