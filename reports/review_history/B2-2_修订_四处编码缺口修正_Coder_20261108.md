## 一 · 缺口 (1)：N3 是否需要拆成两个对象类型

```text
⇒ 【我原提案】：0x83 一个类型 + `grant_kind`（1=授予 2=撤销）。
   并在原文件 Q2 里自己标了"需要复核确认"。
```

### 1.1 反对拆分的理由

```text
· 授予与撤销共享同一组字段（recorder_id / domain / generation /
  grant_epoch / revoke_epoch / predecessor）
· 它们是同一条链上的先后事件，同一对象类型有利于链验证
· 少一个类型 = 少一处域分离维护
```

### 1.2 支持拆分的理由（我认为更强）

```text
⇒ 【理由一：故障语义完全不同】
   · 授予写错 ⇒ 多了一个不该有的资格
   · 撤销写错 ⇒ 少了一个本该失效的资格
   ⇒ 这两类故障在 §6 里是【不同的格】，判定路径不同。
   ⇒ 若同类型，判定器需要先读 `grant_kind` 才能选判定路径，
     而 `grant_kind` 本身是【被判定对象的一部分】——
     一个可能被篡改的字段不能决定如何判定它自己。

⇒ 【理由二：`revoke_epoch` 的语义在同一类型下是二义的】
   · 授予记录里 `revoke_epoch` 是"预期撤销点"，可为全 FF（未定）
   · 撤销记录里 `revoke_epoch` 是"实际撤销点"，不可为全 FF
   ⇒ 同一字段在同一类型下有【两种合法性约束】，
     这违反"一个类型一套约束"的基本要求。
   ⇒ 我在原文件非法反例表里已经写了
     「`grant_kind = 2` 但 `revoke_epoch` 为全 FF ⇒ 非法」
     —— 那一条本身就在承认：这两个东西不是同一个东西。

⇒ 【理由三：域分离的原始动机】
   §2 2.2 的域分离是为了防止"把 A 的字节当 B 用"。
   ⇒ 授予记录与撤销记录【语义相反】，
     把它们塞进同一类型，恰恰是域分离要防的情形。
```

### 1.3 我的建议

```text
⇒ 【建议拆分】：
   0x83  GRANT_RECORD      授予
   0x87  REVOCATION_RECORD 撤销（新编号，接在 0x86 之后）

⇒ 【字段差异】：
   | 字段 | GRANT (0x83) | REVOCATION (0x87) |
   |---|---|---|
   | `recorder_id` | 必填 | 必填 |
   | `authority_domain` | 必填 | 必填 |
   | `generation` | 必填 | 必填 |
   | `grant_epoch` | 必填（生效点） | **不设**（由被撤销的授予决定） |
   | `grant_ref` | 不设 | **必填**（指向被撤销的 GRANT 摘要） |
   | `revoke_epoch` | 不设 | 必填，**不得为全 FF** |
   | `reason_code` | 不设 | 必填（为什么撤销） |
   | `predecessor_digest` | 必填 | 必填 |

   ⇒ 【关键差别】：REVOCATION 不含 `grant_epoch`，
     而是用 `grant_ref` 指向被撤销的那条授予。
     ⇒ 这样"撤销的是哪一次授予"是【显式引用】，
       不是"同一 recorder 的最近一条授予"这种推断。

⇒ 【编号顺延影响】：
   原 0x86 = N5 承诺。新增 0x87 不影响它。
   ⇒ 但若复核者认为 N5 应占 0x86 之后、
     撤销应插在更前，请指定顺序 —— 编号顺序本身无语义，
     但一旦定版就不能改。
```

```text
⇒ 【这不是我能定的】：凌翼要求"复核"，
   所以我给理由与建议，不给结论。
```

## 二 · 缺口 (2)：`max_scope_digest` 必须绑定可复算的集合

```text
⇒ 【我原来写的】：
   `max_scope_digest` = "max 取值集合的摘要"
   ⇒ 【问题】：没说清
     · 集合元素是什么
     · 元素如何规范化
     · 顺序算不算
     · 用哪个对象类型做域分离
   ⇒ 结果：两个人按我的写法可以算出不同摘要，
     而这个字段的全部价值就在于"可复算"。
```

### 2.1 重写：`max_scope_digest` 的规范定义

```text
⇒ 【定义】：
   max_scope_digest = SHA-256(
       OBJECT_TYPE_maxscope ‖ FORMAT_VER ‖
       authority_domain_len ‖ authority_domain ‖
       generation ‖
       range_start_seq ‖ range_end_seq ‖
       element_count ‖
       ELEMENTS
   )

   ⇒ 【新增一个对象类型】用于域分离：
     0x88  MAX_SCOPE_SET   （提案编号）
     ⇒ 若不复用 0x82 的摘要域，可保证"集合摘要"与
       "记录摘要"不可能互换。

⇒ 【集合元素定义】（这是原来缺的核心）：
   一条元素 = 一条【被纳入 max 计算的已提交分配】
   元素字节 = seq(8, BE) ‖ epoch(8, BE) ‖ record_digest(32)
   ⇒ 【只含已提交分配】，不含 PENDING、不含已排除者。
   ⇒ 【必须能对应回 N2 记录】：record_digest = N2 记录的摘要。

⇒ 【顺序】：
   ELEMENTS 按 `seq` 【升序】排列，不得有重复 seq。
   ⇒ 理由：若按集合语义（无序），两个实现可算出不同摘要；
     按 seq 升序则唯一。
   ⇒ 这也回答了我原文件 Q4 的疑问：**纳入顺序**，且顺序固定为 seq 升序。

⇒ 【覆盖范围】：
   range_start_seq = 集合中最小 seq
   range_end_seq   = 集合中最大 seq
   ⇒ 二者与实际元素【必须一致】，否则非法。
```

### 2.2 为什么这样定义才"可复算"

```text
⇒ 复核者拿到一条 N2 记录，应能：
   ① 按 range 从历史里取出全部已提交分配
   ② 按 seq 升序排序
   ③ 逐条算元素字节
   ④ 拼成规范串求 SHA-256
   ⑤ 与记录里的 `max_scope_digest` 比对
   ⇒ 五步全是确定性操作，不依赖实现内部状态。

⇒ 【能检出的东西】：
   · "算对了但来源错"（同 max 不同集合）⇒ 摘要不同
   · "漏算了某条已提交分配" ⇒ 摘要不同
   · "多算了 PENDING" ⇒ 摘要不同

⇒ 【检不出的】：
   · 集合摘要是对的，但实际 max 计算用了别的方式
     ⇒ 这需要【控制流证据】，摘要给不了
     ⇒ 承知微 N99-01：须"记录来源 + 控制流 + 重算"三项同时可核。
```

### 2.3 非法反例补充

| 情形 | 判定 |
|---|---|
| `element_count` 与实际元素数不符 | 非法 ⇒ NOT_COMMITTED |
| 元素 seq 重复 | 非法 |
| 元素 seq 非升序 | 非法 |
| `range_start/end_seq` 与元素不符 | 非法 |
| 存在一条已提交分配未纳入集合 | 摘要不符 ⇒ 可检出 |
| 集合含 PENDING 记录 | 摘要不符 ⇒ 可检出 |

## 三 · 缺口 (3)：N4a 必须给 N4b 足够依据独立验证

```text
⇒ 【我原来写的】：
   `intent_payload_digest` = "拟写入内容的摘要（不写内容本身）"
   ⇒ 【问题】：N4b 拿到这个摘要，能验证什么？
     · 能验证：结案内容与准备意图【一致】
     · 不能验证：那个意图【本身是否合法】
   ⇒ 而 F-1-2/B2 要判的是"排除效果"，不只是"前后一致"。
   ⇒ 若 N4a 只给摘要，N4b 无从判断
     "这条意图是否本来就该被允许"。
```

### 3.1 补充字段

```text
⇒ 【N4a 增补四个字段】：

   | 字段 | 类型 | 说明 |
   |---|---|---|
   | `intent_scope_digest` | bytes[32] | 该意图【成立所依据的历史范围】摘要（用 0x88 同一规范化） |
   | `intent_predicate` | u8 | 该意图声明的【合法性谓词类型】（见下） |
   | `intent_predicate_args` | bytes | 谓词参数，按 `intent_predicate` 定长 |
   | `issuer_ref` | bytes[32] | 发起该意图的身份/授予摘要 |

⇒ 【`intent_predicate` 取值（提案）】：
   0x01 EPOCH_GREATER_THAN_SCOPE_MAX
        args = scope_digest(32) ‖ expected_max(8)
        ⇒ 声明：新 epoch > 该范围内所有已提交分配的最大值
   0x02 IDENTITY_NOT_IN_DOMAIN
        args = domain_digest(32)
        ⇒ 声明：该身份不在该域中
   0x03 GRANT_ABSENT
        args = recorder_id(16) ‖ domain_digest(32)
        ⇒ 声明：该 recorder 在该域无有效授予

   ⇒ 【为什么这样做】：N4b 可以独立复核谓词 ——
     用 `intent_scope_digest` 取范围、重算集合、
     验证谓词是否真的成立。
     ⇒ 而【不需要】相信 N4a 说"我要写 X"。
```

### 3.2 N4b 的独立验证流程

```text
⇒ N4b 收到一条指向 N4a 的结案记录后，应当：
   ① 按 `attempt_ref` 取出 N4a
   ② 用 `intent_scope_digest` 重建该范围（按 2.1 的规范）
   ③ 验证 `intent_predicate` 在该范围下【真的成立】
   ④ 验证 `result_payload_digest` 与 `intent_payload_digest` 一致
   ⑤ 验证 N4a 的 `issuer_ref` 指向的身份/授予合法
   ⇒ 五步全过 ⇒ 结案合法

⇒ 【任一步失败的分类】：
   | 失败步 | 分类 |
   |---|---|
   | ① N4a 不存在 | 结案不可验证（F-1-2/B4） |
   | ① N4a 属于别的 recorder | 关联错配（F-1-2/B6） |
   | ② 范围无法重建 | 范围完整性不可确认 ⇒ STOPPED |
   | ③ 谓词不成立 | **实现缺陷** ⇒ FAIL_IMPLEMENTATION |
   | ④ 内容不一致 | 结案与意图不符 ⇒ FAIL_IMPLEMENTATION |
   | ⑤ 身份/授予非法 | 越权 ⇒ FAIL_IMPLEMENTATION |
```

```text
⇒ 【这解决了什么】：原设计里 N4b 只能验"前后一致"，
   现在能验"这条意图本来就该被允许"。
   ⇒ 而"排除效果"（F-1-2/B2 的 d 项）正是后者。
```

## 四 · 缺口 (4)：N5 不能靠自身前驱摘要宣告不可回滚

```text
⇒ 【我原来写的】：
   N5 有 `commitment_seq` 与 `predecessor_digest`。
   ⇒ 【问题】：凌翼直接指出 ——
     「不能仅通过自身前驱摘要宣告不可回滚」。

⇒ 【为什么前驱摘要不够】：
   若一次整机回滚把 N5 链一起带回到某个自洽的早期版本，
   ⇒ 该版本的 `predecessor_digest` 链条【完全自洽】，
     没有任何断链。
   ⇒ 前驱链只能证明"这条 N5 与其前驱一致"，
     不能证明"曾经存在过更晚的 N5"。
```

### 4.1 N5 增补字段

```text
⇒ 【N5 增补三个字段】：

   | 字段 | 类型 | 说明 |
   |---|---|---|
   | `hwm_value` | u64 | 引用该承诺时，受信高水位的值 |
   | `hwm_digest` | bytes[32] | 高水位记录的摘要（用于定位被替换） |
   | `root_ref` | bytes[32] | 指向信任根（§5 二 (r1)(r3)） |

⇒ 【关键变化】：N5 不再自证不可回滚，
   而是【把判定依据指向 HWM 与 root】：
   · HWM 的不可回退性由介质/边界保证（B2-3/Q3 1.2）
   · root 的身份由 §5 二 (r1)(r3) 保证
   ⇒ N5 只是【记录了一次引用】，
     判定时要【去读 HWM 与 root 核对】，不能只看 N5。

⇒ 【检出条件（修正后）】：
   | 条件 | 说明 |
   |---|---|
   | N5.predecessor_digest 断链 | N5 自身被改 |
   | N5.hwm_value ≠ 当前 HWM | N5 回滚而 HWM 未回滚 |
   | N5.root_ref 无法解析到合法 root | 根被替换/未预登记 |
   | N5.commitment_seq 非单调 | 被插入或删除 |

   ⇒ 【四个条件全部不成立时，仍可能检不出】——
     即"三方一起回滚"。这一点已在八项矩阵 RE-6 登记。
```

### 4.2 与 B2-3/Q3 的衔接

```text
⇒ 本修订【依赖】 Q3 选型文件的可信高水位设计：
   · HWM 只能增不能减（H2）
   · HWM 与 N5 同一受信事务（H3）
   · 恢复第一步读 HWM（H4）

⇒ 【若 Q3 的介质分离前提不成立】，则：
   N5.hwm_value 的比对仍可做，
   但 HWM 可能与 N5 一起被回滚 ⇒ 比对通过而实际已回滚
   ⇒ 此时 `HISTORY_ROLLBACK_DETECTION = NOT ESTABLISHED`。

⇒ 【即】：本修订让 N5 有了正确的引用结构，
   但【不改变】"回滚独立取决于介质边界"这个结论。
```
