# Afterglow 仓库独立审阅

审阅人：知微。用户请求：完整查看 GitHub 仓库。此次为审阅，不是冻结签署或实现修改。

固定提交：[`4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0`](https://github.com/changrongq/ouroboros-afterglow/tree/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0)。结论仅针对该提交。

## 结论

**目前不支持把 RC6 记为独立核验通过的完整 Reference Harness qualification。**

原因有两类：GitHub 发布字节与冻结绑定不一致；若干 fixture 可以在内部证据已经失败时仍输出预期答案。后者通过实际反例测试复现，不能只修文档或更新 hash 解决。

这不否定 substrate / reader / J 的设计。固定长度、SET、精确分数、完整文件长度检查等基础组件已经写成代码并通过现有测试。需要修的是从观察到最终判定之间的执行与证据链。

README 如实注明 OS 级隔离未完成、科学实验不得开始，这是正确的边界。但仅有逻辑层测试，也仍需让判定真实依赖输入证据；不能用已知缺少 OS 隔离来解释本报告中的结果硬编码与漏检。

## 审阅范围与方法

- 获取固定提交的 GitHub ZIP，按原始字节解包到独立工作区；没有使用 Git checkout 的换行转换。
- 又通过 GitHub Git Blob API 单独读取 `harness_constants.py` 与 prereg 主路径文件，确认它们与解包副本逐字节相同，排除了这两项差异由本地解包引入的可能。
- 阅读核心 SPEC、MANIFEST、冻结记录、detached errata、RC6 交付记录、实现模块、fixture、校验脚本及 raw/ledger。历史信件按最新决定与相关问题追溯，不把全部往来信件当成当前规范。
- 运行仓库现有组件测试、evaluator 测试、J 时点检查、绑定检查及 13 项 suite。
- 在内存替换或另建的诊断副本中注入故障，验证已知错误是否会被拒绝。**这些故障运行不是 qualification，也不代表生产代码已经发生了所有这些故障。** 它们证明校验路径不能可靠检出相应问题。
- 未推送 GitHub、未修改下载副本中的原始跟踪文件。原文件逐一 hash 检查保持一致；重跑产物写入脚本原定的独立输出目录。

## 2. [P1] 发布字节与绑定不一致，且 prereg 主路径指向另一份文本

源码绑定漂移涉及 9 个组件与 2 个 driver。逐文件检查发现：**把 GitHub 中对应 `.py` 的 LF 转成 CRLF，恰好得到 MANIFEST 记录的 hash。**

例：

```text
harness_constants.py
GitHub：7863 bytes，SHA-256 前缀 9c31e92d07cbd933…
绑定值：8078 bytes，SHA-256 前缀 a0ce6180ceb6cc2f…
差额：215 bytes，恰好是 215 个 LF 转 CRLF 的差额。
```

`.gitattributes` 对 Python 文件显式设置 `text eol=lf`，而被冻结的源码 hash 对应 CRLF 字节。因此仅保护 SPEC/MANIFEST 不够，源码也属于被绑定对象。[属性文件](https://github.com/changrongq/ouroboros-afterglow/blob/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0/.gitattributes)

父预注册另有实际文件不匹配：

| 位置 | bytes | SHA-256 |
|---|---:|---|
| `prereg/AFTERGLOW_MVP_PREREGISTRATION_v0.1.md` | 32234 | `9da7a60b552a7a88db7ce46e6e32d2f46bd6a547b1b18694551db4ea81e57579` |
| `reports/review_history/AFTERGLOW_MVP_PREREGISTRATION_v0.1_FREEZE_CANDIDATE.md` | 52129 | `ad0855b04561147685f41de2c3cf1529e669cf7535345862a5f9c8b30b40d5f4` |

真正匹配绑定值的文件仍在仓库中，但不在 README/交付说明指向的 prereg 主路径。二者不是换行差异。

SPEC 本次实际为 36719 bytes / `b7ec1fdc…`，MANIFEST 为 22904 bytes / `ba120276…`，两者与当前仓库声明匹配。仓库记录了后续采用 b7ec 作为根引用的决定；本审阅按该声明检查，不继续把本地早先 1386 版本当作当前仓库唯一候选，也不代替全船确认历史签署。

**修复方向：** 明确每个根对象的 canonical 路径与字节；让发布过程保护全部绑定文件。现有 CRLF 绑定若要保留，应从可信原件恢复准确字节；若统一 LF，则更新实际源码绑定、MANIFEST 和资格记录，不能沿用 RC6 PASS。

## 3. [P1] V2/V3 丢弃 Basic L1 结果，写入未发生仍宣称 PASS

位置：[fixtures.py:320](https://github.com/changrongq/ouroboros-afterglow/blob/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0/afterglow_harness/fixtures.py#L320)、[fixtures.py:347](https://github.com/changrongq/ouroboros-afterglow/blob/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0/afterglow_harness/fixtures.py#L347)。

`_three_arm()` 返回真实 L1 结果，但 V2/V3 用 `_` 丢弃它，最终 `actual` 中直接写 `L1=PASS` 以及 C2/C3 层级。循环 ledger 还只保留最后一个 member。

**反例：** 测试中把 `storage_write` 替换成 no-op，让 literal 确实保持零；不改变 extra writer。

```text
V2：内部 ledger.l1 = FAIL，h=0
    actual.L1 = PASS，PRE_RESET_CHANGE_CLASS=C2，oracle_match=True

V3：内部 ledger.l1 = FAIL，h=0
    actual.L1 = PASS，PRE_RESET_CHANGE_CLASS=C3，oracle_match=True
```

这违反正向层级必须先通过 Basic L1 的要求。是否出现字符串 `fixture_id` 分支不能证明无硬编码：fixture 自己写死 `actual` 也会产生同样问题。

**修复方向：** 所有 actual 状态由通用判定流水线返回；fixture 只提供配置与故障注入。逐 member 消费真实 L1/C2 结果，不能由 fixture 填 PASS。把上述 no-op 测试加入回归，要求拒绝提升层级。

## 4. [P1] V5 的 post-reset 判定使用 reset 前数据，部分 C1/C2 结果直接写定

位置：[fixtures.py:562](https://github.com/changrongq/ouroboros-afterglow/blob/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0/afterglow_harness/fixtures.py#L562)、[fixtures.py:657](https://github.com/changrongq/ouroboros-afterglow/blob/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0/afterglow_harness/fixtures.py#L657)、[fixtures.py:717](https://github.com/changrongq/ouroboros-afterglow/blob/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0/afterglow_harness/fixtures.py#L717)。

`per_T_post_j` 在 reset 之前计算，却被直接作为 post-reset C3 输入。V5b 给 `_l2_judge()` 直接传 C1、C2；V5d 直接传 C1 未建立与 C2 FAIL；V5e 直接传 C1 未建立与 C2 UNRESOLVED，而不是从 reset 后新观察推导。

**真实状态故障注入反例：**

| 测试 | 故意执行的错误 J | 真实状态含义 | 实际输出 |
|---|---|---|---|
| V5b | ERASE_EFFECT | literal、q 全清；不能建立 C2 | **L2 PASS / POST C2 / oracle match** |
| V5d | COLLAPSE_SIGN | literal 保留、T 全 +1；至少可建立 C2 | **L2 FAIL / oracle match** |
| V5e | COLLAPSE_SIGN | T 为 +1，不在不确定区 | **L2 UNRESOLVED / oracle match** |

这些注入刻意偏离该 fixture 的冻结操作，用于检验验证器的拒错能力。正确反应应当是操作绑定违规，或测量结果与 expected oracle 不匹配；不能仍通过。

另一个隔离性检查在 `_reset_arm` 返回前改变 q，并保留其传入的 reset-valid 标志，V5a 仍报 POST C3，证实它不消费恢复后的 q。此反例单独检验 post-measurement 接线，**不声称一个真实合格 reset 会允许破坏状态后仍判 valid**。

**修复方向：** reset 后重新读取全部 member 的 B、C、baseline 与 literal；用同一通用判定函数重建 C1/C2/C3。pre/J-after/post 观察必须是独立数据结构，不能复用 pre-reset T 作为 post-reset 证据。

## 5. [P1] Reset 只检查 C 臂，并丢弃前面 member 的失败

位置：[fixtures.py:628](https://github.com/changrongq/ouroboros-afterglow/blob/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0/afterglow_harness/fixtures.py#L628)。

`_v5_common()` 只对四个 C 臂调用 `_reset_arm()`，B 臂与 baseline companion 没有走对应 reset。循环反复覆盖 `any_outcome`，最终只看最后一个 member 的结果。

**反例：** 只令 A1_C 的 reset outcome 为 INVALID，其余保持原状。

```text
实际调用：A1_C, A2_C, B1_C, B2_C
第一条 reset_valid=False
最终 V5a：L2=PASS，POST_RESET_SUPPORTED_CLASS=C3，oracle_match=True
```

**修复方向：** 逐 member、逐 required arm 保留结果，任一所需 reset 无效即阻止相应 post-reset claim；逐个 required arm 检查完成性。pre-reset 结果仍单独保留，不因这项 invalidity 追溯删除。

## 6. [P1] 资格入口漏检 driver、实际父文件与完整 fixture 集合

位置：[run_known_answer_suite.py:33](https://github.com/changrongq/ouroboros-afterglow/blob/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0/afterglow_harness/run_known_answer_suite.py#L33)、[run_known_answer_suite.py:86](https://github.com/changrongq/ouroboros-afterglow/blob/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0/afterglow_harness/run_known_answer_suite.py#L86)。

`capture_frozen_binding()` 只比较 MANIFEST 摘要与 9 个组件源码摘要。它：

- 不检查两个已声明绑定的 driver；独立 verifier 会检查，但 suite 不调用该检查。
- 不读取 SPEC/prereg 的实际文件，只记录常量字符串。
- 不验证 required fixture IDs 的集合、唯一性及全部完成，只对 `run_all()` 返回的结果计数。
- 运行时导入并执行 `manifest_bind.compute_all()`，却把该模块称为纯 build provenance；它实际上参与资格决定。
- 以字符串“出现在 MANIFEST 中”代替对应字段的结构化比较，绑定语义较弱。

**注意反例的基线：** 原始 GitHub 副本已有换行漂移，会先被拒绝。因此另外创建诊断副本，仅将能匹配冻结 hash 的源码恢复为 CRLF，并确认独立 verifier PASS、suite 13/13 PASS。这个诊断副本不是对发布仓库的认证。

在该基线上：

1. 只把 driver 的 `results = run_all()` 改为 `results = run_all()[:1]`。独立 verifier 报 driver drift，但 suite **仅纳入 1 项结果仍输出 PASS / QUALIFYING RUN**。该变体仍调用了 run_all，但另外 12 项结果不再进入资格判断，足以证明完整性门禁缺失。
2. 恢复 driver，随后仅改动真实 SPEC 文件；独立 verifier 与 suite 仍 **PASS**，输出旧的 SPEC 常量 hash。
3. 诊断副本仍包含主路径不匹配的 prereg，suite 同样未发现。

**修复方向：** 统一一个完整的 qualification preflight，suite 必须使用它；检查实际文件、显式 role→hash 映射、全部运行依赖、规范 fixture 集合与完成记录。manifest_bind 若继续参与运行判定，也应纳入执行关键绑定。完整性失败不能由另一个可选命令负责兜底。

## 7. [P1] 资格套件未实际经过 observer/read paths，reset witness 由字面量代入

位置：[fixtures.py:127](https://github.com/changrongq/ouroboros-afterglow/blob/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0/afterglow_harness/fixtures.py#L127)、[fixtures.py:541](https://github.com/changrongq/ouroboros-afterglow/blob/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0/afterglow_harness/fixtures.py#L541)。

- observer.py 被绑定，但 fixture 使用 `Arm.snapshot → RegisteredState.snapshot`，没有调用绑定的 `StateObserver` / `snapshot_paths`。
- `affine_read` 与 `literal_consume` 被导入但没有调用。组件 smoke 测过函数，不等于资格 run 实际完成了两条读路径。
- `_reset_arm()` 未调用 `restart_worker` 或 `access_probe`；直接把 `clear_side_ok=True, access_side_ok=True` 传给 verify。
- 最终 ledger 写 `RESET_VALID: clear+preserve+access all verified`。这比 MANIFEST 承认的逻辑声明更强。
- `StateObserver` 持有可写 RegisteredState 对象；缺少写接口的公共方法不等于 OS 能力隔离。此点属于仓库已承认的隔离缺口，不作为新发现重复追责。

**反例：** 把两条 reader、两个 observer 入口及 restart/access hooks 全部替换成“一调用就抛异常”；整个 suite 仍有 13/13 oracle match。这证实它们没有被资格运行调用。

**修复方向：** 若当前阶段只交付判定器单元测试，名称、结果字段与报告按该范围表述；若要支持完整 reference harness qualification，应接通 observer、两条读路径及规定的 witness。模拟输入只能明确记为模拟/逻辑声明，不能记录为实际完成的 clear/access 验证。

## 8. [P1] 发布 ledger 不足以重新核算 C3/L2

位置：[fixtures.py:83](https://github.com/changrongq/ouroboros-afterglow/blob/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0/afterglow_harness/fixtures.py#L83)、[V5a ledger](https://github.com/changrongq/ouroboros-afterglow/blob/4b758b0ceb064e7cc6b8dafcfac0a34eee4969a0/artifacts/RC6/ledgers/V5a.json)。

例如 V5a 的 `arm_A/arm_B/arm_C/l1/c2/c3/attempted_scope` 均为空。J 的逐 member 三元组 `timing_records` 在内存产生并返回，但没有写入 ledger；只留下布尔值及文字说明。V2/V3 又只保留循环最后一个 member 的 ledger。

当前证据没有完整的逐 member signed T、paired attribution、规则 hash、稳定 pair identity、pre/post execution mapping，无法从 raw ledger 独立重算全部 class/persistence 条件。`manifest_bind.RULE_BUNDLES.PERSISTENCE_MATCH_RULE` 也只写了 C1 的 payload 匹配，没有实例化 C2/C3 的完整 logical identity/matching semantics。

**修复方向：** 保存每个 logical member 的 pre/J/handoff/post 观察、B/C baseline、实际 signed T、归因结果、规则引用与 phase realization。独立复核器应只读取这些证据重新计算结果，并与 suite 结果比较；不能只比较两个都写着 PASS 的 JSON。

## 9. 较小问题与后续加固

这些与上面的已复现主问题分开列，不要求为措辞重新展开规范讨论。

- **C3 输入校验：** `evaluate_c3([], [], [])` 返回 C3，因为 `all([])` 为真。当前正常 fixture 固定四成员，尚未证明正常路径会生成空集合；但若它要作为共用 evaluator，必须校验冻结 member 集合、重复 ID、类数、每类不同 episode 数与比较集合。
- **INVALID 聚合：** `l2_aggregate(INVALID, NOT_ASSESSED, NOT_ASSESSED)` 返回 UNRESOLVED。当前接口应明确禁止该输入并先处理 protocol invalidity，或正确传播 INVALID，不能默默降为不确定。
- **B 复测：** `_three_arm()` 把同一个 `snap_B0` 既当 baseline 又当 final B 输入；函数内部计算了 ΔB，但调用方使它必为零。应在 C 干预之后独立读取 B，并验证未受串扰。
- **V4b：** 当前仅调用 `evaluate_c2_architectural(extra_interface_separable=False)`，没有实现注释所说的隔离 wrapper。这可以测试状态分支，但不能证明已构造了架构性不可识别的被测对象。
- **独立验证说明路径过时：** VERIFY.md 使用不存在的 `manifest/…` 与 `tools/smoke_*.py`，实际位置是 `reports/…` 与扁平的 `afterglow_harness/…`。应修 README/VERIFY 这些非冻结导航文本。
- `tests/` 仅占位，现有 tests 是 smoke 脚本。不要把“没有 fixture_id 特判”和“13/13 match”单独作为充分资格标准。

## 10. 给 Coder 的建议修复顺序

1. 校正发布对象与 canonical 路径，选择源码的冻结字节形式；先让一个全新下载副本能准确校验。
2. 将 pre/post 的统一判定逻辑移入共用 evaluator/pipeline；fixture 不直接填写实际 PASS 或 class。
3. 逐 arm、逐 member 处理 reset，使用真正的 post-reset 测量；实现中间无效状态的传播。
4. 接通 observer / 两条读路径，明确逻辑模拟与实际 reset witness 的范围，完整输出 ledger。
5. 把本报告中已经复现的反例作为回归输入；通过后再冻结新的 MANIFEST、重新执行完整套件。

既有 RC6 产物保留历史，不覆盖成“当时就已通过修正版”。本报告没有提出新的记忆本体论门槛，修复目标均来自当前已声明的 Basic L1、reset 重建证据、版本绑定和独立可核验要求。

## 11. 复现材料

同目录提供：

- `reproduce_review.py`：完整审阅复现脚本。
- `repository-byte-inventory.json`：69 个发布文件的字节数、SHA-256 与 CRLF 计数。

- `evidence/reconstructed-*.log`：独立 CRLF 诊断副本的受控检查；**不能当成原始仓库 PASS**。

运行方式：

```text
python reproduce_review.py --repo <固定提交的仓库副本> --out <独立证据目录>
```

脚本不修改输入仓库的原始文件；原驱动会在输入副本下创建 `afterglow_harness_artifacts/`。所有故障文件改动限于独立复制的 scratch 仓库；临时目录清理被限定在专属 scratch 根内。

未验证：真实模型文件 hash（仓库未提供模型）、真实 Mistral 推理、OS 级隔离、真实用户 episode、科学候选行为；没有执行科学实验。
