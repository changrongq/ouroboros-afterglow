# 定义一 · `OBSERVATION_BOUNDARY`

## 1.1 最低可接受内容（凌翼给定）

> 明确 PID 与创建时间、目标对象身份、哪些句柄被纳入；任何排除项必须有独立依据，不能凭名称或路径猜测。

## 1.2 草案

**观测集 $E$ 的定义**：

$$E = \{\, h \mid h \in \mathrm{Enum}(P),\ \mathrm{Type}(h) = \mathrm{File} \,\}$$

其中 $P$ 由**三元组**锁定：

```text
P = (pid, create_time, image_path)
```

- `pid`：目标业务 worker 的进程号
- `create_time`：`GetProcessTimes` 读出的创建时刻（用于排除 PID 复用）
- `image_path`：进程可执行文件路径（用于排除"同名不同进程"）

**三者必须全部匹配**才承认 $P$ 是我们观测的那个进程；任一不符 ⇒ 整个观测作废，返回 `ERROR`，不得降级解释。

**目标对象身份 $T$**：由 `_target_identities` 的 `(identities, reason)` 给出，**`reason != OK` ⇒ 观测不成立**（不是"目标没有身份"，是"我们没拿到基准"）。

**纳入规则**：$E$ 纳入 $P$ 名下**所有** `File` 类型的句柄，**无例外**。

**排除项**：**本草案不允许任何基于名称或路径的排除。**

这是关键的一条。凌翼要求"任何排除项必须有独立依据"。**我给不出**独立的排除依据——任何"这类名字不用管"的规则，本质上都是"凭名称猜测"，正是 `OPTION_A` 被禁止的那个动作。

因此本草案的边界声明是：

> **$E$ 等于枚举器在观测时刻返回的全部 File 类句柄。排除项集合为空。**
> 于是"句柄不在 $E$ 里"只有一种可能：**枚举器没有返回它**。

这带来一个必须承认的**已知缺口**，见 1.4。

## 1.3 实现机制

```text
q3_handle_audit._iter_handles(pid)          # class 16 枚举（24 字节 stride）
q3_business_handle_audit_v2._target_identities(path) -> (ids, reason)
_process_create_time(pid)                   # GetProcessTimes
```

三者已在 `c_feasibility_probe.py` 中做过**三方计数交叉校验**（`GetProcessHandleCount` vs class-16 vs class-64 = 77/77/77）。

**但计数相等不等于集合相等**——凌翼已裁定 `COUNT EQUALITY ALONE INSUFFICIENT`。所以：

## 1.4 反例（什么情况下本定义失效）—— 这一栏是本草案的核心

**反例 A（致命，本草案无法排除）**：
若在枚举进行的过程中，$P$ **新取得**一个指向 $T$ 的句柄，而枚举器已经越过了该句柄所在的索引位置，则该句柄**不在 $E$ 中**，而它**是**目标句柄。
⇒ 此时 $\forall h \in E, \neg T(h)$ 成立，但 $\exists h \notin E, T(h)$ 也成立。
⇒ **CLEAN 是错的。**

**这条反例不能靠"枚举更仔细"消除**，因为它是枚举这个动作本身的非原子性导致的。要消除它，必须让 $P$ 在枚举期间不能取得新句柄——**而那就进入了定义二**。

**反例 B（流程身份）**：
若 PID 在观测期间被复用（原进程退出、新进程取同一 PID），则 $\mathrm{Enum}(P)$ 可能枚举到**另一个进程**的句柄。
⇒ 本草案用 `create_time` + `image_path` 三重锁定来排除 B。**B 我认为已经封住**，但封住的方式是**事后校验**，不是原子保证。

**反例 C（枚举器自身缺陷）**：
若 `_iter_handles` 因缓冲区竞态漏掉句柄（类 16 枚举在小缓冲区时会返回 `STATUS_INFO_LENGTH_MISMATCH`），则 $E$ 不完整。
⇒ 本草案用 class-16 与 class-64 双枚举 + `GetProcessHandleCount` 三方计数来做**检测**（不一致则判 `ERROR`），但**检测不等于证明**——三方同时漏掉同一个句柄不会被发现。

## 1.5 我的诚实结论

**定义一在"纳入与排除"这一层是完备的（排除项为空，无可指摘），但在"枚举原子性"这一层不完备。**

反例 A 是本定义**无法自证排除**的。它必须靠定义二（覆盖语义）与定义三（时间范围）来补——而定义二战正要说的是同一件事。**若定义二不能解决 A，那么三份定义合起来仍不能支撑 CLEAN。**

# 定义二 · `SNAPSHOT_COVERAGE_SEMANTICS`

## 2.1 最低可接受内容（凌翼给定）

> 明确使用哪种 OS 观测机制、是否具备原子性、如何处理枚举期间的句柄开闭及句柄值复用，以及凭什么认为没有遗漏。

## 2.2 草案

**观测机制**（三选一，本草案只能给出其中之一的可行性判断）：

| 机制 | 原子性 | 本草案判断 |
|---|---|---|
| A. `NtQuerySystemInformation(SystemExtendedHandleInformation)` 单次快照 | **非原子**：内核复制句柄表时不加全局锁，遍历期间可增删 | **不可用于 CLEAN** |
| B. 挂起进程后枚举（`NtSuspendProcess`） | 近似原子：挂起后该进程不再执行，无法 `CreateFile` | **唯一可能可行**，但有前提 |
| C. 内核驱动 / ETW 句柄审计 | 原子（内核侧） | **超出当前范围**，凌翼已排除 |

**本草案只推进 B**，因为 A 已被凌翼的"两次快照不证明静止"排除（A 本质上是采样），C 超范围。

### B 的前提条件（缺一不可）

```text
B1. 挂起前，P 处于已知的可控状态（已在 T1 契约下审计过一次）
B2. NtSuspendProcess 返回成功，且 GetProcessTimes / 线程计数确认全部线程已停
B3. 挂起期间，本账户不具备向 P 注入线程的手段（否则其他线程仍可打开句柄）
B4. 枚举在挂起窗口内完成，且窗口内无失败
B5. 枚举完成后恢复（NtResumeProcess），并验证恢复成功
```

**「凭什么认为没有遗漏」——这是凌翼点名的那个问题，我的答案是**：

> 挂起之后，$P$ 内**没有任何线程在运行**，因此 $P$ **不可能**在这一时刻取得新句柄。
> 于是 $E$ 是 $P$ 句柄集合的**一个真实快照**，而不是"我们尽力的采样"。

**这句推理只依赖一个前提：挂起是彻底的。** 而"彻底"恰好是我**无法证明**的那一环——见 2.4 反例。

## 2.3 实现机制

```python
NtSuspendProcess(hProcess)          # ntdll
... enumerate ...
NtResumeProcess(hProcess)           # ntdll
```

**前置**：需要 `PROCESS_SUSPEND_RESUME`（0x0800）权限。跨账户下本账户是否可以取得该权限，**我未验证**（本轮 `NEW_C_EXPERIMENTS = NOT AUTHORIZED`），因此这一条是**未验证的关键前提**。

## 2.4 反例（本定义失效的条件）

**反例 D（致命，我认为无法在用户态排除）**：
`NtSuspendProcess` **不保证**在返回时所有线程都已停止。它向每个线程发送挂起请求，但线程可以在任意指令边界响应，返回时可能有线程仍在运行、正在 `CreateFile`。
⇒ 于是"挂起后不可能取得新句柄"这一句**可能为假**。
⇒ 且没有任何用户态 API 能确认"所有线程此刻确实都在等待状态"（`NtQuerySystemInformation(SystemProcessInformation)` 的线程状态是采样，同样非原子）。

**要封住 D，需要一个"所有线程都已停"的确认**。我在用户态找不到这个确认。**因此反例 D 我排除不了。**

**反例 E（句柄值复用）**：
挂起期间枚举到的句柄值 $h$，若在恢复后被关闭并复用给另一个对象，则"我们审计过 $h$"这件事在恢复后**不再成立**。
⇒ 本草案的应对：**审计结论只对挂起窗口内有效**，恢复后不作任何声明。这正是定义三要界定的时间范围。

**反例 F（枚举本身需要跨进程操作）**：
`DuplicateHandle` 需要目标进程处于可操作状态。**挂起的进程能否被 `DuplicateHandle`，我不确定**——若不能，B 方案根本跑不起来。
⇒ 这是一个**必须在实验中验证**的可行性前提，本轮未授权，我未验证。

## 2.5 我的诚实结论

**机制 B 是唯一可能可行的方向，但它依赖三个我无法在用户态证明或验证的前提：**

1. `NtSuspendProcess` 是否彻底（反例 D）
2. 跨账户能否取得 `PROCESS_SUSPEND_RESUME`
3. 挂起状态下能否 `DuplicateHandle`（反例 F）

**在这三个前提未验证之前，本定义不构成"可信观测机制"。** 按凌翼第 2 条，此时应当直接记 `C_FEASIBILITY_NOT_ESTABLISHED`。

# 定义三 · `TIME_SCOPE_OF_ASSURANCE`

## 3.1 最低可接受内容（凌翼给定）

> 明确证明从哪个事件开始、到哪个事件结束；如果业务 worker 在此期间能继续取得新句柄，须说明用什么机制保持安全性。

## 3.2 草案

**时间范围 $[t_{\text{start}}, t_{\text{end}}]$ 的定义**：

```text
t_start = NtSuspendProcess 返回成功的时刻
t_end   = 枚举完成的时刻（最后一轮 class-64 枚举返回）
```

**保证**：在 $[t_{\text{start}}, t_{\text{end}})$ 内，$P$ 的句柄集合等于 $E$。

**$\geq t_{\text{end}}$ 之后：本定义不作任何声明。** 恢复（`NtResumeProcess`）之后 $P$ 取得的新句柄，**在保证范围之外**。

**"若 worker 在此期间能继续取得新句柄，须说明安全性机制"** —— 我的回答是：

> 本定义的设计**不允许** worker 在窗口内取得新句柄，手段是**挂起**。
> 若挂起不能保证这一点（反例 D），则本定义**失效**，而不是"靠别的机制兜底"。
> 我不会为它编一个兜底机制。

## 3.3 实现机制

```text
t_start: NtSuspendProcess 成功 + 线程计数确认（脆弱的，见反例 D）
t_end:   枚举完成
恢复:    NtResumeProcess，且验证进程仍在运行
```

## 3.4 反例（本定义失效的条件）

**反例 G**：`t_start` 取"返回时刻"，但线程可能在返回**之后**才响应挂起请求。
⇒ 窗口的起点**早于**真正的静止时刻。
⇒ 在 $[t_{\text{start}}, t_{\text{真实静止}})$ 这个子区间内，$P$ 仍可取得句柄，而这些句柄**不在** $E$ 中。
⇒ **保证为假。**

**反例 H**：worker 在挂起前一刻刚发起一个缓慢的 I/O 打开（如网络路径、慢盘），该打开在挂起生效后才完成并产生句柄。
⇒ 即使挂起彻底，这个**已在途**的打开仍会落地。
⇒ 本定义中我**没有**机制解决 H。

## 3.5 我的诚实结论

**反例 G 与 H 我排除不了，且我认为在用户态都排除不了。**

G 需要"确认所有线程已静止"（前面说过做不到），H 需要"确认没有在途的内核 I/O"（用户态无此 API）。

**因此：定义三在当前机制下不能成立。**
