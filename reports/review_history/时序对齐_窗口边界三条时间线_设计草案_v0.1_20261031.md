# 0 · 本文要说的一件事

上一份文档指出：

```text
③ 写入窗口  storage.py L95-97  _assert_write_open
             _write_open 是【进程内布尔量】
             ⇒ 它知道窗口【开着】，不知道【为谁开着】

④ 观测快照  storage.py L73-74  两次独立读
             ⇒ 两次读之间若有写入，快照不属于任何一个时刻
```

这两件事看似无关，其实是**同一个缺陷的两面**：

```text
③ 缺的是「时刻归属」   —— 写入发生在哪个区间里
④ 缺的是「区间的原子性」 —— 两次读是不是同一个时刻
⇒ 两者都缺同一个东西：【可以相互比较的时刻标记】
```

所以本文提议的不是「加一个检查」，而是**先让时刻成为可比较对象**。
没有这一步，任何「谁写的」「哪一次的快照」都无法判定。

# 1 · 先否决一个做法：不能照抄 BD-52

上一轮我建议「形式照抄 BD-52 的 `(S_write, J_after, S_handoff)`」。
**核过源码之后，这个建议要撤回。** 理由如下。

## 1.1 BD-52 实际做了什么

`evaluator.py` L117-130：

```python
@dataclass
class JTimingWitness:
    s_write_digest: str
    j_after_digest: str
    s_handoff_digest: str

    @property
    def timing_valid(self) -> bool:
        return self.j_after_digest == self.s_handoff_digest
```

`evaluator.py` L135-141 `assert_j_timing()`：不等则抛 `J_TIMING_VIOLATION`。

## 1.2 等值判定是对称的，先后关系不是

实测（`JTimingWitness` 直接构造，未改任何文件）：

```text
case                                   j_after      s_handoff    timing_valid
legal (J_after == S_handoff)           ja           ja           True
BD52 case2 (J after handoff)           ja2          ja1          False
BD52 case3 (labelled 'post-handoff')   pre_handoff  handoff      False

对称性检验：
  (j=alpha, s=beta).timing_valid = False
  (j=beta,  s=alpha).timing_valid = False
  ⇒ 两种【完全相反】的先后关系，得到【同一个】结果
```

**结论：`==` 只能回答「是不是同一时刻」，不能回答「谁在前」。**

复现方式（未改任何文件，直接构造 dataclass）：

```python
from evaluator import JTimingWitness
print(JTimingWitness("sw", "alpha", "beta").timing_valid)   # False
print(JTimingWitness("sw", "beta",  "alpha").timing_valid)  # False
```

## 1.3 后果：BD-52 的声称比它能证明的更强

`evaluator.py` L112-113 注释写：

```text
# fixture is INVALID (not PASS). This makes "a legal J" and "an injected
# post-handoff fault" machine-distinguishable by TIME, not by wording.
```

但 `bd52_timing_witness_check.py` L35-42 的第三个用例是：

```python
# (3) a post-handoff injected fault has J_after != handoff too -> INVALID
injected = JTimingWitness("sw", "pre_handoff", "handoff")
```

```text
它的字面值 j_after = "pre_handoff" —— 字面意思恰好是【在 handoff 之前】。
它被当作「post-handoff 注入」的例子，但它与 case2 走【同一条】拒绝路径。
脚本自己的输出就写着："same path as illegal J"。
```

⇒ **BD-52 区分的是「等 / 不等」，不是「早 / 晚」。**
⇒ 它确实堵住了一个真实的洞（J 未完成即 handoff），这一点成立。
⇒ 但「合法 J 与 post-handoff 注入由时间区分」这句话，**它没有证明**。
⇒ 这是 `Reproducibility != Attribution` 在同一处的又一次现身：

```text
  能拒绝「不等」
  ≠ 能判定「晚于」
```

## 1.4 因此本文的提议与上一轮相反

```text
上一轮：形式照抄 BD-52 的三元组
本轮：  三元组的形式可以借，但【判定式不能借】
        等值判定不足以表达「窗口在写入之后关闭」这件事
```

# 2 · 提议：三种时刻，一种比较

## 2.1 三个时刻

```text
T_open    写入窗口【开】的时刻
T_close   写入窗口【关】的时刻
T_snap    观测快照【读】的时刻
```

## 2.2 需要判定的两条关系

```text
(甲) 写入被包含在窗口内：      T_open  <  T_write  <  T_close
(乙) 快照不落在窗口内：        ¬( T_open < T_snap < T_close )
```

**关键：这两条都是不等式，不是等式。** 这正是 BD-52 的 `==` 表达不了的。

## 2.3 但不等式需要「时刻」是序数，不能是摘要

```text
digest 是【内容】的身份，不是【时刻】的身份。
两个不同时刻可能有相同 digest（无写入时）。
两个不同 digest 也不代表先后（digest 无序）。

⇒ 若沿用 BD-52 用 digest 表示时刻，不等式【无法成立】。
⇒ 这是 BD-52 只能用 == 的【根本原因】，不是它的疏忽。
```

**这是本文最重要的一句**：BD-52 用 `==` 不是因为没想到 `<`，是因为
**digest 上没有定义序**。想要 `<`，就必须引入一个**有序列**。

## 2.4 有序列的三条候选

| 候选 | 有序列？ | 跨进程？ | 与 digest 的关系 | 缺口 |
|---|---|---|---|---|
| 写入计数器（单调递增） | 是 | 需共享存储 | 正交，可并存 | 计数器本身可被回绕/伪造 |
| 单调时钟（`perf_counter_ns`） | 是 | 否（进程内基准不同） | 正交 | 跨进程不可比 |
| 外部见证者签发的序号 | 是 | 是 | 正交 | 需要第 6 阶段那样的外部权威 |

```text
⇒ 时钟【跨进程不可比】：两个进程的 monotonic 基准不同。
   这直接杀掉了最自然的做法。
⇒ 计数器需【共享存储】，而 storage.py 目前只写两个文件（literal/substrate）。
⇒ 外部见证者 = ⑥ 封存那一层，但那是事后，不能用于事前判定。
```

**结论：没有一条候选是「加上就能用」的。三条各有各的前提。**
这就是为什么本文只到设计为止——选哪条是凌翼的裁定，不是我的。

# 3 · 与「六阶段表」的接口

本设计**不动**六阶段表的任何一格，只补 ③④ 之间的判定关系：

```text
③ 写入窗口        T_open / T_close 产生于此
     ↓  （甲）T_open < T_write < T_close
④ 观测快照        T_snap 产生于此
     ↓  （乙）¬(T_open < T_snap < T_close)
⑤ 交接与裁决      接收判定结果，而不是重新判定
```

## 3.1 判定必须发生在 ⑤，不能发生在 ③④

```text
理由：③④ 是【产生证据】的阶段，⑤ 是【裁决】的阶段。
      若在 ③ 就判定，写入方同时是判定方 ⇒ 违反 observer != write operator
      （observer.py L4-7 的同一原则）
⇒ ③④ 只【记录】时刻，⑤ 才【比较】时刻。
⇒ 记录与判定分离，是本文唯一给出的一条硬约束。
```

# 4 · 本文明确没有做的四件事

```text
1. 没有选有序列（三条候选各有前提，需凌翼裁定）
2. 没有定义「时刻相等」怎么办（T_snap == T_close 算不算窗口内）
3. 没有处理「窗口未关」（进程崩溃，T_close 永不产生）
4. 没有证明本设计可建立证据链 —— 它只给出【可判定的形式】，不给结论
```

## 4.1 第 3 条的严重性要单独说

```text
进程崩溃 ⇒ T_close 不产生 ⇒ （甲）永远无法判定
⇒ 这【不是】边缘情况：崩溃正是最需要证据的时刻
⇒ 所以「窗口关闭」本身必须是一个【可被外部观察到的事件】，
   而不能只是进程内存里的 write_window.__exit__
⇒ 这是 storage.py L112-124 目前的结构性缺口
```
