## 三 · ZB-03 · UNKNOWN / 违规 / 停止三者混入同一流程

### 3.1 三处冲突确认

```text
⇒ 【冲突 1】：F1 说"先判 STOPPED 或 INCONCLUSIVE 再判违反"，
   F2 又说"确定违反优先于不确定"。
   ⇒ 若照 F1 早退，已确认的违规会被缺证据项遮掉。

⇒ 【冲突 2】：S4 中 Perm=True 且某 V 为 UNKNOWN：
   先命中 not(all PASS) ⇒ 返回 VIOLATED，
   随后"UNKNOWN ⇒ STOPPED"分支【不可达】。

⇒ 【冲突 3】：S3 在 UNKNOWN 且未创建时走末尾 HOLDS，
   与我紧接着写的"这种情况不能判 S3 成立"相反。
```

### 3.2 修正：先分层，再定优先级

```text
⇒ 【知微指出的根本问题】：
   我把【五个不同层次的东西】放进了一个返回流程：
   ① 被测系统实际知道什么、做了什么
   ② 观察者能确认什么、哪些证据缺失
   ③ 已确认的不变量违例是什么
   ④ 验证是否完成、是否具备整体判定资格
   ⑤ 系统【应】停止 vs 系统【是否真的】停止
```

```text
⇒ 【修正后的分层（五层，逐层产出，不混用）】：

   L-A  观测层
        · 观察者能确认的事实
        · 产出：observed_facts + evidence_gaps
        · 【不产出判定】

   L-B  证据完整性层
        · 是否具备判定资格
        · 产出：COMPLETE / INCONCLUSIVE / NOT_ELIGIBLE
        · 【这一层不判违反】

   L-C  违例判定层
        · 基于 L-A 的事实，判定是否存在确定的 S 违反
        · 产出：VIOLATED（需确定证据）/ NO_VIOLATION_FOUND

   L-D  系统状态层
        · 被测系统【实际处于】什么状态（RUNNING / STOPPED / UNKNOWN）
        · 【这是对系统的观测，不是对它的要求】

   L-E  合规层
        · 系统【应当】停止时，是否真的停止了
        · 产出：FAIL_CLOSED_OK / FAIL_CLOSED_VIOLATED / 无法判定
```

### 3.3 优先级规则（替换原 F1 / F2）

```text
⇒ 【规则 R1（确定违规不可被遮掉）】：
   若 L-C 有确定违反证据 ⇒ 最终结果【必须】含 VIOLATED，
   无论 L-B 是否完整。
   ⇒ 【这修正了 F1 的早退问题】。

⇒ 【规则 R2（不确定不制造违规）】：
   若只缺证据、无确定违反 ⇒ 结果为 INCONCLUSIVE 或 STOPPED，
   【不得】记为 VIOLATED。
   ⇒ 【这修正了 F2 的过度】。

⇒ 【规则 R3（STOPPED 是结论，不是判定函数自己返回的）】：
   判定函数【不得】因为"我不确定"就返回"系统应 STOPPED"。
   ⇒ "系统应 STOPPED"是【规范的处置要求】，由上层决定。
   ⇒ 判定函数只回答：事实是什么、证据够不够、有没有违规。

⇒ 【规则 R4（应停止 ≠ 已停止）】：
   L-E 必须由【独立证据】确认被测入口确实关闭。
   ⇒ 【不得】用审计函数自己返回 STOPPED 代替
     "独立证据确认被测入口已关闭"（知微原文）。
```

### 3.4 三态决策表（知微要求的小型表）

| L-B 证据完整 | L-C 有确定违反 | 最终结论 | 能否计入合格 |
|---|---|---|---|
| COMPLETE | 是 | **VIOLATED** | 否（阻断）|
| COMPLETE | 否 | **NO_VIOLATION_FOUND**（可 HOLDS）| 可（限该窗口）|
| INCONCLUSIVE | 是 | **VIOLATED**（违规优先）| 否 |
| INCONCLUSIVE | 否 | **INCONCLUSIVE** | 否（需重验）|
| NOT_ELIGIBLE | 任何 | **NOT_ELIGIBLE** | 否 |

```text
⇒ 【第一行与第三行】：只要确定违反，就报违反。
   ⇒ 【这是 R1 的落地】。
```

### 3.5 两种 UNKNOWN 必须分开

```text
⇒ 【知微的最小反例 B，我完整接受】：
```

## 四 · ZB-04 · S1 观测对象与 API 语义

### 4.1 四处硬伤逐条接受

**（a）持有句柄 ≠ 拥有 mutex**

```text
⇒ 知微引用 Microsoft CreateMutexW 文档：
   多个进程可持有同一 mutex 的句柄；
   【同一 mutex 同一时刻只有一个线程拥有所有权】。

⇒ 【我错在哪】：我在 3.4 的 O1 里写
   "若同时存在两个不同名称的 mutex 被各自持有 ⇒ VIOLATED"
   ⇒ 这句话本身没错（不同名称确实是绕过），
     但我没写清【同一名称下多句柄是正常的】。
   ⇒ 若有人按我的写法去"数句柄"，会把正常状态判成违规。

⇒ 【修正】：
   S1 的集合是【有效签发资格集合】，
   必须建立"该实例的实际签发路径受同一锁域及有效授予约束"这个关联。
   ⇒ 【不能】用"持有句柄数"代理"有效资格数"。
```

**（b）API 返回值语义混用**

```text
⇒ 【我的错】：B9 里写"OpenMutex + ALREADY_EXISTS"
   ⇒ ALREADY_EXISTS 只表示【对象存在】，不表示【被持有】。

⇒ 【正确语义】：
   | API / 返回值 | 含义 |
   |---|---|
   | CreateMutexW + ALREADY_EXISTS | 对象已存在（**不表示被持有**）|
   | WaitForSingleObject 返回 WAIT_OBJECT_0 | **取得所有权** |
   | 返回 WAIT_ABANDONED | **同样取得所有权**（前持有者异常退出）|
   | 返回 WAIT_TIMEOUT | 未取得，有人持有 |
   | 返回 WAIT_FAILED | 错误，**不能**解释为"有人占用" |

⇒ 【§4 本来是对的】：§4 已正确区分这些值（4.6(a) 与 WAIT_ABANDONED 的处置）。
   ⇒ 我在 B9 退回旧误解，是【把已经写对的东西写错了】。
```

**（c）采样间隔 < 阈值 ≠ 无空白**

```text
⇒ 知微的纸面反例：
   观察者在 t=0、10ms 采样；错误资格重叠仅出现在 4–5ms。
   两次都读到基数 ≤ 1，间隔 10ms 也不超登记阈值，
   但"整个区间无重叠"仍为假。

⇒ 【我接受】。缩短采样间隔改变不了这个逻辑，
   除非另有机制证明"所有相关转换必被覆盖"。

⇒ 【另一个我没想到的】：以"第一次看到占用"为起点、
   以"第一次看到空闲"为终点，会漏掉起点前与后续重新授予。
   ⇒ 【观测窗口必须由事前登记的生命周期事件确定】，
     不能事后按采样结果裁切。
```

**（d）同一大区间两次签发 ≠ 资格同时有效**

```text
⇒ 先 A 合法释放、再 B 合法接手，也会在同一区间出现两次签发。
   ⇒ epoch/seq 冲突可以证明【顺序或身份约束】有问题，

⇒ 【我原来的 O2 写得太快】：
   我写"若存在两条 epoch/seq 冲突 ⇒ 并发成立 ⇒ VIOLATED"。
   ⇒ 【冲突 ≠ 重叠】。需补时间先后证据。
```

## 六 · 钳星的 N3 key 碰撞处置

### 6.1 缺陷确认

```text
⇒ 钳星："key 的唯一性范围是 (domain, generation, key)
   —— 域内 + 世代内仍可能碰撞。
   需要 Coder 明确『key 碰撞』的处置规则。"

⇒ 知微补充：「同 key 只是查找线索，不是身份凭证；
   不同 key 对同一已撤销授予也不得创造第二次效果。」
```

### 6.2 修正：五条最低合同

```text
⇒ 【采纳知微的五条，逐条落地】：

   C1  查到旧请求后，仍须核对【可信调用主体 / 代理授权 / 重试权限】
       ⇒ 不得绕过无权撤销检查

   C2  `request_digest` 由【可信核验路径按固定格式重算】
       ⇒ 不接受调用方自报摘要代替核验

   C3  摘要必须绑定：
       · 操作类别
       · authority_domain
       · generation
       · 精确的 grant_ref
       · 登记的有效请求参数
       ⇒ 调用主体可纳入摘要或独立绑定，但必须有明确位置

   C4  只有【同 key + 同内容 + 旧结果已确认 + 来源与权限均合规】
       才返回旧结果，且不新增撤销效果
       ⇒ 异内容 ⇒ 冲突拒绝
       ⇒ 旧状态不明 ⇒ 停止

   C5  【不同 key 也要检查同一授予是否已撤销】
       ⇒ 不能把"每个 key 最多一次"当成
         "每份授予最多一个撤销效果"
```

### 6.3 key 碰撞的处置（钳星要的那条）

```text
⇒ 【情形】：两个不同调用方恰好给出同一 key。

⇒ 【处置】：
   | 若... | 则... |
   |---|---|
   | 内容不同（request_digest 不符）| **冲突拒绝**（C4 第二行）|
   | 内容相同但调用主体不同 | **核对 C1**：若新调用方无撤销权 ⇒ 拒绝；<br>若有且内容确实一致 ⇒ 返回旧结果，不新增效果 |
   | 内容相同且主体相同 | 幂等，返回旧结果 |
   | 旧状态不明 | STOPPED（C4 第三行）|

⇒ 【钳星判断"这主要是可用性问题"是对的】：
   合规的冲突拒绝只是让调用方重试；
   ⇒ 【真正的错误接受】是把不同操作或未授权请求当成旧成功。
   ⇒ 故 C1 与 C4 是关键，不是"UUID 够不够随机"。
```

```text
⇒ 【知微的补充我接受】：不追求数学上永不碰撞的 UUID，
   而是【规定碰撞的后果】。
```
