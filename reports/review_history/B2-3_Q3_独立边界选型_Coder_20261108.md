## 一 · 四项条件逐条落地

### 1.1 写入独立性

```text
⇒ 【要求】：N5 由 S 按独立权限创建/更新；
   W 及被测业务写入路径不得修改、删除或替换。

⇒ 【设计】
   | 手段 | 内容 | 可验证性 |
   |---|---|---|
   | 权限 | N5 载体对 W 所在账户【无写权限】，仅 S 账户可写 | ACL 可导出、可定期复核 |
   | 代码路径 | W 的进程内【不存在】N5 写入接口 | 静态可查：接口只链接到 S 侧 |
   | 字段 | N5 含 `commitment_seq` 单调号 + 前驱摘要 | 断链可检出 |
   | 协议 | N1–N4 编码中【不含】任何写 N5 的字段 | 编码层面无法表达 |

⇒ 【我的判断：这一项可以做到，且可机械验证】
   ⇒ 但有一个前提我必须写明：
     "W 无写权限"依赖【账户隔离真的成立】。
     若 W 与 S 跑在同一账户下，权限层立即失效，
     只剩代码路径与字段检测两道。
   ⇒ 本机原型【很可能】同账户运行。故：
     `N5_WRITE_ISOLATION = PERMISSION_DEPENDENT`
     ⇒ 【不得】记为已建立，除非能证明账户分离。
```

### 1.2 回滚独立性 —— 这是唯一真正的难点

```text
⇒ 【要求】：对于本原型声称能检出的
   删除 / 替换 / 回滚 三类故障，
   N5 及其可信高水位【不能随业务历史同步回退而无法察觉】。

⇒ 【先分清"能检出"与"检不出"】：
   设业务历史回滚到时刻 T_rollback，N5 回滚到 T_rollback'。

   | 情形 | 能否检出 | 依据 |
   |---|---|---|
   | N5 不回滚（T'=now） | **能** | N5 声称 range_end=N，实际读到 M<N |
   | N5 回滚到更早（T' < T） | **能** | 同上，且 N5 自身前驱断链 |
   | N5 与业务【同步】回滚（T' ≈ T） | **不能** | 两侧自洽，无矛盾可判 |

   ⇒ 【第三行就是凌翼说的"无法察觉"】。
   ⇒ 而这正是"两侧在同一恢复操作中一起回滚"的情形
     （在他要求的第三组反例里）。

⇒ 【软件层能不能解决第三行？】
   ⇒ 【不能】。理由：
     若 N5 与业务历史在同一份备份里、同一次恢复中回退，
     那么恢复后世界状态【完全自洽】——
     没有任何一条记录说"你少了一段"。
   ⇒ 要打破这个自洽，必须有【一个不在该备份/恢复域内的东西】
     记得"曾经到过哪"。那个东西只能是：
     · 物理上分离的介质，或
     · 单调且不可回退的硬件/固件计数器，或
     · 外部（人/另一台机）持有的记录

⇒ 【故我给出的结论，与我自己的偏好相反】：
   在本机原型范围内，没有任何纯软件方案能满足 (2)。
   ⇒ 若实验环境没有分离介质或不可回退计数器，
     必须写：
     `HISTORY_ROLLBACK_DETECTION = NOT ESTABLISHED`
   ⇒ 凌翼原文已给出这个出口，我【采纳并主动登记】，
     不等被追问才承认。
```

### 1.3 恢复独立性

```text
⇒ 【要求】：恢复 N1–N4 时，不得默认同步恢复 N5；
   N5 的有效版本及恢复依据须独立验证。

⇒ 【设计】
   (R1) 恢复流程【不包含】任何写 N5 的步骤
   (R2) N5 的读取独立于业务历史恢复：
        先读 N5 → 取得 (range_end, head_digest, hwm) →
        再扫描业务历史 → 比对
   (R3) 【顺序不可颠倒】：若先扫业务历史再读 N5，
        实现可能"按扫到的结果去解释 N5"，
        等于让业务历史定义承诺
   (R4) N5 的"有效版本"由 hwm 判定，不由文件 mtime 判定

⇒ 【这一项可以做到】，但同样有前提：
   它要求恢复流程的【第一步】是读 N5。
   ⇒ 这是流程约束，可写进 §7 判定器顺序。
```

### 1.4 证据独立性

```text
⇒ 【要求】：业务历史不能通过自己的
   最后序号、内部摘要、当前文件长度，
   证明其应有历史已经全部存在。

⇒ 【已有约束，需补一条硬规定】：
   已在 B2-1 2.2(P3) 写了「禁止用 PRAGMA integrity_check 当范围完整性依据」，
   在 B2-1 1.1 写了「`SELECT max(seq)` 禁止作为完整性依据」。

⇒ 【现补第三条，是针对 SQLite 特有的】：
   (E1) 【禁止】用 `PRAGMA page_count` / 文件大小 /
        `-wal` 文件长度 推断"记录是否齐全"
        ⇒ 这些量随 checkpoint 时机变化，
          与"记录应当有多少"无固定关系。

   (E2) 【禁止】用 SQLite 的 `rowid` / `AUTOINCREMENT` 序列
        作为历史连续性证据
        ⇒ rowid 可因 VACUUM / 删除 / 回滚而改变或重复，
          它不是 §5 的 seq。

   (E3) 【必须】用 N5 的 `range_end_seq` + `head_digest` 比对，
        且比对对象是【按 §2 规范重算的链摘要】，
        不是数据库返回的任何内部值。

⇒ 【这一项完全可以做到】，因为它是"禁止用某些值"，
   不需要外部介质。
```

## 三 · 可信高水位（HWM）设计

```text
⇒ 【定义】：HWM = 受信侧记录的、业务历史【曾经达到过】的最大 seq。
   ⇒ 它不是"当前最大 seq"（那是业务历史自己说的），
     而是"受信方确认过的最大 seq"。

⇒ 【关键性质】：HWM 只能增，不能减。
   ⇒ 若某次读取发现 当前 seq < HWM ⇒ **回滚**（或截断）
   ⇒ 这是检出 (1.2) 第一、二行的机制。
```

### 3.1 HWM 的更新规则

```text
⇒ (H1) HWM 只在【N5 成功提交之后】推进
   ⇒ 顺序：业务 COMMIT → N5 写入 → N5 提交成功 → HWM 推进
   ⇒ 不得先推进 HWM 再写 N5

⇒ (H2) HWM 推进必须【幂等且单调】：
       新值 = max(旧值, 本次 range_end_seq)
   ⇒ 任何写入路径都不得使 HWM 减小

⇒ (H3) HWM 与 N5 的写入【同一受信事务】
   ⇒ 若二者不同事务，会出现"HWM 已推、N5 未写"
     或"N5 已写、HWM 未推"两种中间态。
   ⇒ 【这是允许同一事务的唯一地方】——
     因为两者同属受信侧、同一权限边界、同一恢复域。
   ⇒ （与第六节 B2-1 修订呼应：不是禁止多对象事务，
     是要求【原子边界与恢复后果被审查】。）
```

### 3.2 HWM 的读取规则

```text
⇒ (H4) 恢复开始时【第一件事】是读 HWM
   ⇒ 若读不到 / 不完整 / 无法验证 ⇒ `STOPPED`
     （凌翼第三组反例的最后一项）

⇒ (H5) 读到 HWM 后，把它与业务历史实际最大 seq 比对：
   | 关系 | 含义 | 判定 |
   |---|---|---|
   | actual == HWM | 正常 | 继续 C1–C5 |
   | actual > HWM | 有未承诺的新记录 | 见第四节（签发生效） |
   | actual < HWM | **回滚或截断** | `STOPPED` + 保留两侧证据 |

⇒ (H6) 【HWM 自身不可由业务历史推导】
   ⇒ 禁止：`HWM := SELECT max(seq)`
   ⇒ 这是第四节 (4) 证据独立的直接要求。
```

### 3.3 HWM 缺失/损坏/不可验证（凌翼反例第三组末项）

```text
⇒ 【三种情形，分开处置】：

   | 情形 | 判定 | 依据 |
   |---|---|---|
   | HWM 记录不存在 | `STOPPED` | 范围完整性不可确认（P4-3.1(d)）|
   | HWM 存在但摘要校验失败 | `STOPPED` | 同上，且登记为损坏 |
   | HWM 存在但无法验证其来源 | `STOPPED` | 承 §5 二 (t3)：来源本身须可独立复核 |

   ⇒ 【三者都 STOPPED，但证据不同、修复方向不同】：
     · 缺 HWM ⇒ 查是否从未初始化
     · 损坏 ⇒ 查介质/写入
     · 来源不可验证 ⇒ 查信任根链

   ⇒ 【不得合并成一句"历史不全"】（P4-2.5(d) 原文）。
```

## 四 · 业务提交 → N5 承诺 → 权威效果生效的时序

```text
⇒ 【凌翼三节的核心裁定】：
   「对外发生权威效果的操作不得使用尚未可信锚定的历史。」
   「在 N5 提交及核验完成前，
     不得将相应权威操作宣布为有效完成。」
   「不允许对具有权威效果的提交采取无限延迟承诺策略。」

⇒ 【这改变了我原来的设计】：
   我原来写"承诺滞后于业务是可接受的滞后"，
   并允许"超出已承诺范围 ⇒ STOPPED"。
   ⇒ 【那是把滞后当成正常态】。
   ⇒ 凌翼裁定：对【权威效果】的操作，滞后不可接受。

⇒ 【修正后的三阶段】：
   | 阶段 | 内容 | 此时可对外声称什么 |
   |---|---|---|
   | P1 业务提交 | N1–N4 写入并 COMMIT | **什么都不可声称**（只是内部状态） |
   | P2 N5 承诺 | N5 写入、提交、HWM 推进 | 仍不可声称 |
   | P3 权威生效 | N5 核验通过 | **此时才可**宣布该操作有效 |
   ⇒ 【P3 是唯一可对外生效的时点】。

⇒ 【若 P1 成功、P2 失败】：
   ⇒ 该操作【未生效】，须回滚或标记为未完成
   ⇒ 【不得】说"业务已提交所以算完成"
   ⇒ 这与凌翼原文「业务事务完成只是必要前置」一致。
```
