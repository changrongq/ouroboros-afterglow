# 一 · 首选方案与选择理由

## 1.1 首选：定长前缀 + 显式长度 + 有序字段 的二进制编码

```text
⇒ 方案名（本节自用标识）：ALIGNED-LEN-BE
   ⇒ 定长魔数前缀 + 每字段「标签 + 显式长度 + 内容」+ 大端定宽整数
```

```text
⇒ 【为什么选它，而不是别的三条路】

  路径 ① 直接对 Python 对象做 pickle / json.dumps
     ⇒ 排除：表示不唯一（键序、空白、浮点表示、编码），
       不可跨进程复现。违反裁定「唯一、确定、可跨进程复现」。

  路径 ② 用现有 repr() / f-string 拼接
     ⇒ 排除：与 v0.2 §2.2c 已定的【单射性】要求冲突。
       例：("A","1","23") 与 ("A","12","3") 无分隔拼接同为 "A123"。

  路径 ③ 只用 SHA-256，字段顺序交给实现
     ⇒ 排除：字段顺序自由 ⇒ 同一逻辑记录可算出多个合法摘要 ⇒
       违反「唯一」。

  ⇒ 本方案 ④：字段有固定顺序、每字段有显式长度、
     整数定宽大端、字符串带长度前缀。
     ⇒ 单射由「长度前缀」保证（见 2.3），不依赖分隔符。
```

## 1.2 与裁定六条偏好的对照

| 裁定偏好 | 本方案如何满足 |
|---|---|
| 唯一、确定、可跨进程复现 | 字段顺序固定；无空白；无 locale 依赖；整数定宽大端 |
| 每条引用明确对象类型、协议版本、完整字节范围 | 头部含 `object_type` 与 `protocol_version`；尾部含总长度 |
| 多字节整数固定大端 | 全部用 BE；不使用原生端序 |
| 显式长度、严格顺序、边界检查 | 每字段 `len` 前缀；总长自检；拒绝多余尾随字节 |
| SHA-256 + 对象类型域分离 | 见 2.4 的 domain separation |
| 规范样例、预期摘要、非法反例 | 见第四节与第五节 |

# 二 · 完整字节布局

## 2.1 通用框架

```text
编码单位（encoded unit）=
    MAGIC            8  字节   固定 "AFGLREF\x00"
    FORMAT_VER       2  字节   大端，本节为 0x0001
    OBJECT_TYPE      1  字节   见 2.2
    RESERVED         1  字节   必须为 0x00
    FIELD_COUNT      2  字节   大端
    FIELDS          变长        按固定顺序；每字段见 2.3
    TOTAL_LEN        4  字节   大端，含本字段在内的总字节数

⇒ 所有整数字段【一律大端无符号】。
⇒ 所有长度字段【不含自身】。
```

```text
⇒ 【为什么写 TOTAL_LEN 在末尾而不是开头】
   放末尾 ⇒ 生成时可一次算完；解析时可校验「看起来读完了」与
   「声称的总长」是否一致，从而发现截断与多余尾随。
⇒ 若放开头，则截断时 READING 仍可能"刚好"满足前缀声明的字段数，
   反而看不出尾部丢失。
```

## 2.2 OBJECT_TYPE 取值（域分离）

```text
0x01  ATTEMPT_REF       对权威记录的发送侧引用
0x02  RECEIPT_REF       对权威记录的收据侧引用
0x03  KEY_TRIPLE        (recorder_id, epoch, seq) 三元组本身
0x00  保留（不得使用）
0x80-0xFF 保留给后续版本（本节不得出现）
```

```text
⇒ 【域分离要求】
   摘要输入 = OBJECT_TYPE 单字节 ‖ 编码正文（不含 MAGIC 与 FORMAT_VER 之外的解释）
   ⇒ 即：不同 OBJECT_TYPE 的相同正文字节，得到【不同】摘要。
   ⇒ 理由：防止把一条 ATTEMPT_REF 的字节当作 RECEIPT_REF 复用。
   ⇒ 详见 2.4。
```

## 2.3 字段编码（含单射性保证）

```text
FIELDS 按【固定顺序】排列。每个字段：
    TAG      1 字节   字段标签（见下表）
    LEN      2 字节   大端，本字段内容的字节数
    VALUE    LEN 字节

⇒ 【单射性由 LEN 保证，不依赖分隔符】
   ⇒ 任意两个不同的字段值组合，若其 LEN 或 VALUE 不同，
     则编码不同字节。
   ⇒ 证明思路：给定编码，唯一可解析出每个 (TAG, LEN, VALUE)；
     给定 (TAG, LEN, VALUE) 序列，唯一可编码。
```

```text
字符串类字段（VALUE 为 UTF-8 字节，不得含 NUL）：
    TAG  LEN  VALUE
⇒ 【禁止】空字符串：LEN 必须 ≥ 1。
   ⇒ 理由：空值与"字段缺失"必须可区分，否则
     「没有 submitter_id」与「submitter_id 为空」编码相同。

整数类字段（VALUE 为定宽大端，LEN 必须等于该字段规定宽度）：
    TAG  LEN  VALUE
⇒ 【禁止】非规定宽度的整数编码（例如用 LEN=3 表示一个 seq）。
   ⇒ 理由：变宽整数会引入前导零歧义（0x000001 vs 0x01）。
```

## 2.4 摘要定义

```text
digest = SHA-256( OBJECT_TYPE ‖ header_fixed ‖ fields_encoding )

  其中 header_fixed 按【不含 MAGIC、不含 FORMAT_VER 的解释】定义如下：
      FORMAT_VER(2) ‖ OBJECT_TYPE(1) ‖ RESERVED(1) ‖ FIELD_COUNT(2)
  ⇒ 注：OBJECT_TYPE 出现两次上述理由不同：
     · digest 前缀那次 = 域分离
     · header_fixed 内那次 = 编码自描述
     ⇒ 【这一点是刻意冗余，不是笔误】；它使
       「编码完整」与「域分离」两件事各自独立可验。
```

```text
⇒ 【摘要覆盖什么、不覆盖什么】
   覆盖：FORMAT_VER、OBJECT_TYPE、RESERVED、FIELD_COUNT、全部 FIELDS、TOTAL_LEN
   不覆盖：MAGIC
   ⇒ 理由：MAGIC 是定值，覆盖它不增加区分度；
     但【保留】它使解析可尽早拒绝非本格式输入。

⇒ 【必须明写的一句】
   摘要匹配只说明「所读字节与本摘要一致」，
   【不说明】来源可信、不说明独占、不说明写入归属。
   ⇒ 依据：§0 A-3 / D-2，裁定第二节「完整性不等于可信身份」。
```

# 三 · 各对象类型的字段表

## 3.1 ATTEMPT_REF (0x01)

```text
⇒ 字段集合与 v0.2 §2.2b「AttemptRecord 完整性覆盖范围【必须包含】」一致：
     event_id / attempt_id / authority_record_key / submitter_id /
     sent_state / observed_state / attempt_note
⇒ 本节【不增不减】，只规定其编码形式。
```

| 顺序 | 字段 | TAG | 类型 | 约束 |
|---|---|---|---|---|
| 1 | `event_id` | `0x01` | 字符串 | 1..255 字节，UTF-8，无 NUL |
| 2 | `attempt_id` | `0x02` | 字符串 | 1..255 字节 |
| 3 | `authority_record_key` | `0x03` | 嵌套 KEY_TRIPLE | 见 3.3 |
| 4 | `submitter_id` | `0x04` | 字符串 | 1..255 字节 |
| 5 | `sent_state` | `0x05` | 枚举 | 1 字节，取值见下 |
| 6 | `observed_state` | `0x06` | 字符串 | 0..1024 字节（可为空在此字段） |
| 7 | `attempt_note` | `0x07` | 字符串 | 0..1024 字节 |

```text
⇒ `sent_state` 取值：0x01 = ACK_SENT；其他值保留。
⇒ 【注意】`observed_state` 与 `attempt_note` 允许空内容，
   但其 LEN 仍须存在（LEN=0）。
   ⇒ 这与 2.3「禁止空字符串」不冲突：
     2.3 禁的是【标识类】字段为空（无法与缺失区分）；
     此处两者是【内容类】字段，LEN=0 是有效且可区分的取值。
```

## 3.2 RECEIPT_REF (0x02)

```text
⇒ 与 v0.2 §2.2b「ReceiptRecord 完整性覆盖范围【必须包含】」一致：
     event_id / attempt_id / authority_record_key /
     receipt_fact / receipt_seq / received_by
```

| 顺序 | 字段 | TAG | 类型 | 约束 |
|---|---|---|---|---|
| 1 | `event_id` | `0x11` | 字符串 | 1..255 |
| 2 | `attempt_id` | `0x12` | 字符串 | 1..255 |
| 3 | `authority_record_key` | `0x13` | 嵌套 KEY_TRIPLE | 见 3.3 |
| 4 | `receipt_fact` | `0x14` | 枚举 | 1 字节，0x01 = ACK_RECEIVED |
| 5 | `receipt_seq` | `0x15` | 整数 | 8 字节 BE，≥ 1 |
| 6 | `received_by` | `0x16` | 字符串 | 1..255 |

```text
⇒ 【TAG 按对象类型分段（0x0x / 0x1x）】
   理由：误把 ATTEMPT_REF 的 TAG 表用于 RECEIPT_REF 时，
   解析会立刻失败，而不是悄悄解析出错误结构。
```

## 3.3 KEY_TRIPLE (0x03) 嵌套编码

```text
⇒ `authority_record_key = (recorder_id, epoch, seq)`（v0.2 §2.1/§2.2c）。
⇒ 它在此作为【嵌套 VALUE】出现，自身也按同一框架编码：
     TAG(1) LEN(2) | <KEY_TRIPLE 的完整编码字节>
⇒ 内层同样带 MAGIC / FORMAT_VER / OBJECT_TYPE=0x03 / TOTAL_LEN。
```

| 顺序 | 字段 | TAG | 类型 | 约束 |
|---|---|---|---|---|
| 1 | `recorder_id` | `0x21` | 字符串 | 1..255 |
| 2 | `epoch` | `0x22` | 整数 | 8 字节 BE，≥ 1 |
| 3 | `seq` | `0x23` | 整数 | 8 字节 BE，≥ 1 |

```text
⇒ 【为什么嵌套也带 MAGIC 与 TOTAL_LEN】
   ⇒ 若内层是"裸三字段"，则外层 LEN 一旦记错，
     内层仍可能被解析出一组看似合理的值。
   ⇒ 带内层自校验后，外层 LEN 错误会被内层 TOTAL_LEN 发现。
```

## 4.2 向量 V2 · 必须不同的两个近邻

```text
V2a: ("A","1","23")   V2b: ("A","12","3")
⇒ 本编码下二者必然不同：
   V2a: recorder_id LEN=01, epoch=..., seq=23
   V2b: recorder_id LEN=01, epoch=..., seq=3
   ⇒ epoch 与 seq 为【定宽 8 字节】，数值不同即字节不同。
⇒ 【这是 v0.2 §2.2c 单射性要求的直接检验点】：
   无分隔拼接下二者同为 "A123"；本节方案下不同。
```

## 4.3 独立复算方法（给复核者）

```text
⇒ 复算步骤（不需信任作者）：
   ① 按 2.1 与 2.3 从字段值构造字节序列；
   ② 手工计算 N 与 M（各段字节数之和）；
   ③ 按 2.4 公式算 SHA-256：
        digest = SHA-256( OBJECT_TYPE ‖ header_fixed ‖ fields_encoding )
   ④ 与文档给出的期望值逐字节比较。
⇒ 【若你算出与我不同，以你算的为准，请退回。】
```

# 五 · 非法输入与非目标反例

```text
⇒ 每个反例给出：构造 / 期望拒绝原因 / 由哪条规则拒绝。
```

| # | 构造 | 期望 | 依据 |
|---|---|---|---|
| N1 | MAGIC 不等于 `AFGLREF\0` | 拒绝 | 2.1 |
| N2 | `FORMAT_VER` 非 0x0001 | 拒绝（本版不解析其他版本） | 2.1 |
| N3 | `OBJECT_TYPE` = 0x00 或 ≥ 0x80 | 拒绝 | 2.2 |
| N4 | `RESERVED` ≠ 0x00 | 拒绝 | 2.1 |
| N5 | `FIELD_COUNT` 与实际字段数不符 | 拒绝 | 2.1 |
| N6 | 字段顺序与本节表不符 | 拒绝 | 2.3 |
| N7 | 标识类字段 `LEN=0`（如 `event_id=""`） | 拒绝 | 2.3 |
| N8 | 整数以非规定宽度编码（如 `seq` 用 LEN=3） | 拒绝 | 2.3 |
| N9 | `TOTAL_LEN` 小于实际字节数（有尾随） | 拒绝 | 2.1 |
| N10 | `TOTAL_LEN` 大于实际字节数（被截断） | 拒绝 | 2.1 |
| N11 | 内层 KEY_TRIPLE 的 `TOTAL_LEN` 与外层字段 LEN 不一致 | 拒绝 | 3.3 |
| N12 | 同名字段重复出现两次 | 拒绝 | 2.1（FIELD_COUNT 与顺序） |
| N13 | **对象替换**：把一条 RECEIPT_REF 的字节以 OBJECT_TYPE=0x01 重标 | 摘要不同 ⇒ 不被接受为同一对象 | 2.2 / 2.4 域分离 |
| N14 | **跨对象 TAG 混用**：用 ATTEMPT_REF 的 TAG 表解析 RECEIPT_REF | 解析失败 | 3.2 |
| N15 | 合法编码被整体重放（同一字节第二次提交） | **本层不拒绝** ⇒ 见下 |
| N16 | 输入长度 < 头部长度（连 17 字节都不到） | 拒绝 | 2.5 前置长度检查 |
| N17 | 字段 VALUE 被截断（LEN 声称 8，实际只剩 3） | 拒绝 | 2.5 前置长度检查 |

```text
⇒ 【2026-11-04 二次修正（自查）：N10 / N17 原先"拒绝理由"写错了】

⇒ 我按本节规则写了一个最小实现做验证，发现：
   输入被截断时，解析在读到 TOTAL_LEN 那 4 个字节时会先抛异常，
   【根本走不到】"TOTAL_LEN 与实际长度不符"这条判断。
⇒ 也就是说：N10 写的"依据 2.1"在实现上是不完备的——
   它假定能读到 TOTAL_LEN，而截断输入恰恰读不到。

⇒ 故新增 2.5「前置长度检查」，并新增 N16 / N17 两条反例。
⇒ 这不是文字问题：若不补，实现者按本节写会得到
   「异常」而不是本节承诺的「拒绝」，
   而"抛异常"与"按规则拒绝"在验收时不是同一件事。
```

## 2.5 前置长度检查（解析顺序，不可颠倒）

```text
⇒ 解析器必须【按下列顺序】检查，任一步失败即拒绝，
   【不得】先尝试解析字段再回头判断长度。
```

```text
步骤 0  输入总长 L ≥ 17              —— 否则拒绝（N16）
        （17 = MAGIC 8 + FORMAT_VER 2 + TYPE 1 + RESERVED 1
              + FIELD_COUNT 2 + TOTAL_LEN 4 中，
              至少头部 + 末尾 4 字节都要在；
              若 L < 17，连结构都无从谈起）
步骤 1  读 MAGIC（8）                —— 不等则拒绝（N1）
步骤 2  读 FORMAT_VER（2）           —— 非 0x0001 拒绝（N2）
步骤 3  读 OBJECT_TYPE（1）          —— 非法取值拒绝（N3）
步骤 4  读 RESERVED（1）             —— 非 0x00 拒绝（N4）
步骤 5  读 FIELD_COUNT（2）          —— 先不校验，仅记录
步骤 6  逐字段读 TAG(1)+LEN(2)，
        每次读 VALUE 前先检查
        「剩余字节 ≥ LEN + 4」        —— 不足则拒绝（N17）
        （+4 是为末尾 TOTAL_LEN 保留）
步骤 7  读 TOTAL_LEN（4）            —— 之后必须无剩余字节
步骤 8  校验 TOTAL_LEN == L          —— 不等拒绝（N9 / N10）
步骤 9  校验 FIELD_COUNT == 实际字段数 —— 不等拒绝（N5）
```

```text
⇒ 【为什么步骤 6 要预留 4 字节】
   ⇒ 若允许字段 VALUE 一直读到输入末尾，
     则 TOTAL_LEN 会被字段吞掉，
     于是"截断"表现为"字段内容变短"而【不是】解析失败。
   ⇒ 这正是 N17 要拦的情形：看起来解析成功，实际内容已被截断。
```

```text
⇒ 【关于 N10 与 N17 的关系（按上列顺序会先命中 N17）】
   ⇒ 一条被截断的输入，通常在【步骤 6】就因剩余字节不足而拒绝，
     而不是走到步骤 8 才由 TOTAL_LEN 发现。
   ⇒ 这不是标错：这是【解析顺序决定的正确行为】。
   ⇒ 只有当输入长度足够读到 TOTAL_LEN、
     但 TOTAL_LEN 声明值 ≠ 实际长度时，才是真正的 N10。
   ⇒ 故验收时须区分：
        "因长度不足而拒绝"  ⇒ 命中 N16 / N17
        "长度足够但声明不符" ⇒ 命中 N10
     ⇒ 不得把两者合并统计为一条。
```

```text
⇒ 【实现层的核验义务（§0 B 类右列）】
   "按上述顺序检查"属【本地核验义务】，
   不是外部前提。
   ⇒ 本申请须在验收时证明实现确实按此顺序检查，
     而不是"调用了校验函数"。
```

```text
⇒ 【N15 必须单独说明，因为它不是"编码"能解决的问题】
   ⇒ 本层只能保证：相同字节 ⇒ 相同摘要。
   ⇒ 【不能】保证「同一摘要只出现一次」。
   ⇒ 「重放」属【幂等性 / 唯一绑定】问题，
     由 P4-2.3（首次绑定为权威）与 D1 的不可变性处理，
     【不在 P1 编码范围内，也不在本节声称已解决】。
   ⇒ 依据：§0 A-1 / §0 A-4。
```

```text
⇒ 【被替换的"对象"是什么，本节给出界定以免混淆】
   本节所谓「对象替换」= 用【另一类对象】的合法编码冒充本类对象。
   ⇒ 不含：用【同一类对象】但不同字段值替换
     （那由摘要不等自然检出）。
   ⇒ 不含：把文件整体换成同内容另一文件
     （§0 D-2，非本层职责）。
```

# 六 · 与 P2 / 持久化的接口边界

```text
⇒ 裁定第二节两条边界，本节必须各自写明，不可合并。
```

## 6.1 P1 → P2

```text
⇒ 本节输出：一条引用记录的规范字节 + 其摘要。
⇒ 本节【不】输出：这条引用「是谁写的」「是否可信」。
⇒ P2 负责的部分（不在本节）：
   · 提交方身份凭证的格式与可信来源
   · 核验结果如何绑定到 (event_id, attempt_id)
   · 消费者接受身份绑定的五条判据（v0.2 §4.3）
```

```text
⇒ 【接口点】
   P2 的 ATTESTATION 若需要引用本节的字节，
   应按 2.2 新增 OBJECT_TYPE（0x04，预留），
   【不得】复用 0x01/0x02/0x03。
   ⇒ 否则域分离失效。
```

## 6.2 P1 → 持久化

```text
⇒ 本节输出的是【内容与摘要】，不是【已持久化的保证】。
⇒ 裁定第二节原话：「规范编码不等于原子持久化」。
⇒ 本节【不主张】：
   · 写了这些字节就落在了持久介质上
   · 摘要相同就意味着磁盘上只有一个副本
   · 编码正确就意味着崩溃后还能读回来
⇒ 持久化边界见 §5；崩溃相关见 §0 A-2a / A-2b。
```

```text
⇒ 【一个具体的耦合风险，必须写明】
   ⇒ 若持久化实现把"编码 + 写盘"合在一个函数里，
     则 §0 D-1 的无 fsync 问题会【传染】本节：
     编码正确，但落盘不保证。
   ⇒ 故本节要求：编码函数【不负责】写盘；
     写盘由 §5 的持久化层负责，二者可分别测试。
```

# 七 · 哪些性质仍未被证明

```text
⇒ 承 §0，本节【不主张】以下任何一条：
   ① 摘要匹配 ⇒ 来源可信（§0 A-3）
   ② 摘要匹配 ⇒ 独占（§0 D-2）
   ③ 编码正确 ⇒ 已持久化（6.2）
   ④ 摘要唯一 ⇒ 无重放（N15）
   ⑤ 本方案在本机实现中与本文一致（本节只定义规范，未实现）
   ⑥ 【已改】本节的测试向量【已实际计算并回填】（4.1），
      但仍属【作者单方计算】—— 尚未经他人独立复算。
      ⇒ 依 §0 A-1：「我算过」不等于「已复核」。
      ⇒ 本节只声明值存在且给出复算方法，不声明它已被验证。

⇒ 本节新增的、§0 尚未覆盖的一条：
   ⑦ 本编码的【实现】是否单射 —— 规范单射 ≠ 实现单射
      ⇒ 属实现核验义务（§0 B 类右列），本申请须在验收时核。
```
