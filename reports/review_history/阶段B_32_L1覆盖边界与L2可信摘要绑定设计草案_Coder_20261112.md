### 2.2 可信预期摘要的来源（设计）

```text
⇒ 【本节给的是设计，不是候选清单。】三处硬约束先写死：

   约束 1  EXPECTED_DIGEST_WRITER != RECORD_WRITER
           （写入预期摘要的主体，不得是产生被验证记录的那一方）
   约束 2  EXPECTED_DIGEST_SCOPE = 单条记录，不得"整批一个摘要"
           （整批摘要会让单条记录的替换不可见）
   约束 3  EXPECTED_DIGEST_BINDING = (record_id, snapshot_id, digest) 三元组
           （只存 digest 而不绑 record_id，等于可以张冠李戴）

⇒ 约束 1 是目的，2 和 3 是防止"形式上满足约束 1，实际上仍然无效"。
   我先把这三条立起来，再说来源怎么实现。
```

#### 2.2.1 预期摘要条目（ExpectedDigestEntry）的字段设计

```text
⇒ 【设计产物】：一个可被第三方独立读取、独立比对的条目。

   ExpectedDigestEntry :=
     record_id      : 记录的唯一标识（与记录内的 id 字段一致）
     snapshot_id    : 该记录【完整原始编码字节】的 SHA-256
     protocol_digest: 按 §2.0 口径（现有规范，不变）算出的摘要
     issued_at      : 条目写入时间
     issuer         : 写入主体标识
     prev_entry_id  : 前一条的 id（仅 append-only 来源使用，见 2.2.3）

⇒ 【为什么 snapshot_id 和 protocol_digest 都要存】：
   · protocol_digest 是"内容绑定"要验的东西
   · snapshot_id 是"验的是不是同一份字节"要验的东西
   ⇒ 只存一个，就无法区分【内容不符】与【验错了对象】。
   ⇒ 这两者在 §2.4 里必须落到不同的状态（UNBOUND vs UNDETERMINABLE）。
```

#### 2.2.2 来源分级（按"能否被第三方核对"，不按实现难度）

```text
⇒ 【关键设计：来源不是一个坐标，而是分级。】
   因为现实中没有任何一种来源能一次满足全部要求，
   所以我定义【等级】，并规定每一等级允许声称什么、不允许声称什么。

   S0 · 无来源
     · 预期摘要由记录方自行提供
     ⇒ 允许声称：无
     ⇒ 不允许声称：BOUND（最高只能到 UNDETERMINABLE）
     ⇒ 这一级【不是失败】，而是"没有可信基础"，必须如实标注

   S1 · 同仓库不同文件
     · 与记录在同一 repo，不同路径
     ⇒ 允许声称：无独立写权
     ⇒ 不允许声称：独立写权
     ⇒ 理由：同一个 commit 可同时改两处 —— 结构性证明在此【不成立】

   S2 · 独立仓库 / 独立凭据
     · 写入需另一套凭据，且凭据不由记录方持有
     ⇒ 允许声称：写权分离【在当前实现下成立】
     ⇒ 不允许声称：密码学独立（因为凭据可能被同一人持有）
     ⇒ 这一级需要 §2.3 的【可检验证据】，否则仍是声明

   S3 · 外部根锚点（裁定 A.4：DEFERRED，非增强版 S2）
     · 由仓库外锚点固定，改动留外部可见痕迹
     ⇒ 【裁定 A.4】：S3 不因编号高于 S2 就自动拥有更强信任保证。
     ⇒ 外部锚点由谁提供 / 保管 / 监督，如何防整体替换，
        须在具体候选方案出现后【另行裁定】。
     ⇒ 本轮不指定任何云服务、仓库、设备或人员为外部可信根。
     ⇒ 【我上一版写「S2 的增强」是误导，已删。】

⇒ 【每一级都必须能被写进报告并接受反驳】。
   所以条目里必须有 §2.2.3 的 source_level 字段。
⇒ 【不许做的事】：把 S1 写成 S2，或把 S2 写成 S3。
   这是我最容易犯的错 —— 用"另一个目录"冒充"独立写权"。
```

#### 2.2.3 存储形态

```text
⇒ 【明确不采纳】：把预期摘要写进记录本身。
```

### 2.3 独立写权证明（设计 · 2026-11-13 按 C-3 补充证明边界）

```text
⇒ 【立场】：独立写权【不是】可以"声明"的属性，
   而是必须【逐条给证据、且允许被推翻】的判定。

⇒ C-3 裁定指出我上一版三处"把字段存在当成证据成立"：
   WE-3  append-only 链本身【不能】排除整体重写
   WE-4  issued_at 只是时间声明，【不能】独立证明先后
   WE-6  三个字段"非空"不等于绑定可验证
   ⇒ 本轮逐项改写：每一项都要写清【它证明了什么、证明不了什么】。
```

#### 2.3.1 证据项（WE-1 … WE-6，含证明边界）

```text
  WE-1  写入凭据归属
        命题：写入 expected digest 所用凭据的持有者集合，
              与 RECORD_WRITER 的持有者集合【交集为空】
        检查：列出两套凭据持有者，求交集
        判定：交集为空 → 通过；非空 → 不通过
        ⇒ 【证明不了】：持有者名单本身的完整性。名单可能漏人。
           ⇒ 所以还需 CREDENTIAL_HOLDER_REGISTER（裁定 A.3 第 2 条）。
        ⇒ 【无法纯代码判定】。

  WE-2  提交路径隔离
        命题：不存在一条命令/一次提交流程能同时修改记录与预期摘要
        检查：审查 CI、hook、管理员路径、代理凭据、自动化流程
        判定：存在任一路径同时改两侧 → 不通过
        ⇒ 【证明不了】：未列出的间接路径（如直接改存储后门）。
           ⇒ 因此本项通过【不构成】"不可能"，只构成"已检查的路径里没有"。
        ⇒ 【S1（同仓库不同文件）必然不通过本项】。

  WE-3  历史不可改写（C-3 重点修订）
        命题：expected digest 历史条目不可被删除或就地修改
        ⇒ 【C-3 裁定原文】：append-only 链只能在存在可信链头或外部见证时，
          才提供有意义的防改写证据；【链自身不能排除整体重写】。
        ⇒ 所以本项【拆成两级】：

           WE-3a  局部篡改可见性
                  检查：删除中间一条，观察是否断链
                  判定：断链可见 → a 级通过
                  ⇒ 【只证明"局部改动会被发现"】

           WE-3b  整体重写抵抗
                  前提：存在【可信链头】（锚定在记录/预期摘要双方都无法
                        单方面改写的位置），或存在外部见证
                  判定：无可信链头 → 【本项不通过，且不得声称 a 级通过就够了】
                  ⇒ 【a 通过 ≠ WE-3 通过】。这是我上一版最大的错。
                  ⇒ 可信链头本身属 §2.5 信任根问题，不在本节解决。

  WE-4  时序声明（C-3 重点修订）
        命题（原）：issued_at 早于验证动作
        ⇒ 【C-3 裁定】：issued_at 只是时间声明，不能独立证明先后。
        ⇒ 修订为：
           WE-4a  时间声明存在且格式合法        → 只能说明"写了这个时间"
           WE-4b  时间来源可信（时钟不可由写入方调整）
                  ⇒ 若时间源与 RECORD_WRITER 同源 → 本项【不通过】
                  ⇒ 若无可信时间源 → 本项【UNDETERMINABLE】
        ⇒ 【绝不允许】：因为 issued_at 数值较小就判"先于验证"。
           那等于信任写者填的数字。

  WE-5  单条粒度
        命题：每条记录对应独立条目，不存在"一批共用一个摘要"
        检查：检查条目与记录的基数关系
        判定：存在批量摘要 → 不通过
        ⇒ 【能纯代码判定】，对应 §2.2 约束 2。

  WE-6  绑定可验证性（C-3 重点修订）
        命题（原）：三个字段均存在且非空
        ⇒ 【C-3 裁定】：不能停留在"非空"，需设计与记录、授权发行者、
          快照的可验证绑定。
        ⇒ 修订为三个子项：
           WE-6a  字段齐备（record_id / snapshot_id / protocol_digest）
                  ⇒ 仅"非空"，【不足】
           WE-6b  record_id 与记录内 id 【一致】（哈希或等值比对）
                  ⇒ 防张冠李戴
           WE-6c  发行者可验证：条目可追溯到 issuer，且 issuer 属于
                  已登记的凭据持有者集合
                  ⇒ 依赖 CREDENTIAL_HOLDER_REGISTER；无登记 → UNDETERMINABLE
        ⇒ 【三子项全过才算 WE-6 通过】。
```

#### 2.3.2 判定规则

```text
⇒ 【默认不信】：证据不足时判 UNDETERMINABLE，不是 BOUND。

   独立性判定 = ESTABLISHED      ⇔  WE-1..WE-6 【全部】通过
                              （含 WE-3b 与 WE-4b，不含仅 WE-3a / WE-4a）
               NOT_ESTABLISHED  ⇔  任一项明确不通过
               UNDETERMINABLE   ⇔  无明确不通过，但至少一项无法检查

⇒ 【合取，不是加权】：独立写权是合取条件。
   "五项通过、一项不通过"不是"八成独立"，是【不独立】。

⇒ 【单列 UNDETERMINABLE 的理由】：
   无法检查 ≠ 检查失败。
   "查不了"写成"不独立"会冤枉实现者；写成"独立"会放过真实风险。
```

### 2.4 三态失败语义（设计 · 2026-11-13 按 C-1/C-2 修订）

```text
⇒ 【核心纪律，先写死】：三态由【证据状态】决定，不由程序路径决定。
   同一个输入，只要证据相同，判定必须相同 —— 不允许"偶尔 BOUND"。

⇒ 【本次修订动了两处，都是我上一版的真错误，不是表述问题】：
   C-1  上一版在比较摘要不等时直接判 UNBOUND，直到之后才查独立性。
        ⇒ 等于【用未经信任的预期值下"确定失败"的结论】。顺序错了。
   C-2  上一版把"解析失败"判成 UNDETERMINABLE。
        ⇒ 那是【L1 结构拒绝】被伪装成 L2 内部状态。违反三层分离。
```

#### 2.4.0 分层前置：L1 结果先于 L2 三态

```text
⇒ 【C-2 的落实】：L2 三态【不是在空白上开始的】，它有一个前置门。

   L1 校验结果只有两种：
     L1_REJECTED  ⇒ 【不进入】L2 三态判定。
                     L2 侧记录为 L1_REJECTED（独立结果，非三态之一）。
     L1_VALID     ⇒ 允许进入 L2 三态判定。

⇒ 【关键】：L1_REJECTED 不得被记录成 UNDETERMINABLE。
   ⇒ 前者是"结构就不对"（R-V2-xx 系列，L1 已给出明确规则号）
   ⇒ 后者是"结构对，但绑定关系判不了"
   ⇒ 混同的后果：L1 失败会被统计成"L2 无法判定"，
     从而掩盖 L1 的真实拒绝率。

⇒ 既有依据：B_23 §3.4「三层分离」（Q-V2-03 裁定）。
```

#### 2.4.1 判定算法（七步，顺序不可调换 · C-1 已修正）

```text
  前置：record_bytes（完整原始编码字节）, expected_store
  前置门：若 L1 校验为 REJECTED → 返回 L1_REJECTED，【不进入下列步骤】

  step 1  snapshot_id := SHA256(record_bytes)
          ⇒ 口径由 §2.0 固定：完整原始编码记录，规范化 FORBIDDEN

  step 2  record_id := 从已通过 L1 的记录中取 id
          ⇒ 注意：走到这里说明 L1 已通过，取 id 不应失败。
            若仍失败（实现矛盾）→ UNDETERMINABLE + INFRA_ERROR 标记，
            【不是 L1_REJECTED】——因为 L1 明明已放过它。

  step 3  entry := expected_store.lookup(record_id)
          不存在 → UNDETERMINABLE（"没有预期值"≠"错"）
          残缺   → UNDETERMINABLE
          ⇒ 【不许在缺预期值时返回 BOUND】，也不许返回 UNBOUND

  step 4  【C-1 修正点 · 可信来源先于摘要比较】
          先做条目完整性 + 来源可信性 + 独立写权证据（§2.3.2）判定。
          若独立性判定 != ESTABLISHED → UNDETERMINABLE
          ⇒ 【必须在这里返回，不能往下走】。
             因为下面的 protocol_digest 比较只有在"预期值本身可信"时
             才有意义。用不可信的预期值说"确定不符"，是把
             【我们自己的取证失败】说成【记录的确定性缺陷】。

  step 5  【C-1 修正点 · 绑定核对】
          若 entry.snapshot_id != snapshot_id → UNDETERMINABLE
          ⇒ 这是"验错了对象"，不是"内容不符"。
            若返回 UNBOUND，等于冤枉记录 —— 记录可能没问题，
            只是手上的预期值对应的是另一份字节。

  step 6  【只有走到这里，比较才有意义】
          recomputed := 按 §2.0 口径计算 protocol_digest
          若 recomputed != entry.protocol_digest → UNBOUND
          ⇒ 此时三前提均已成立：
             (a) L1 通过  (b) 预期值来源可信  (c) 验的是同一份字节
          ⇒ 所以这个"不等"才是【可信依据下的确定否定】。

  step 7  任何一步抛异常（IO/超时/实现异常）→ UNDETERMINABLE
          ⇒ 【失败关闭】：异常绝不允许落到 BOUND。
```

```text
  行 | L1       | 预期条目 | 来源/独立写权 | snapshot_id | digest  | 判定
  ---|----------|----------|---------------|-------------|---------|------------------
   1 | REJECTED | —        | —             | —           | —       | L1_REJECTED
   2 | VALID    | 不存在    | —             | —           | —       | UNDETERMINABLE
   3 | VALID    | 残缺      | —             | —           | —       | UNDETERMINABLE
   4 | VALID    | 存在      | NOT_ESTAB     | （不核对）   | （不比较）| UNDETERMINABLE
   5 | VALID    | 存在      | UNDETERM      | （不核对）   | （不比较）| UNDETERMINABLE
   6 | VALID    | 存在      | ESTABLISHED   | 不等        | （不比较）| UNDETERMINABLE
   7 | VALID    | 存在      | ESTABLISHED   | 相等        | 不等    | UNBOUND
```

#### 2.4.3 验收计数口径（B 裁定落实）

```text
⇒ 凌翼裁定 B：UNDETERMINABLE 属未通过，但【必须独立计数】。

   L2_TOTAL            = L2_BOUND + L2_UNBOUND + L2_UNDETERMINABLE
   L2_NONPASS          = L2_UNBOUND + L2_UNDETERMINABLE

   L2_ACCEPTANCE_PASS  = (L2_UNBOUND == 0)
                       AND (L2_UNDETERMINABLE == 0)
                       AND (ALL_REQUIRED_RECORDS_EVALUATED)
                       AND (NO_INFRASTRUCTURE_ERROR)

⇒ 【三条禁令，逐条对应裁定原文】：
   · 不得因为证据不足就把记录【排除出分母】
     ⇒ L2_TOTAL 必须包含 UNDETERMINABLE 的记录
   · 不得把 UNDETERMINABLE 计为成功
   · 不得把它伪装成 UNBOUND

⇒ 【L1_REJECTED 不进 L2_TOTAL】：

   ⇒ 但 L1 拒绝必须【单独统计】，不能因此消失。
```

#### 2.4.4 测试判定与业务判定必须分开（B.3 落实）

```text

   若用例【预期】就是 UNDETERMINABLE，而验证器正确返回它：

     L2_BINDING_STATUS  = UNDETERMINABLE

⇒ 【必须三个字段同时记录】，不允许只记 TEST_VERDICT。
   ⇒ 否则报告里会出现"58 项全 PASS"，读的人以为记录都可信了，
     实际上其中若干条的业务状态是 UNDETERMINABLE —— 不能消费。

⇒ 这一条我上一版【没有】写清楚，是 B 裁定补上的。
```

#### 2.4.5 每态必须有独立用例

```text
⇒ 「会失败的检查，最怕的不是失败，是没响。」

  L2C-L1-REJ-01      L1 结构拒绝 → L1_REJECTED（非三态）
  L2C-BOUND-01       全部合法 + 独立性 ESTABLISHED → BOUND
  L2C-UNBOUND-01     L1/来源/绑定全对，digest 差 1 字节 → UNBOUND
  L2C-UNDET-01       预期条目不存在 → UNDETERMINABLE
  L2C-UNDET-02       预期条目缺 record_id → UNDETERMINABLE
  L2C-UNDET-03       来源 NOT_ESTABLISHED，digest 也对不上
                     → 【必须 UNDETERMINABLE，不得 UNBOUND】  ← C-1 专属用例
  L2C-UNDET-04       snapshot_id 不等 → UNDETERMINABLE
  L2C-UNDET-05       过程抛异常 → UNDETERMINABLE

⇒ 【L2C-UNDET-03 是 C-1 的回归用例】：
   构造"来源不可信 + digest 也不一致"，期望 UNDETERMINABLE。
   ⇒ 若实现按旧顺序先比 digest，会返回 UNBOUND ⇒ 该用例变红 ⇒ 能抓住回归。
   ⇒ 【没有这个用例，C-1 修好了也会被下一次重构改回去。】

⇒ 【反向检查】：把 UNBOUND 分支改成提前 return，
   L2C-UNBOUND-01 必须变红；把来源判定挪到 digest 之后，
```
