## 二 · L2 可信摘要绑定设计草案

> 本节按凌翼给的六个问题逐条展开。**每节只列方案与权衡，不给结论。**

### 2.1 问题一：可信预期摘要从哪里产生、由谁持有和保护

```text
⇒ 【要解决的核心】：预期摘要【不能】由产生被验证记录的一方写。
   否则就是自证：写者改字节、同时改预期值，永远"验证通过"。

⇒ 可选方案：

  方案 A · 独立写权的预期摘要清单
    · 预期摘要由【另一个写权主体】产生并存放在独立位置
    · 优点：概念简单，与现有"写权边界"语言一致
    · 风险：需证明两者写权【真的】独立 —— 靠什么证明？不能靠声明

  方案 B · 摘要由不可回改的追加日志得出
    · 预期摘要来自只可追加的日志（append-only），记录方无改写权
    · 优点：篡改需被发现性更高；可审计
    · 风险：日志本身仍可能被整体替换；需要锚点

  方案 C · 外部根锚点（类似 SPEC RootAnchor 的既有做法）
    · 预期摘要的根由仓库外部锚点固定
    · 优点：与项目已有的 RC11 冻结实践同构
    · 风险：锚点载体本身也要可信

⇒ 【共同难点】：三种方案都要回答同一个问题——
   「凭什么相信这个预期摘要是对的？」
   ⇒ 这正是 §5 C2 信任根要求，不能被新方案削弱。
```

### 2.2 问题二：怎样证明预期摘要与待验证记录具有独立写权边界

```text
⇒ 【不能只声明，必须可验证】。可能的形式：

  ① 结构性证明：两者物理位置不同 + 目录权限/仓库权限不同
     ⇒ 但"不同目录"不构成独立写权（同一个 commit 就能一起改）

  ② 流程性证明：修改预期摘要需要另一道审批（双人签）
     ⇒ 属流程保证，不是机制保证

  ③ 密码学证明：记录方【不可能】算出预期值
     ⇒ 需要记录方缺少某个密钥；这会引入密钥管理（新信任根）

⇒ 【诚实的话】：目前三者都无法仅凭代码断言成立。
   ⇒ 建议设计成【可检验的声明 + 明确的失败语义】，
     而不是宣称"已保证独立"。
```

### 2.3 问题三：怎样保证 L1 与 L2 消费同一不可变字节快照

```text
⇒ 【这是最容易做砸的一处】。
   若 L1 校验字节 A、L2 比对字节 B，两者都"通过"也可能来自不同记录。

⇒ 可选机制：

  方案 A · 同一进程内传递字节（不重新读文件）
    · 优点：天然同源
    · 风险：跨进程/跨服务时不成立

  方案 B · 快照身份（snapshot id = 字节的 SHA-256）
    · L1 与 L2 各自记录自己消费的 snapshot id，必须相等
    · 优点：【可验证】，不依赖"我们保证"
    · 风险：多算一次哈希；需规定算法与口径（原字节 vs 规范化）

  方案 C · 单次读取 + 传递句柄
    · 只读一次，把只读视图交给两层
    · 优点：结构上不可能分歧
    · 风险：实现耦合

⇒ 【本文倾向 B】——因为它把"同源"变成【可被第三方核对的等式】，
   而不是"我们说它是同源的"。
   ⇒ 但这是建议，不是结论；且 B 需要先定口径（见 2.6）。
```

### 2.4 问题四：如何区分 BOUND / UNBOUND / UNDETERMINABLE

```text
⇒ 【三态必须由"证据状态"决定，不能由"程序心情"决定】。

  提议定义（供讨论）：

  BOUND
    预期摘要存在 且 来源可追溯 且 与记录摘要相等
    ⇒ 且【快照 id 相等】（见 2.3）

  UNBOUND
    预期摘要存在 且 来源可追溯 且 与记录摘要【不相等】
    ⇒ 这是【确定的否定】，不是"可能错"

  UNDETERMINABLE
    无法作出判断，至少包括：
      · 预期摘要不存在
      · 预期摘要来源不明 / 无法追溯
      · 快照 id 不一致
      · 摘要算法/口径无法确定
      · 验证过程本身失败（IO、解析异常等）

⇒ 【关键纪律】：UNDETERMINABLE ≠ UNBOUND。
   ⇒ 前者是"不知道"，后者是"知道是错的"。
   ⇒ 不得把 UNDETERMINABLE 写成 UNBOUND（会冤枉记录），
     也不得写成 BOUND（会放过错误）。
```

### 2.5 问题五：失败关闭语义

```text
⇒ 以下情形【一律不得视为通过】：

  ① 预期摘要不存在              → UNDETERMINABLE，失败关闭
  ② 预期摘要来源不明            → UNDETERMINABLE，失败关闭
  ③ 快照 id 不一致              → UNDETERMINABLE，失败关闭
  ④ 验证过程抛异常              → UNDETERMINABLE，失败关闭
  ⑤ UNBOUND                    → 明确失败（这是确定的错误）

⇒ 【本项目的既有教训适用】：
   "会失败的检查，最怕的不是失败，是没响"。
   ⇒ 所以 L2 的默认必须是【失败关闭】，只有 1.4 的全部条件成立才是 BOUND。
   ⇒ 并且：三态各自必须有【独立用例】，不能只测 BOUND。
```

### 2.6 问题六：如何保持 §5 C2 信任根要求不被削弱

```text
⇒ C2 当前要求：可信预期摘要 = REQUIRED_FOR_C2（B_23 状态块）。

⇒ 新增 L2 机制后，必须证明【信任根没有变得更弱】：
   · 若引入新组件（日志 / 密钥 / 外部锚点），
     该组件本身成为新的信任根 ⇒ 必须单独论证
   · 若预期摘要的存放位置可变，则"可信"退化为"当前这一版可信"
     ⇒ 需要固定点语义（可参照 B_30 的做法：值集中、来源可追）

⇒ 【必须显式记录的一件事】：
   本草案【不产生】任何新的信任根声明。
   若后续引入，须单独提请裁定。
```
