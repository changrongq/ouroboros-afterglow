## 一 · 为什么现在提

知微在两次复核中重复指出 §2 有编码规范歧义（第一次：2026-11-05 §3/§4 复核的非阻塞项；第二次：2026-11-06 复核的"交给后续章节的明确事项"第三行）。

我此前一直把它记为"挂账不改"，理由是 §2 是 `NOT_NORMALIZED` 且改动会影响 §3 的引用。

**但现在已经不能再推了。** 原因：

1. **§5 的 C2 直接依赖 §2 的摘要定义。**
   §5 第二节把 `COMMITTED` 的条件之一 C2 定义为「其摘要可被独立重算并一致」。
   若 §2 的摘要输入区间有歧义，"独立重算"就没有唯一答案，
   C2 即悬空 —— 而 C2 是"可信提交"五项条件之一，
   而"可信提交"是 §4 签发总判据第 (2) 项。

2. **§3 的 `OBJECT_TYPE = 0x04` 明确声明"沿用 §2 全部规则"。**
   §3 3.4 写「摘要、端序、长度检查、解析顺序【全部沿用 §2】」。
   若 §2 的长度检查下限本身算错，§3 与将来 §5 都会继承这个错误。

3. **我已用实际代码验证，三处都是真问题，不是措辞问题。**
   下面是可复算的证据，不依赖"作者算过"。

## 二 · 问题 1：步骤 0 的头部长度 17 应为 18

**位置**：§2 `2.5 前置长度检查`，步骤 0；以及反例 N16 的描述。

**原文**：

```
步骤 0  输入总长 L ≥ 17              —— 否则拒绝（N16）
        （17 = MAGIC 8 + FORMAT_VER 2 + TYPE 1 + RESERVED 1
              + FIELD_COUNT 2 + TOTAL_LEN 4 中，
              至少头部 + 末尾 4 字节都要在；
              若 L < 17，连结构都无从谈起）
```

**问题**：原文自己列出的六个分量相加为

$$8 + 2 + 1 + 1 + 2 + 4 = 18$$

不是 17。**这不是"保守取小"**：若下限定为 17，一个恰好 17 字节的输入会通过步骤 0，
然后在某一步失败 —— 而它的真实问题是"连固定结构都不完整"，应当在前置检查就被明确拒绝。

**影响**：
- N16 反例的描述「连 17 字节都不到」与实际阈值不符；
- 实现者按 17 写，会在 17 字节输入上得到"后续步骤的拒绝"，而不是"前置长度拒绝"
  —— 与 §2 自己在"二次修正"里立的规矩冲突：
  「"抛异常"与"按规则拒绝"在验收时不是同一件事」。

**建议**：改为 `L ≥ 18`，并把 N16 改为「连 18 字节都不到」。

## 三 · 问题 2：摘要公式不含 `TOTAL_LEN`，但覆盖清单说含

**位置**：§2 `2.4 摘要定义`。

**原文**：

```
digest = SHA-256( OBJECT_TYPE ‖ header_fixed ‖ fields_encoding )

  其中 header_fixed 按【不含 MAGIC、不含 FORMAT_VER 的解释】定义如下：
      FORMAT_VER(2) ‖ OBJECT_TYPE(1) ‖ RESERVED(1) ‖ FIELD_COUNT(2)
```

同节下方又写：

```
覆盖：FORMAT_VER、OBJECT_TYPE、RESERVED、FIELD_COUNT、全部 FIELDS、TOTAL_LEN
```

**问题**：把三项代入公式的实际输入区间是

$$\text{OBJECT\_TYPE} \;\|\; \text{FORMAT\_VER} \;\|\; \text{OBJECT\_TYPE} \;\|\; \text{RESERVED} \;\|\; \text{FIELD\_COUNT} \;\|\; \text{FIELDS}$$

**`TOTAL_LEN` 不在其中** —— 它既不在 `header_fixed`，也不在 `fields_encoding`。
故"公式"与"覆盖清单"直接矛盾。

**已发布的值是按哪个算的？我复算过，是按公式（不含 `TOTAL_LEN`）：**

| 对象 | 文档值 | 我按"公式"重算 | 我按"含 TOTAL_LEN"重算 |
|---|---|---|---|
| KEY_TRIPLE("R1",1,1) | `cc0cb88ee5757e79…` | `cc0cb88ee5757e79…` ✅ | `91705da1…` ✗ |
| ATTEMPT_REF V1 | `52fe16c5cb53f94b…` | `52fe16c5cb53f94b…` ✅ | `a189351e…` ✗ |

⇒ **已发布的值本身是对的；错的是"覆盖清单"那一句。**

**建议（二者择一，需凌翼裁定）**：

- **方案 A（改措辞，不改值）**：覆盖清单删去 `TOTAL_LEN`，并明写
  「`TOTAL_LEN` 不参与摘要；它由步骤 0 与 N9/N10 独立校验」。
  优点：已发布向量不变，§3/§5 引用不受影响。
  代价：`TOTAL_LEN` 不在摘要保护内 —— 但它是长度字段，本身由长度检查保护，不参与摘要并不削弱完整性。

- **方案 B（改公式，重算全部向量）**：把公式改为含 `TOTAL_LEN`，
  重算 §2 全部已发布向量，并同步 §3 的 `0x04` 语义。
  代价：所有已核对过的字节身份全部作废，睫已逐位核过的值要重新核。

**我的建议是 A**，理由：`TOTAL_LEN` 是自描述长度，其正确性由解析顺序独立保证；
把它塞进摘要会让"摘要不覆盖 MAGIC"与"摘要覆盖尾部长度"这两条规则读起来不自洽
—— 一条说"定值字段不参与"，一条说"尾部的定长字段参与"，读者难判边界。
但这属设计取舍，**我请凌翼裁定，不自行决定**。

## 四 · 问题 3：注释里的 `dd6a3a05` 溯源错误

**位置**：§2 `4.1 向量 V1` 末尾的"一处易错点"。

**原文**：

```
⇒ 若把 MAGIC 也算进摘要，得到的是 dd6a3a05…，与本节的 52fe16c5… 不同。
```

**问题**：我按"把 MAGIC 算进去"实际计算，得到的是

$$\text{SHA-256}(\text{OBJECT\_TYPE} \| \text{MAGIC} \| \text{header\_fixed} \| \text{FIELDS}) = \texttt{d86719fa36a518d7…}$$

**不是 `dd6a3a05…`。**

我继续追，发现 `dd6a3a05` 实际来自：

$$\text{SHA-256}(\text{MAGIC} \| \text{header\_fixed} \| \text{FIELDS} \| \text{TOTAL\_LEN}) = \texttt{dd6a3a05638ae87a…}$$

即 **"对整个完整编码字节求摘要、且不加 `OBJECT_TYPE` 前缀"**。

**影响**：这句话是写给复核者的判别提示。
用错的值做提示，复核者按它算会得到第三个值，
然后无法判断是自己算错还是文档写错 —— 这正是"指针要能追"的反例。
（睫在 2026-11-06 复核中就抓到过同类问题：一句指向 §0 的话抄错了一个字。）

**建议**：把提示改为实际可复现的两个对照值：

```
⇒ 对照：
   · 只把 MAGIC 并入（仍在 OBJECT_TYPE 后）：d86719fa36a518d7…
   · 直接对完整编码求摘要（不加 OBJECT_TYPE 前缀）：dd6a3a05638ae87a…
   ⇒ 本节的值是 52fe16c5cb53f94b…（按 2.4 公式：OBJECT_TYPE ‖ header_fixed ‖ FIELDS）
```

## 五 · 复算方法（给复核者，不要求信任我）

```python
import hashlib, struct
MAGIC = b'AFGLREF\x00'

def field(tag, val):
    return bytes([tag]) + struct.pack('>H', len(val)) + val

# 内层 KEY_TRIPLE("R1", 1, 1)
f_in = (field(0x21, b'R1') + field(0x22, struct.pack('>Q', 1))
        + field(0x23, struct.pack('>Q', 1)))
body_in = struct.pack('>H', 1) + bytes([0x03]) + b'\x00' + struct.pack('>H', 3) + f_in
inner = MAGIC + body_in + struct.pack('>I', len(MAGIC) + len(body_in) + 4)
assert len(inner) == 45
d_inner = hashlib.sha256(b'\x03' + body_in).hexdigest()

# 外层 ATTEMPT_REF V1
f_out = (field(0x01, b'E1') + field(0x02, b'A1') + field(0x03, inner)
         + field(0x04, b'U1') + field(0x05, b'\x01')
         + field(0x06, b'') + field(0x07, b''))
body_out = struct.pack('>H', 1) + bytes([0x01]) + b'\x00' + struct.pack('>H', 7) + f_out
assert len(MAGIC) + len(body_out) + 4 == 91
d_out = hashlib.sha256(b'\x01' + body_out).hexdigest()
```
