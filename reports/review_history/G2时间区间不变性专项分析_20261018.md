## 0 · 前置：一处必须首先更正的技术前提（M-1 勘误）

凌翼要求"同时修订 M-1 的 `bInheritHandles` API 前提"。**我实测了，我原来写错了。**

原草案 M-1 写的是：

```text
bInheritHandles=FALSE + PROC_THREAD_ATTRIBUTE_HANDLE_LIST
```

**实测结果**（驱动 `afterglow_harness/c_verify_m1_inherit_premise.py`，本机，不触碰任何受保护对象）：

| 配置 | 结果 |
|---|---|
| `inherit=FALSE`，无列表 | `ok=True err=0` ✅ 有效 |
| `inherit=TRUE` + `HANDLE_LIST` | `ok=True err=0` ✅ 有效 |
| **`inherit=FALSE` + `HANDLE_LIST`** | **`ok=False err=87`**（`ERROR_INVALID_PARAMETER`）❌ **不是合法配置** |

**结论：那两个 API 参数不能这样组合。** 正确表述只有两种：

- **(a)** `inherit=FALSE`，不给列表 ⇒ **什么都不继承**
- **(b)** `inherit=TRUE` + `HANDLE_LIST` ⇒ **只有列出的句柄继承**

**这是设计分析层的勘误，不构成任何隔离结论。** 我原来把两个互斥的选项并成了一个不存在的配置。

## 1 · 形式化目标（照凌翼给定）

$$\forall t \in [t_{\text{start}}, t_{\text{end}}],\quad \neg\,\mathrm{ForbiddenAccess}(W, P, t)$$

| 符号 | 本分析中的取值 |
|---|---|
| $W$ | 真实业务 worker 进程 **+ 它能直接或间接指挥的执行主体**（子进程、代理、IPC 对端） |
| $P$ | 受保护对象集合，**由稳定 OS 身份定义**（卷序列号 + 文件 ID），不用路径 |
| $t_{\text{start}}$ | 边界生效的可信事件 |
| $t_{\text{end}}$ | worker 终止的可信事件 |
| $\mathrm{ForbiddenAccess}$ | 见 §2 |

**前提（凌翼限定，本分析不越界）**：**排除受信任宿主管理员**、**排除内核被攻破**。因此"管理员能撤销"不作为反例；但"worker 自己能绕过"**必须**排除。

---

## 2 · `ForbiddenAccess` 的访问类别（必须先定义，否则"未观察到"无意义）

| 类别 | 含义 |
|---|---|
| **D-直接读** | worker 通过任何句柄读取 $P$ 内容 |
| **D-直接写** | worker 修改 $P$ |
| **I-间接** | worker 使**其他主体**代其访问 $P$（IPC 请求、服务调用、命令行指令） |
| **I-代理** | worker 通过已存在的对端（父进程、服务）的既有权限读 $P$ |

**关键**：$\mathrm{ForbiddenAccess}$ 涵盖**直接与间接能力路径**。只防直接路径的机制，在这一形式化下**不能算通过 G-2**。

## 3 · 候选逐一分析（凌翼限定的四项）

### 3.1 候选 1 · 受限令牌 + 独立安全主体 + DACL/MIC 组合

| 项目 | 内容 |
|---|---|
| **谁创建并控制边界** | 创建方（本账户或受信任服务）在 `CreateProcessAsUser` 时施加受限令牌；DACL 由目标的 ACL 施加 |
| **谁可以修改/撤销/绕过** | ① 对象属主可改 DACL；② 若 worker 令牌含 `WRITE_DAC` 则自改；③ **管理员**（已排除） |
| **worker 能否获得这些权限** | 取决于令牌：受限令牌去掉 SID 后，worker **没有**改 DACL 的权限——**这一点是可论证的** |
| **创建前能力与已有句柄** | **难点**：受限令牌**不撤销已存在的句柄**。父进程若在创建前持有 $P$ 的句柄并继承（或通过 `DuplicateHandle` 给 worker），令牌管不到 |
| **新句柄** | worker 新开 $P$：受 DACL/MIC 约束：**在访问检查层面是可论证的** |
| **子进程** | 子进程默认继承受限令牌 ⇒ **同受限**（这是强项） |
| **IPC / 代理** | **不覆盖**。worker 可请求一个**未受限**的服务替它读 $P$。若该服务有权限，$\mathrm{ForbiddenAccess}$ 通过 I-代理成立 |
| **对象替换** | **不覆盖**。DACL 绑定在对象上；重解析点/符号链接可指向另一对象 |
| **边界生效/失效事件** | 生效：令牌在进程创建时确定（`t_start` = 进程创建返回）；失效：进程终止 |
| **依赖的可信主体/OS 行为** | ① 内核访问检查不可绕过（内核假设，凌翼已排除攻破）；② ACL 不被第三方修改 |
| **不可由本设计消除的假设** | **$P$ 必须无可用的代理通道**，或代理方本身同样受限 |

**G-2 判定**：**部分**。对 D-直接读写、子进程、新句柄这三条，时间区间不变性**可论证**——因为令牌在创建时固定，worker 无权限改它。
**但 I-代理与 T-5 对象替换不覆盖 ⇒ 整条不满足 $\forall t$ 的完整形式。**

---

### 3.2 候选 2 · AppContainer / LPAC

| 项目 | 内容 |
|---|---|
| **谁创建** | 创建方通过 `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` 指定 AppContainer SID + 能力集合 |
| **谁可修改/撤销** | 包 SID 与能力集合**在进程创建时确定**；worker 不能自行增删能力（这是 AppContainer 的核心性质） |
| **worker 能否获得** | 不能：能力只能在创建时授予 |
| **创建前能力/已有句柄** | **同样不撤销既有句柄**。继承的句柄仍有效 |
| **新句柄** | 受 AppContainer 的**默认拒绝**（无 `ALL APPLICATION PACKAGES` / 特定 capability 的 ACE ⇒ 拒绝）。**这是比 DACL 更强的性质**：默认拒绝而非默认允许 |
| **子进程** | 子进程留在同一 AppContainer ⇒ 同受限 |
| **IPC / 代理** | **不覆盖**。AppContainer **可以**与外部进程通信（正是它的设计目的之一）；代理路径仍旧存在 |
| **对象替换** | 部分覆盖：AppContainer 的文件访问走 broker，但仍受重解析点影响 |
| **生效/失效** | 生效：进程创建完成；失效：进程终止 |
| **依赖** | 内核对象管理器强制；broker 进程（`RuntimeBroker`）可信 |
| **不可消除的假设** | 代理/通信通道受控 |

**G-2 判定**：**比候选 1 更强**，因为"默认拒绝 + 能力创建时固定"两者都指向时间区间不变性。
**但 I-代理仍未覆盖。**

---

### 3.3 候选 3 · Job Object

| 项目 | 内容 |
|---|---|
| **能回答什么** | **生命周期**：`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 保证进程组随句柄关闭而终止；可限制子进程逃逸 |
| **不能回答什么** | **完全不涉及访问控制**。Job Object 不改变 worker 对 $P$ 的访问能力 |
| **G-2 判定** | **不是 G-2 候选**。它是 `t_end` 的可信化机制（生命周期辅助），不产生边界 |

**凌翼原文已定性**："Job Object 作为生命周期辅助机制的限制"——**我确认：它只能辅助定义 $t_{\text{end}}$，不能承担 $[t_{\text{start}}, t_{\text{end}}]$ 内的不变性。**

---

### 3.4 候选 4 · Hyper-V 隔离（仅在上述不足时简要分析）

| 项目 | 内容 |
|---|---|
| **是否改变信任边界** | **是**。它把"同一内核内的访问控制"换成"**不同内核**"。这是**质变**：$\mathrm{ForbiddenAccess}$ 的间接路径需要跨 VM 通道，攻击面大幅收窄 |
| **代价** | ① 需要 Hyper-V（非所有目标环境可用）；② worker 与 $P$ 必须分处不同 VM 或 host/guest；③ **数据通路需重新设计**（worker 如何读它**该**读的数据）；④ 观测与证据采集变复杂；⑤ 性能与运维成本 |
| **G-2 判定** | **这是唯一可能**满足 $\forall t$ 且覆盖 I-代理的路径——**因为跨 VM 通道是显式的、可枚举的**。但仍需证明该通道本身受控 |

## 4 · 三个不可回避的卡点（本轮必须写出，不能留到实现阶段）

### 卡点 A · 创建前的既有能力

**任何"进程创建时施加边界"的机制，都不撤销创建前已存在的句柄。**

若父进程在 `CreateProcess` 之前已持有 $P$ 的句柄，并让其继承，则：
- 候选 1/2 的令牌/AppContainer **不会**使该句柄失效
- 唯一的防线是**不继承**（M-1 的 `(a)` 或 `(b)` 配置）

**这一点是可设计的**：`inherit=FALSE`（配置 a）即可，且已实测有效。
**但它要求 $t_{\text{start}}$ 定义在"进程创建完成"而非"首次使用"**，且要求**创建方本身守法**。

### 卡点 B · 施加者可撤销性 ← **我原草案认为的致命卡点，需要修正**

我原草案说："若边界由本账户施加，则本账户可撤销它 ⇒ 策略假设"。

**凌翼的威胁模型排除了管理员。** 在这个前提下，**"创建方守法"是一个合法假设**，与"内核不被攻破"同级。

**所以我撤回原草案中"这必然降格为策略假设"的断言**——在排除管理员的威胁模型内，它不是致命卡点。

**但剩余风险必须写明**：若 worker 与创建方**同一安全主体**（本账户），则 worker 取得 `WRITE_DAC` 即可改边界。**受限令牌/AppContainer 的价值正在于此：它们使 worker 不再是创建方的等价主体。**

### 卡点 C · 整个执行区间

worker 持久运行。边界必须在 $[t_{\text{start}}, t_{\text{end}}]$ **始终**成立。

**这对候选 1/2 是可论证的**：边界在创建时固定，worker 无权修改，且子进程继承同级限制。
**前提是 I-代理被排除**——而这恰恰是候选 1/2 都做不到的。

## 5 · 本轮结论

```text
G-2 结论 = G2_REQUIRES_THREAT_MODEL_REVISION
```

**理由（三层，逐条对应凌翼的验收规则）**：

**第一层**：候选 1（受限令牌 + DACL/MIC）与候选 2（AppContainer/LPAC）在 **D-直接读写、子进程、新句柄** 三条上，**时间区间不变性是可论证的**——边界创建时固定，worker 无权修改。

**第二层**：但两者**都不覆盖 I-间接与 I-代理**。在凌翼给定的形式化中，$\mathrm{ForbiddenAccess}$ **明确要求涵盖间接能力路径**，因此候选 1/2 **不满足** $\forall t$ 的完整形式。

**第三层**：唯一可能覆盖 I-代理的是 Hyper-V 隔离（跨 VM 通道显式可枚举），但那已超出当前威胁模型与代价框架。

**因此**：不是"没找到机制"，而是**在现有威胁模型下，机制存在但覆盖不足**。

**这正对应凌翼给定的第三个结论 `G2_REQUIRES_THREAT_MODEL_REVISION`。**

## 6 · 我需要凌翼裁定的一个威胁模型问题

**问题**：$\mathrm{ForbiddenAccess}$ 是否**必须**涵盖 I-间接/代理？

**两种裁法导致完全不同的结论**：

| 若裁定 | 结论 |
|---|---|
| **I-代理必须覆盖** | `G2_REQUIRES_THREAT_MODEL_REVISION`（当前）——需把"无可用代理通道"作为**独立前提**写入威胁模型，或转向 Hyper-V |
| **I-代理可单列** | 候选 2（AppContainer）**可能达到 `G2_CANDIDATE_IDENTIFIED`**——明确记录"仅覆盖直接路径"，进入下一轮设计评审 |

**我不自行选择。** 因为这一条决定了整个路线是否值得继续。
