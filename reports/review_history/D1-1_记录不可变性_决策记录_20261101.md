# 一 · 方案 A 的结构

```text
两类记录，职责分离：

  EventRecord        创建后【永不修改】
     内容固定，digest 覆盖固定字段

  StateTransition    追加写，永不修改
     只记录「某 event_id 的 commit_state 从 X 变为 Y」
```

```text
⇒ 关键设计点：
   commit_state 不再存在于 EventRecord 中。
   当前状态 = 该 event_id 所有 StateTransition 折叠所得。
```

```text
⚠ 这是对协议 §3.1 的【结构性更正】。
  原 §3.1 把 commit_state 放在 EventRecord 内，
  正是 R-2 指出的矛盾根源。
⇒ 本文提出把它移出，但【不修改】协议正文，等裁定。
```

# 二 · 五问逐条回答

## 问 1 · 事件内容何时成为不可变记录？

```text
答：在【首次通过校验并持久化】的那一刻。

具体时点：
  (a) 提交方发送 SUBMIT(event_id, attempt_id, ...)
  (b) 记录者校验提交身份与绑定对象
  (c) 记录者分配 seq
  (d) 记录者写入 EventRecord【并 fsync 返回】
  (e) 【此点之后】该记录的内容不可再变

⇒ 不可变性的起算点是 (d) 的 fsync 返回，
   不是 (a) 发送、(b) 校验、或 (c) 分配 seq。
```

```text
为什么不能更早：
  (b)(c) 阶段记录内容仍可能因校验失败而废弃。
⇒ 若在 (a) 就算不可变，则一次失败提交也会留下永久记录，
   而它从未被确认过。
```

```text
为什么不能更晚：
  若等到 ACK 之后才算不可变，
  则 (d) 与 ACK 之间可以被改写 ⇒ 不可变性失效。
```

**可否定点：**

```text
若某 EventRecord 在其 fsync 返回后被修改内容
⇒ RECORD_IMMUTABILITY_VIOLATION → INVALID
```

## 问 2 · 状态转换如何与原始事件绑定？

```text
答：通过 event_id 单向引用，且转换记录本身也不可变。

StateTransition {
    event_id              指向的原始事件（不可变记录的键）
    transition_seq        该 event_id 下转换的单调序号
    from_state            先前的 commit_state
    to_state              变更后的 commit_state
    reason                ACK_RECEIVED | ACK_TIMEOUT | CRASH_RECOVERY
                        | RETRY_OBSERVED | MANUAL_RECLASSIFY(不允许)
}
```

```text
绑定规则：
  (i)   transition_seq 在同一 event_id 下严格递增
  (ii)  from_state 必须等于【上一条转换的 to_state】
        首条转换的 from_state 必须为初始值
  (iii) 不得出现 from/to 相同且 reason 相同的重复转换
```

```text
⇒ 当前状态 = 按 transition_seq 折叠出的最后一个 to_state
⇒ 若折叠过程发现断链（from ≠ 上一条 to）：
     TRANSITION_CHAIN_BROKEN → INVALID
```

**为什么不允许 MANUAL_RECLASSIFY：**

```text
⇒ 它等于「事后改写状态判定」。
⇒ 若允许，则不可变性只对内容有效，对判定无效——
   而判定才是证据的关键部分。
⇒ 若确需重新分类，应写【新事件】引用旧 event_id，
   而不是修改旧事件的状态链。
```

## 问 3 · 同一 event_id 重试时如何保证唯一权威绑定？

```text
答：权威绑定在【首次达到 CONFIRMED】时建立，此后不变。

映射：
  event_id → authority_record_seq   （一次建立，永不改写）
```

**三种重试情形（与协议 §5.2 一致，本节给出可变性视角）：**

| 情形 | 判定 | 是否写 StateTransition |
|---|---|---|
| 甲 · 重复确认（内容一致） | 不是冲突，保留原映射 | 是（记 RETRY_OBSERVED，不改状态） |
| 乙 · 未确认后重试，映射未建立 | 新 attempt 可建立映射 | 是 |
| 乙' · 未确认后重试，映射**已**建立 | 保持原映射 | 是（记 RETRY_OBSERVED） |
| 丙 · 内容不同的双确认 | 真冲突 | **不写**，直接 INVALID |

```text
⇒ 关键：情形丙【不】通过写转换记录来消解，
   因为那等于用追加记录掩盖冲突。
⇒ 冲突必须显式暴露为 INVALID，不得被状态链吸收。
```

## 问 4 · ACK 丢失、记录者崩溃及恢复不确定时如何处理？

**三种情形，分开处置：**

```text
情形 A · ACK 丢失（记录者已 fsync，提交方未收到）
  ⇒ 记录存在且不可变；commit_state 停在 UNKNOWN_ACK
  ⇒ 提交方重试 ⇒ 命中幂等 ⇒ 重发 ACK ⇒ 写 transition UNKNOWN_ACK→CONFIRMED
  ⇒ 判定：可继续，但该事件在 UNKNOWN_ACK 期间【不得】用于因果约束

情形 B · 记录者崩溃（落盘中或落盘后确认前）
  ⇒ 恢复时扫描尾部
  ⇒ 不完整记录 ⇒ 截断 + 写 RECOVERY_TRUNCATED
  ⇒ 完整但未确认 ⇒ 保持 UNKNOWN_ACK
  ⇒ 判定：需要该事件的阶段 ⇒ INVALID（O-2）

情形 C · 恢复不确定（无法确定映射是否已建立）
  ⇒ 暂停判定，标记 AUTHORITY_MAPPING_UNDETERMINED
  ⇒ 【不得】通过「选最后成功的」消除歧义
  ⇒ 判定：NOT ESTABLISHED（不是 INVALID）
```

```text
⇒ 情形 C 之所以是 NOT ESTABLISHED 而非 INVALID：
   我们并不知道是否真的存在冲突，
   只是【无法确定】。
⇒ 把「无法确定」写成 INVALID，等于把未知当成了否定。
```

## 问 5 · 何种情形必须 INVALID，何种情形只是 NOT_ESTABLISHED？

```text
分界线：是否【已经观察到一个实际的违反】。
```

**必须 INVALID（已观察到违反）：**

| 情形 | 依据 |
|---|---|
| EventRecord 在 fsync 后被修改 | 不可变性被违反 |
| StateTransition 链断裂（from ≠ 上条 to） | 状态链不完整 |
| 同一 event_id 两个内容不同且都 CONFIRMED | 真冲突（情形丙） |
| transition_seq 重复 | 顺序不可判定 |
| 记录指向不存在的 event_id | 引用失效 |

**只是 NOT ESTABLISHED（无法观察）：**

| 情形 | 依据 |
|---|---|
| 映射是否已建立不确定 | 情形 C |
| 无记录者 ⇒ 无法确认日志持久化 | 材料不存在 |
| 无 fsync ⇒ 无法确认状态持久化 | 材料不存在 |
| 无时序号 ⇒ 无法判定顺序 | 材料不存在 |
| 崩溃后是否有未截断的尾部 | 取决于恢复是否可执行 |

```text
⇒ 判别口诀：
   看见了违反 ⇒ INVALID
   看不见证据 ⇒ NOT ESTABLISHED
⇒ 不得把第二类写成第一类（违反 D 项纪律）
```

# 三 · 反例对照

## 反例 1 · 用追加记录消解冲突

```text
构造：同一 event_id 出现两条内容不同且都 CONFIRMED 的记录。
      实现写一条 transition「以较新的为准」。

错误实现：认为追加式记录天然消解冲突。

为何错：
  追加记录只能【描述】状态变化，不能【裁定】哪个内容是真的。
⇒ 内容冲突是 EventRecord 层的问题，
   不能用 StateTransition 层的操作解决。

期望：INVALID（情形丙），且【不得】写吸收型 transition
```

## 反例 2 · 在 fsync 前就当作不可变

```text
构造：记录已写入缓冲，但 fsync 失败或未返回。

错误实现：认为「已写入」即「已不可变」。

为何错：
  若 fsync 失败，记录是否完整落盘未知。
⇒ 此时既不能说它已确立，也不能说它不存在。

期望：NOT ESTABLISHED（记录状态未知），不是 INVALID
```

## 反例 3 · 把 commit_state 留在 EventRecord 内

```text
构造：仍按协议 §3.1 原结构，commit_state 属语义字段。

后果（R-2 已指出）：
  ⇒ 每次状态变化都要改摘要 ⇒ 记录被修改
  ⇒ 或 commit_state 不被摘要覆盖 ⇒ 可被任意改写
⇒ 两者不可兼得。

期望：必须移出（本文方案 A），否则不可变性与状态可变性无法共存
```

# 六 · 一句

```text
不可变记录最容易写错的地方，
不是「记下来之后不许改」，
而是「什么时候算记下来了」。

早一步，失败提交也会留下永久痕迹。
晚一步，fsync 与 ACK 之间可以被改写。
```
