## 3. 待修复项

以下行号均针对固定提交 153a86f。P1 表示下一次完整集成验收前应闭合，不表示已在现场造成业务故障。

### ZW-01 / P1：隔离响应未绑定真实 worker 和本次请求

位置：`afterglow_harness/q3_reset_adapter.py:265–281`；`q3_business_worker_entry.py:81–88`。

请求只有 op/path；响应虽含 pid，控制器只取 `result`。没有核对响应 PID、进程创建时间、事务/请求 nonce、目标对象，也没有记录这些字段的关联证据。删除旧响应文件不能排除另一轮的延迟响应在之后写入。

独立反例使用真实跨账户但不响应请求的受控入口 PID 41276。审查脚本在请求出现后写入 `DENIED`，同时提供错误 PID 1041276、`WRONG-RUN` 和 `WRONG-TARGET`；`prove_persistent_isolation()` 仍返回 True。见 `response_binding_missing`。**这是受控邮箱注入，不是真实读取被拒绝，也不是证明任意外部攻击者能够写该目录。** 它准确证明当前裁决不校验响应归属。

建议：使用每事务独立的通信空间；绑定一次性请求 ID、预期进程身份、目标对象与响应，并检查通道的写入权限/发送者身份。仅增加 JSON 字段而不核验发送端不够。错 PID、旧 nonce、错对象、延迟响应、重复响应都应失败，不能计入本轮隔离证明。

### ZW-02 / P1：holding 被直接声明，未核验握手及入口身份

位置：`q3_reset_adapter.py:126–156`、`:215–231`；`q3_business_worker_entry.py:60–78`。

启动后直接赋 `started_and_holding=True`；supervisor 没有消费 READY 文件。`witness_ok()` 核对 SID 与进程存活/创建时间，却不核对 READY。入口 hash 是启动前对路径内容的计算，当前没有与获准入口身份或实际执行映像建立完整核对。

受控负例将入口换成不实现 holding、启动即写入合成业务标记的脚本。没有 READY、没有 release，标记已经产生；supervisor 仍给出 holding=True、witness_ok=True。见 `holding_not_verified`。**这是替换测试入口的反例，不声称原版 worker 已抢跑，也不声称能绕过可信控制器任意替换入口。** 但目前的通用 supervisor 不能把该布尔值称为已核验的 holding 见证。

建议：将允许的入口身份纳入绑定，保护启动期间入口字节；启动后等待与本进程/本事务绑定的 READY_HOLDING，超时、错身份、未 READY 都回收。明确 READY 能证明的是受信任入口遵守协议，不能仅靠一个自报字段证明任意程序没有处理输入。测试应包含未 READY、错 READY、延迟 READY、抢跑入口及重复 release。

### ZW-03 / P1：回收结果被忽略，失败后重试被锁死

位置：`q3_reset_adapter.py:469–479`；相关底层路径 `:317–336`。

`_cleanup()` 在终止前先置 `_cleaned=True`，随后忽略 `terminate()` 的返回值。底层明确可能返回 `STILL_ALIVE`；这种情况既未进入审计记录，也不能通过再次 `_cleanup()` 重试。底层还会在确认退出前关闭并丢弃所持句柄，且没有检查 TerminateProcess/等待返回状态，应一起修正。

独立负例启动真实原版 worker PID 40736，但受控让 supervisor 的第一次 terminate 返回 STILL_ALIVE。适配器返回 INVALID/FAILED 后再次 cleanup，终止总调用次数仍是 1，worker 仍活着，audit 为空。见 `cleanup_return_ignored`。**Q3 在此例被替换为失败结果，这是资源回收逻辑测试，不是实际 Q3 失败链证据；也不表示本机正常 TerminateProcess 失败。** 审查脚本随后显式调用原终止实现，完成回收。

建议：把“发起清理”和“已确认清理完成”分开；消费退出/等待/关闭结果，保留可重试的控制权和原始错误，在未证实回收时显式记录 cleanup 未完成。增加真实新 worker 已启动后的隔离失败、终止失败/超时、重复清理与句柄检查。

### ZW-04 / P1：对象绑定只是登记，不是最终通过门禁

位置：`q3_reset_adapter.py:440–451`、`:553–590`、`:593–620`。

protected 与 substrate 的 OS 文件身份只在构造时比较。`_stage_bind()` 在结尾重新读取身份，却只写进字典；不因身份不同或不可读而拒绝，也未实现设计要求的完整业务 nonce、run-id 映射及证据 hash 核验。

独立负例先以两个硬链接通过构造检查，再替换 substrate 别名所指文件。记录中的 OS 身份已不同，最终仍是 `integration_valid=True / DONE`。见 `object_replacement_not_rejected`。**此例注入了 Q3 成功结果，只用于隔离验证后续绑定门禁；不能称为绕过真实 Q3 的端到端成功。** 业务 worker 和读取拒绝部分是真实执行的。

同例提供的相等快照与磁盘 literal 不同，RC11 比较仍通过。接口注释明确把输入视为已可信，故这不是冻结 verify 的缺陷，也不是“不应接收任何调用者参数”的主张；待闭合的是可信快照究竟在哪里、何时捕获，如何绑定当前对象和事务。当前绑定中将直接传入的 old_worker_pid 标记为 supervisor 权威，也不能替代实际来源证据。

建议：将 V_binding 实现为可拒绝的门禁；在受保护的捕获/使用窗口核验对象身份，处理路径替换竞争；由可信控制器捕获或验证快照来源、实际旧进程身份，并与 Q3 结果和业务证据关联。不能只在最后增加一次比较就声称整个时间窗口已受保护。补测替换硬链接、对象消失、旧快照/旧事务、缺失证据字段。

### ZW-05 / P1：原版 B/C 层未覆盖本次要求的真实失败传播和事务时序

位置：`test_q3_reset_adapter.py:239–264`、`:296–326`。

- B3 的各门负例均通过 `_FakeQ3Result(valid=False)` 注入结果，没有改变实际 Q3 输入后执行真实链。它们只能归入逻辑层，不能满足设计 v3 §4 的受控 Windows 负向要求。
- B10 使用无效测试 SID，在安装 deny ACE 时就失败，根本未到“真实新 worker 启动后隔离证明失败”。Coder 原始日志和本次原始复跑均可见 `rc=1332`。该测试会以错误失败原因得到 PASS。
- C1 只调用 supervisor，没有经过 `run_reset_transaction()`；并且先 release，再调用会安装 deny ACE 的 prove。**这是测试路径的问题；生产适配器自身确有 boundary-before-worker 的调用顺序，不能混为一谈。** 现有 C1 不能验证该生产时序。
- C2 实际测无密码拒绝，不是实际同账户进程身份拒绝。A3 只覆盖失败后重复调用，未覆盖成功后重复调用及旧产物消费。

建议：保留这些有用的逻辑用例并准确改名；B 层在真实链调用前修改输入，记录确切失败阶段；C 层走完整适配器，按事件记录 Q3 的 DACL 恢复、独立持久边界建立、真实进程 READY、读取拒绝和 release。读取检查应观察既有边界，避免检查函数重新装 deny ACE 掩盖较早的边界遗漏。加入启动后失败、成功后重入与跨事务陈旧响应；失败测试同时断言目标阶段已经到达，防止“失败在别处也算通过”。调用冻结函数进行新增集成测试，与重开冻结资格裁决应明确区分。
