## 0. 一句话

**完整跨进程"眼睛隔离"证出来了**：worker 是**真正不同的安全主体**，被 OS **真正拒绝**；observer **保留读**——**在同一对象上同时成立**。

```text
worker (afterglow_worker) 读被 deny 的对象 -> SECRET=DENIED   （OS 拒绝）
observer (admin)          读同一对象        -> GRANTED        （保留读）
worker                    读未 deny 的兄弟 -> SIB=READ        （可归因的拒绝）
```

这直接落实 SPEC §16.1.1：**"隔离的是命名空间，不是眼睛"**；也落实凌翼 Q3-A：**observer 保留读，preserve 才能独立验**。

## 1. 阻塞是怎么打通的（诚实复盘）

我上一版报告说 `CreateProcessAsUserW` 受限 token 子进程退出 `0xC0000142`（`STATUS_DLL_INIT_FAILED`），判定为"本机不可达"。诊断后发现两件事：

1. **根因**：restricted SID 的 token **丢掉了对交互式窗口站（`winsta0\default`）的访问**，子进程 GUI 子系统初始化失败 ⇒ `DLL_INIT_FAILED`。启用 `SeAssignPrimaryToken/SeIncreaseQuota` **无效**。
2. **正面路径**：改用**真正不同的本地账户**（船长建的 `afterglow_worker`）+ `CreateProcessWithLogonW(WITH_PROFILE)` ⇒ 子进程正常启动。

**还有一个坑（写进契约）**：
```
worker 用 admin 私有的 venv python (C:\Users\Administrator\...\uv\...) -> rc=103（读不到）
worker 用全局可读的 D:\Python39\python.exe (Users:(RX))                -> 正常
```
即 **worker 的解释器必须在全局可读位置**，不能用 admin 私有 profile 下的 python。

## 2. 新增模块：`afterglow_harness/win32_worker_process.py`

- `run_cross_process_worker(account, password, work_dir, python_exe, child_script, verdict_path)`
  —— 经 `CreateProcessWithLogonW` 以 worker 账户运行，等待退出，读回 verdict。
  **FAIL CLOSED**：spawn 失败 / 超时 / 无 verdict ⇒ 抛 `WorkerSpawnError`（**不把"没输出"当成拒绝**）。
- `deny_read(account, path)` / `grant(account, path, perm)` —— ACL 助手（仅限可丢弃目录）。
- 常量：`WORKER_ACCOUNT_DEFAULT = "afterglow_worker"`、`PUBLIC_PYTHON_DEFAULT = "D:\Python39\python.exe"`。

### 自测（本机实测，4/4 PASS）
```text
[PASS] CROSS-PROCESS: worker spawned as a DIFFERENT account
[PASS] CROSS-PROCESS: worker verdict = SECRET=DENIED (OS denied read)
[PASS] CROSS-PROCESS: observer STILL reads the same object (GRANTED)
[PASS] CONTROL: worker CAN read an allowed sibling (attributable denial)
```

`win32_isolation.py` 的 docstring 已更新：指向本模块作为跨进程沙箱的正面实现；该模块保留**同进程认证 witness** 机制。两模块合计：`win32_isolation.py` 19/19、`win32_worker_process.py` 4/4。
