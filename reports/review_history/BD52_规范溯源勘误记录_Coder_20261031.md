# 二 · 我的事实错误：跨进程时钟（凌翼 C 项指出）

## 2.1 我原来写的（错误）

`给凌翼_BD52两项裁定请求_Coder_20261031.md` 第四节表格：

```text
| 单调时钟 perf_counter_ns | 是 | 否（进程基准不同） | 跨进程不可比 |
```

并附一句判断：

```text
单调时钟被「跨进程不可比」直接否掉 —— 这是最自然的选择，也是最先错的选择。
```

## 2.2 实测结果（凌翼正确，我错误）

环境：`Python 3.11.15` / `win32` / `perf_counter` 实现 = `QueryPerformanceCounter()`

```text
parent before : 3335194932477500
child         : 3335194960072800
parent after  : 3335194965156700
⇒ child 读数【落在】parent 观测区间内
```

三子进程并发复测：

```text
parent window: [3335198510456300, 3335198552131200]  (41.67 ms)
  child0 = 3335198538371400  inside=True
  child1 = 3335198542480400  inside=True
  child2 = 3335198548142500  inside=True
ALL_CHILDREN_INSIDE = True
```

## 2.3 修正后的表述

```text
错误：perf_counter_ns 跨进程不可比
正确：在 Windows CPython 上，perf_counter 由 QueryPerformanceCounter()
      提供，是系统级共享计数器，跨进程【同源、可比】。
```

## 2.4 这条错误是怎么来的

```text
我没有实测，直接套用了「monotonic 时钟通常进程私有」的一般印象。
那个印象在别的平台/别的 API 上可能成立，
但在【本环境、本 API】上不成立。
⇒ 我是用【一般印象】替代了【本机事实】。
⇒ 这正是我自己写过的那条：没有建立 ≠ 已经证明不存在。
   只不过这次方向反了：我把「可能不同源」写成了「确定不可比」。
```

## 2.5 但凌翼的告诫我照录，不简化

```text
"跨进程共享时钟并不等于时间戳天然可靠。
 仍须验证采集来源、时钟语义、事件身份及记录延迟。"
```

```text
⇒ 同源可比 ≠ 可用于判定先后。
⇒ 因为可比的时钟读数，仍可能：
   · 采集点与事件实际发生点不一致（记录延迟）；
   · 被同一进程在事件前后读取（拿不到他人时刻）；
   · 精度不足以区分紧邻事件。
⇒ 所以 2.3 的修正【不构成】任何时序能力的恢复。
   它只是把一个错误说法改对。
```

# 五 · D 项：目标先后关系（凌翼给出的形式，我照录并标注缺口）

## 5.1 我原来写的（不足）

```text
(甲) T_open  <  T_write  <  T_close
(乙) ¬( T_open < T_snap < T_close )
```

凌翼指出的缺陷：

```text
(乙) 不能证明快照发生在窗口关闭之后。
     它同样允许快照发生在窗口打开【之前】。
⇒ ¬(在区间内) 包含两种相反情形：早于开、晚于关。
⇒ 我把「不在窗口内」当成了「在窗口之后」。这是同一个对称性错误的【第二次】出现。
   （第一次是 BD-52 的 == 分不清早晚。）
```

> 这条我必须记下来：**我用 BD-52 的对称性错误批评 BD-52，
> 然后在自己提的方案里犯了同一个错误。**
> 不是巧合——是因为我用「否定区间内」去表达「之后」，
> 而否定从来不能定序。

## 5.2 应表达的目标关系（凌翼）

```text
WINDOW_OPEN      precedes WRITE_COMMIT
WRITE_COMMIT     precedes WINDOW_CLOSE
WINDOW_CLOSE     precedes SNAPSHOT_BEGIN
SNAPSHOT_END     precedes HANDOFF
```

```text
⇒ precedes 必须有可信事件顺序证据，不是用摘要比较推导。
```


# 六 · 凌翼指定必须保留的七条反例（照录，逐条标注当前状态）

| # | 反例 | 当前能否被看见 |
|---|---|---|
| 1 | 写入窗口尚未关闭，writer 进程崩溃 | 不能。`_write_open` 是进程内布尔量，崩溃即丢失；`__exit__` 不会执行 |

| 4 | 文件在观察期间被替换 | 不能。两次 `read_bytes()` 无身份校验 |

| 6 | 相同状态摘要对应不同执行 | 不能。`run_id` 只在 Q3 链路，未进 C1 evaluator |
| 7 | 事件采集顺序与实际写入提交顺序不一致 | 不能。当前**没有**事件采集者 |

```text
⇒ 七条反例，七条都看不见。
⇒ 这不是七个独立缺陷，是同一个：没有独立的时序材料。
```

## 6.1 缺证时的处置（凌翼要求的边界）

```text
缺少必需关闭见证或来源证据时：
  · 不得补造时间标记
  · 不得生成正向科学结论
  · 若属实际执行的必需证据缺失
    ⇒ 按 invalidity 条款处理
    ⇒ 【不能】写成科学 FAIL
```

> 这条区别很关键，我记下：**证据缺失是 INVALID，不是 FAIL。**
> FAIL 是「测了，不成立」；INVALID 是「没测成」。
> 把缺证写成 FAIL，等于把一个未知当成了否定结论。

# 七 · C 项：设计方向（照录，不当已批准架构）

## 7.1 凌翼建议优先探索的方向

```text
独立事件采集者 + 受信排序记录 + 原始状态摘要绑定
```

约束（照录）：

```text
· 事件采集者必须独立于被测 writer；
· 事件序号由可信记录路径产生；
· 时钟值可作为辅助时间证据；
· 对象身份、execution 身份及事件类型必须同时绑定；
· 第⑥阶段负责封存，不得假设外部见证只能在第⑥阶段出现；
· 不得将记录顺序无条件等同于实际发生顺序。
```

## 7.2 我对这两条的自我提醒

```text
· 「时钟值可作为【辅助】时间证据」
  ⇒ 直接在纠正我的根本误判：我以为时钟不可用（错），
    又暗含「有了同源时钟就能定时序」（也错）。
    正确定位：辅助，不是判据。

· 「不得将记录顺序无条件等同于实际发生顺序」
  ⇒ 记录顺序是【记录者看到的顺序】，不是【系统发生的顺序】。
    这与 BD-52 的原始错误同构：把摘要相等当成时刻相同，
    就是把【表征】当成【事实】。
```
