# 3 · 裁定请求 B · BF-9 与 §7.2 的冲突

## 3.1 字节事实

```text
harness_constants.py L192-197  EPISODE_PAYLOADS
     A1 = b"cls=L;sample=01;"    A2 = b"cls=L;sample=02;"
     B1 = b"cls=R;sample=01;"    B2 = b"cls=R;sample=02;"

harness_constants.py L85-93    canonical_state_digest(literal, q_raw)
     = sha256(canonical_state_bytes(literal, q_raw)) = sha256(literal + q_raw)
     ⇒ 输入域 24 字节，【不含 episode】

prereg §7.2 L326-350           明禁下列进入 substrate state digest：
     timestamp / wall-clock / audit log / provenance record /
     sequence number / write_count / episode_id / file mtime /
     before_state_digest / after_state_digest
prereg §7.2 L343-350           闭合规则：digest input = STATE_FIELDS only
```

## 3.2 这个冲突是规范性的，不是实现缺陷

```text
§7.2 禁止 episode_id 进入 digest
⇒ 这是正确的（防止身份污染状态度量、防止自引用）
⇒ 而结果是：reference 里"这一次是哪一次"的唯一字节载体，
   是 payload 里那两个字符 sample=01 / sample=02

⇒ 于是 episode 与 payload 是同一个字节串，
   二者之间的关联不是被证明的，是被假定的。

⇒ 而这不能用"给 digest 加 episode 字段"来修
   —— 那会直接违反 §7.2。
```

**⇒ 也就是说：这个缺口在冻结规范内部，不是代码写错了。**

## 3.3 请求裁定

```text
B-1  是否确认：episode 与 payload 同一载体是【§7.2 的直接后果】，
     而非实现缺陷？（若是，则不是修代码问题）
B-2  META↔STATE 的可验证关联应当建在哪一层？
     · META 侧独立记录（episode_id / execution_id / writer_identity / before-after digest）
```

> **同一个系统的下一个 episode，读取上一个 episode 写入的内容。**

**⇒ 而这正是 §37 `UNREGISTERED_EPISODE_REINJECTION`（L2253）的对象。**

## 4.2 于是同一条通路有两面

```text
要证明"这次写入是真的、是有后果的"
  ⇒ 需要"后续有人读了它"
而"后续有人读了它"
  ⇒ 恰恰就是再注入通路

⇒ 同一条通路，同时是：
   · C1 证据完整性【需要】的东西
   · §37 【可能判停】的东西

⇒ 区别只有一个：它有没有在 outcome 之前被登记为合法通路。
```
