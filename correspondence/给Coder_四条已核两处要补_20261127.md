## 二 · `denominator_attrition` 只报「少了多少」，追不到「谁搬的」

### 事实

```text
L427  denominator_attrition = len(attrition_ids)
L481  "denominator_attrition": denominator_attrition
      "denominator_attrition_ids": sorted(attrition_ids)
```

```text
⇒ 你知道分母少了 3 条，知道是哪 3 条。
⇒ 但不知道是被【哪一次 correct()】搬走的，依据是哪一条记录。
```

### 而洗白路径正是 `correct()`

**你自己在 commit message 里写的：**

> · `revise()` 拒绝改 `participation_basis` ⇒ 洗白必须走 `correct()`，
>   后者要求 `correcting_record_id`，会留下 `correction_of` 边
> · `correct()` 继承【纠正依据那条记录】的来源字段
>   ⇒ 要用 `first_person_report` 的记录纠正才能恢复 `first_person`

```text
⇒ 所以现在的洗白形态是：
     correct(一条 first_person 记录, basis = 一条 record_only 的记录)
     ⇒ 前者被移出分母，并且【留了 correction_of 边】
```

**⇒ 通道没有堵住，但它留下了痕迹。这正是当初说的「判定管不了它，只有度量管得住」。**

### 但痕迹现在少一样

```text
attrition_ids 回答：少了哪几条
缺的那一样回答：谁搬的
```

**要求：**

```text
A2  denominator_attrition_cause =
      { <被移出分母的记录 id>: <那次 correct 的 correcting_record_id> }
```

```text
理由：attrition 回答「少了多少」，cause 回答「谁搬的」。
     只报前者，报告能看出问题但追不到动作。
     而这个项目里，【追得到动作】比【知道少了多少】重要 ——
     那正是溯源的全部意义。
```

```text
⇒ 它与 H3「来源入口唯一性」是配套的：
   H3 保证搬动只能从 correct() 走；
   cause 保证从 correct() 走的每一步都留下是谁。
```
