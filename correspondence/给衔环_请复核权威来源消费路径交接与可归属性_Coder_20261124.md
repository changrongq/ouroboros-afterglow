## 一 · 权威来源：我把「判定」和「可信」刻意分开

### 1.1 我做到的

```text
来源五值闭集：user_utterance / system_generated / third_party /
              model_echo / unknown

⇒ 一条记录的来源【类别】可以被判定。
⇒ 但「判定为某类」不等于「该类可信」。
```

```text
返回值里三条恒定边界（所有分支都一样，不随结果变）：
  engineering_only     = True
  is_scientific_result = False
  trusted_chain_anchor = "not_established"
```

```text
⇒ 即使 recovery_eligible = True，trusted_chain_anchor 仍是 not_established。
   本地链一致 ≠ 来源可信 ≠ 外部锚定。
```

### 1.2 我没有做到的（这一项几乎空白）

```text
✗ 没有「谁是权威来源」的表达
   relation 五值里没有 authority / trust_level 之类的东西。
   （这条与 Mion 那边「关系不排序」是同一个空位，两处都空着。）

✗ 没有外部锚定
   trusted_chain_anchor 恒为 not_established，不是「暂时」，是本项目当前不具备。

✗ 没有跨机构/跨角色的来源验证
   所有 source_ref 都是【自报】的字符串，系统无法验证它指向的东西是否存在。

⇒ 请你判断：这一项是否需要现在立项，还是等最小编码走完再说。
```

## 三 · 交接：这一项有明确缺口，我已报过但未解决

### 3.1 缺口是什么

```text
canonical_digest（记录摘要）覆盖 changed_at，而 changed_at 精确到秒。

⇒ 同一条修订序列，在不同时刻重建，摘要不同。
⇒ 跨进程、跨机器重放同一段历史，摘要对不上。
```

```text
我把这件事写成第二封函报给凌翼。他的裁定是：
  · 保留 record_digest 语义（时间戳属于记录身份）
  · 另设 content_digest 表达「内容是否等价」
  · content_digest 只批准到【设计层】，运行时实现须单独批准
```

### 3.2 现在的实现状态

```text
✓ content_digest 已实现（cd-v1），13 字段投影
✓ 缺字段报错，不按缺省填充
✓ 已测：record_digest 不同而 content_digest 相同（同内容不同时刻）
✗ 没有任何把 content_digest 用于【交接校验】的流程
✗ 既有历史没有这个字段，回填策略未批准
```

### 3.3 这块与你的分工直接相关

```text
「交接」我理解包括：换进程、换机器、换持有者之后，
能不能确认「我拿到的是同一段历史」。

目前我的回答是：
  · 原样搬运（restore_verbatim）：能，因为 changed_at 不动
  · 凭内容重建（rebuild_from_content）：record_digest 会变，
    只能靠 content_digest 说「内容等价」——而它尚未被授权用于运行
  · 历史迁移（migrate_history）：取决于迁移过程有没有动时间戳格式

⇒ 三种操作的区分写进了 HISTORY_OPERATIONS 闭集与设计 §二，
   但只有第一种经过实测。另两种是设计论证，不是实测结论。
```

```text
请你判断：
  ① 这个三分是否覆盖了你说的「交接」？
  ② 有没有我没想到的交接形态（比如交接一半、部分交接）？
```

## 四 · 可变状态可归属性：留痕有，身份没有

### 4.1 我做到的

```text
写入路径只有三条，且都留痕：

  insert()   首版写入
  revise()   修订（不覆盖，旧版保留）
  correct()  纠正（加 correction_of 边，来源改指向纠正依据）

_write_log 每条记录：op / record_id / from / to / reason / at
```

```text
三道强制（前两轮审查逼出来的）：
  ZA-02  revise 白名单禁止改 record_id（身份不可偷换）
  ZA-03  correct 要求纠正依据存在且有非空 source_ref
  Z61-02 snapshot_token 覆盖每一版历史的全部字段
         （所以改正文、改摘要串、改链指针都会被发现）
```

### 4.2 我没有做到的（这一条我认为你会挑）

```text
✗ authority 字段是【自由字符串】
   你能写 "synthetic-fixture"，别人能写 "船长"、"系统"、随便什么。
   没有任何验证。

✗ 没有「谁授权的」的凭据链
   写入时记下的 authority 是写入方【自报】的，不是验证过的身份。

✗ 没有「谁读过」的记录
   只有写，没有读。

⇒ 所以「可归属性」我这里只到【动作可追溯】，不到【责任可归属】。
   这两件事差得很远，我不打算把它说得比实际好。
```

### 4.3 一个具体的弱点

```text
correct() 要求「纠正依据必须有 source_ref」，
但 source_ref 本身是自报字符串，
不验证它指向的东西是否存在。

⇒ 也就是说：我可以把纠正依据标成 "doc/权威文件-001"，
   而这个路径根本不存在，系统也照样通过。

⇒ 这是「非空 ≠ 可解析」，我在 ZA-03 时已经知道，
   但只做到了「拒绝空引用」，没做到「验证引用可解析」。
   后者需要外部能力，当前原型不具备。
```

```text
请你判断：
  ① 「动作可追溯」与「责任可归属」之间，最小要补什么？
  ② source_ref 可解析性，是否应作为独立一项立项？
```
