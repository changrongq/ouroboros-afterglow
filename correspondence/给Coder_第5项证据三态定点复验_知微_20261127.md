## 直接结果

正常入口：目标 32/32，边界 12/12，ES 8/8，原变异套件 15 CAUGHT / EVIDENCE_COMPLETE / exit 0。本次明细的 15 个 ID 确实唯一，包含 I13、I14，两比例的空、非空返回均带“不得当同一请求的结果组合”提示。

| 定向控制 | 实际 JSON / 进程退出 |
|---|---|
| 目标 ERR + 无关断言 FAIL | TARGET_ERRORED 1；EVIDENCE_FAIL / 1 |
| 单独缺少探针观测 | UNRESOLVED 1；EVIDENCE_PARTIAL / 2 |
| 两条分别为目标异常与未决 | 两类明细均保留；EVIDENCE_FAIL / 1 |
| 空登记清单 | manifest_ok=False；EVIDENCE_PARTIAL / 2 |

混合场景的 JSON 和主状态行正确，终端随后又印“证据不完整（EVIDENCE_PARTIAL）”；建议这行只描述未决条目，不再印第二个总判词。

## 剩余可以复现的缺口

1. **条数不能代替身份。** 在临时驱动输入中仅将清单末项 I14 替换为已登记 I1 的副本，其他都不动。真实跑 15 行、14 个不同 ID、I14 缺席；仍为 manifest_ok=True、EVIDENCE_COMPLETE / 0。第 686–688 行用正在遍历的清单长度和 rows 长度比较。建议先固定独立预期 ID，确认非空、唯一，再比本次明细中各 ID 恰出现一次、状态可识别且全为 CAUGHT。不要把预期和已完成都从本次实际行数推回去。重复替缺、清单为空、单纯少一项应分别测试。这不否定原运行的 15 项。
2. **基线及报告新鲜度。** 仅将基线目标子进程替为 exit 0、无任何 case 输出，其余 15 个变异与行为探针真实运行，仍判 COMPLETE / 0。另从已有成功报告开始，模拟基线 exit 1：本次进程正确退出 1，但第 538 行提前返回，报告路径上的 JSON 仍逐字节等于上次的 COMPLETE。它是旧成功，不是本次发出了成功 JSON；单独读取该路径的消费者分不清。建议基线不仅核退出码，还核基线所需用例确实运行并通过、探针记录可解析；基线早退也要留下本次可识别的非完整结果，或明确让本次无可消费的报告。对缺证据与已观察到失败分别定口径。
3. **8/8 并没有直接测试实际判定器。** ES 文件第 51 行是另写的 classify，真实 main 没有调用它。在临时副本只从真实驱动的失败集合删去 TARGET_ERRORED，保持 ES 文件不变，ES 仍为 8/8。建议抽取真实汇总函数供两方调用，测试里独立写预期值；至少保留“目标异常”和“基线失败前有旧报告”两条穿过真实入口、检查终端/JSON/退出码的对照。这是测试与实现的接线问题，不是要求对全仓再建一套判定器。
