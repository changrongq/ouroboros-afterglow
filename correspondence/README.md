## 零 · 这个目录放什么

```text
⇒ 只放【通信】—— 一方写给另一方的内容。

   ✅ 请求复核
   ✅ 裁定请求 / 回执
   ✅ 答复某人的意见
   ✅ 交接说明（写给特定人的）
   ✅ 跨窗口/跨成员的信息传递

   ❌ 规范定稿（如 B_22 编码卷、B_23 版本扩展）
   ❌ 实测报告（如 B_44 行为验证）
   ❌ 登记表（如 B_30 文件版本登记表）
   ❌ 设计与方案（如 B_45/46/47）
```

```text
⇒ 【判断标准一句话】：
   如果这份文件的读者是【具体的人】，它属于通信；
   如果读者是【任何后来的执行者或审查者】，它属于文档。
```

```text
⇒ 【历史文件一律不动】。

⇒ 【新规则只对新文件生效】：
   2026-11-18 起新写的通信，放本目录。
```

```text
⇒ 【检索影响】：今后找通信类文件，需同时看两个位置。
   ⇒ 本文件第三节给出旧通信清单，作为过渡索引。
```

## 二 · 命名规则

```text
⇒ 沿用既有习惯，但加一个方向标记：

   发给某人      ： 给<收件人>_<主题>_<作者>_<YYYYMMDD>.md
   某人发来      ： 来自<发件人>_<主题>_<YYYYMMDD>.md
   多方收件      ： 给<甲><乙><丙>_<主题>_<作者>_<YYYYMMDD>.md

⇒ 示例：
   给凌翼_证明层级表复核请求_Coder_20261118.md
   来自知微_层级表审查意见_20261119.md
   给睫知微钳星_最小因果对照审查请求_Coder_20261118.md
```

```text
⇒ 【为什么加"来自"前缀】：
   旧目录里对方发来的文件混在"给*"里（如 `知微_RC10独立复核_*.md`），
   一眼看不出方向。
   ⇒ 新规则让【方向】成为文件名的一部分。
```

## 四 · 与 B_30 登记表的关系

```text
⇒ 本目录的文件【也要登记】进 B_30，理由不变：
   凡是要被引用的文件，都应有可追溯的版本记录。

⇒ 【登记方式】：与现有条目一致，blob 用
     git hash-object -w -- <path>
   计算，登记表记录路径 + blob + 日期。

⇒ 【注意】：新目录路径含 `correspondence/`，
   登记时路径要写全，不能只写文件名。
```

## 五 · 一份文件该放哪（快速判断）

```text
问自己：这份文件是写给【谁】的？

├─ 写给具体的某个人/某几个人
│    ⇒ correspondence/
│
├─ 写给"所有后来者"（规范、方案、报告）
│    ⇒ 仍放 reports/review_history/
│
└─ 是登记/索引性质
     ⇒ 仍放 reports/review_history/（与 B_30 同处）
```

```text
⇒ 【边界情况】：一份文件既写给某人、又含方案内容怎么算？
   ⇒ 看【主要目的】。
   ⇒ 主要目的是"请对方看/裁定" ⇒ 通信
   ⇒ 主要目的是"留下可复用的方案" ⇒ 文档
   ⇒ 两边都重要 ⇒ 【拆成两份】：方案入文档，请求入通信
```

## 六 · 一句

```text
⇒ 把信和文档分开，不是为了整齐，
   是因为【它们的寿命不同】。

   ⇒ 一封"请复核"的信，在复核完成后就完成了使命，
     它的价值转为【记录】，不再是【依据】。
   ⇒ 一份规范，会一直被引用，直到被明确取代。

   ⇒ 混在一起时，后来的读者无法从目录判断：
     "这条结论现在还有效吗，还是只是一次对话？"
```
