## 3. Z61-01 · P1：G6 默认路径没有消费本次检查的快照

位置：[afrecover.py 第 241 行](https://github.com/changrongq/ouroboros-afterglow/blob/9a12e28d292399416af3a4360a2ff4739a6c3f75/afterglow_a/prototype/afrecover.py#L241)。

`check_integrity()` 自己取得并返回 `scope.snapshot`，但步骤 4 不比较这个值，只在调用方显式传入 `expected_snapshot` 时进行快照检查。默认值为 `None`，于是 G6 被整体跳过。

独立反例：调用原版 `check_integrity()`，确认它已返回 `verified`；在返回结果被主入口消费之前，对同一对象执行公开的 `store.revise()`；再让原版 `verify_recovery()` 继续。注入仅安排发生时点，不替写校验算法或资格算法。

| 调用 | 检查后的实际变化 | 返回 |
|---|---|---|
| 默认调用，不传令牌 | 当前内容、版本和快照令牌改变 | `verified / recovery_eligible=True / reasons=[]` |
| 同一反例，传入原令牌 | 相同变化 | `recovery_eligible=False`，包含 `stale_check` |

这条反例位于“检查完成后、资格计算前”。它不是设计 §九已经声明开放的“先读取、后检查”问题。

现有 RG-7 是先取令牌、再修改库、最后才调用恢复入口；它确实证明“显式旧令牌会被拒绝”，但没有覆盖本次入口内部的检查后变化，也没有覆盖默认调用。

修正要求：G6 至少必须消费本次实际检查的快照身份，不能依赖可省略参数才能生效。外部令牌可以保留为额外前提。需要明确保证的终点：若承诺的是返回结果之后仍可安全消费，还须让消费者使用被验证的不可变快照，或在相应临界区/消费入口重新验证；单次函数末尾比较本身不证明无限期有效。

## 4. Z61-02 · P1：快照没有绑定被检查的历史内容

位置：[afcore.py 第 461 行](https://github.com/changrongq/ouroboros-afterglow/blob/9a12e28d292399416af3a4360a2ff4739a6c3f75/afterglow_a/prototype/afcore.py#L461)，实际投影在第 477 行。

当前投影为每个 live 对象的 `record_id / revision / canonical_digest(live) / len(history)`。而 `verify_chain()` 检查的是历史记录的实际字段、摘要、链指针。历史长度不变、live 不变时，历史内容可以改变而快照令牌不变。

独立反例：

1. 合成记录及历史原本正确，取得令牌，并显式传入 `expected_snapshot`。
2. 原版完整性检查真实执行并得到 `verified`。
3. 在结果被主入口消费前，改变历史记录的 `content`，保持历史长度和 live 对象不变。
4. 主入口的令牌比较仍相等，最后返回 `verified / recovery_eligible=True / reasons=[]`。
5. 对同一库立即再调原版 `verify_chain()`，得到 `False`，原因是历史摘要不符。

这是摘要输入域遗漏，不是发现 SHA-256 碰撞。注入直接修改合成历史，属于 RG-3 本来就在测的历史字段破坏类别；本复核没有声称真实攻击者具有某种未证明的权限，也没有建立外部真实性。

修正要求：快照身份必须覆盖本次实际检查、随后使用的历史数据。不能只加入历史里自报的摘要串，因为正文破坏而摘要串保持不变正是需要检测的情形。可以设计同一份不可变检查快照，或覆盖实际相关字段的快照摘要，并与消费边界结合。仅修 Z61-01 的“总会比较令牌”，仍挡不住本例。

## 5. Z61-03 · P2：空登记身份被判为 independent

位置：[afrecover.py 第 104 行](https://github.com/changrongq/ouroboros-afterglow/blob/9a12e28d292399416af3a4360a2ff4739a6c3f75/afterglow_a/prototype/afrecover.py#L104)。

当前只检查五个键是否存在，只对 `registered_at` 检查非空；`registered_by`、`registered_rev` 未验证值。以下两组都实测通过：

```python
registered_by = "";   registered_rev = ""
# 或
registered_by = None; registered_rev = None
```

其余字段给出非空时间、两个 `yes`，结果均为：

```text
present=True
independent=True
problems=[]
recovery_eligible=True
```

登记人和版本没有值，却被报告为“已给出合格登记”，不符合这两个字段回答“谁登记、用哪一版登记”的用途。

要求补齐身份字段的类型与非空约束，并将缺失、null、空串、纯空白等情况纳入负向测试。时间格式及可接受的版本标识也应明确；本项不要求凭空实现未授权的外部权威系统。

另外，两个 `yes` 加上结构合法，最多验证声明满足本地格式与标志条件，不能独立证明“确实来自独立观察者、确实早于结果暴露”。保留当前工程边界，不把 `independent=True` 自动提升为已建立的独立来源证据。

## 6. Z61-04 · P2：发现链失败后，stale 分支覆盖了失败类型

位置：[afrecover.py 第 247 行](https://github.com/changrongq/ouroboros-afterglow/blob/9a12e28d292399416af3a4360a2ff4739a6c3f75/afterglow_a/prototype/afrecover.py#L247)。

独立构造“历史已经损坏，同时提供过期令牌”。本次链检查实际返回 `failed`；步骤 4 将其覆盖为 `not_checked`，最终原因码只有：

```text
integrity_not_checked
stale_check
```

`integrity_detail` 仍保留摘要不符的文字，因此并非证据完全丢失；资格也确实被拒绝。但结构化状态把“查过且失败”变成了“未检查”，`integrity_failed` 没进入原因集合。消费原因码的后续统计会得到错误分类。

这不是末尾 G1/G2 的 `if/elif` 本身错误，而是进入它们之前发生了状态覆盖。建议分别保留实际检查结果与快照有效性；若仍用现有三值状态，则至少不能让已知 `failed` 被过期状态改写成 `not_checked`，同时保留独立的 `stale_check` 原因。

## 7. 回答本函四问与两处措辞

**① content_digest R2：本轮接受这个局部修复。** 我独立逐个删除 13 个投影字段，全部收到 `SchemaError`；显式 `participant_id=None` 与空串产生不同摘要。没有再把缺字段默默补成空值。这不验证所有字段语义，也不授予真实运行时或历史回填权限。代码中已有可执行辅助函数，报告应称“合成原型中的实验性编码实现”；不能笼统说完全没有实现。设计明示的真实运行时/迁移授权仍未取得。

**② 判定顺序：末尾 G1/G2 对互斥状态用 if/elif 是合理的。** `not_run` 和 `no_expected_ids` 依当前定义也允许区分。实际问题是 Z61-01 的可选跳过，以及 Z61-04 的前置覆盖；不能仅从最后几行的布尔表达式证明六条规则都已执行。

**③ 缺登记与坏登记：当前 G5 明文允许区别待遇，原 RG-8 也明确登记缺失是兼容路径。** 本轮没有擅自增加“没有登记一律不合格”的新门禁。但 `present=False` 的 eligible 只能是该限定工程资格，不能被消费者读成“独立期望集验证成立”；删掉坏登记即可走无登记路径，正说明这两个能力层次不能混称。已经提供登记时，必须修复 Z61-03 的空身份通过问题。

**④ snapshot_token：不充分。** 对公开 insert/revise/correct 的变化敏感是局部性质，不能推出它覆盖历史检查对象；两种实测遗漏分别见 Z61-01、Z61-02。

**“验证方式不是读代码，是变异测试”建议改为：** “我们结合源码审查、正负场景和指定变异验证。在这组已执行场景中，移除指定阻断会使测试失败；这不证明所有路径已覆盖，也不证明规则自身正确。”

**M7 从 MISSED 到 CAUGHT：** RG-5c 的补充正确，隔离了“非空取回 + 空期望集”分支。它证明这个已知盲点被补测，不推出其余分支无盲点，也不应据此估计未知缺陷数量。本轮已经给出不同于 M7 的具体反例，下一步补这些场景即可，不要求无边界扩展测试。
