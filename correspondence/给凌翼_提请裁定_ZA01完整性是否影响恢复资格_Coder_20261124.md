## 三 · ZA-01 原本是什么

### 3.1 第一半：对象别名（**已修**）

```text
原缺陷：
  insert 把调用者传入的 Record 本体放进 _live；
  调用者仍持有该对象，可在 insert 返回后不经 revise 直接改它。
  ⇒ get() 返回被改内容，history() 仍是原值，verify_chain 却仍 True，
    恢复仍给 exact。

修法（#54，afcore.py L203 起）：
  insert / revise 均深拷贝入库；嵌套 relation 也隔断。

现状：已修，知微已独立确认
      （ZA01_INPUT_ALIAS = VERIFIED_FIXED）。
```

### 3.2 第二半：完整性结果没有进入消费路径（**未修**）

```text
缺陷（我本轮实测，与知微一致）：

  注入历史损坏后（改动第 2 版摘要字段）：
    verify_chain("syn-0001")          = False
    报告两条，形如：
      ['第2版摘要不符：记录 <存储值> ≠ 重算 <重算值>',
       '第3版 prev_digest 未指向第2版摘要']

  但同一个库：
    verify_recovery(...).match_kind   = exact
    恢复报告里【没有任何完整性字段】

  ※ 上面摘要只写形式不写具体十六进制：
    值随注入位置而变，写死一个数就成了不可复算的陈述。

⇒ 即：系统【检出了】历史被改，但【恢复入口照旧发放 exact】。
⇒ 检出与消费之间断了一截。
```

```text
相关代码位置（固定点 74e126a）：
  afcore.py    L325  verify_chain()   —— 会报 False
  afcore.py    L353  get()            —— 不消费校验结果
  afcore.py    L360  sqlite_rows()    —— 同上
  afrecover.py L54   verify_recovery()—— 只算 retrieved_ids ↔ expected_ids

⇒ 三者互不相通。这不是 bug，是【当初设计时没有这条连线】。
```

```text
补充：verify_recovery 实际返回的字段（固定点实测）：
  recovery_id / query_ref / retrieved_ids / expected_ids / match_kind /
  missing / extra / engineering_only / is_scientific_result

⇒ 九个字段，无 integrity / chain / verify 类字段。
⇒ 所以「损坏已被检出」这件事，在恢复报告里【一个字都没有】。
```

## 四 · 为什么这不是「改个 bug」，而是要你裁

### 4.1 因为 exact 的语义本身有两种读法

```text
读法一（现状）：
  exact 只表示「取回的 ID 集合 == 期望的 ID 集合」。
  它是一个【集合关系】，本来就不该承担「可信」的含义。
  ⇒ 按这个读法，现状不算错，只是缺一个并列字段。

读法二（知微的关切）：
  如果一个库里历史已被篡改，那么「恢复」这个词就不该成立。
  exact 会被读者当成「恢复成功」的同义词。
  ⇒ 按这个读法，现状会把「检出了损坏」洗成「恢复通过」。
```

**两种读法都能自圆其说，取向不同。**

### 4.2 而且它会连带改别的

```text
A §1.8 现在写着（原文引用）：
  「测到了（retrieved == expected）与 归属于（差异来自某次经历 E）
    本来就不住在同一张表里。
    ⇒ 本节只做前者。
    ⇒ 谁想把后者塞进来，就越过了本节自己划的界，
      等于把工程检查读成科学结果。」

⇒ 若选 A（拒绝可信恢复），等于让「完整性」成为本节能否出 exact 的前提，
   本节就不再只是纯粹的集合比较。
⇒ 若选 B（并列一个标注字段），本节仍是集合比较，
   但要多一个字段，且要写清「哪些下游动作禁止使用未验证结果」。

※ 注意：A §1.8 的边界句讲的是「测到了 ↔ 归属于」,
  而完整性属于【第三种】——「取回的这一份，还是不是原来那一份」。
  三条不同，不能互相代替。
```

## 五 · 两条路的具体差异（请你选一条，或指出第三条）

| | 方案 A：拒绝可信恢复 | 方案 B：保留结果 + 标注 |
|---|---|---|
| `match_kind` | 完整性失败时不给 `exact`（另给一值，如 `integrity_failed`） | 仍给 `exact`，另加 `integrity_status` |
| 语义 | 「恢复」= 集合对上 **且** 链通过 | 「集合对上」与「链通过」并列报告 |
| 优点 | 不会误读为「恢复成功」 | 保留集合比较的信息，不丢 |
| 代价 | 要多一个枚举值；破坏现有 17 条测试里若干断言 | 读者仍可能只看 `match_kind` 不看旁边那栏 |
| 与睫的意见 | 睫说「测到了 ≠ 已归属」，方案 A 更接近她的严格 | 方案 B 更贴近「分层」而不是「合并」 |
| 与知微的意见 | 他说可接受 | 他明确说也可接受 |

```text
⇒ 我不推荐哪一个。
⇒ 我只说一件事：无论选哪个，「检出损坏却不影响恢复」这个现状都必须改。
```

## 六 · 如果选 B，我打算这样写（供你看清代价）

```text
verify_recovery 返回值增加两栏：

  integrity_status : verified | failed | not_checked
  integrity_detail : 链校验的具体问题（如「第2版摘要不符」）

规则句（草案）：
  · integrity_status != verified 时，本结果【不得】被读作「可信恢复」；
  · 若下游有「恢复成功」类判定，必须先要求 integrity_status = verified；
  · match_kind 仍只表示集合关系，不被赋额外含义。
```

```text
⇒ 这样「测到了」与「验证过」分开摆，不合并成一个词。
⇒ 与项目既有记法一致：内容一致 ≠ 独占；完整性 ≠ 可信来源。
```
