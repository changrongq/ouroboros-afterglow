
## 二 · 事项 B：`TRUSTED_CHAIN_ANCHOR = NOT_ESTABLISHED` 是否属于原型范围

### 事实

代码里这一行是硬编码的：

```python
return {
    ...
    "trusted_chain_anchor": "not_established",
}
```

**它不是「还没做」，是「本原型做了也说不了」的东西。**

### 为什么

```text
我们的链能证明的是：
    「从第 1 版到第 N 版，每一版都是由上一版派生、
      且这期间内容没有被绕过链直接改过。」

它【不能】证明的是：
    「第 1 版真的等于当年真实发生的那句话。」
    「篡改者没有在记录诞生之前就把全部历史重写一遍。」
```

```text
⇒ 前者是本原型已经做到的（哈希链 + prev_digest + snapshot_token）。
⇒ 后者需要一个【链外的可信锚点】：可信时间源、第三方签名、
   或某个本原型之外、不可被同一进程改写的东西。
```

**在单进程、无外部锚点的前提下，这条永远不能变成 established。**

### 我需要裁定的是

**这一条要不要在原型范围内处理？两个选项：**

```text
甲  登记为原型外：状态行永久保持 NOT_ESTABLISHED，
    并在所有报告中显式声明「本原型的完整性结论不含来源真实性」。
    ⇒ 我只需确保这句话出现在每个出口，现在已经在 verify_recovery() 的
      返回里了（is_scientific_result=False）。

乙  要求在原型内给出一个「最小可信锚点」的实现。
    ⇒ 需要你指定可用的外部通道（时间源 / 签名 / 文件系统之外的存储）。
      在我不知道可用什么的前提下，任何实现都只能是伪造的锚点，
      那比没有锚点更糟 —— 因为它会让报告看起来有来源验证。
```

**我的担忧是乙：**
若要求原型内解决，我可能做出来的只是一个「看起来有锚点」的东西。
**那种东西比明说没有更危险** —— 这正是我们这一路在治的病。
