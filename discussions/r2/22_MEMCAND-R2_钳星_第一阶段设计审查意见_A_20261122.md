## 二、我核到的一处真实问题（非偷换，属工程缺陷，已修复）

### 发现（我的复算）

`afterglow_a/prototype/test_mutations_v4.py` 在 Windows GBK(cp936) 控制台下，打印 U+21D2（`⇒`）字符时抛 `UnicodeEncodeError`，导致脚本以 **exit 1** 退出。判定数字（CAUGHT 7 / REDUNDANT 2 / MISSED 0）其实已算出，但观感为"失败"，且违反作者"Python 3.9+ 可复算"的跨平台承诺。

### 我最初的表述不准确，应纠正（诚实）

我最初口述时，笼统表述为"三个脚本在 GBK 下会崩"。这个表述**不准确**。Coder 复现后给出的定位更准：

- `probe_source_role.py` —— 本来就有 `reconfigure`，**不崩**；
- `test_p1_p5.py` —— 其中的 `⇒` 在**注释**里，不输出，**不崩**；
- `test_mutations_v4.py` —— 第 235 行的 `⇒` 在 **print** 里，**才崩**。

关键不是"哪个文件"，是"哪个 `⇒` 会被打印出来"。我应接受 Coder 更准的这一层，而不是让本意见显得"全对"。

### Coder 的修复（本轮已核）

Coder 加了 `_harden_stdio()`：优先 `reconfigure(encoding="utf-8")`，切不动降级 `errors="backslashreplace"`；并把会崩的 `⇒` 替换为 ASCII `->` / `=>`。

**复算结果（修复后）：**

```
变异 9：CAUGHT 7 / REDUNDANT 2 / MISSED 0 / INVALID 0
VERDICT: PASS
退出码 = 0
```

`test_p1_p5.py` 与 `probe_source_role.py` 也均退出码 0。

### 对该修复的评价

- Coder 描述的原因与我发现的一致（且他在代码注释里如实标注了我这个审查来源，未隐瞒）；
- 他定位得比我更准：不是"哪个文件"，是"哪个 `⇒` 会在 print 里输出"，并精确定位到第 235 行；
- 修复方式正确：三个脚本均加 `_harden_stdio()`（优先 UTF-8、降级 backslashreplace），并把 print 里的 `⇒` 全部替换为 ASCII `=>`/`->`，双管齐下（只做其一在真实 GBK 控制台仍可能出问题）。

修复后复算：三脚本均 exit 0，`VERDICT: PASS`。修复已提交（`5abf7cf` #47）。
